# WP-60: a caller's new static never takes an inlined, deleted helper's static (R-57; ADR-0047)

Branch `wp/60-inlined-helpers`, one PR. Review: high (bind planner). Diagnostic: CML3207 (no new id).

## The defect

WP-51's spike (round 1, point 4) found that clang-cl at `-O2` records the function-local statics of an internal-linkage helper
it inlined (a `static` function, a member of a class in an anonymous namespace) as plain `S_LDATA32` records of the calling
procedure, in the shape of the caller's own statics, exactly as it does for an inlined lambda (R-54). An edit that deletes the
helper and declares a static of that name in the caller leaves one record of that name in the caller, and the planner paired the
caller's new static with it: the patch took the helper's live object and its initialiser never ran. WP-51 refused only closure
code and logged the wider case (`WP51-WOULD-REFUSE`).

Reproduced on main (b819151) with clang 18.1.3 (`clang-cl --target=x86_64-pc-windows-msvc /O2 /Ob2 /Z7`, `lld-link /DEBUG`):

```
old:  static Obj& h() { static Obj x = make(1); return x; }
      void f(int* a, int) { ++s_count; Obj& o = h(); o.hits += a[0] + s_count; sink(o.hits); }
new:  void f(int* a, int) { ++s_count; static Obj x = make(2); x.hits += a[0] + s_count; sink(x.hits); }

S_GPROC32 `f`
  S_INLINEES  0x100C (h)
  S_LDATA32 `x`                               <- h's static, a plain record of f
  S_INLINESITE inlinee = 0x100C (h)           <- no procedure of h: every call was inlined
```

main's plan: `?x@?1??f@@...` `bind-old-data ... matched record 'x' (compiland-static)`, `$TSS0` "inferred ... from the unchanged
layout": the reload applies and `f::x` is h's object (case `h1_r57`). The same holds for a member of an anonymous-namespace class
(`h7`). Where the edit changes the order the globals are created in, the guard finds no layout and the reload is refused with
CML3600 by luck (as WP-53 and WP-57 noted).

## What was built

The rule of R-54/R-61/R-59 (WP-51, WP-53, WP-57), applied to helpers, with WP-57's machinery: no second proof.

### `cml_pdb`: the parent scope of an inlined function (`core/cml_pdb`)

`PdbIndex::Inlinee` gains `scope` / `scope_known`: for an `LF_FUNC_ID` the `LF_STRING_ID` its parent-scope field names (`JPH`,
`` `anonymous namespace' ``, "" for none). A scope that cannot be read (not in the IPI, another record kind, an unterminated
string) leaves the inlinee readable with `scope_known == false`; WP-51's verdicts are unchanged by it.

### Planner (`broker/cml_core/src/bind_plan.cpp`, `bind_plan.h`)

- WP-51's verdict per procedure also lists its **helpers** (`InlineHelper`, kept in WP-55's cache with the verdict): every
  readable inlinee that is not closure code (any depth): a free function (`kind=free-function`: `LF_FUNC_ID` does not say
  whether it is `static`, so every free function counts, its name qualified by its scope), a member of a class in an anonymous
  namespace, local to a function or without a unique name (`internal-class`), a member of any other class (`external-class`).
- Where WP-51 finds no closure risk for the procedure `P` that holds an own static's record, `helper_risk` asks of each helper
  whether its statics could hold the record's name. A helper **clears** the record when
  - it is an `external-class` member and the record is local (`S_LDATA32` / `S_LTHREAD32`): a static of a function with external
    linkage is one object of the program, a global record (case `h8`: `Ext::bump`'s `ex` is in the globals stream, not in `f`);
  - or its own procedure is in the compiland (the out-of-line copy: same qualified name and the same canonical signature) and
    holds no data record of that name: the out-of-line copy records the same statics at the same addresses (case `h5`, the
    helper's address is taken). The procedure itself inlined into itself counts as its own.

  Otherwise the helper is **risky**: its statics cannot be read ("the compiland has no procedure of 'h' (every call to it was
  inlined)", "the scope of 'h' cannot be read"), or its own procedure holds a static of that name (`h6`).
- A risky helper makes the static go WP-57's way: with `PlanInput::prove_inlined_owners` (the pipeline) the static is paired,
  listed in `BindPlan::inlined_owner_statics` with the risk and the new field `helper`, and teaches no layout (`wp57_listed_`).
  The pipeline's `prove_inlined_owner_statics` (unchanged) keeps it only when WP-25's comparator proves `P` unchanged under the
  plan, else CML3207 with WP-51's message and the risk:

  `static data 'f::x' (?x@?1??f@@YAXPEAHH@Z@4UObj@@A) in h1_r57.patch.obj cannot be paired with the record 'x' at rva 0x3010 of its
  function: 'f' (rva 0x12d0) inlined 'h', a helper function (free-function), and the compiland has no procedure of 'h' (every call
  to it was inlined), so its statics cannot be read, and a compiler records the statics of inlined code as records of the calling
  procedure under their own names, so the record may be that code's static and not this one; only an unchanged 'f' proves it is
  this one, and the code of 'f' changed (<reason>)` / `Leave 'f' unchanged while the program runs (edit other functions
  of the file), rename the static, or hot-restart.`
- Without the flag (unit tests that plan only) such a static pairs as before WP-60, so WP-51's tests are unchanged; the closure
  rule without the flag still refuses, as it did.
- Logs: `WP60-HELPER record=... proc=... helper=... kind=... cleared (...)|risky: ...` (trace, per helper asked),
  `WP60-LISTED static=... risk=...` (trace, instead of `WP57-LISTED` for a helper's risk), `WP60-UNPROVEN` (trace, flag off), and
  one `WP60-HELPERS object=... checked=N risky=N cleared=N listed=N` per object at Info when any own static's procedure inlined a
  helper and no closure code. The proof's outcome is WP-57's `WP57-OWNER object=... listed=N proven=N refused=N skipped=N`
  (Info). `WP51-WOULD-REFUSE` and `WP51-INLINEES ... would_refuse=N` are unchanged, so the corpus numbers stay comparable.

Cost: nothing new is read. The helpers come from the inline-site walk WP-51 already makes for these procedures; the
compiland's procedures are indexed by name once per plan, and only when a helper is asked about.

## Corpus

WP-51's `WP51-WOULD-REFUSE` (any free function or member of an internal class inlined into the procedure of an own static whose
record it holds) counted 0 in every cell it reported (run 46052330588: jolt clang-cl and msvc, imgui clang-cl and msvc), so the
rule is expected not to fire there. WP-60's set is a little wider than WP-51's evidence line (members of a class without a unique
name, and the record-kind check for external classes), and narrower where an out-of-line copy clears a helper. Every planned object
whose own statics meet a helper logs `WP60-HELPERS ... checked=N risky=N cleared=N listed=N`, and `WP57-OWNER ... refused=N` gives
the refusals per cell; the orchestrator reads them from the dispatched corpus run.

## What it refuses that a perfect rule would allow (proposed for KNOWN_LIMITATIONS)

- **Any edit of the caller itself** while it holds an own static and inlined a helper that may have a static of that name (h4):
  the records cannot tell h4 from h1 (one record `x` in `f`, an inline site of a helper with no procedure); only the code can, and
  it changed. As for lambdas (WP-57), editing other functions of the file reloads.
- **Inlined external free functions** (h10): `LF_FUNC_ID` does not record linkage, so an `inline` header function (`std::min`, a
  math helper) counts as a helper whose statics cannot be read, unless the compiland keeps an out-of-line copy of it. A member of a
  class with external linkage does not count (its statics are global records).
- As WP-57: a caller the comparator cannot judge, not hooked, or without its old image; a listed static that is the only pairing
  of its object section leaves clang-cl's record-less guard without a layout (CML3600, WP-57's s17).

## Found on the way (not changed)

- **The mirror of R-57, a helper kept (WP-51 round 1, point 4b), resets the helper's static.** With the helper unchanged and
  still inlined (`static Obj& h() { static Obj y = make(1); return y; }` in `f`, another function of the file edited), the
  patch's `?y@?1??h@@...` looks for a record in a procedure of `h`, finds none (h has no procedure), and is decided new
  ("static data 'y' has no record in compiland 1: new", its guard new too); `f` is hooked (it refers to a new target), so the
  patched `f` runs `h`'s initialiser again and the running `y` is lost. Reproduced with clang 18 on the spike's case
  `h9_keep_helper` (not kept in the inputs). WP-52's "would be new while its function has an old record" check does not see it,
  because the record lies in the caller, not in a procedure of `h`. A fix would look for a helper's static in the procedures whose
  inline sites name the helper (WP-56's chain, for helpers) and refuse when that is not proven. Proposed as a roadmap item.
- The deferred evidence of WP-53/WP-57 applies here as well: R-64 (the build tree's original object names every static by its
  decorated name) would settle R-57 by name; R-65 (cl's inline-site position) would let cl prove a record outside every inline
  site to be the caller's own.
