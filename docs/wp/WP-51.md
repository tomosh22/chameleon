S_INLINESITE layout: parent, end, inlinee (IPI index), annotations; S_INLINESITE2 adds an invocation count before the
annotations. clang also writes `S_INLINEES` (0x1168) per procedure; cl is not known to, so the walk of the inline sites
is the source.

### What the data says

1. Telling "f really inlined a lambda" from "f has a closure" is possible per procedure, from the old procedure's own
   inline-site tree, without any display-name match: the procedure is the candidate record's parent (its address), so
   overloads and C linkage need no lookup at all.
2. "Of its own closures" (ADR-0044's wording) is too narrow: a lambda of another function inlined through it (`d_g`'s
   lambda in `d_caller`) records its static in the outermost procedure too. The rule should take any closure.
3. A call operator reaches a caller also through `__invoke`, and templates over a closure are internal-linkage functions
   whose statics land in the caller the same way.
4. **Beyond R-54 (not lambdas):** an internal-linkage helper inlined into its caller records its statics in the caller
   (`bx`). (a) Deleting the helper and adding `static bx` to the caller pairs it wrongly, as in R-54; (b) keeping the
   helper, its static finds no record in a procedure of its own and is decided new. Neither is covered by a lambda rule;
   an inlinee's linkage cannot be read from LF_FUNC_ID (`b_helper` and `c_helper` look the same).

Orchestrator's ruling on round 1 (ADR-0044): the rule below as proposed, widened to any closure at any depth; non-lambda
helpers are R-57 (roadmap, KNOWN_LIMITATIONS), not refused here, with a log-only evidence line.

## Round 2: what was built

### `cml_pdb`: `PdbIndex::proc_inlinees(proc)` (`core/cml_pdb/src/index_inlinees.cpp`)

Walks the procedure's records in its module stream (found by section:offset, as `proc_statics` does) up to its `S_END`
and lists every `S_INLINESITE` / `S_INLINESITE2` at any depth (blocks included), one entry per distinct inlinee id with
its number of sites and smallest depth. Each inlinee is resolved through the IPI: `LF_FUNC_ID` (name, type) or
`LF_MFUNC_ID` (class, type, name), the class through the TPI (name and unique name without the unit's discriminator), and
the canonical signature of its type (`function_signature`). An inlinee that cannot be read (id not in the IPI, another
record kind, an unterminated name, a class that is not in the TPI, a site record too short to name one) is listed with
`readable == false` and a reason, never left out; an unknown signature is `signature_known == false` with the reason.
Nothing is cached; the stream is read only when the planner asks (no cost on any other path). More than 4096 distinct
inlinees: `complete == false`. A procedure that is not found or has no end record: CML1413. Checked on the real lld PDBs
of round 1 (`o2_step`: three closure call operators at depth 1, `o2_make` at depth 2 with 3 sites; `GetRTTIOfType`: the
`JPH::RTTI` constructor only; `run<lambda>`: an `LF_FUNC_ID` named `run` whose signature holds the closure's unique name).

### Planner (`broker/cml_core/src/bind_plan.cpp`)

A static that would be paired with an old record lying **directly in its own function's procedure** P (the record's
parent procedure, by address; `last_component(parent) == ` the static's enclosing function, so a lambda's static looked
for in the function its call operator was inlined into, WP-40's case, is not affected) is refused with CML3207 when P's
inline tree holds a risky inlinee:

- a member of a closure class (unique name `.?A?<lambda_`, or the class's last name component `<lambda_...>`), whatever
  its name (`operator()`, `operator()<...>`, `__invoke`, cl's `<lambda_invoker_*>`, anything unknown), except a conversion
  operator (`operator <type>`), a constructor (named like the class), a destructor and `operator=`;
- any inlinee whose name, class or signature mentions `<lambda_` (a template over a closure: clang names it `run` only,
  the closure is in its signature);
- an inline site that cannot be read, or an inlinee whose signature cannot be read (it cannot be shown not to be a
  template over a closure), or more inlinees than the reader lists.

Where it runs: pass A before the one-to-one name pairing and before that pair teaches the section layout; the closure step
(B0) before a pair by closure teaches the layout; and once over every remaining pairing of pass B (exact name, layout,
place in the function) before the guards are settled, so a refused static takes its guard along (settle_guards). One
verdict per procedure and plan (`inline_verdicts_`). Guards and functions are not checked (a guard follows its static).
Overloads need no name match (P is the record's own procedure), and C-linkage functions (`??main@@9`) none either.

Logs: `WP51-INLINEE` and `WP51-INLINEES proc=...` (trace, per inlinee and per procedure), `WP51-PAIR` / `WP51-SKIP`
(trace, per static), `WP51-OWN-STATIC static=... refused (...)` (Info, one per refusal), `WP51-WOULD-REFUSE static=...
inlinee=... kind=free-function|internal-class` (Info, R-57 evidence: the static pairs; a wider rule would have refused
it because P inlined a free function, or a member of a class in an anonymous namespace or local to a function), and one
Info summary per object that needed a verdict: `WP51-INLINEES object=... procs=N sites=N closures=N unreadable=N
refused=N would_refuse=N`.

Cost: one walk of the compiland's module stream per procedure that holds the only candidate record of an own static
(Jolt clang-cl: about 191 `GetRTTIOfType` procedures in the unity batches, the same pattern as WP-46's `proc_statics`
per procedure).

## After the high review of 2a3580d (ADR-0044 rulings)

| # | Finding | Fix |
|---|---|---|
| 1 | Every call operator was taken for a closure static's own function (`encl == "operator()"`), so an inner lambda's static recorded in the outer lambda's call operator, which inlined it, was refused (WP-40 bound it) | For a static of a call operator the record is its own only when its procedure is the call operator of the static's own closure: the closure of the procedure's type (`closure_of`, without the unit's discriminator) must begin the static's decorated scope after `??R` (`own_closure_scope`, with rule (d)'s closure pairing applied). Another closure's call operator: `WP51-SKIP`, WP-40 decides. When either closure cannot be read the record counts as the static's own and is checked (refused when risky) |
| 4 | `proc_inlinees` counted the inline sites of a procedure nested in the wanted one as its own | A procedure record opens a scope of its own wherever it appears; its sites are its own (or nobody's) |
| 5 | Inlinees were deduplicated by a linear scan, and the module stream was read and walked once per procedure | A hash map per procedure, and `PdbIndex::procs_inlinees(procs)`: one walk for several procedures of one compiland, each id resolved once. The planner asks, on its first verdict, for every procedure of the compiland that holds a function-local record (the only ones a static can be paired into) in one call; when that batch fails it reads the asked procedure alone, so its own error is reported |
| 6 | A truncated inlinee list was not counted as unreadable when a risk had been found already | Counted always |

Rulings without a code change: (2) the breadth (any own static of a function that inlined any closure code is refused,
`std::sort` or `std::call_once` with a lambda included) is the spike ruling's; it goes to KNOWN_LIMITATIONS and wave 13. (3) A
refused static's record left in `free_cands` has no effect: CML3207 is raised through `error()`, the plan fails and the module's
reload applies nothing (WP-47).

Tests (`unit.bind`): the inner lambda's static bound by the layout (fails on 2a3580d, which refused it); the R-54 edit one
level down, the inner lambda deleted and its static's name declared in the outer lambda (refused; fails on main, which paired);
