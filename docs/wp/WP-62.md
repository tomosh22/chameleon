# WP-62: lock order of fault injection and AgentLink::send; a TSan job (R-70)

Branch `wp/62-lock-order`, one PR. Wave 15 (ADR-0047). Review: medium. No new diagnostic id, no change to the agent, to the
IPC protocol or to what inject-failure, restart, revert, exception-action or the save watcher answer.

## The report

WP-58's TSan run (GCC, Linux) reported a lock-order inversion in `unit.broker_core`. It reproduces on main (b819151)
with this WP's TSan job configuration: `cml_test_broker_core -tc="*R-51*"` gives two `lock-order-inversion (potential
deadlock)` reports, one from each of the two tests the roadmap names. The two edges are:

| Edge | Where | Code |
|---|---|---|
| gate -> send lock | `inject_failure` (fault_injection.cpp:671 on main) | For a stage whose group has an end-of-operation cleanup (restart, revert, exception-action, watch), `inject_failure` took `FaultInjector::gate()` and held it until it returned, across `arm_agent` -> `AgentLink::request` -> `AgentLink::send`, which locks the link's `send_mutex_` (agent_link.cpp:110). This is R-51's design: the gate kept an operation from starting between the arming's records and its last ArmFault. |
| send lock -> gate | test_reload.cpp:2477, test_restart.cpp:2248 (the two `R-51 1` tests) | The scripted agents of the unit tests answer a request inside the rig's `SendFn`, so they run while `AgentLink::send` holds `send_mutex_`. In both tests the hook `on_arm` (test_reload.cpp:409, test_restart.cpp:304) calls `inject_failure` while the restart's or revert's `finish_injection` sends its ArmFault(count 0), and that `inject_failure` takes the gate. |

TSan reports the cycle as a potential deadlock. As the tests are written it cannot deadlock: that needs a second thread to
hold the gate in `inject_failure` and wait for the same link's send lock at the same moment.

## Can the release broker hit it?

No. This holds both for the release package and for a default developer build.

* **Release package** (`tools/package/package.ps1`: `-DCML_FAULT_INJECTION=OFF`). Nothing locks the gate. The four
  operations that take it (`RestartCoordinator::restart`, `ReloadService::revert`, `ExceptionService` actions, the save
  watcher's `Operation`) do so only under `#if defined(CML_FAULT_INJECTION)`. `finish_injection` returns before it sends
  anything. `inject_failure` is still compiled, but nothing can call it: the control server registers `inject-failure`
  only under `#if defined(CML_FAULT_INJECTION)`. So the first edge does not exist.
* **Default build** (`CML_FAULT_INJECTION=ON`, which is what developers and CI build). The first edge exists. The second
  edge needs code that takes the gate while a link's send lock is held, which means code that runs inside a link's
  `SendFn`. The broker has one production `SendFn` (connection_server.cpp:56): `connection.pipe.send(message, 5000)`, a
  named-pipe write that calls nothing else in the broker. The connection thread's own replies go through the same
  `link->send(reply)` and only write. An agent's answer comes back on the connection thread, through
  `Session::on_message` -> `AgentLink::deliver`, which takes only the link's `mutex_`. Neither path takes the send lock and
  then the gate. So the second edge exists only in the unit tests' scripted agents.

The inversion is therefore an artefact of the test transport. There was still a hazard in the product: `inject_failure`
held a broker-wide mutex across a blocking agent round trip (up to 10 s per agent, `arm_agent`). Any later transport or
hook that calls back into the broker from inside a send would have turned the potential deadlock into a real one. The WP
asks to fix the order either way, so both halves are fixed: the product no longer sends under the gate, and the tests'
scripted agents no longer run their hooks under the send lock (see "Lock order and the invariant" below).

### Lock order and the invariant

Nothing that holds the gate locks a link's `send_mutex_`. Under the gate there are only `FaultInjector::mutex_`, the
operations' run locks (taken with `try_lock`) and `AgentLink::mutex_` (`snapshot()`). None of those is held while the gate
is taken.

That alone does not make a callback from inside a send safe. `lock_gate()` waits on a condition variable for an arming
to end. TSan does not see that wait as a lock edge, so it cannot report a cycle through it. A thread that holds a link's
send lock and calls `lock_gate()` can wait for an arming whose ArmFault needs that same send lock: a hang with no report.
The rule, stated in `fault_injection.h`, is therefore:

> Never call `lock_gate()`, `inject_failure`, or an operation that takes the gate (restart, revert, an exception action,
> a compile-on-save batch) from code that runs under an AgentLink send lock, that is, from inside a link's `SendFn`.

The broker's only `SendFn` is a pipe write. The scripted agents now run their gate-taking hooks after the send has
returned. With both of those, no code in the repository takes the gate under a send lock. The test `a hook that calls
inject-failure while another inject-failure arms the same agent finishes` checks this case. It hangs under the old
scripted agent and is guarded by a watchdog (see Tests).

### The index callbacks and ~ReloadService

**The race.** The 24-suite TSan set reported an intermittent data race. It appears on main too, and only when several
copies of `cml_test_broker_core` run at once.
* The report is on `ReloadService::save_watcher_`: `rearm_save_watcher()` on a module index thread (its `on_change`
  callback, at Ready) against the `swap` in `~ReloadService` (reload_service.cpp:131).
* It shows up in `a session directory the user supplied is never removed` (`user_dir.service.reset()`).

**Root cause.** This is a product lifetime bug, not a test artefact.
* The service handed every `ModuleIndex` three callbacks that capture `this`: `on_change` (which calls
  `rearm_save_watcher()` and `queue_image_prefetch()`), and `on_audit` and `on_skipped_archive_members`, which publish on
  the service's `EventBus`.
* `~ReloadService` stopped the index threads only by dropping its `ModuleState`s in `agents.clear()`. That joins an index
  thread only when the service held the last reference.
* Anyone else who still holds the state keeps the thread running past the destructor, and its next callback runs on a
  destroyed service. Such a holder can be a reload in flight, a client, or the test rig's `rig.module`.

**The fix** does not depend on reference counts.
* `CallbackGate` (new, header-only) is a closable scope counter. The service keeps one (`index_callbacks_`), and each of
  the three callbacks holds a `shared_ptr` to it.
* Each callback runs its body only inside a `CallbackGate::Scope`.
* `~ReloadService` calls `index_callbacks_->close()` before anything else. `close()` marks the gate closed and waits for
  the scopes in flight to end. From then on every callback finds the gate closed and does nothing, however long its
  thread runs.
* `close()` holds no lock of the service while it waits. A callback does not destroy the service, so it never waits for
  itself.
* These three are all the callbacks a `ModuleIndexSpec` carries apart from the two scan hooks for tests. The service's
  own threads (re-apply, prefetch, the save watcher and its retiring reloads) are still stopped and joined by the
  destructor as before.

**Test.** `an index thread that outlives the service never calls into it (WP-62): its Ready callback is closed by
~ReloadService` (test_reload.cpp). It uses `ReloadService::set_index_callback_hooks_for_testing`: `before` runs on the
index thread before the callback enters the service, `entered` once it has.
1. The index thread is held at Ready by a latch in `before`. The rig still holds the `ModuleState`.
2. The service is destroyed, then the latch is released.
3. Dropping the last reference joins the index thread.
4. `entered` was never called after the destruction; it was called for the earlier status changes.

There is no sleep, and a watchdog turns a hang into a failure. Without the gate's early return the test fails:
`entered_after_destruction == 1`, and TSan reports nothing for that call into the destroyed service.

## Tests

`unit.broker_core`, test_reload.cpp:

* `revert injection (WP-62): inject-failure lets go of the gate before it sends ArmFault; it is marked as arming until it
  is done`. While the scripted agent handles ArmFault, the gate is free and the arming is marked. Afterwards the mark is cleared. Subcase: an arming the agent refuses also clears the mark and leaves no record.
  A revert afterwards starts and disarms what was armed for it.
* `revert injection (WP-62): a revert that starts while inject-failure sends ArmFault without the gate waits for it and
  finds the record`. This is the revert counterpart of the restart test `R-51 2`. A revert asked for from inside the ArmFault
  has not started 300 ms later. Once it runs, its end disarms the stage in the agent and lists it as unused. The thread is
  joined by a scope guard, so a failed REQUIRE does not leave a joinable `std::thread` behind (that would terminate the binary).
* `revert injection (WP-62): a hook that calls inject-failure while another inject-failure arms the same agent finishes`.
  1. During the revert's end-of-operation ArmFault, the hook starts a second client's inject-failure of `pre-restart-hooks`,
     which makes its record and sends ArmFault to the same agent.
  2. The hook then waits until that client is arming, and arms the revert's stage itself.
  3. That arming is refused busy (CML5978) once the other arming has ended. The other arming stands, with its record.

  Under the old scripted agent the hook ran under the link's send lock, so the other client waited for that lock and the
  hook waited in `lock_gate()`. Checked locally by running the hook inside the send again: the test hung, and its watchdog
  (`HangWatchdog`, 60 s) ended the binary with `FAILED (hang)` and exit code 3 instead of hanging until ctest's timeout.
* `fault injection (WP-62): {"stage":"none"} waits for an inject-failure that is arming agents, so no agent is left armed
  without a record`.
  1. While `revert-restore` is being armed, a second client sends `{"stage":"none"}`. It has not finished 300 ms later.
  2. Once the arming ends, the disarm clears the record and its ArmFault (`none`) reaches the agent after the arming one.

  Checked locally against the old disarm path: `CHECK_FALSE(disarmed_early)` fails.

The existing R-51 tests still pass unchanged. `R-51 1` (both sides) is the case TSan reported, and `R-51 2` (restart)
checks that an operation waits for an arming.

```

      "-DCMAKE_CXX_FLAGS=-fsanitize=thread -Wno-maybe-uninitialized" -DCMAKE_EXE_LINKER_FLAGS=-fsanitize=thread

TSAN_OPTIONS="halt_on_error=1 second_deadlock_stack=1" ./build-tsan/bin/cml_test_broker_core
```

On a kernel with more than 28 bits of mmap randomisation, GCC's TSan runtime stops with "unexpected memory mapping". The
fix is `sudo sysctl vm.mmap_rnd_bits=28`, which the job runs.

## What was learned

* TSan's lock-order detector also flags cycles that need a test-only edge. The analysis above is what separates those from
  a reachable deadlock. The fix here removes the product half of the cycle, so the tests' transport is free to call back.
* The tests' scripted agents answer inside `SendFn`, under `AgentLink`'s send lock. A real agent answers on another thread.
  A hook in those agents runs under a lock the real broker never holds at that point.
* A thread that a reference count keeps alive can outlive the object that started it. A callback that captures `this` needs an
  explicit end (CallbackGate), closed by the destructor; TSan only sees such a call when it happens to race.
* Replacing a mutex with a condition-variable wait removes a lock edge from TSan's view, not necessarily the cycle. The first
  version of this fix hid the cycle that way: a hook under the send lock that waited in `lock_gate()` would have hung
  silently. Taking the hook out of the send, and a test that would hang otherwise, close it.

## Deferred

* The Windows-only suites (pipes, the agent DLL, hooks in a live process, fixtures) are not run under a sanitizer for
  races. The fuzz workflow's AddressSanitizer covers the readers only. clang-cl has no ThreadSanitizer for Windows.
* The scripted agents' other hooks (`on_hooks`, `during_prepare`, the new agents' `on_request`) still run inside the send.
  None of them takes the gate. A future hook that does must follow `on_arm` and run after the send.
