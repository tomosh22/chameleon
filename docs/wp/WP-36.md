# WP-36: image-relative references to old data (R-01, corpus finding F-2; ADR-0042)

One branch (`wp/36-imgrel`), one PR. Planner and fix-ups in `broker/cml_core`, one fix-up kind in `core/cml_ipc`, its
application in `agent/src/loader`. No new message type, no ABI change.

## The problem

Under cl with optimisation, a function that has `__ImageBase` in a register (it has a switch jump table, or indexes two or
more global arrays) addresses globals as `[reg + index*scale + sym@IMGREL]`: an `IMAGE_REL_AMD64_ADDR32NB` relocation on the
32-bit displacement of a ModRM/SIB memory operand. The planner refused every such translation unit with CML3101, whichever
function was edited, and every header included by it. raylib's `rcore.c` (`PlayAutomationEvent`) is one.

ADR-0042 decides against re-pointing `__ImageBase`: the same functions load their jump-table entries zero-extended
(`mov eax,[rdi+rax*4+$LN16]` / `add rax,rdi` / `jmp rax`), which needs the patch's own base. So `__ImageBase` stays the
patch's, and only the sites that reference **old data** are rewritten.

### The proof (ADR-0042 decision 3)

A site is accepted only when all of this holds; anything else is CML3101, never a guess.

1. The section is code.
2. The instructions are decoded linearly with the shared length decoder from the nearest **function symbol** at or before
   the site (COFF type `DTYPE_FUNCTION`, external or static), up to the next function symbol or the section end. A section
   can hold several functions (`/Gy-`, `#pragma code_seg`), and each one's jump table follows its code.
3. The sweep reaches an instruction with `disp_size == 4` whose `disp_offset` is exactly the site.
4. That instruction has none of `kInsnRipRel`, `kInsnAddr32` (a `67` prefix), `kInsnSegFsGs`; its memory operand has a
   **base register** (`[index*scale+disp32]` and the absolute `[disp32]`, i.e. mod=00 with SIB base=101, have no register
   that could hold `__ImageBase`); and it is not a **`lea` with a 32-bit or 16-bit destination** (`8D` without REX.W).
   Such a `lea` truncates the address it computes and zero-extends it: with the patch above the module the displacement
   is negative, and after `add rax, rdi` the result is 4 GiB away from the old data. A 32-bit *load* through the same
   operand (`mov eax,[...]`) is fine; only `lea` puts the address itself into a register.
5. Every relocation the sweep passes, the site's own included, is **exactly** the 32-bit displacement of one decoded
   instruction or lies wholly inside its immediate. A relocation that covers prefix, opcode, ModRM or SIB bytes or
   straddles two instructions means the sweep ran into data (the entries of a jump table are relocations on bytes that
   decode as something else) or lost the instruction boundaries: the sweep stops there and nothing behind it is trusted.
   Sites before the stop stay proved.
6. An instruction the decoder reports as Unknown or Truncated stops the sweep in the same way.

**Where the immediate starts (`parse_layout`).** The decoder reports the length and the displacement, not the position
of ModRM or of the immediate, and it is not edited here. The prover re-derives the layout from the instruction's own
bytes: legacy prefixes, REX (only when it is the last prefix), the opcode (one byte, `0F xx`, `0F 38/3A xx`), ModRM,
SIB, displacement. It then **checks** the displacement it found against the decoder's `disp_offset` / `disp_size`; on any
disagreement the layout is unknown and no relocation in that instruction is accepted. The immediate starts behind the
displacement, or behind ModRM/SIB when there is none. Whether an opcode has a ModRM byte is not looked up in a second
opcode table: the handful of opcodes *without* ModRM whose immediate a relocation can fill are listed (`E8`, `E9`,
`0F 80..8F`, `B8..BF`, `68`, `A9` and the `op eAX, imm32` row `05 0D 15 1D 25 2D 35 3D`), and every other opcode is read
as if it had one. When it has none (`6A ib`, `EB cb`, `7x cb`, `A8 ib`, ...) either the pretended ModRM asks for a
displacement the decoder did not report (layout unknown) or what is left behind it is shorter than a relocation. A
relocation in an immediate must be 4 or 8 bytes wide and end with the instruction. For a VEX/EVEX instruction (`C4`,
`C5`, `62` after the prefixes; Unknown to the decoder until WP-38) only the displacement is located, and a relocation is
accepted nowhere else. On 128569 instructions of optimised library code (gcc `-O2`, a Linux pre-check) the layout agreed
with the decoder for every one of the 40853 instructions with a displacement, and the immediate of every one of the 18795
`rel32` branches was located; the 3408 instructions with an unknown layout were all `imm8` / `rel8` forms without ModRM.

The CML3101 message now reads, for example:

```
'compute_value' ('?compute_value@@YAHXZ') references '?g_tick@@3HA' in old.exe image-relatively (ADDR32NB) at +0x8 of section
'.text$mn' in logic.cpp.obj, and the site is not proved to be an address displacement: the site at +0x8 is not the 32-bit
displacement of a memory operand of the instruction at +0x7 (b8 00 00 00 00): it is an immediate operand; this cannot be retargeted
```

### The fix-up

`S + A` is the absolute target as for the other kinds. The triple holds `int32(S + A - patch_base)`; the wire carries the
absolute target and the agent subtracts the base the image really has, so the range check is made against the real
address (as for REL32). An agent older than this change rejects wire kind 4 ("unknown fix-up kind", CML5201): the reload
fails cleanly and the patch is unloaded, so `agent_abi_version` does not change.

Plan-time reach uses the same window as REL32 (`rel32_reachable`): data bound to another module more than 2 GiB from every
place the patch can be loaded is CML3550 before anything is linked.

## Diagnostics

| Id | Meaning |

| CML3550 (new, planner) | the image-relative displacement to old data does not fit 32 bits (plan time: no patch base can reach it; triple time: this base cannot) |
| CML4700 (new, agent) | `Addr32NbDisp`: `target - patch image base` does not fit a signed 32-bit displacement; nothing is written |

## Fixture and scenario

`tests/fixtures/imgrel` is a C program. `imgrel.c` (the edited TU) is the source of the orchestrator's spike: `ig_mixed`,
a switch with a jump table whose cases read and write a global struct of arrays (`CORE`), a file-static array (`sarr`) and
a table of function pointers (`fptab`); and `ig_wide`, which indexes two global arrays. `main.c` is never patched and
touches the same globals directly.

The scenario edits both functions and then requires, on one TICK line: `key=2` (the patched case wrote `CORE.keys[77]`,
which `main.c` had cleared and reads back itself), three different values of `count` (the patched code increments
`CORE.count`, `main.c` resets it at 16), `seed=1004251` (`sarr[9]` was written once, before the first tick), `fp=43` (the
function pointer `main.c` stored), `fl=7` (`CORE.f[2]` set by `main.c`), `g3=4244` (the switch dispatches through the
patch's own jump table) and `wide=2004328`. A patch with its own copies would print `key=0`, a count that stops,
`seed=1000000`, `fl=0`, `wide=2000000`, and crash on the null function pointer.

The image-relative path is taken only where cl emits it (RelWithDebInfo: `/O2 /Ob0 /Gy`). In Debug and under clang-cl the
same scenario runs through REL32; it must pass there too.

## What was learned

* **The shape matters, not the array.** One global array indexed by a variable is `lea rax,[table]` + `[rax+rcx*4]` (REL32):
  the old repro never hit F-2. cl switches to `sym@IMGREL` displacements once `__ImageBase` is in a register anyway: a jump
  table, or two or more global arrays (orchestrator spike, run 45402685481, cl 19.44 `/O2 /Ob0 /Gy` and `/O1`). `/Od` has
  none; clang-cl has none (its jump tables are table-relative, `IMAGE_REL_AMD64_REL32` against `.text` in `.rdata`).
* **C tentative definitions.** `struct Core CORE;` in a C file is a COMMON symbol under cl; the planner already binds those
  like externals, and the image-relative reference to it is retargeted the same way.
* **The addend is in place and signed.** `cmp byte ptr CORE[rbx+rdi+200h],0` carries `00 02 00 00` at the site; the fix-up
  value is `S + A - patch_base` with `A` read from the object (ADR-0025).
* **The fixture under cl RelWithDebInfo has 10 such sites** (cl 19.44, `unit.bind_fixtures`): eight in `ig_mixed`
  (`CORE` with addends 0, 0, 512, 1024 and 1092, `sarr` twice, `fptab`) and two in `ig_wide` (`sarr`, `CORE` + 1024). The
  reload of the scenario reports the same number (`WP36-IMGREL sites=10 verified=10 fixture=imgrel compiler=cl
  config=RelWithDebInfo`); Debug and both clang-cl configurations report 0.
* **raylib 5.5 under cl (corpus run 45409834371, job `raylib / msvc`).** The edit of `raymath.h` recompiles three
  translation units; the answer carries `"imgrel_sites":97,"imgrel_verified":97`. Per object (broker log):
  `WP36-IMGREL sites=89 verified=89 object=rcore.obj` (every one a reference to `CORE`), `sites=8 verified=8
  object=rmodels.obj` (`m3d_propertytypes`, `m3d_commandtypes`, `first_row_filter` and five `_m3dstbi__*` tables), 0 for
  the example. The instruction forms: `mov byte ptr [r+r+d32], r8` (`42 88 84 ..`, 35 sites), `movzx r32, byte ptr`
  (`0F B6`, 35), `mov byte ptr [..], imm8` (`42 C6 84 ..`, 13), `movss` loads and stores (`F3 4x 0F 10/11`, 5), dword
  `mov` loads and stores (`8B` / `89`, 6), `lea r64, [r+d32]` (2), `cmp byte ptr [..], imm8` (1).
* **No instruction of `rcore.c` (or `rmodels.c`) stopped a sweep.** All 97 sites were reached; nothing was refused. A sweep
  is only made for a function that has such a site, and it ends at the site's function, so this says nothing about
  functions without image-relative references to old data.
* **`PlayAutomationEvent` is still hooked on every reload of `rcore.c`** (`hook PlayAutomationEvent: unverifiable -
  IMAGE_REL_AMD64_ADDR32NB to '$LN30' in code`): its jump-table load is not judged by narrowing (see "Deferred").
* **"Sign-extended displacement" is necessary, not sufficient (PR #67 review).** The first version accepted
  `lea eax,[rdi+rcx*4+sym@IMGREL]` (the truncated address is wrong once the patch lies above the module),
  `mov eax,[rax*4+sym@IMGREL]` and `mov eax,[sym@IMGREL]` (no register holds the image base), and it took any relocation
  that ended with an instruction for "the immediate", even one covering `81 c0` of `66 41 81 c0 iw`. cl emitted none of
  these in the fixture or in raylib (all 97 raylib sites have a base register; the two `lea` sites are `48 8D`), so the
  acceptance runs could not show it; the byte vectors are now unit tests.
* **Decoder coverage (pre-check on a Linux host, not acceptance).** The sweep was also run over every exported function of two
  optimised C libraries (gcc `-O2`: sqlite3 and libpng, 1649 functions, 128569 instructions) and never stopped on an unknown
  instruction.

## Deviations from ADR-0042

* **The immediate field is located by a local parse** (see "The proof"), because the decoder reports the displacement
  only and is not edited by this package. A relocated immediate must also be 4 or 8 bytes wide and end with the
  instruction, and a relocated displacement must be exactly the displacement: narrower than "wholly inside", never wider.
* **Two refusals the ADR does not list** (PR #67 review): a `lea` without REX.W, and a memory operand without a base
  register. Both are sign-extended displacements of a plain 64-bit address computation, but the result is not the address
  of the old data.
* **A site with no function symbol at or before it is refused** (verdict `no-function`). The ADR does not say what to do
  when there is nowhere to start; refusing follows "nothing is guessed".
* **ADDR32NB to a synthesized import slot is left to the linker** instead of CML3101. The placeholder *is* the slot and
  lives in the patch, so the image-relative reference to it is correct as linked (the REL32 and ADDR64 cases already work
  like this). No fix-up, not counted as a site.
* **Reach at plan time is CML3550, not CML3205**, so that the message can say "image-relative". The ADR names only the
  agent's CML47xx.
* **Evidence line.** The planner cannot print into the CI log. The line is produced in three places from the same two
  counters: the broker log (per object), cmltest (per reload, from the answer) and `unit.bind_fixtures` (per fixture, into
  the summary the existing CI step prints). The cmltest print is a change to `tests/harness/src/runner.cpp`, outside the
  package's directories.

## Deferred

* **Elision of functions with a jump table.** Their table load is an ADDR32NB to a patch-local label (`$LNnn`, decided
  `patch-fresh`), which narrowing does not judge, so such a function is hooked on every reload of its TU even when it did
  not change (more hooks, never fewer, as before this package). This package makes only the retargeted sites (old data)
  comparable; it does not change the jump-table case. It is not limited to optimised code: WP-39 found that under cl `/Od`
  every function with a switch is kept as `unverifiable - IMAGE_REL_AMD64_ADDR32NB to '$LN13' in code` (274 of 275 hooks in
  its benchmark project), and raylib's `PlayAutomationEvent` is kept the same way under `/O2`. Comparing the table (the
  entry count and each entry's target offset inside the function) with the old image's would lift that; the orchestrator
  records it as a roadmap item.
* **ADDR32NB to old data outside an instruction** (a table of image-relative offsets to bound data in `.rdata`, as some
  hand-written tables or `/jumptablerdata`-style constructs could produce) stays CML3101: there is no register to add, the
  consumer adds *some* base, and which one cannot be known.
* **Instructions the decoder does not know.** VEX/EVEX arrive with WP-38; until then a function compiled with `/arch:AVX`
  that reaches old data image-relatively behind a VEX instruction is refused (CML3101, the message shows the bytes).
* **`tests/fuzz/gen_seeds.cpp`** has no seed with the new wire kind (not in this package's directories).
