# WP-34: early debugger re-attach after a hot-restart (`restart {hold_new}`)

ADR-0040, diagnostic ids CML5813-5819 (broker) and the existing CML5994-5997 (Visual Studio extension, ADR-0038). Control capability
`restart-hold`, event `restarting`, command `restart-resume`. Builds on WP-21 (hot-restart) and WP-31 (Visual Studio extension).

## Why

WP-31 attaches the debugger after `restarted`, when the new process has already run its start-up code: a breakpoint in `main()`,
a static initialiser or a `DllMain` is never hit. With `hold_new` the broker creates the new process **suspended**, tells the client, and
keeps it suspended until the client has attached the debugger.

## Protocol

Capability `restart-hold` is advertised in `status` when `restart` is (the Windows broker). A client that does not see it must not send
`hold_new`; a broker that cannot hold answers it with CML5819 and touches nothing.

| | Shape |
|---|---|
| request | `restart {pid?, timeout_ms?, registration_timeout_ms?, hold_new?: bool, hold_ms?: 1..60000}`. `hold_ms` defaults to 10000 (0 or absent), the maximum is 60000. Anything else (`hold_new` not a boolean, `hold_ms` out of range) is CML5818 before anything is touched. |
| event | `{"event":"restarting","old_pid":N,"new_pid":M,"hold_ms":H}`: published once, when the new process exists and is suspended. Opt-in like `restarted` (`subscribe {events:["restarting", ...]}`); sent only to a held restart. |
| command | `restart-resume {pid: M}` -> `{pid, resumed:true, held_ms}`. Answers when the process runs. `pid` is the `new_pid` of `restarting`. |
| result | the `restart` result and the `restarted` event are unchanged and come after the resume and the registration. |

Without `hold_new` (absent or `false`) the request, the sequence, the events and the result are exactly those of WP-21: the process is
created running, no `restarting` event, no hold bookkeeping.

### Timeline of a held restart

1. prepare (pre-restart hooks), take over, snapshot the baselines, terminate the old process: as WP-21, within `timeout_ms`.
2. `CreateProcessW(... CREATE_SUSPENDED)`: the new process exists, **its first thread has not run**, so the agent is not loaded and nothing
   connects to the broker. `restarting` is published.
3. The restart waits (the *hold*) for the first of: `restart-resume` (resume, no diagnostic), `hold_ms` elapsed (resume, warning
   CML5813), the requesting client's connection closed (resume, warning CML5816, the restart goes on), the broker stopping (resume, error
   CML5815, the restart ends), the held process ended by somebody else (CML5812).
4. The thread is resumed. **The registration budget (`registration_timeout_ms`) starts now**: the time held does not count against it.
   From here on the restart is WP-21's (register by token and pid, re-enable modules, re-apply edits, `restarted`).

**The agent DLL.** The application creates its agent itself (`CreateDefaultAgent` loads `cml_agent.dll` from its own start-up code), and
a suspended process runs no start-up code, so the new process neither loads the agent nor connects to the broker while held. This is
why the registration wait begins at the resume, and why the `Hello` of the new agent can only arrive after it.

**Reloads** stay held off for the whole restart, the hold included (the reload lock is taken before the preparation and released when the
restart ends): a `reload` during the hold is refused busy (CML5304), a second `restart` is CML5803.

**Same connection.** `restart {hold_new}` is served on a worker thread of its control connection, while the connection thread keeps reading.
So `restart-resume` may be sent on the very connection that sent `restart` (the Visual Studio extension does), and a client that disconnects is
noticed at once. Every other request, and `restart` without `hold_new`, is served inline as before. (The Visual Studio control client
serialises calls; `restart-resume` is its one `concurrent` call.)

## Every way out of the hold (the process is never left suspended)

| Situation | What happens | Id |
|---|---|---|
| `restart-resume {pid}` | resumed; `restart-resume` answers `resumed:true` | none |
| nobody resumes within `hold_ms` | the broker resumes it; the restart goes on | warning CML5813 |
| the requesting client disconnects while held | resumed at once (the pipe's end is noticed by the connection thread); the restart goes on to `restarted` | warning CML5816 |
| broker shutdown (`ReloadService::cancel()`, then the control server stops) | resumed; the restart ends before registration | error CML5815 |
| the held process is ended by a debugger or the user | detected (the process handle is signalled), reported at once | CML5812 |
| `ResumeThread` fails | the process is terminated (a frozen process is worse), reported to the restart **and** to `restart-resume` | CML5817 |
| the new process does not register after the resume | as WP-21: left running | CML5808 |
| an error before the process exists (agent refuses, open/terminate/launch fails) | nothing is held, no `restarting` event; `restart-resume` for the pid is CML5814 | the WP-21 id |
| any other return path while held | `end_hold` runs on every path of the hold; the process object's destructor (Windows host) also resumes a still-suspended thread | none |
| `restart-resume` for a pid that is not held (never, or already resumed) | clean diagnostic, nothing else happens; the message says "not held any more (it was resumed: restart-resume / hold_ms expired / client disconnected / broker shutdown / process exited)" for the last 16 | CML5814 |
| `restart-resume` without a usable `pid` | diagnostic | CML5818 |
| a second `restart-resume` while the first waits | both answer ok (idempotent) | none |
| the broker would exit as idle while a restart runs | it does not: `--exit-when-idle` waits for `ReloadService::restart_active()` | none |

**Not covered:** a broker that is *killed* (not stopped) while it holds a process cannot resume it, and nothing else does; the process
stays suspended until it is killed. The hold is at most 60 s, but the timer lives in the broker. A watchdog child process that resumes
the thread when the broker's process object is signalled would close this gap; it was left out (see "Deferred").

## Visual Studio extension

* Decision (`ReattachCoordinator.ShouldHoldNewProcess`): re-attach is on **and** the broker has `restart-hold`. Then `HotRestartAsync`
  sends `restart {pid?, hold_new:true, hold_ms: 30000}` (`ChameleonSettings.RestartHoldMs`), after `ExpectRestarting()`.
  Otherwise it sends the WP-31 `restart` and attaches after `restarted`.
* `BrokerSession` subscribes to `restarting` when the broker has `restart-hold`. A `restarting` event is handled only when
  `TryClaimRestarting()` says this extension asked for it (another client's held process is that client's to resume).
* `ReattachCoordinator.OnRestartingAsync(old, new, resume)`: attach (the WP-31 engine reuse and retry loop, `OnRestartedAsync`), **then**
  `restart-resume {pid: new}`. The resume runs in a `finally`: it happens when the attach succeeded, was not needed (the debugger was not
  attached to the old pid), failed (CML5997, after the usual 3 attempts), was too slow (`HoldAttachTimeoutMs` 20 s, shorter than the hold, CML5997
  "did not finish attaching within 20 s"), was cancelled, or threw. A resume that fails is reported as CML5997 ("could not tell the broker to
  resume"); the broker resumes by itself after `hold_ms`. CML5814 (the broker had resumed it already) is only logged.
* The later `restarted` event finds the pair handled (`Duplicate`): one attach per restart.
* Diagnostics stay in CML5994-5997 (no new ids).
* The `restart-resume` request does not wait behind the unanswered `restart` on the same pipe (`ControlClient.CallAsync(..., concurrent: true)`).

## Manual checklist (Visual Studio UI; the user runs it)

Needs the Chameleon VSIX from this branch, a build of an application with the agent, and a breakpoint in start-up code.

1. Build `fixture_hot_restart` (or your application) with the agent. Start `cml_broker.exe --headless` (or let the agent start it).
2. In Visual Studio open the project, set a breakpoint on the first line of `main()` (and, if you like, in a static initialiser).
3. Start the application under the debugger (F5, or Attach to Process). Let it run past `main()`.
4. Tools > Chameleon: "Re-attach debugger after hot-restart" is checked. The Output pane "Chameleon" says `connected ... capabilities: ... restart-hold ...`.
5. Tools > Chameleon > Hot-Restart. Expect in the pane: `hot-restart ..., holding the new process for the debugger`, `hot-restart: pid N is held ...`,
   then `debugger attached to pid N before it ran ...`, then `hot-restart ok`.
6. **Expect: the breakpoint in `main()` is hit** in the new process (before the first output line of the new process), the call stack shows `main`.
   Continue; the application runs; `Show Output` has no CML5997.
7. Switch the setting off, hot-restart again: no `holding` text, the old behaviour (attach after `restarted`; the `main()` breakpoint is not hit).
8. Slow attach: with the setting on, restart while VS is busy (for example while it indexes); if the attach takes more than 20 s the process
   runs without the debugger and CML5997 "did not finish attaching" is in the Error List with the manual-attach advice.
9. Close Visual Studio while a restart is held (Hot-Restart, then immediately close): the application must run (CML5816 in the broker log), not stay frozen.

## Deferred

* A watchdog for a **killed** broker (see above). A helper process that duplicates the thread handle and resumes it when the broker's
  process handle is signalled (and is told by an event that the broker resumed already) is the plan; it needs a second mode of `cml_broker.exe`
  and was judged too large for this package.
* The Tools > Options page does not expose `RestartHoldMs` / `HoldAttachTimeoutMs`; they are settings of `ChameleonSettings` (30 s / 20 s).
* VS Code has no debugger hand-over and does not use `restart-hold`.
