## How the scenario finds the externally built program

The generated project is not a fixture: cmltest cannot copy it (the PDB holds the absolute paths of `bench-src`) and should
not build it (900 TUs). So the scenario declares `external = true` and the job passes the two paths:

```
python tests/bench/gen_pdb_project.py bench-src --tus 900 --funcs-per-tu 1000 --headers 24 --seed 1 --debug-format Z7
cmake -S bench-src -B bench-build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_CXX_COMPILER=cl -DCML_REPO_ROOT=<repo>
cmake --build bench-build --parallel
cmake --build build --target cmltest cml_broker cml_agent
build/bin/cml_broker.exe check --verbose bench-build/bench_project.exe
CML_PERF_JSON=perf-large-reload.json build/bin/cmltest.exe --scenario tests/bench/scenarios/large_pdb_reload.toml \
    --build-dir build --require-all-capabilities --external-exe bench-build/bench_project.exe --external-source bench-src
pwsh tests/ci/perf_results.ps1 ... -LargeReloadJson perf-large-reload.json -Out perf-results.json
```

Godot: `pwsh tests/corpus/run_corpus.ps1 -Project godot -Compiler msvc -ChameleonBin <bin> -WorkDir <dir> -ReloadBudgetMsPerTu 3000`.

## What was learned

* **A warm reload inside a 546 MiB PDB costs about 107 ms beyond the compiler**, against 39 ms in the small fixture. The
  difference is the plan stage (34 ms: 1159 functions of the TU compared with the running image) and the sweep (10 ms:
  927 tracked files are stat'ed, one is hashed). Nothing in a warm reload scales with the PDB size: the index is not
  mapped again (`release_pdb_after_reload` is off by default) and no stage walks the symbols of other compilands.
* **The first reload of a session is ten times slower (1139 ms), still under the plan target.** Three one-off costs, from
  the broker log of the run:
  * plan, 317 ms: the broker reads the whole module file (297 MiB) to compare function bodies (`Run::module_image`, kept
    for the session);
  * link, 403 ms of which about 320 ms is `detect_module_linker`: it reads the whole module file a second time and opens a
    second index of the PDB (126 ms) to learn which linker built the module; the link itself is 47 ms;
  * hooks, 395 ms inside the agent's `InstallHooks` for 275 hooks, against 2.3 ms for the same 275 hooks afterwards. The
    agent log carries no timestamps, so what the first installation spends its time on was **not determined**.
* **Broker memory is 14 MiB under its limit, and that is the finding of this package.** The peak (836.8 MiB) is the PDB
  index (about 215 MiB of allocations) plus two private copies of the 297 MiB executable at the first link: the one kept
  for the function comparison and the transient one of `detect_module_linker`. After the session's first reload the
  broker holds 528 MiB. The generated executable is large for its PDB (0.54 x; Godot: 119 MB for 529 MB), which is why this
  shows here and would not in Godot. The limit was not touched. Anything that adds memory at reload time (WP-37's type
  reader, for one) will cross it; reading only the headers in `detect_module_linker`, or mapping the module file instead of
  reading it, would take 297 or 594 MiB off the peak. Both are in `core/cml_toolchain` / `core/cml_pe`, outside this
  package, and ADR-0042 allows broker changes here only for the time budget, so nothing was changed.
* **cl /Od switch statements defeat hook narrowing.** 275 hooks are installed for an edit of one function: the 274 others
  are the TU's functions with a jump table (`unverifiable - IMAGE_REL_AMD64_ADDR32NB to '$LN13' in code`). They are
  re-hooked on every reload of the TU. It costs about 2 ms here; it is noted for whoever touches hook narrowing next.
* A cold build of the generated project takes 3 minutes on the runner (the job's old comment called it "the long
  build"), so a change of the generator, of `Chameleon_API.h` / `fixture_runtime.h` or of the runner's MSVC toolset costs
  one 3-minute build per cache scope (branch, pull request, main).
* PowerShell: the first corpus runs ended red after a green matrix with "Argument types do not match". The export used
  `@($list)` on a `List[object]` of custom objects and wrote `$row.line` into a `List[string]` without a cast; both were
  replaced (`ToArray()`, `[string]`) in one commit and the next run was green, so which of the two it was is not known.

## Guards against a budget that passes without measuring

* `perf_report`: fewer than five recorded reloads, a `timing_ms` without one of the ten stages, a non-number, a negative
  value or `total < compile` fail the step (WP-27's `validate_timings`, unchanged); every `reload` step must report
  `patched = 1` and the program must print the new value, so a reload that did nothing cannot be counted.
* The CI step fails when the scenario exits 0 without the `WP39-RELOAD` line (five reloads, budget 3000).
* The cached program is checked against the generated sources (manifest in the cache key, and `--ticks 2` prints the
  initial value).
* Corpus: `Add-ReloadTiming` throws on a missing or non-numeric stage, a negative value, `total < compile` or a result
  without `compiled >= 1`; `reload-budget` fails when nothing was measured or fewer reloads were measured than edits passed.
* Median and maximum are both reported; nothing is averaged.

## Deviations from ADR-0042

* None in the budgets or the measure. No broker code was changed.
* The evidence lines carry more than the ADR's prefix: `WP39-RELOAD` is followed by the ten stage medians
  (`<stage>_median_ms=`), `WP39-GODOT` by `tus=N` and the eight remaining stages.
* The raylib and ImGui cells print `WP39-RAYLIB` / `WP39-IMGUI` lines too (recorded, `budget_ms=none`); only Godot asserts.
* The Godot budget is a parameter of the driver (`-ReloadBudgetMsPerTu`, set in `corpus.yml`), not a key of
  `godot/project.json`: WP-37 edits that file, and its hash keys the Godot build cache.

## Deferred / limitations

* **The first reload's one-off costs were measured, not removed** (they are under the plan target). Removing the second
  read of the module file and the second PDB index in `detect_module_linker` would cut about 320 ms and 297 MiB.
* **The 395 ms of the first `InstallHooks` are unexplained** (see above).
* **One program, one TU shape.** The reload target has 1000 functions and no header shared with other TUs is edited; a
  header edit that recompiles many TUs of the large project is not measured here (the Godot cell has two 3-TU edits).
* **Shared runners.** The medians are far from the thresholds. The memory figure is 14 MiB from its limit but repeated
  to 0.26 MiB over five runs (WP-39b below takes the second copy of the module file out of it). The first Godot reload (up to 1241 ms) is under the plan target by a margin smaller than
  its run-to-run spread; the CI threshold is 3000 ms.
* The scenario edits the generated tree in place; cmltest restores it, but a killed cmltest leaves `src/tu_0450.cpp`
  edited. Run the generator again (it is deterministic).
* The index of the benchmark program is ready 5.2 s after the module is enabled; that is reported, not budgeted.

## WP-39b: the broker does not read the module file twice (follow-up, branch `wp/39b-module-read`)

The orchestrator ruled that the memory finding above is fixed at once: a gate 14 MiB under its limit goes red on the next
unrelated broker change. The limit (1.5 x PDB + 32 MiB) and the 3000 ms budget are untouched.

### What proves it

* `tests/unit/pe/test_pe_file_headers.cpp`: of a 32 MiB file exactly 4096 bytes are read and they parse like the whole
  file; NT headers at offset 0x2000 are followed and the read ends at the section table; every truncation gives the
  whole-file reader's diagnostic.
* `tests/unit/toolchain/test_linker_detection_file.cpp`: a module file that ends right after its section table (its
  section claims 256 MiB of raw data that are not there) is detected like the same headers followed by 24 MiB; header
  errors are still CML1301/1303/1305/1306/1300 with the path in the message. On Windows, with everything after the first
  64 KiB locked through another handle, `pe::read_file` fails (the control) and the detection succeeds.
* `tests/harness/tests/test_unified_diff.cpp`: a patch whose second write fails hands back the first file's content.

### Not done

* **`Run::module_image` still holds a private copy of the module file** (297 MiB here, for as long as the module is
  enabled). Turning it into a file mapping is not a local change: `pe::OwnedImage` owns a `std::vector`, the type is shared
  by `ModuleState`, `FileProcessModules` and the pipeline, the only mapping class lives privately in `cml_pdb`, and a
  mapping of the module file held by the broker is the ADR-0017 hazard again (a relink of the module during a hot-restart
  would fail with `ERROR_USER_MAPPED_FILE` where a private copy lets it through), so it needs a release point and a
  Windows test of its own.
* The transient whole-file reads of the module at enable time (`audit_opened_module`) are untouched; they are not at the
  peak.
* The first `InstallHooks` cost and the jump-table narrowing finding are recorded in the roadmap by the orchestrator.
