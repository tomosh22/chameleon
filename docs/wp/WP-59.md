# WP-59: clang's `??_B` bitmask guards are guards (R-67; ADR-0046)

Branch `wp/59-bitmask-guards`, one PR. Review: high (bind planner). Diagnostics: CML3600 (two new messages), no new id.

## The defect

WP-52 found it (docs/wp/WP-52.md, "Deferred"): without thread-safe statics (`-fno-threadsafe-statics`, which clang-cl's
`/Zc:threadSafeInit-` turns on) clang guards the statics of an inline (externally visible) function with ONE external
bitmask per function, `??_B<scope>@5<n>`, in a COMDAT of its own. `is_guard_variable` knew `?$TSS<n>@` and `?$S<n>@` only,
and the guard rules (`settle_guards`, `require_bound_guards`, `guard_scope_statics`) looked at internal symbols only, so
the bitmask was planned as ordinary data: `decide_defined` bound it to the old bitmask by its public symbol, or made it new,
whatever the edit did to the function's statics. Two ways that goes wrong (both accepted on main, see the tests):

- a static declared in front of the others (`b2_front`): the new static takes bit 0, which the running program set for the
  old first static, and is never constructed; the old first static now takes bit 1, which is clear, and is constructed
  again over the live object;
- a static that was constant-initialised becomes dynamic (`b4_late`): the old image has no bitmask of that name, the patch
  gets a fresh one, and the bound static is constructed again over the live object.

### Evidence: clang-cl 18's names and bits

Built on Linux with clang-cl 18.1.3 (`--target=x86_64-pc-windows-msvc /O2 /Z7 /Zc:threadSafeInit-`), names from the
symbol table, storage classes from `llvm-readobj --symbols`:

| Function | Statics | Bitmask |
|---|---|---|
| `inline int f()`, statics in blocks 1 and 2 | `?a@?1??f@@YAHXZ@4UObj@@A`, `?c@?2??f@@YAHXZ@4UObj@@A`, ... | `??_B?1??f@@YAHXZ@51` (external, .bss COMDAT): one for both blocks |
| `inline int nested_first(int)`, the first static in block 4 | `?in@?4??nested_first@@YAHH@Z@4...`, `?out@?1??...` | `??_B?4??nested_first@@YAHH@Z@54` |
| `ns::nf()` | `?n1@...`, `?c@...` (`static int c = 3;`), `?n2@...` | `??_B?1??nf@ns@@YAHXZ@51` |
| a lambda in an inline function | `?ls@?1???R<lambda_1>@?0??lam@@YA?A?<auto>@@XZ@QEBA?A?3@XZ@4UObj@@A` | `??_B?1???R<lambda_1>@?0??lam@@YA?A?<auto>@@XZ@QEBA?A?2@XZ@51` |
| `S::m()`, `tf<int>()` | `?q@?1??m@S@@QEAAHXZ@4...`, `?tt@?1???$tf@H@@YAHXZ@4...` | `??_B?1??m@S@@QEAAHXZ@51`, `??_B?1???$tf@H@@YAHXZ@51` |
| `static int h()` (internal) | `?s@?1??h@@YAHXZ@4...` | `?$S1@?1??h@@YAHXZ@4IA` (unchanged rule) |
| `inline` with a `thread_local` | `?q@?1??with_tl@@YAHXZ@4...` | `??__J?1??with_tl@@YAHXZ@51` in `.tls$` (not this WP: thread_locals are WP-24's) |

- The bitmask is named in the scope of the function's first guarded static (`?4?` for `nested_first`), then `@5` and a
  number (in every probe the digit of that block). It guards every block of the function.
- The special name `?_B` is written raw, never put in the back-reference table: the lambda's `<auto>` is `?2` in the
  bitmask and `?3` in the static (whose own name `ls` is entry 0), clang 18's "not counted" reading of `$S1`.
- Bits (disassembly of `ns::nf()`): `n1` tests `0x1`, `n2` tests `0x4`; bit 1 is `c`'s, which is constant-initialised and
  never uses it. clang numbers the bits by the static-local number Sema gives every static of the function in declaration
  order (`ASTContext::getStaticLocalNumber`, constant-initialised statics and thread_locals counted too), not in the order
  they are reached; cl's `$S1` of an internal function hands them out as reached (WP-40). Either way only the unchanged
  function proves the old bits are the patch's.
- An inline function with more than 32 guarded statics is an error in clang ("cannot yet compile more than 32 guarded
  initializations in this ABI"): one bitmask per function always.

## What was built

- `bind_names`: `is_inline_bitmask_guard` / `inline_bitmask_scope` read `??_B<function scope>@5<n>` (`<n>` a digit or
  hexadecimal letters closed by `@`); `is_guard_variable` is true for it. `local_scope_key` reads its scope with an empty
  back-reference table (both readings the same) and writes the closing `@5` as the statics' `@4`, so that the bitmask's key
  is the key of its function's statics.
- `bind_plan`:
  - `guard_scope_statics`: a `??_B` is a bitmask (the function, every block) and is tied to the external statics of its
    function too (an inline function's statics are external). `raw_guard_covers` and `bitmask_function` read the name
    (`??_B?1??counter@@YAHXZ@51` -> `?counter@@YAHXZ`).
  - `settle_inline_bitmask` (called by `settle_guards` for every `??_B`), the rules of cl's `$S1` (ADR-0043 ruling) for a
    bitmask that `decide_defined` bound by its public symbol or made new; the section layout never places it:
    a static of its function refused: not bound either; statics bound next to new ones: CML3600; every static new: a new
    bitmask (also where the old image has one of that name); every static bound: the old bitmask, found by its name, and
    where the old image has none: CML3600; no static tied: kept as decided (new and untied: the warning CML3211).
  - A bound `??_B` is listed in `BindPlan::bitmask_guards` with its function; the pipeline's `prove_bitmask_guards`
    (hook_narrowing.cpp, unchanged) keeps it only when the function's code is the old code, CML3600 otherwise.
  - `require_bound_guards`: an external static counts where a guard is tied to it (only a `??_B` ties external statics).
- Fixture `planner_pairing_o2`: `bitmask.cpp`, compiled with `/Zc:threadSafeInit-`: `o2_bits_counter()` is `inline` and
  `noinline` with two statics `first` / `second` (bits 0 and 1). `TICK ... bits= bsec= bmade= bmark=`; edit `bits_5`
  changes `o2_bits_mark()` only. The scenario requires `patched = 1` under clang-cl and allows CML3207 / CML3211 /
  CML3600 under cl; `bits` and `bsec` must continue from their last values (`since_reload`), `bmade` stays 2.

## Tests that fail on main

All in `test_bitmask_inline.cpp` (main 910f203, the names tests without the new function):

- `R-67: clang's bitmask of an inline function's statics is a guard variable (real clang 18 names)`:
  `CHECK(is_guard_variable(kBits))` (main: false).
- `R-67: the bitmask's scope is its function's, ...`: `REQUIRE(g.has_value())` (main: no key for `??_B`).
- `b1_other` (another function edited): `REQUIRE(c.plan.bitmask_guards.size() == 1)` (main: 0, the bitmask bound as data
  with nothing to prove it).
- `b2_front` (a static in front): `CHECK_FALSE(c.planned)` (main: planned, the reset above), then the CML3600 naming
  `??_B?1??counter@@YAHXZ@51` and `counter::z`.
- `b3_edit` (counter itself edited): `REQUIRE(c.plan.bitmask_guards.size() == 1)` (main: 0), then the proof's CML3600
  "the code of 'counter' changed".
- `b4_late` (a constant-initialised static made dynamic): `CHECK_FALSE(c.planned)` (main: planned, a fresh bitmask over
  the live `a`), then CML3600 "the old image has no bitmask of that name".
- `b5_new` (counter gains its statics) passes on main as well: a new bitmask, no warning.

## What was learned

- `??_B` (and `??__J`) are clang's spelling of MSVC's guard of an inline function's statics; clang's own comment in
  MicrosoftMangle.cpp says MSVC uses the same mangling there. So cl may name the fixture's bitmask the same way; whether cl
  records it (S_GDATA32 next to the statics) is not known: the scenario allows a refusal under cl.
- The bits are clang's static-local numbers (declaration order, every static of the function), not the order of first
  use; the code proof covers both.

## Deferred

- `??__J<scope>@5<n>`, the thread-local bitmask of an inline function's `thread_local` statics: not recognised. Its
  statics are thread_locals, which WP-24's rules (CML3400 and the S_GTHREAD32 lookup) govern; binding it is a change of
  those rules.
- A bitmask whose function is inlined into its callers as well as emitted: the proof compares the function's own code
  only (as for cl's `$S1`). An inline function inlined everywhere is not in the patch, has no hook, and its bound bitmask
  is refused ("not the old version of a function of the running program"): an edit of a file whose inline function with
  such statics was inlined everywhere is refused under `-fno-threadsafe-statics`.
- The proof's message still says the bits go "in the order they are reached" (cl's `$S1`); for `??_B` it is declaration
  order. The proof itself (an unchanged function) is the same.
