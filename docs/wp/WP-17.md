## Hook records

The macro writes one 24-byte constant `{u32 magic 'CMHK', u32 kind, fn, const char* key}` into `.cmlhk$a`
(pre-patch), `.cmlhk$b` (post-patch) or `.cmlhk$c` (the rest); the linker merges them into `.cmlhk`. `key` is
`"<__FILE__>|<function expression>"`. The layout is part of the agent ABI (`cml_hook_entry`); ABI version stays 2
because the change is additive. The agent reads the section with `ReadProcessMemory` (an error instead of a fault),
rejects records whose function or key lies outside the image, and caps a module at 4096 records.

## When the hooks run

* **Pre / post patch**: inside the handler of one `InstallHooks` request that installs at least one function. One
  collection (`user_hooks::Session`) serves the whole request: pre-patch hooks, install (the only part with
  threads stopped), commit of the patch(es), post-patch hooks, then the answer. **Once the pre-patch hooks ran the
  post-patch hooks always run**, also when the install failed (state torn down in `pre` must be rebuilt); they ask
  `cml_last_patch_status()` (0 or the CMLnnnn id; export `cml_agent_last_patch_status`, resolved by name from the
  loaded `cml_agent.dll`, needs no handle). Synchronised mode: the whole handler is one SyncPoint job, so it runs on the
  thread that calls `SyncPoint()`. Immediate mode: on the agent thread. A revert or an empty request runs no patch hooks.
* **Compile hooks**: `CompileEvent`. Synchronised mode: queued like the patches and run at `SyncPoint()` in the order
  the broker sent them. Immediate mode: on a separate worker thread (created on first use, ordered, bounded queue of
  256, joined by `stop()`), so a slow compile hook never stalls `ReserveRange` / `LoadPatch` / `InstallHooks`.
* No agent lock, no installer lock and no suspended thread while an application hook runs.
* A hook that raises a processor exception (or lets a C++ exception escape) is caught with SEH, reported as
  CML5652, and the next hook runs. A stack overflow is caught too: the guard page is restored with `_resetstkoflw()`
  (as WP-08 does for initialisers); if that fails the thread runs no further hooks (CML5657).
* **What a hook may not do** (`Agent::HookThread`, a thread-local): `DestroyAgent` from inside any hook is refused
  (`CML_STATUS_INVALID_ARGUMENT`, CML5655 in the log); a blocking `WaitForRequest` (timeout above 0) from a hook on
  the agent thread (immediate-mode patch hooks) fails at once with status 5656; polling with timeout 0 is fine.
  Hooks run by `SyncPoint()` on the application's thread may wait: the agent thread is free.

## Which records run (patches repeat hooks)

A reload recompiles a whole unit, so the patch image holds a copy of every hook record of that unit. A record's
identity is `(module, kind, file name, function expression)`: the key the macro writes is `"<__FILE__>|<fn>"`, and only
the file NAME (lower case) is compared, because the original build and the broker's recompile spell `__FILE__`
differently (relative or absolute, `/` or `\`). Rules:

1. every record of an **enabled** module runs (the original function reaches the patched code through the installed hook);
2. a patch image counts only when it is **committed** (its InstallHooks succeeded, `PatchLoader::commit_hooked`) and
   the module it patches is enabled. A patch is invisible after LoadPatch, during fix-ups and initialisers, while a
   synchronised-mode InstallHooks is pending, and after a CML5309 timeout until its hooks really apply. The target
   module is found from the hooks themselves (the module that holds the old entries; for a function an earlier
   patch added, that patch's target);
3. a record of a committed patch runs only if its target module has no record of the same identity (a hook the patch
   added); of several patches of one module the newest copy wins. Identities are scoped per module.

A hook deleted from the source keeps running (its original record is still in the module). A patch that hooks no
function is never committed, so records it adds stay invisible.

**Unload and running hooks.** `PatchLoader::acquire_hook_lease()` pins every live patch while a `Session` exists.
`unload_patch()` first hides the patch (committed = false, no new lease lists it), then waits (10 s, configurable for
tests) for the leases, and only then calls `FreeLibrary`. If a hook is still running after the wait the unload fails
with CML4212 (`kLoaderPatchBusy`), the patch stays loaded and stays hidden. A hook therefore never runs from an
image that is being freed. Module enumeration for a `Session` does not hold the loader's mutex.

## Diagnostics (CML5650-5699, `agent/src/hook/user_hook_ids.h`)

| id | message | what to do |
|---|---|---|
| 5650 | N hook record(s) of X point outside the image or have an unknown kind | build module and hooks with the same `Chameleon_API.h`; the records are skipped |
| 5651 | the hook section of X cannot be read | the module may have been unloaded; its hooks are skipped |
| 5652 | the K hook F raised exception 0x... | fix the hook; the next hook runs and the application continues |
| 5653 | X has more than 4096 hook records | register fewer; the rest are skipped |
| 5654 | no memory for a compile notification / hook collection | the hooks of that event are skipped |
| 5655 | `cml_destroy_agent` called from inside an application hook | do not destroy the agent from a hook; refused |
| 5656 | a blocking `cml_wait_request` from a hook on the agent thread | poll with timeout 0, or wait outside the hook; returned as the status |
| 5657 | a hook overflowed the stack and the guard page could not be restored | fix the recursion; no further hook runs on that thread |

## Decisions

* **Self-describing records with a key** instead of bare pointers in `$a/$b` with begin/end markers: no sentinel
  objects, kind in the record, and the key makes de-duplication against patch copies possible without the patch PDB.
  The plan said "via the patch PDB"; the in-memory section headers of the patch image give the same information.
* **FU-06**: a process-wide mutex/condition variable (static storage), not an Agent member, because the thread that
  drops the call count to zero must notify after its decrement, when the Agent may already be freed. Interpreted
  "event" as "blocking wait instead of polling".
* Pre/post hooks run per patch (one patch per recompiled unit), not once per reload.
* De-duplication key: file NAME (not path) plus function expression plus kind, scoped to the module (reviewer item
  5; the plan's "function name plus kind" would conflate two static functions of one name in different files).
* Post-patch hooks after a failed install: the hook signature stays `void(void)`; the outcome is a query,
  `cml_last_patch_status()`.
* The scenario error id for the synchronised timeout is CML5309 (the id the pipeline returns; CML5320 is the inner
  reason in its message).

## Deferred / limitations (for KNOWN_LIMITATIONS)

* A patch that hooks no function (only new functions or data) sends no `InstallHooks`, so no pre/post hooks run and
  the patch is never committed: hook records it adds stay invisible.
* `unload_patch` can wait up to 10 s for a running hook (and then refuses); in synchronised mode that stalls the
  agent thread meanwhile.
* Hooks run once per patch, so a reload of several units calls them several times.
* Hook deleted from the source keeps running.
* `CML_PRERESTART_HOOK` is registered but nothing calls it before restart exists.
* Hooks are not isolated from corrupting state; only the processor exception is contained.
* A hook must not call `DestroyAgent` (refused with INVALID_ARGUMENT).
* `ScheduleReload`, hotkeys and the per-session "apply automatically" toggle are not part of this package.
