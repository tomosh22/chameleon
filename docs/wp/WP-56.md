# WP-56: bind a nested lambda's static instead of refusing it (R-68, R-66; ADR-0046)

Branch `wp/56-nested-statics`, one PR. Review: high (bind planner). Diagnostics: none new (CML3207 as before).

## The cause (proven)

WP-52 refused, by its ruling, the two shapes in which a nested lambda's static was decided new next to its live record
(docs/wp/WP-52.md, "Ruling on the cl nested-lambda reset"). WP-56 finds the record instead.

So the cause is the one WP-52 guessed:

The static's name and the closure's unique name are each mangled with a back-reference table of their own. In the
static's name the table starts with the static's own name (`nested`), so the outer closure `<lambda_1>` is slot 1 when the
nested call operator's scope names it again (`??R1?1??`); in the inner closure's unique name the table starts with that
closure's own name, so the same `<lambda_1>` is slot 0 (`??R0?1??`). WP-37/40 compared the text after `??R` with the
unique name after `.?AV` as written (a prefix test), and the two never matched: no closure of the function had the static
(as far as the closure step could tell), `nested` and its guard were new, and the reload reset `nest` (CI 857fa31), which
WP-52 then refused.

### R-66: clang-cl, the record two lambdas up

clang 18 locally (`clang-cl --target=x86_64-pc-windows-msvc /O2 /Ob2 /Z7`, lld-link; `llvm-pdbutil dump --symbols`) for
nested.cpp without the fixture's `noinline`:

```
S_GPROC32 `f`
  S_LDATA32 `nested`
  S_INLINESITE        (f::<lambda_0>::operator())
    S_INLINESITE      (f::<lambda_0>::operator()::<lambda_1>::operator())
      S_INLINESITE    (o2_nest_make)
```

The planner looked for a lambda's static in its call operators and in the function that encloses its lambda
(`lambda_enclosing`: one level, here the outer call operator, which has no procedure). The record is a level further up.

## What was built

- `bind_names`: `resolved_qualified_name(text)` reads a qualified name (a unique name after `.?AV`) with WP-52's
  back-reference reader and a table of its own, and writes every name back-reference out; `resolved_decorated_name(name)`
  does the same for a whole decorated name (a call operator's `??R...`, whose operator name is not in the table). The text
  after the closing `@` (cl's TU discriminator) is kept as written; anything the reader cannot read gives no name.
- `bind_plan`, the closure comparisons (`closure_begins`): the static's scope after `??R` with its names written out (WP-52's
  `local_scope_key`; a guard in the patch compiler's spelling, `guard_spelling`, or both spellings where they agree) against
  the closure's unique name resolved (`ClosureId::key`). Where either side cannot be read, or rule (d)'s `closure_pairing`
  renames the closure, they are compared as written, as before. Used by the closure step (`pair_statics_by_closure`: the
  record of a member's closure, the records in a closure of its function, the closure's display name, the patch's call
  operator whose signature rule (d) step 1 compares), by WP-53's `own_closure_twin` and by WP-51's `refuse_inlined_owner`
  (the record's closure and the closures its procedure inlined). Log: `WP56-CLOSURE static=... closure=... resolved=...
  as-written=same|differs` (trace).
- The display of a function-local static whose scope has name back-references is read from the resolved key
  (`local_display`: cl's `1?1??o2_nest_step::operator()::...::nested` becomes
  `o2_nest_step::<lambda_1>::operator()::<lambda_1>::operator()::nested`) where the planner compares displays: the
  groups of pass A/B, the closure step's function, WP-40's enclosing function, the undefined-symbol chain, WP-53's list.
  The decisions keep `display_name`'s display (plan JSON unchanged). A scope without back-references keeps it everywhere.
- The enclosing-procedure search (R-66): `is_inlined_record` takes a record of every function of the chain of the static's
  enclosing functions (`o2_nest_step::<lambda>::operator()`, then `o2_nest_step`), not only the first. Such a record is an
  inlined record as in WP-40 (never paired by name; the layout or the place pairs it, or the counts refuse it), WP-40's
  count includes the own statics of every level of the chain, and WP-53 lists the pairing for the proof by the code of the
  procedure that holds the record.
- The proof (WP-53, `prove_inlined_lambda_statics`): an unchanged procedure proves a record only where the patch's version
  of the procedure refers to the static (a relocation inside the function names it). Otherwise CML3207, "the patch's 'f'
  does not refer to the static, so its unchanged code does not show whose the record is". WP-53's argument ("the old f used
  that record exactly as the new f uses the lambda's static") assumed the reference; with the chain search a procedure up
  the chain may not inline the lambda at all in the patch, and the canonical names WP-40 compares do not tell sibling
  lambdas apart (`f::<lambda_0>::operator()` and `f::<lambda_2>::operator()` are both `f::<lambda>::operator()`).
- Rule (d) is not given a resolved-only pairing to confirm: `note_lambda` and the pipeline's code comparison find closures
  as written. Where a pairing needed the resolution and another lambda of the same function holds a static of the name,
  none of them is paired by number (CML3207, "... cannot be confirmed by the code of their call operators ..."). One such
  lambda per function needs no confirmation (WP-37's same-set rule).
- WP-52's refusal (`refuse_reset_statics`) is unchanged: a static still decided new next to a record of its name in its
  function is refused.
- Fixture `planner_pairing_o2`: nested.cpp gains `o2_nest2_step()`, the same nest without `noinline` (R-66 under clang-cl),
  with its own `nested2` and maker; `TICK ... nest2=<800000+n> n2made=<1>`. The scenario's nest step now allows no
  refusal, requires `patched = 1` in every cell, `nmark=4`, and `nest` and `nest2` continuing (`since_reload`).

## Deferred

- WP-53's (1b), cl's inline-site position: under cl with `/OPT:REF` a nested lambda's static recorded only inside the
  inline site in the caller is still refused (`WP-52 ruling, kept by WP-56: cl's nested static recorded only in
  o2_nest_step, without a layout`). Not changed.
- Rule (d) with closures spelled by back-references: `note_lambda`, `closure_twin` and the pipeline's code comparison
  find closures as written. Two lambdas of one function with same-named statics that only the resolved names tie are
  refused instead of confirmed by code (above).
- The decisions' display names (messages, plan JSON) still come from `display_name`, which does not resolve
  back-references (cl's `1?1??o2_nest_step::operator()::...`). The planner's comparisons use the resolved display.
- The canonical names WP-40 compares (`canonical_lambda_names`) do not tell lambdas of one function apart; a record in a
  sibling lambda's call operator counts as an inlined record of the chain. The proof now requires the reference, which
  closes that hole for the pairings it judges.
