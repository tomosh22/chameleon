# WP-20: Crash -> patch -> continue

Plan section 4.11 with **Continue**, **Leave function** and **Ignore**. Re-execute function is WP-23.

## What was built

* **Agent** (`agent/src/crash/`): `ExceptionGate`, a vectored exception handler registered first (`AddVectoredExceptionHandler(1, ...)`
  at `Agent::start`). It does nothing until the broker switches it on. When on, it holds a thread that faulted in application code
  until a decision arrives, then resumes it (Continue), resumes it in the caller with RAX = 0 (Leave) or passes the fault on (Ignore).
  `exception_agent.cpp` is the agent-thread half: configuration, reporting held threads, executing decisions.
* **IPC** (`core/cml_ipc`, ADR-0032 block 0x0050-0x005F): `Exception` 0x0050 (agent -> broker event), `ExceptionAction` 0x0051
  (broker -> agent request, answered by `Reply`), `ExceptionConfig` 0x0052 (broker -> agent request, answered by `Reply`).
* **Broker** (`broker/cml_core`): `ExceptionService` turns `Exception` into the control event `exception`, remembers the held threads,
  answers the commands `exception-action` and `exceptions`, and tells the agents whether to hold anything at all (see "When a thread is
  held"). Options `crash_handler` (default `on`) and `break_with_debugger` (default `off`) via `set-option`.
* **Control pipe** (ADR-0032 shapes, fields were only added): capability `exceptions`; event
  `{"event":"exception","pid","tid","exception_id","code":"0xC0000005","address","module","function","offset","actions":["continue","leave","ignore"]}`
  plus `module_path`, `in_patch`, `access` (`read`/`write`/`execute`), `data_address`, `stack_pointer`; command `exception-action`
  `{pid, exception_id, action}` -> `{pid, exception_id, action}` (`pid` may be left out when the id is unambiguous); command `exceptions`
  `{pid?}` -> `{pending:[<event bodies>]}`. `subscribe` accepts the event name `exception`; it is **not** in the default subscription.
* **Harness** (`tests/harness/src/exception_steps.*`): steps `watch_exceptions`, `expect_exception`, `exception_action`,
  `expect_pending_exceptions` (see below).
* **Fixture** `tests/fixtures/crash` and the scenarios `crash_null_deref_fixed` and `crash_leave_function`.

## When a thread is held

The handler is first in the chain, so it also sees faults the application handles itself (`__try/__except`, guard pages, ...). The rules that
keep applications working:

1. Only the codes `EXCEPTION_ACCESS_VIOLATION`, `EXCEPTION_INT_DIVIDE_BY_ZERO`, `EXCEPTION_ILLEGAL_INSTRUCTION`. C++ exceptions, breakpoints and
   stack overflows are not touched.
2. Only if the faulting instruction lies in an **enabled module** or in a **loaded patch image**. A fault inside a system DLL that the
   application's code called (`memcpy(nullptr, ...)` in ucrtbase) is not held: the faulting address is the system DLL's.
3. Never on the agent's own threads (the agent thread and the compile-hook worker), never while the hook installer has the other threads stopped
   (`heap::alloc_forbidden()`), never when a debugger is attached unless `break_with_debugger` is on.
4. **Only while a control client listens for `exception` events and `crash_handler` is on.** The broker sends `ExceptionConfig` when a
   client subscribes or leaves and when the options change. Without a listener the handler returns `EXCEPTION_CONTINUE_SEARCH` at once: the
   application behaves as if Chameleon were absent. When the last listener disconnects (or the option is turned off) every held thread is
   released as Ignore and the pending list is cleared. A fault that reaches the broker after the listener left is answered Ignore.
5. **An application that handles one of these exceptions itself, in an enabled module, will see the prompt first while a client is
   subscribed.** Choose Ignore and the application's own handler runs as usual.

## The handler's rules (it runs on the faulting thread)

The faulting thread may hold the process heap or the loader lock. The handler therefore allocates nothing, logs nothing, takes no lock and
never calls the IPC layer. It fills one of `kMaxSlots` (8) preallocated slots (thread id, a copy of the `CONTEXT`, code, address), signals the
agent thread through the agent's wake event and waits on the slot's own event. The agent thread does everything else. A fault that finds no free
slot is passed on and counted (CML4403 is logged by the agent thread). The "is this address application code" table is double-buffered and
rebuilt by the agent thread only when the module list, the enabled set or the patch set changed (a dirty flag; enabled modules + live patch
images). The handler reads it without a lock: it counts itself in as a reader of the table it found active, re-checks that it is still the active
one, scans, and counts out; the writer fills the inactive table only when its reader count is zero, then flips (tested by "range table: lookups
never see a table that is being rewritten"). A held thread wakes every 500 ms to check that the gate is still on, so it can never wait for a gate that was switched off.

## The actions

* **Continue** resumes at the faulting instruction with the registers it had. See "Continue: the rule".
* **Leave function** computes the frame above the faulting one on the agent thread: `RtlLookupFunctionEntry` + `RtlVirtualUnwind` one frame
  (callee-saved registers are restored, so the caller carries on with its own locals); a function without unwind information is a leaf and
  its return address is read at `RSP`. Then `RAX = 0`, `XMM0 = 0`, resume at the return address. It works for patch code too (a patch DLL
  carries its own unwind data). It is refused with CML4401/CML4402 when the frame cannot be unwound; the thread stays held and the client may
  choose another action. Handlers in the frames that are left (`__try`/`__finally`, destructors) do not run.
* **Ignore** returns `EXCEPTION_CONTINUE_SEARCH`: the next handler, then the process's unhandled-exception handling.

### Continue: the rule

Continue re-executes the faulting instruction with the **register values it had at the fault**. It is safe exactly when the fix changes the
*memory* the instruction touches (or the function the instruction jumps through), not a register: a pointer that was null in a register stays
null and the instruction faults again. The same holds for a division: a zero divisor in a register stays zero; `idiv [mem]` with a repaired
operand works (`divide_by_zero_continue` in the unit test). Functions on the stack keep running their old code; only calls made after the hook
install see the new code. So the fixture is built so that the **fix runs on another thread while the faulting thread is held** and repairs
state the instruction reads (`tests/fixtures/crash`: the patched `maintain()` makes an inaccessible page accessible). If Continue does not help,
the instruction faults again and the thread is held again (a new `exception_id`, a new event): nothing is lost.

## Ordering of configuration

`ExceptionConfig` goes to an agent only after its Welcome is on the wire (`agent_ready` runs after the replies of the Hello were sent), so the
handshake is never disturbed. `refresh()` and `agent_ready()` hold one mutex from computing the configuration to sending it, so configurations never
cross; the last one sent was computed last, from the newest state of the event bus and the options. `refresh()` sends nothing when the answer is
unchanged, and asks several agents in parallel (one timeout, not one per agent). `holding_` (are the agents holding) is set and the pending list
cleared under the same mutex `on_exception` checks and inserts under, so no entry survives a switch-off. `subscribe` with `"events": []` is the default
set (the event bus reads an empty set as "everything", which would switch `exception` on unasked).

## Control commands and harness steps

```
exception-action {pid?, exception_id, action: "continue"|"leave"|"ignore"}  -> {pid, exception_id, action}
exceptions       {pid?}                                                      -> {pending: [<event>, ...]}
set-option       crash_handler (bool, default true), break_with_debugger (bool, default false)
subscribe        events: [..., "exception"]       (the answer comes after the agents acknowledged ExceptionConfig)
```

Harness steps (all need the broker capability `exceptions`, so they fail under `--require-all-capabilities` if it is missing):

| Step | Keys | Meaning |
|---|---|---|
| `watch_exceptions` | | `subscribe` for diag, patch_applied, log **and** exception; from here on faulting threads are held |
| `expect_exception` | `code`?, `function`?, `within_s` | the next `exception` event; code and function (substring) must match; it becomes the current exception |
| `exception_action` | `action`, `expect_error`? | `exception-action` for the current exception; with `expect_error` it must be refused with that id |
| `expect_pending_exceptions` | `count` | `exceptions` lists exactly `count` threads |

## Diagnostics

Agent, `agent/src/crash/diag_ids.h` (CML4400-4449):

| Id | Meaning | What to do |
|---|---|---|
| CML4400 | `ExceptionAction` for a thread that is not held (answered already, or never held) | Query `exceptions` for the open ones |
| CML4401 | Leave: no unwind information and the stack top is unreadable | Use Ignore, or Continue after a patch fixed the cause |
| CML4402 | Leave: the unwound frame is not a caller (RIP 0, RSP not above the old one, or not executable) | The stack looks damaged; use Ignore, or Continue after a patch |
| CML4403 | more threads faulted at once than the 8 slots: the extra faults were passed on (log) | Answer the held threads |
| CML4404 | `AddVectoredExceptionHandler` failed: crash handling is off (log) | none; the application's faults are unaffected |
| CML4405 | the handler's wait events could not be created: crash handling is off (log) | Free system resources |

Broker, `broker/cml_core/include/cml/core/exception_diag_ids.h` (CML5750-5799):

| Id | Meaning | What to do |
|---|---|---|
| CML5750 | `exception-action` / `exceptions`: missing or mistyped argument | Send `{pid, exception_id, action}` |
| CML5751 | no held thread with that `exception_id` (and `pid`) | Query `exceptions` |
| CML5752 | the agent did not answer / the connection is gone; the thread was dropped from the pending list | The application may have exited |
| CML5753 | an agent did not accept the crash-handler configuration (log) | Check the agent log |
| CML5755 | `exception-action` without `pid` while several processes hold a thread with that `exception_id` | Add `pid` |
| CML5754 | (info, log) a fault was released as Ignore because no client listens for exception events | Subscribe to `exception` before the fault |

## How to run

```
cmltest --scenario tests/harness/scenarios/crash_null_deref_fixed.toml ...
cmltest --scenario tests/harness/scenarios/crash_leave_function.toml ...
ctest -R "unit.agent_exception|unit.ipc|unit.broker_core|unit.harness|fixture.crash"
```

By hand: start the broker with `--control-pipe`, `subscribe` with `{"events":["exception"]}`, run an application with the agent and
`EnableModule`; when a fault arrives in an enabled module the event appears and the application's thread waits.

## Decisions

* The handler is registered once per process and never removed (the agent DLL is never unloaded); with the gate off it is a few loads and a
  return.
* The agent never decides whether a client exists: the broker does, and tells it (ExceptionConfig). The agent also switches itself off when its
  session ends, so a dead broker never leaves threads held.
* `exception-action` waits for the agent's verdict (a `Reply`), so a refused Leave is reported to the caller and the thread stays held.
* `subscribe` is answered after the agents acknowledged the configuration, so a client knows holding is in effect when `subscribe` returns.
* Function names come from the module's PDB index (`find_proc_by_rva` + `display_name`); a fault in a patch image reports `module: "(patch)"`,
  `in_patch: true` and no function (patch PDBs are not indexed).
* Breakpoints (`EXCEPTION_BREAKPOINT`) "when configured" are not handled: not needed for the acceptance scenarios (see below).

## Deferred / limitations (for KNOWN_LIMITATIONS)

* Continue cannot repair a register (see "Continue: the rule"); Re-execute function is WP-23.
* Only faults whose faulting instruction is in an enabled module or a patch image are held; a null pointer passed to a system DLL function
  faults inside that DLL and is not held.
* A thread that holds the loader lock or a lock the agent needs while it is held can block loading a patch (the agent loads patches with
  `LoadLibrary`). Holding is meant for ordinary application threads.
* The vectored handler is registered "first" at the time of the call; a handler registered later with `First = 1` by the application runs
  before it.
* Breakpoints and other exception codes are not handled.
* Leave skips `__try/__finally` and destructors of the frames it leaves; it is for getting past a fault, not for clean unwinding.
* A fault in a patch image reports no function name.
* One agent per process is assumed for the gate (it is process-wide state).
* More than 8 simultaneous faults: the extra ones are passed on.
