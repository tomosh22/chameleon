## How the checks decide

* **Image**: `cml_pe` loads the module; PE32 (CML1303) or a machine other than AMD64 is CML1106 (FAIL).
* **PDB**: `PdbIndex::open_for_pe` (use_cache off, ADR-0017); a PDB that is missing or of another build is a FAIL finding with the
  reader's id (CML1410 / CML1411), and the remaining checks, which need the PDB, are not evaluated.
* **CML1101 (full PDB)**: the PDB is the evidence. FAIL when up to 16 sampled compilands that contributed code list no function symbol (a
  FASTLINK or stripped PDB). Only when nothing could be sampled does the linker's command line decide: `/DEBUG:FASTLINK` is fatal for
  link.exe, where `/DEBUG` is last-wins (`/DEBUG:FASTLINK /DEBUG:FULL` is a full PDB), and never for lld-link, which writes a full PDB
  whatever it is given.
* **Per compiland** (source compilands only: not library members, imports, `* Linker *`, MASM/CVTRES): the recorded command from
  `S_ENVBLOCK` or `S_BUILDINFO` (CML1102), `cml_toolchain::detect_compiland_flags` for `/GL`, `/guard:cf`, `/Gy` (with the recorded `.obj`
  when it is still on disk, up to 8 MiB each and 128 MiB in all), the S_COMPILE3 managed bits (CML1504), and whether the command allows
  inlining (optimised and no `/Ob0` / `-fno-inline`; a command with no `/O` option is `/Od`). At most 4000 compilands are examined.
* **CML1104 (`/guard:cf`)** is decided by the module: `detect_module_guard_cf` (DllCharacteristics plus a non-empty function table, never
  GuardFlags alone: ADR-0015), or, when that is unknown, the linker's `/GUARD:CF`. A CFG-enabled image is a FAIL. A compiland compiled
  with `/guard:cf` in a module linked without `/GUARD:CF` is a WARN: the image has no CFG table.
* **CML1601**: up to 64 function publics of source compilands, evenly spread; PASS when all of them have six `CC`/`90` bytes before the entry.
  A WARN when some do not, or when none could be sampled.
* **CML1602**: from the linker command line in the `* Linker *` compiland (`/OPT:` lists, last wins; with `/DEBUG` the defaults are NOREF and NOICF).
  When no linker command line is recorded the check is a WARN "cannot be determined", never a FAIL.

## CML3104: what is and is not true

The first wording ("copies inlined into other translation units keep the old code") was wrong for every configuration the audit
accepts. Without `/GL` (refused by CML1103) a function defined in a `.cpp` can only be inlined into callers of the SAME translation
unit; those callers are recompiled with it, their bytes change, and narrowing keeps them hooked. An inline function in a header is
recompiled in every includer (WP-15 re-reads all compilands that include the changed header). So no stale copy lives in a translation
unit that is not recompiled. What can still keep old code: (1) a caller on a thread's stack, which is the documented behaviour for
every function, and (2) a caller whose hook was narrowed away because its bytes did not change; in that case its inlined copy did not
change either, so it is not stale. The message now says only this: a caller that is still executing, or whose own code did not change,
keeps the old code. It is one warning per compiland and reload (it names the small changed functions), advisory, and I conclude it can
**never flag a genuinely stale copy** under the accepted configurations; it flags the circumstance in which the surprise is likeliest
(an optimised compiland, a small function that was inlined). The orchestrator may decide to drop it; the scenario `optimised` and the
`check.fixture_optimised` test (CML1603) would then change.

## Deferred, with reasons

* **CML3103 (layout of a type changed)**: it needs the UDT layouts of the old PDB and of the patch (TPI: member lists, sizes, vtable
  slots), and `cml_pdb` does not read type records (WP-04 left them out). Building a TPI reader and the comparison is a package of its own; the
  planner has no type access either (ADR-0029). The id stays reserved and `docs/KNOWN_LIMITATIONS.md` says so.
* **CML2300-2399**: no compile-time check needed an id. The compile-time conditions of plan 1 and 4.2 already have ids in the ranges
  `cml_toolchain` owns (CML1504, CML2102, CML2210), or are module properties (CML16xx).
* **Enable-time negative scenarios through cmltest**: the harness builds exactly `fixture_<name>` per scenario, so one scenario per bad build
  would need one fixture directory per bad build. The `check.*` ctest tests assert the exit code and id on the real bad builds, and the
  enable-time path is covered by unit tests (the same function runs in both places). The only cmltest scenario is `optimised`.
* **clang-cl cells have no `fastlink` / `gl` negative `check.*` tests (CI log: only guard_cf, no_pdb and no_command run there).** In the CI
  cells CMake links clang-cl builds with lld-link, not link.exe. lld-link ignores `/DEBUG:FASTLINK` and writes a full PDB, so there is
  nothing to reject and `bad_build_fastlink` is not created (`CMAKE_LINKER` matches lld-link); that is also why CML1101 must not FAIL on
  the option for lld-link. `bad_build_gl` is built by cl only: clang-cl's `/GL` is `-flto`, whose bitcode objects link with lld-link in
  principle but whose recorded PDB/command forms were not investigated here. The `/GL` and FASTLINK logic is covered in every cell by the
  unit tests on synthetic modules, and the real negative builds run in the msvc cells.
* **The PCH header diagnostic** is WP-15's (CML5550).
