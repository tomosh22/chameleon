# WP-52: a nested lambda's guard is tied to its bound static (R-60; ADR-0045)

Branch `wp/52-nested-guards`, one PR. Review: high (bind planner). Diagnostic: CML3211, which is now also an error (no
new id).

## The defect

WP-51 found it (docs/wp/WP-51.md, "Found on the way"): `guard_scope_statics` ties a guard `?$TSS0@<scope>@4HA` to the
statics `?<name>@<scope>@4...` of its block by comparing `<scope>` as written. The Microsoft mangling writes a name it has
seen before in the same decorated name as one digit, the index of that name in a back-reference table (at most ten
names, in order: simple names, class templates as a whole, anonymous namespaces, `<auto>` of a deduced return type). A
guard and its static write the same scope with different digits when the table counts different names in front of the
scope. clang 18 does not count the guard's own name `$TSS0` (`$S1`), but counts the static's name:

```
?$TSS0@?1???R<lambda_1>@?0???R<lambda_0>@?0??g@@YAXXZ@QEBA?A?<auto>@@XZ@QEBA?A?3@XZ@4HA     guard:  3 = <auto>
?gx@?1???R<lambda_1>@?0???R<lambda_0>@?0??g@@YAXXZ@QEBA?A?<auto>@@XZ@QEBA?A?4@XZ@4UObj@@A   static: 4 = <auto>
```

So the guard was tied to no static, got a fresh guard (warning CML3211) while `gx` stayed bound to the running process,
and the patch ran `gx`'s initialiser again over the live object (`made` counts up, the state is reset).

## What was built

- `bind_names`: `local_scope_key(decorated, guard_name_counted)` reads the scope of a function-local static or guard and
  writes every name back-reference out (`LocalScopeKey`: the block `?1?`, the rest with the names written out and the
  storage class, and the outermost function). It reads qualified names, templates (their arguments with a table of their
  own that starts with the template's name; a class template is one entry of the enclosing table, a function template's
  own name none), anonymous namespaces, local scopes (`?<n>?` and the letters form of block 11 on), free, member and
  static member functions, C functions (`9`), deduced return types, pointers, references, arrays, function pointers and
  the `$` forms of template arguments. Type back-references in parameter lists are kept as written (the parameter lists in
  front of them are the same in the guard and the static). Anything else gives no key, never a guess.
- `bind_plan`: `guard_scope_statics` compares the keys. A guard is read in both spellings (clang 18's, its name not
  counted; cl's and clang 20's, counted); the spellings agree on every scope without a back-reference. Where they tie the
  guard to different statics it is tied to none (logged). A name the reader cannot read is compared as written, as
  before (`raw_guard_covers`). The ties are computed once per guard; WP-46's pairing of statics by procedure
  (`pair_statics_by_procedure`) uses the same ties (`guard_ties`).
- `settle_guards`: a guard tied to no static, without a record, is refused with CML3211 as an error when the patch has a
  function-local static bound to the running process that no guard is tied to and that has the guard's outermost
  function (or a scope that cannot be read): `untied_guard_owner`. Otherwise it stays the warning (a fresh guard can
  only construct a static that is not in the patch).
- Fixture `planner_pairing_o2`: `nested.cpp`, a static in a nested lambda whose call operators return `auto` (the
  back-reference case), the outer one `noinline` under clang (WP-51's repro shape). `TICK ... nest= nmade= nmark=`, edit
  `nest_4`; the scenario requires `patched = 1` under clang-cl and allows CML3207 / CML3211 / CML3600 under cl.
- cmltest: a reload refused under `allow_error` leaves no reload result, and `expect_reload_result` checks its
  `compiler` first, so that a cl-only refusal passes a clang-cl-only expectation (a refused reload read the previous
  reload's result before).

## Tests that fail on main

- `R-60: the guard of a nested lambda's static is tied to the static and placed with it (clang 18 names)`:
  `CHECK(guard.decision == DecisionKind::BindOldData)` (main: PatchNewData), and the source, the RVA and
  `count_code(r->warnings, diag::kGuardUnmatched) == 0` (main: 1).
- `R-60: a guard that cannot be tied next to a bound static without a guard is refused (CML3211, an error)`:
  `REQUIRE_FALSE(r.has_value())` (main: the plan is accepted with the warning), for a guard whose back-reference is outside
  the table, the guard of another block of the same function, and the outer lambda's guard.
- `R-60: a guard tied to no static, of another function than every bound static, is still the warning CML3211` passes on
  main too (the warning is kept where no bound static can be the guard's).

## Corpus

CML3211 lines in the corpus logs of run 46079672032 (WP-48 head 6b72ecb, main's content; trace logs): 0 in each of the
eight cells. Every one of the 386 `bind: guard ...` trace lines (jolt cl and clang-cl, 193 each) has one static in its
scope, bound. The decorated names of those logs (126 guards, 193 statics, both compilers) were run through
`local_scope_key`: every guard is tied by its key to exactly the statics the comparison as written ties it to, none is
ambiguous, none untied. After the change: see the PR.

The reader was also run under ASan/UBSan on 2 million random mutations of those names (and 200-deep scope nests): no
finding.

## Deferred

- A nested lambda inlined all the way into its function. clang-cl 18 at `/O2` without the `noinline` records `nested` in
  `o2_nest_step` itself, two lambdas up. The planner looks for a lambda's static in its own call operator and in the
  function that directly encloses the lambda (WP-40 item 1), here `<lambda_0>::operator()`, which has no procedure: the
  static is decided new (`static data 'nested' has no record in compiland 0: new`) together with its guard, without a
  diagnostic, and the reload resets it. Also on main. Looking further up (every enclosing function of the chain) touches
  WP-40's counting and WP-51's inline verdicts; it is a planner change of its own (proposed as an R item in the PR).
- `??_B<scope>@51`: clang's bitmask of an inline function's statics under `-fno-threadsafe-statics` (seen in the local
  probe). `is_guard_variable` does not recognise it; it is external (COMDAT) and not settled by `settle_guards`. Not
  changed.
- Type back-references are not resolved. They cannot differ between a guard and its static (their parameter lists in
  front are the same), so the comparison does not need them.
