# WP-52: a nested lambda's guard is tied to its bound static (R-60; ADR-0045)

Branch `wp/52-nested-guards`, one PR. Review: high (bind planner). Diagnostic: CML3211, which is now also an error (no
new id).

## The defect

WP-51 found it (docs/wp/WP-51.md, "Found on the way"): `guard_scope_statics` ties a guard `?$TSS0@<scope>@4HA` to the
statics `?<name>@<scope>@4...` of its block by comparing `<scope>` as written. The Microsoft mangling writes a name it has
seen before in the same decorated name as one digit, the index of that name in a back-reference table (at most ten
names, in order: simple names, class templates as a whole, anonymous namespaces, `<auto>` of a deduced return type). A
guard and its static write the same scope with different digits when the table counts different names in front of the
scope. clang 18 does not count the guard's own name `$TSS0` (`$S1`), but counts the static's name:

```
?$TSS0@?1???R<lambda_1>@?0???R<lambda_0>@?0??g@@YAXXZ@QEBA?A?<auto>@@XZ@QEBA?A?3@XZ@4HA     guard:  3 = <auto>
?gx@?1???R<lambda_1>@?0???R<lambda_0>@?0??g@@YAXXZ@QEBA?A?<auto>@@XZ@QEBA?A?4@XZ@4UObj@@A   static: 4 = <auto>
```

So the guard was tied to no static, got a fresh guard (warning CML3211) while `gx` stayed bound to the running process,
and the patch ran `gx`'s initialiser again over the live object (`made` counts up, the state is reset).

### Evidence: who counts the guard's name

`llvm-undname` reads a guard as cl writes it (it shows clang 18's `?3@` as `g`, not `<auto>`).

Where clang changed (review round): `clang/lib/AST/MicrosoftMangle.cpp`, `mangleThreadSafeStaticGuardVariable`, at the
release tags. llvmorg-17.0.6 and llvmorg-18.1.8 write `Mangler.getStream() << "?$TSS" << GuardNum << '@'` (raw: not in
the table); llvmorg-19.1.0, 19.1.5, 20.1.8 and 21.1.0 write `Mangler.mangleSourceName("$TSS" + llvm::utostr(GuardNum))`
(memorised: counted, as cl does). So clang counts `$TSS<n>` from 19.1.0 on. `mangleStaticGuardVariable` writes
`"?$S1@"` raw in every one of them (17.0.6 .. 21.1.0): clang never counts `$S1`. For cl's `$S1` there is no evidence
(no cl bitmask name with a back-reference in its scope was found).

## What was built

- `bind_names`: `local_scope_key(decorated, guard_name_counted)` reads the scope of a function-local static or guard and
  writes every name back-reference out (`LocalScopeKey`: the block `?1?`, the rest with the names written out and the
  storage class). It reads qualified names, templates (their arguments with a table of their
  own that starts with the template's name; a class template is one entry of the enclosing table, a function template's
  own name none), anonymous namespaces, local scopes (`?<n>?` and the letters form of block 11 on), free, member and
  static member functions, C functions (`9`), deduced return types, pointers, references, arrays, function pointers and
  the `$` forms of template arguments. Type back-references in parameter lists are kept as written (the parameter lists in
  front of them are the same in the guard and the static). Anything else gives no key, never a guess.
- `bind_plan`: `guard_scope_statics` compares the keys, reading the names as the compiler that wrote the PATCH OBJECT
  does (`guard_spelling`, from the object's own S_COMPILE3 in its `.debug$S`, logged once per object as
  `WP52-GUARD-SPELLING`): cl's `$TSS<n>` and clang >= 19.1's are counted, clang <= 18's are not, clang's `$S1` never is;
  anything else (no S_COMPILE3, a version that cannot be read, clang 19.0.x, another compiler, cl's `$S1`) is unknown,
  and then both readings are tried and a guard they do not tie to the same statics (also when only one ties) is tied to
  none (`guard_ambiguous_` keeps what either tied). Only patch names are compared (the guard and its statics), so the
  old compiland's compiler is not read. A name the reader cannot read is compared as written, as before
  (`raw_guard_covers`). The ties are computed once per guard; WP-46's pairing of statics by procedure
  (`pair_statics_by_procedure`) uses the same ties (`guard_ties`).
- `require_bound_guards` (after `settle_guards` has decided every guard): the rule is the static's (convergence
  ruling). Every function-local static of the patch bound to the running process that needs a guard must have a guard
  tied to it that is bound to the old guard; otherwise it is refused, CML3211 as an error naming the static. It needs a
  guard when a guard is tied to it (not bound), when a reading of an untied guard gives its scope (the spelling not
  known), when an untied guard's scope cannot be read, when its own scope cannot be read and the patch has an untied
  guard, or when the old image records a guard in the procedure of its old record. No function is matched. A guard tied
  to no static keeps the warning, unless a refusal names it. Statics whose tied guard already has an error (CML3600) and
  thread-locals (CML3400) are left to those.
- Fixture `planner_pairing_o2`: `nested.cpp`, a static in a nested lambda whose call operators return `auto` (the
  back-reference case), the outer one `noinline` under clang (WP-51's repro shape). `TICK ... nest= nmade= nmark=`, edit
  `nest_4`; the scenario requires `patched = 1` under clang-cl and allows CML3207 / CML3211 / CML3600 under cl.
- cmltest: a refused reload (`allow_error` or `expect_error`) leaves no reload result, and `expect_reload_result` checks
  its `compiler` first, so that a cl-only refusal passes a clang-cl-only expectation (a refused reload read the previous
  reload's result before). `expect_monotonic` takes `since_reload = N` (and `within_s`): at least N samples since the last
  reload, the first not below the last one before it (`check_continues`, unit-tested on Linux).

## Convergence ruling (re-review of 835ee2c..85b7a68; ADR-0018)

The re-review found four important issues in deciding which function a guard belongs to (template arguments, names that
end in a back-reference, and the round-1 rule that an unreadable function keeps the warning, which is the unsafe
direction). Ruled:

- A. The error is the static's (`require_bound_guards`, above). `untied_guard_owner`, `outermost_function_as_written`
  and the `outermost` of the key are removed: nothing matches functions.
- B. Each name is read in the spelling of the compiler that wrote it: the patch's names by the patch object's own
  S_COMPILE3 (`object_compiler_version`, the first S_COMPILE3 of its `.debug$S`). clang 19.0.x is unknown. Unknown: tie
  only when both readings agree; a bound static left untied is then refused (A).
- C. CML3211 names the static that lacks a bound guard and says why; "of the same function" is never claimed.

Tests (unit.bind): patch by clang 19.1 against a module by clang 18 (`JPH::GetRTTIOfType`'s `rtti`, whose guard spells JPH
`2` when counted): the patch's spelling ties and places the guard; the reverse; `clang version 19.0.0git`: unknown,
the bound `rtti` refused; no S_COMPILE3 in the patch (the module's clang 18 not used): refused. The refusal cases now
name the static (`check_static_refused`): the unreadable guard next to `gx`; an unknown compiler's one-sided match; the
member-pointer static `pm::q` next to other()'s untied guard (refused now: its scope cannot be compared, round 1 kept
the warning); `cinit::n` next to an unreadable guard of another block (refused now). Kept as warnings: an untied guard
whose scope differs from every bound static's, and `static int n = 0;` next to a readable untied guard of another block.
Synthetic objects carry S_COMPILE3 (`SynthObj::compile3`); six WP-37/WP-40 tests whose patches left out the guards the
old image records now define them (or count only their own diagnostic): a bound static there needs a bound guard.

Corpus cells and the rule's inputs: no corpus guard is untied (above), clang records no guard (rule "old record" never
applies there), and the untied corpus statics (`ContactConstraintManager::...::table`, `ImTextCharFromUtf8::lengths`,
...) are in functions of which no guard appears in the corpus logs (the only guards there are `GetRTTIOfType`'s and
`SetThreadName`'s). cl patch objects carry `.debug$S` symbols (`WP37-TYPES ... procs=1333` in
the jolt cl cell), so their S_COMPILE3 is read.

## Merged with WP-53 (70f7e7d)

WP-53 lists a lambda static the planner pairs with a record in its caller's procedure (`inlined_lambda_statics`) and
the pipeline refuses it (CML3207) unless the caller's code is unchanged. `require_bound_guards` runs in the planner and
sees such a static as bound. Checked on WP-53's real clang-cl 18 images (tests/unit/bind/wp53, all ten cases; the
mirror tests pass 8/8 with this planner, c7, c11 and c13 bind):

- the guard of every listed static is the one its scope ties in the patch's spelling (clang 18, from the objects'
  S_COMPILE3); WP-53 lists the statics, not their guards, which settle_guards places from the same layout;
- where the static is proven (c7, c11, c13, and c1/c8/c10 in the planner), its guard is bound (c7's `x` is
  constant-initialised and has none, and nothing says it needs one): no CML3211;
- where WP-53's proof refuses (c1, c8, c10) the planner raises nothing and the pipeline refuses once, CML3207; where the
  guard found no layout (c3, c4, c5, c12) the planner's CML3600 is the refusal, and require_bound_guards adds nothing
  (a static whose tied guard has an error is left to it).

## Deferred

- A nested lambda inlined all the way into its function. clang-cl 18 at `/O2` without the `noinline` records `nested` in
  `o2_nest_step` itself, two lambdas up. The planner looks for a lambda's static in its own call operator and in the
  function that directly encloses the lambda (WP-40 item 1), here `<lambda_0>::operator()`, which has no procedure: the
  static is decided new (`static data 'nested' has no record in compiland 0: new`) together with its guard, without a
  diagnostic, and the reload resets it. Also on main. Looking further up (every enclosing function of the chain) touches
  WP-40's counting and WP-51's inline verdicts; it is a planner change of its own (proposed as an R item in the PR).
- `??_B<scope>@51`: clang's bitmask of an inline function's statics under `-fno-threadsafe-statics` (seen in the local
  probe). `is_guard_variable` does not recognise it; it is external (COMDAT) and not settled by `settle_guards`. Not
  changed.
- Type back-references are not resolved. They cannot differ between a guard and its static (their parameter lists in
  front are the same), so the comparison does not need them.
