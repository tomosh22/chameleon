# WP-25: Unchanged-function elision

One branch (`wp/25-unchanged-elision`), one PR. Everything is in `broker/cml_core` unless noted. No agent, wire or ABI change.

## What was built

WP-12 already dropped a planned hook when the new code equals the code in the module file (ADR-0030, `docs/wp/WP-12.md`, "Hook narrowing"). This
package closes the remaining gaps.

| Gap | Change |
|---|---|
| 1. Functions an earlier patch hooked were always re-hooked (`NarrowReason::AlreadyHooked`) | The broker now records the code of every function a patch brings (`CodeImage`, `capture_code`) and compares a later compile of the same function with it, with the same three rules as WP-12. |
| 2. Old-bytes source | Decision below: the module file stays. |
| 3. "No functional change" feedback | A reload in which every recompiled compiland compiles to identical code and adds nothing loads nothing: warning **CML3450**, `no_functional_change` in the response, no generation, no patch. |
| 4. Counts | The reload response, the per-module `patches[]` entries and the `patch_applied` event report planned / dropped / installed hook counts. |

### Code records (gap 1)

`hook_narrowing.h` gets `CodeImage` (`bytes` with the relocation sites zeroed, and per relocation: offset, type, the in-place addend, and the
`CodeTarget` it resolved to), `capture_code()`, `finalize_code()` and `NarrowInput::prior_code`.

* A `CodeTarget` is one of: `Address` (the old address of a bound symbol, a hooked function or `__ImageBase`), `SecRel` (the planned
  section-relative value), `Constant` (the content of a fresh read-only constant such as a string literal), or `NewSymbol` (something the
  patch itself introduced). A `NewSymbol` becomes an `Address` once the patch is linked (`finalize_code`, with the layout's address of the
  symbol), which is also what the next patch resolves the same symbol to through the registry, so a function that calls a function introduced by
  patch 1 compares equal in patch 2.
* The comparison (`Narrower::check_prior`) is: same length, equal masked bytes, same number of relocations, every relocation with the same offset,
  type, in-place addend and target. Whatever cannot be recorded (a constant that holds pointers, a relocation type that cannot be judged, a
  function the patch's own copy of which is a `PatchFresh` function) gives no record, and the function is hooked ("when in doubt, hook").
* `ModuleState::code` maps the **address of the patch code** (the new entry of a hook, or the address of a function a patch introduced) to its
  record. `code_running_at(entry)` follows `hooked[entry]` first. Keying by the patch address, not by the old entry, makes the records immune to
  `hooked` changing (a revert re-pointing a hook to an older patch, WP-22): the record that applies is always that of the code the entry
  currently jumps to. Records are never removed, the patch DLLs stay loaded.
* The records are made in `apply_unit` right after the hooks are installed (also in the "no HooksInstalled in time" case, where the hooks
  are remembered as installed). A function introduced by a patch (no entry in the module file) is recorded too, so it can be compared (and not
  re-hooked) in the next patch: the planner hooks such a function at its patch-N entry.

### No functional change (gap 3)

`apply_unit` already returned without loading when `hooks`, new functions, new globals and initialisers were all empty. It now counts such
compilands (`PatchReport::units_unchanged`); when every compiland of the module's reload was like that and nothing was patched, `run()` sets
`no_functional_change` and publishes **CML3450** (warning, stage `plan`): "the edit compiled to identical code (N of M planned hooks are
identical to the running code, nothing new): no patch was loaded for <module>". The source baseline is accepted as before, so the next sweep
does not report the file again. WP-22 (`PatchBatch`, per-reload revert batches) is unaffected: no patch means no batch (its batch is only made
when `applied_` is not empty).

### Counts (gap 4)

Reload response (existing names unchanged): `hooks_installed` (as before), new `hooks_planned`, `hooks_dropped` (sums over the reload; "N
functions changed" is `hooks_planned - hooks_dropped`), `modules_unchanged`, `no_functional_change` (true when a module was unchanged and nothing
was patched), `warnings` (one line per warning of every module). Per module (`patches[]` entries): `no_functional_change` next to the existing
`hooks_planned`, `hooks_installed`, `hooks_dropped`. `patch_applied` event: `hooks_planned`, `hooks_dropped` added.

## Decisions

* **Old bytes: the module file stays (gap 2).** For an entry that was never hooked, the file on disk and process memory hold the same code (code
  relocations are handled by the load-base arithmetic of WP-12). With gap 1 closed, memory would add nothing for entries that were hooked
  (their old bytes are not what runs). It would cost: a `ReadMemory` round trip per function, and false "differs" results where something else
  writes the code (a user hook of WP-17, a debugger's breakpoint, another hot-patch tool).
* **Records are compared structurally, not through the patch DLL's bytes.** The brief says "that patch DLL's bytes and its resolved relocation
  targets". The DLL on disk holds linker-resolved values only for thunks and patch-local symbols, the rest are agent fix-ups written at load time,
  so the object's bytes plus the planner's resolved targets (which are exactly what the fix-ups are made from) carry the same information.
* **`patch_applied` is not published for a reload that loads nothing**, since nothing was applied. The "no functional change" feedback is the
  CML3450 `diag` event and the response (the brief names both events; this is the reading that keeps "do not apply that patch at all").
* Existing unit tests that reload the same object twice (`the resolved linker follows set-option linker / linker_path`, `compile cache: ...`)
  test other things (the linker cache, the compile cache) and relied on the second reload being loaded. They now switch `narrow_hooks` off first;
  none of their assertions changed.

## How to run

`cmltest.exe` scenario `only_one_function_changed` (fixture `elision`, `tests/fixtures/elision`): edit `elision_base` -> exactly one hook; a
stacked edit of `elision_inner` -> exactly one hook (`elision_base` was hooked by patch 1: this is gap 1); a comment-only edit -> `patched` 0,
`hooks_installed` 0, `generation` unchanged, diag `CML3450`, the program keeps printing the same values. `set-option narrow_hooks false`
switches the elision off.

## Tests

* `tests/unit/broker/test_narrowing.cpp` (`elision: ...`): already-hooked equal (dropped), differing bytes, different length, relocation
  retargeted between the two patches, in-place addend, string literal same / edited, symbol introduced by the earlier patch (same address, other
  address, another new symbol), function defined by an earlier patch, nothing recorded, narrowing off, a function that cannot be recorded.
* `tests/unit/broker/test_reload.cpp` (`elision: ...`): the second identical reload loads nothing (no `LoadPatch`, no link, generation 1,
  CML3450 in the response and as a diag event, no second `patch_applied`); a partly unchanged reload (new function, unchanged hooked one) reports
  planned 1 / dropped 1 / installed 0 in the response and the event; a changed function is hooked again; `narrow_hooks false` hooks everything
  again.
* Scenario `only_one_function_changed` (Windows CI, all cells).

## Deferred / limitations

* A function that cannot be recorded (a relocation the check cannot judge, a constant holding pointers such as a vtable, a table larger than 64 KiB)
  is always re-hooked by later patches, as before.
* The records live in the broker's `ModuleState` of one process: whoever creates a fresh module state (a new session) starts without them, and
  the first reload then compares with the module file, as in WP-12.
* The comparison cannot see data a function reads through a bound symbol: a changed initialiser of a global is not part of the function. Nothing
  changes there compared with WP-12 (globals are bound to the old storage).
* Header-only edits whose effect is inlined into another translation unit are outside this package (CML3104, WP-18).
