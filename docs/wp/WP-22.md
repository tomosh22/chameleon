Plan section 8 (WP-22), ADR-0032 (ids, control-pipe shapes), diagnostic range CML5850-5899 (broker; CML4500-4549 for the
agent is not used). Acceptance: scenario `revert`.

## Semantics

* **Unit of revert: a reload.** A reload that recompiles three translation units makes three patches; they are one
  *batch*. `last` undoes the newest batch, `all` every live batch. (Undoing one of three patches of the same save would leave
  a state no source file describes.) A reload that fails halfway keeps the patches it applied, and they form a batch.
* **LIFO.** For every function the reverted batches hooked: if an older patch that stays also hooked it, the jump is
  re-pointed at that patch's function (an `InstallHooks` with `kInstallHooksQuiet`); otherwise the original bytes come back
  (`InstallHooks` with `kInstallHooksRevert`). So after `last` the *previous patch* is live, not the original code; after
  `all` the original code is. The agent's own revert restores the bytes saved by the FIRST hook of a function, which is why
  the intermediate state needs the re-point and not a revert. Both go through the WP-10 stop-the-world installer
  (nothing allocates or locks in the window; no agent code changed in the installer). Re-points go first; if the revert request
  is then refused, the re-points are undone (CML5854 if even that fails).
* **Nothing is unloaded.** Patch DLLs stay loaded (code on a stack may still run there) and keep their globals; globals the
  reverted patch created stay alive and unused. The reservation is not rewound and `patch_counter` never goes back, so a later
  patch gets a new address range and a new file name.
* **Broker state goes back.** (1) The module's generation (`generation_before` of the oldest reverted batch) and the
  broker-wide generation (it counts live patches). (2) The hook table `hooked` (original bytes: entry removed; re-pointed: the
  older patch's address). (3) The symbol registry: each patch's registry additions are undone newest first, restoring what the
  name resolved to before (so a name defined by patch 1 and redefined by patch 2 resolves to patch 1 again after `last`). A reload
  after `all` therefore cannot bind to the reverted patch's new functions and globals (FU-13's second-reload case); it defines
  them afresh. (4) The source baseline: the reload that was reverted had re-baselined the files it compiled; the revert puts the
  previous stamps back. The files stay changed on disk relative to the live code, so the next reload recompiles them.
* **Pre/post-patch hooks (WP-17) do not run around a revert.** Decision: those hooks announce "new code is about to be
  written"; WP-17 already makes a plain revert silent, and the re-points of a LIFO revert use the same rule (the new quiet
  flag). An application that must know can listen for the `patch_reverted` event on the control pipe. Known gap: hooks that
  live in a reverted patch's DLL (`CML_PREPATCH_HOOK` defined in a patched file) are still collected by the agent from that DLL
  and keep running; the agent's hook collection has no notion of a revert.
* **Concurrency.** A revert takes the same one-at-a-time lock as `reload` (a second one is CML5304) and counts as "running" for
  `wait idle`.
* **Synchronised mode.** The hook changes wait for `SyncPoint()` like an install, bounded by the option `hooks_timeout_ms`. If
  no answer comes in time the broker still commits its own state and reports CML5852 as a warning (the agent may apply the change
  at the next `SyncPoint()`), the same stance as CML5309 for installs.

## Diagnostics (CML5850-5899; `revert_diag_ids.h`)

| id | meaning | what to do |
|---|---|---|
| 5850 | no live patch in the targeted modules (nothing reloaded, already reverted, or no module matches `pid`/`module`) | reload first |
| 5851 | the agent refused the hook change (its CML43xx id and text are in the message); nothing changed | wait until the application leaves the function, retry |
| 5852 | (warning) no `HooksInstalled` in time | in synchronised mode call `SyncPoint()` |
| 5853 | `scope` is neither `last` nor `all` | |
| 5854 | the second half of a revert failed and the first could not be undone | restart the application or reload |

## Session reset (not implemented)

Plan section 11 mentions "session reset unloads everything after revert". The brief makes unloading optional and only allowed when no
thread's stack is inside the patch DLL. It is **deferred**: the revert leaves the DLLs loaded on purpose, and unloading needs the
WP-17 unload-lease check (is any thread inside the image?) plus undoing the loader's registrations in the agent, which is agent work
beyond this package. After a `revert all` the process runs the original code and the patch DLLs are inert (only their globals
remain).

## How to run

* Unit: `ctest -R "unit.(broker_core|harness|ipc|agent_hook)"`. The revert tests are `revert*` in `tests/unit/broker/test_reload.cpp`
  (portable, they run on Linux with `-DCML_ALLOW_NON_WINDOWS=ON`); the quiet flag in `tests/unit/lib/test_ipc_hooks.cpp` and
  `tests/unit/agent_hook/test_dispatch.cpp`; the step in `tests/harness/tests/test_wp22_scenarios.cpp`.
* Scenario: `cmltest --scenario tests/harness/scenarios/revert.toml ...` (CI runs every scenario with `--require-all-capabilities`).

## Deferred / limitations

* Session reset / unloading the patch DLLs (above).
* The `revert` command has no per-batch selector (`last`, `all` only; ADR-0032).
* Hooks defined in a reverted patch's DLL keep running (above).
* If a hook-change request times out in synchronised mode the broker's view may differ from the process until the next `SyncPoint()`.
* The agent-side id range CML4500-4549 is unused.
