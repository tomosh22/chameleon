# WP-48: the agent sees every module load and unload (R-53)

Branch `wp/48-module-events`, ADR-0044 (review: high, agent). Diagnostic ranges: agent CML4720–CML4739 (four used; ruling D2,
recorded in ADR-0044), broker CML5620–CML5629 (two used). New agent message `ModuleEvents` (0x0015); the agent's wire ABI
(`Hello::agent_abi_version`) goes from 2 to 3; the C interface `CML_AGENT_ABI_VERSION` stays 2 (ruling D1).

Status: **review round 3 fixed** (the orchestrator's design ruling: the hook bytes are the arbiter; see "Review round 3"). Before
it: **review round 2 fixed**, **review round 1 fixed** (round 1, 9c2f313, met the acceptance: `plugin_reload passed=36` with `QUICK gap_ms=0 same_base=1`
and `WP48-PAIR ... seq=8,9` in all 8 cells, plugin_late_load 32, restart_inject 54, revert_inject 44, WP10-REPEAT 25/25,
godot-gdextension `pass=21 fail=0`, fuzz and package green; the high review's findings are fixed in the round after it, see
"Review round 1").

## The defect (R-53)

`Agent::poll_modules` compared two module-list snapshots every 500 ms. A FreeLibrary + LoadLibrary at the same base between two
polls (same base, size and path) looked like no change: the new image ran its original code, the broker kept the state of the old
instance, nothing was re-applied, nothing was reported. WP-45's re-enable path (carry, `forget_range`, re-apply) only ran for an
unload the poll happened to see.

## Decisions (ruled by the orchestrator, recorded in ADR-0044)

* **D1, which ABI number goes up (accepted: wire ABI 3, C ABI unchanged).** ADR-0044 says `agent_abi_version` goes up by one. The agent sent `CML_AGENT_ABI_VERSION` in
  Hello; that macro (agent/include/Chameleon_API.h, outside this package) versions the C interface between the application and
  cml_agent.dll, and ADR-0034 keeps it at 2 because a bump makes every application rebuild (the header refuses a DLL of another
  version). This package bumps the wire ABI instead: `ipc::kAgentAbiVersion = 3` in Hello (`hello.agent_abi_version` was 2 and is
  now 3); `CML_AGENT_ABI_VERSION` stays 2, so applications need not be rebuilt and an old agent DLL still loads. If the C interface
  should go to 3 as well, it is the header line and `tests/unit/agent/fake_agent_abi.cpp`, outside these directories.
* **D2, the agent range (ruled: CML4720–CML4739).** ADR-0044 gives the agent CML4700–CML4719, but WP-36 (ADR-0042) owns that block already (CML4700 is
  `kLoaderAddr32NbOutOfRange`). This package uses CML4720–CML4723 (the next free block, CML4720–CML4739). Renumbering is four
  constants and the TROUBLESHOOTING headings.

## Not changed / limits

* A ring overflow (more than 256 loads and unloads between two drains; it is drained every 500 ms and when half full) falls back to
  the snapshot diff for that poll, so a free + load at the same base in that moment can still be missed; it is reported (CML4721,
  CML5620), never silent.
* An agent from before WP-48 (ABI 2) keeps the 500 ms diff; the broker accepts it and says so (CML5621).
* Sequence numbers are per agent (per ring); an application has one agent, so they are per process in practice.
* The fuzz seed corpus (`tests/fuzz`, outside this package) has no ModuleEvents seed yet; the fuzz target reaches the decoder through
  its type field anyway.

## Review round 3 (final delta check of 5c398da; design ruling recorded in ADR-0044)

Every round had tightened a timing heuristic about when the loader's module list is up to date, and opened another window. The
ruling replaces them as the judge: **the hook bytes are the arbiter.**

* `hook::Installer::hooks_in_range(base, size)` (`agent/src/hook/installer.{h,cpp}`): under the installer's batch mutex (so never
  racing an install or a revert, and never while threads are suspended), for every record whose target lies in the range, reads
  (ReadProcessMemory on the own process: fails instead of faulting) the entry and padding bytes the agent wrote (`current_entry`,
  `current_padding`, which follow re-points). `None`: no record; `Present`: all in memory; `Absent`: any missing or unreadable.
* `track_modules` takes the probe (`HookProbe`, `Agent::hook_probe`):
  * an unload at a known base whose image is `Present` is never reported and never forgotten. It is checked again at the next
    `kHookedUnloadRechecks` (4) polls (the loader can notify a moment before it unmaps the image) and reported as soon as the hooks
    are gone, with its own sequence number; when they stay, it was an earlier image's unload and is dropped. Later events at that
    base wait behind it (order per base);
  * a load at a known base: `Present` → redundant (the hooked image is live); `Absent` → the known entry's unload (seq 0), then the
    load, even with the same path, size and base; `None` → as before (redundant if it is the known entry and no unload was seen
    at that base since);
  * a snapshot diff (resync, untrusted list, disagreement correction) and a list sent again never unload or replace a known entry
    whose image is `Present` (`hooked_missing`, `list_with_hooked`); the session's first list keeps it too (`apply_before_list`).
* `unloads_seen` stays as the hint for modules without hooks, and is no longer cleared by later lists (round 2's poll stamps and
  `adopt_full_list` clearing are gone): without hooks, an extra unload + load costs a re-enable that re-applies nothing, while a
  missed one would lose nothing either (no applied edit).
* A refused ModuleList keeps `known` as what the broker believed before it (`known_before_list_`), not an empty list (round 2's
  change reverted): unloads are still diffed against the broker's view, so a same-base reload is an unload and a load.
* A list sent again first reports what was held back and what is drained now against the broker's view, as an ordinary poll, and
  only then goes out: no older ring event or deferred event is applied after the list (finding 3).
