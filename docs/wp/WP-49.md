# WP-49: hook narrowing verifies jump tables in a function's own code (R-46; ADR-0044)

Branch `wp/49-jump-tables`, one PR. Review: high (hook narrowing). No new diagnostic, no wire or ABI change, no agent change.

## The defect

Under cl a `switch` with a jump table compiles to

```
lea  rcx, [__ImageBase]              ; REL32 to __ImageBase
mov  eax, [rcx + rax*4 + $LN9]       ; ADDR32NB to the table's label
add  rax, rcx
jmp  rax
...                                  ; the cases
$LN9: DD $LN4, $LN5, $LN6            ; ADDR32NB entries to the case labels, behind the code, inside the function
```

at `/Od` and at `/O2` alike (with `/Gy` each function has a COMDAT section of its own and the PDB's size includes the table).
Hook narrowing (WP-12, WP-25) judged only the image-relative sites WP-36 retargets to old data; every other ADDR32NB in code was
"unverifiable", so every function with a switch was hooked on every reload of its translation unit. WP-39's benchmark project
(`/Od /Gy`, 1000 functions per TU) installed 275 hooks for a one-function edit: 1159 planned, 884 dropped, and 274 of the 275
kept as `unverifiable - IMAGE_REL_AMD64_ADDR32NB to '$LN13' in code`.

## The rule (`broker/cml_core/src/hook_narrowing.cpp`, `Narrower::local_targets`)

An ADDR32NB of the function whose target symbol lies in the function's own section is a **local reference**. Its target is the
symbol's value plus the in-place addend (labels have addend 0; a reference through the section or function symbol carries the
offset in place). Then:

1. **Leaves the function.** A local reference whose target is outside `[start, start + size)` is not judged (the function is
   hooked): `ADDR32NB to '<sym>' reaches +0x.. of the section, outside the function (a jump table that leaves the function)`.
2. **Tables.** A table starts where a local reference points and an entry lies there; it is the run of consecutive 4-byte
   local ADDR32NB entries from there. A reference may also name the table's label with an index bias (`$LNt[rcx+rax*4-4]` for
   a switch whose first case is 1): only a negative, 4-byte-aligned offset of at most 64 bytes is taken for that (review). Every local reference must be an entry of a table or point
   at the start of one; anything else (a byte index table of a two-level switch, a stray label reference) is not judged:
   `... which is not the start of a jump table (no entries there)`.
3. **Bounds.** A table that runs to the end of the function while an ADDR32NB lies right behind the function might go on past
   the bytes compared: not judged (`its end cannot be told`). Otherwise the table's bounds are the run's, and they are equal on
   both sides: the table lies inside the function, whose length and non-relocated bytes (the index check `cmp ...; ja` included)
   are already compared; every entry of the new table is compared with the old bytes at the same offset.
4. **Entry by entry.** Against the module file: the old linker wrote `RVA(target)`, so `old - old_rva` must be the new target's
   offset from the function start (`TargetChanged`: `the jump-table reference at byte N reached byte A of the old function, now
   byte B`). Against the record of an earlier patch (WP-25): the record holds `CodeTarget::Kind::Local` with that offset.
5. **Another section.** An ADDR32NB to another section (a table in `.rdata`), or one the planner retargets to old data (WP-36),
   is judged by the existing rules, which keep it as before. clang-cl writes its tables to an associative `.rdata` section with
   REL32 entries (seen with clang 18 at `-O0` and `-O2`), and the function references the table through a REL32 to that section's
   symbol, which has no decision: such a function stays unverifiable and is hooked, as before.

Why the comparison is sound: when the masked bytes are equal and every relocation reaches the same thing, the old function is a
relocated copy of the new one. A local reference adds the image base it runs with (`lea rcx,[__ImageBase]` is compared as a
linker-provided target): the old code reaches its own case labels, the patch its own; both reach the same place relative to the
function. A local reference is decided per site in relocation order, so a function reports the reason of its first relocation that
differs, and a function whose bytes differ is still `bytes-differ` (the order matters for WP-40/WP-46's proofs, which treat
`unverifiable` as "unknown" and `bytes-differ` as "changed").

**R-50 (the same nit as in the WP-36 prover).** A relocation that starts less than 8 bytes before the function and reaches into it
(or has a width this check does not know) would leave function bytes unmasked or unexplained: the function is not judged and gives
no record. In a COMDAT function (start 0) it cannot happen. It is refused **before** the bytes are compared, on both paths (review),
so the unmasked bytes never read as a spurious `bytes-differ`.

**Extent in a section with other symbols (review, a pre-existing gap of WP-25).** Without `/Gy` several functions share a code
section and a function's extent runs to the next symbol, so a label inside it (a case label, a jump table) cuts it short. Against
the module file the extent is checked against the PDB's size (as since WP-12). Against an earlier patch's record it was not: the
record was cut at the same label, so an edit behind the label compared equal and the entry kept jumping to the stale copy.
`check_prior` now keeps the hook for a function in a non-COMDAT section unless its extent equals the PDB's size (`size-differs`),
and when the PDB gives none (a function an earlier patch introduced) as `unknown-old-size`. A COMDAT function is its whole section
and is not affected (its length may differ from the module's because an earlier patch changed it). In a `Kind::Local` record entry
only the offset and the target count (the same place named through a label or through the section with an offset is equal).

Trace lines (`WP49-JUMPTABLE function='...' tables=N entries=N references=N refused=N verdict=comparable|unverifiable`, one per
refused site with its reason, `verdict=equal`, and `verdict=target-changed byte=N old=+.. new=+..`).

  the module away from its preferred base, and with entries that name the function symbol with the offset in place); a changed
  case target (`case 1:` and `case 2:` exchanged: same bytes, two entries differ), a table load that reached another place and a
  last entry one byte off are `target-changed`; an entry past the function end and an entry into another function's section are
  `unverifiable`; a table that ends at the function end with an ADDR32NB behind it is `unverifiable`, the same without it is

## Deferred / limitations

* **Two-level switches** (a byte index table read with `movzx eax, byte ptr [reg + rax + $LNi]`, then the jump table): the
  reference to the byte table has no entries to compare and its extent is not given by relocations, so such a function stays
  hooked. Accepting it would need the byte table's bounds.
* **clang-cl** tables live in `.rdata` (REL32 entries relative to the table, in an associative COMDAT); those functions stay
  hooked. Comparing them needs the associative section's entries resolved against both images.
* A function in a non-COMDAT section (`/Gy-`): its extent is taken up to the next symbol of the section; where a label symbol
  inside the function cuts it short, the size differs from the PDB's and the function is kept (`size-differs`), against the module
  file and (since the review) against an earlier patch's record. Not measured (Chameleon requires `/Gy`).
