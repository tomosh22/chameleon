# WP-57: WP-51 refuses an own static only when the inlined closure cannot be proven unchanged (R-59; ADR-0046)

Branch `wp/57-narrow-inlined`, one PR. Review: high (bind planner). Diagnostic: CML3207 (no new id).

## Round 1: spike (evidence before code)

WP-51 (R-54) refuses with CML3207 every own static of a function whose old procedure `P` holds the static's record and
inlined closure code (a call operator, an invoker, a template over a closure, or inline sites that cannot be read). The
hazard is one edit: the lambda whose static was recorded in `P` is deleted (or loses its static) and `P` declares a static
of that name, which then pairs with the lambda's live object. The rule refuses whether or not the lambda changed, so a
function with a `static` and a `std::sort` or `std::call_once` with a lambda cannot be reloaded once its TU is edited.

### Sources

### What main does

Every case is refused by WP-51 (CML3207, pass A): s1/s2 because `f` inlined `sort` ("a function over a closure type",
34 inline sites, 9 closure inlinees), s3/s4 because it inlined `once`, the rest because it inlined `f::<lambda_0>::operator()`.

### Candidate 1: WP-25's comparator on the patch's call operators against the old inline sites

There is nothing to compare. clang drops a lambda's call operator once every call is inlined: the patch objects of s1, s3
and s11 define `f`, `g`, the guard and the statics, and (s1) `std::__introsort_loop<..., <lambda_0>...>`, but no `??R`
symbol. On the old side the inline site of a call operator is not a unit of code: its ranges are interleaved with `f`'s
own code, and optimised code moves across inline boundaries (WP-53 rejected the same idea for R-61). **Rejected.**

The lambda's code can be separable, though, when it is inlined into another function: in s1 the comparator is inlined into
`std::__introsort_loop<...>`, a static function of the patch with an old counterpart (Candidate 4).

### Candidates 2 and 3: closure identity (numbering, rule (d)) and the closure's own statics

s10 against s11 settles both. The old images record the same shape: one `S_LDATA32 x` (type `Obj`) directly in `f` and one
`S_INLINESITE` of `operator()` (`LF_MFUNC_ID` type 0x1017, class `.?AV<lambda_0>@?0??f@@YAXPEAHH@Z@` in both), whether the
record is the lambda's (s10) or `f`'s (s11). The patch of s10 is s11's old source, so the patch objects are of one shape too:
the same closure (same unique name and number, same call operator type), no static of the closure, `?x@?1??f@@...` and its
guard. s6 is the same with another call operator signature. So:

- the closure the old `P` inlined still exists, with the same identity and signature, in the hazard (s10) as well as in the
  benign case (s11): identity proves nothing;
- the closure's statics in the patch are known by their decorated names, but the old ones are plain records of `P`
  (WP-53's finding): "the closure has no static `x` now" does not say whether it had one before.

What tells s10 from s11 is the code alone. **Rejected** as proofs; rule (d) still decides which closure is which where the
comparator pairs lambdas (WP-40).

### Candidate 4: WP-53's proof of the caller unchanged under the plan (`prove_inlined_lambda_statics`)

The argument WP-53 ruled sound applies unchanged: if the patch's `P`, with the own static at the old record's address and
its guard where the plan put it, is byte for byte the old `P` with the same targets, the old `P` used that record exactly as
the new `P` uses the own static, so the running program cannot tell the binding from "nothing changed", whatever the record
was in the old source. It does not depend on what `P` inlined, so it covers unreadable inline sites as well.

With WP-51 switched off in the spike (the plan pairs `f::x` with its record, `compiland-static`, guard by layout) the
comparator judges `f`:

| Case | `f` judged (main's comparator) | with the callee step | Right answer |
|---|---|---|---|
| s1_sort_other | `target-new` (`__introsort_loop<..lambda..>`) | `unchanged` | reload |
| s3_once_other | `unchanged` | `unchanged` | reload |
| s8_both_other | `target-new` (`__introsort_loop<..lambda..>`) | `unchanged` (also proves WP-53's `y`) | reload |
| s7_r54_samecode | `unchanged` | `unchanged` | reload (as ruled for WP-53's c7) |
| s2, s4, s9, s11 (`f` edited, lambda unchanged) | `size-differs` | `size-differs` | reload; not provable (s10 = s11) |
| s5, s6, s10 (R-54) | `size-differs` (plan also fails: CML3600) | `size-differs` | refuse |
| s12_r54_layout (R-54, guard placed) | `size-differs`; **the plan succeeds** | `size-differs` | refuse |

s12 is the case that matters for safety: with WP-51 off, R-54 plans (`f::x` bound by `compiland-static`, `$TSS0` by the
layout), so the proof is then the only thing that refuses it, and it does. (s5/s6/s10 also fail with CML3600 because the
edit changed the order the globals were created in; that is luck, as in WP-53.)

**The `std::sort` case needs one more step.** `std::sort`'s out-of-line part is a static template instantiation over the
closure (`??$__introsort_loop@...V<lambda_0>@?0??f@@...`, `t` in the object; MSVC's STL has `_Sort_unchecked<..., lambda>`
the same way), and the planner never pairs those (`bridge_statics`: "static function template instantiation: not matched
to the old image, not hooked"; the PDB names it ``std::__introsort_loop<int *,long long,..._Iter_comp_iter<`lambda at
s1_sort_other.old.cpp:5:69'> >``, by source position). `f`'s call to it is therefore a reference to a new symbol and the
comparator says `target-new`, so WP-53's proof alone refuses exactly the acceptance case.

The callee step (prototyped in the spike): where a relocation of the judged code reaches a function the patch introduces
(`PatchNewFunction`, a static definition) and the old code's rel32 reached address `O`, compare the new function with the
old code at `O` under the same rules, recursively; a pair already being compared counts as equal (`__introsort_loop` calls
itself). Equal pairs are a bisimulation: same bytes, and every relocation reaches the same bound target or a pair of the
relation, so running the new one is running the old one. In s1 and s8 the old `O` is the old `S_LPROC32` of
`__introsort_loop<...>` at 0x14F0 / 0x1580, code size 791, the new one's length; the lambda's code inlined into it compares
equal, and `f` is `unchanged`.

## Proposed rule

1. WP-51's verdict stays as it is (same reader, same risks, same `WP51-*` lines). When `refuse_inlined_owner` finds a risk,
   the planner no longer refuses on its own **when the caller will prove the pairing** (`PlanInput::prove_inlined_owners`,
   set by the pipeline): the pairing goes ahead and the static is listed (`BindPlan::inlined_owner_statics`: static, record
   RVA, `P` and its entry RVA, the risk, the step). Without that flag (every existing caller and WP-51's unit tests) it
   refuses exactly as today, so those tests stay unchanged.
2. The pipeline, next to `prove_inlined_lambda_statics`, keeps a listed static only when WP-25's comparator proves `P`
   unchanged under the plan (one verdict per procedure, shared with WP-53's list; earlier patches' code through
   `prior_code`). Anything else (changed, `P` not hooked, old image unavailable, not comparable) is CML3207 with WP-51's
   message plus why the proof failed and the "what to do": "Leave `P` unchanged while the program runs (edit other
   functions of the file), rename the static, or hot-restart." A refusal there refuses the module's reload as before (WP-47).
3. For both proofs (WP-53's and this one) the comparator gets the callee step: a relocation to a static function the patch
   introduces counts as the old target when the old target is the start of an old procedure (`find_proc_by_rva`) of the same
   code size and the new function compares equal with it under the same rules (recursively, a pair in progress equal; at
   most a fixed number of pairs, then not judged). Only for these proofs: hook narrowing keeps its rules (it re-hooks such
   callers, as today).
4. Logs: `WP57-LISTED static=... proc=... risk=...` (trace, planner), `WP57-OWNER-PROOF static=... proc=... proven=unchanged|refused
   <why>` (trace), `WP57-CALLEE caller=... callee=... old va=... verdict=...` (trace), and one `WP57-OWNER object=... listed=N
   proven=N refused=N skipped=N` per planned object at Info, only when it lists any.

Where the change lives: `refuse_inlined_owner` (the one branch where it calls `error()`), `bind_plan.h` (input flag, list),
`hook_narrowing.cpp` (the proof, the callee step), `pipeline.cpp` (one call next to WP-53's). Nothing in the steps WP-56 and
WP-59 edit.

## What it would still refuse

- **Any edit of `P` itself**, also when the lambda did not change (s2, s4, s9, s11): nothing in the old records or the
  patch tells s11 from s10 (R-54), only the code does, and the code changed. The user's way out is the one CML3207 names:
  edit other functions of the file, or hot-restart. Under cl a record directly in `P` outside every inline site is `P`'s own
  (WP-53 round 1: cl writes an inlined lambda's static inside the closure's `S_INLINESITE`); reading that position is WP-53's
  deferred item (1b) and would lift this for cl only. Not proposed here; it is a separate ruling.
- `P` not comparable: a relocation the comparator cannot judge, a constant holding pointers (a `std::function` built from
  the lambda references its `_Func_impl` vtable), a callee whose old target is not the start of an old procedure of the same
  size, or a reference to a new symbol that is not a static function (a new guard, a new data item).
- `P` not hooked (the patch does not define it), or the old image not available.
- Not new: R-57 (non-lambda helpers) stays log-only; c2 (WP-40's count) as it is.

## The ruling (ADR-0046)

1. The rule as proposed: with `PlanInput::prove_inlined_owners` a risky own static is paired and listed
   (`BindPlan::inlined_owner_statics`); the pipeline keeps it only when WP-25's comparator proves `P` unchanged under the plan
   (one verdict per procedure, shared with WP-53); anything else is CML3207 with WP-51's message and the reason. Without the
   flag the planner is exactly as before.
2. The callee step for the WP-53 and WP-57 proofs only; hook narrowing (WP-25) is unchanged. The old target must start an old
   procedure of the same size; a pair being compared counts as equal; the number of pairs is capped, and reaching the cap
   cannot be judged (refused). Every callee pair is logged at trace.
3. s7 (an R-54 edit with the old machine code) is accepted through the proof, as WP-53's c7: the running program cannot tell
   the difference.
4. cl's record position (WP-53's (1b)) stays on the roadmap as R-65.
5. Accepted limitation: any edit of `P` itself stays refused, also with the lambda unchanged (s2, s4, s9, s11); s10 against
   s11 is the reason.
6. `spike/wp57/` leaves the branch; the real inputs the tests need live in `tests/unit/bind/wp57/`.

## Round 2: what was built

### Planner (`broker/cml_core/src/bind_plan.cpp`, `bind_plan.h`)

`PlanInput::prove_inlined_owners` (default false) and `BindPlan::inlined_owner_statics` (`InlinedOwnerStatic`: the static,
the old record's RVA and name, the procedure `P` that holds it and its entry RVA, WP-51's risk, the step). The only change in
the planner is the branch of `refuse_inlined_owner` that refused: with the flag it lists the static (`WP57-LISTED`, trace)
and returns false, so the step that asked (pass A, the closure step, pass B's sweep) pairs it as it would without a risk.
WP-51's reader, verdicts, cache (WP-55) and logs are unchanged; `WP51-INLINEES ... refused=N` counts only the planner's own
refusals, which the pipeline no longer makes (they come from the proof).

### Proof (`broker/cml_core/src/hook_narrowing.cpp`, `hook_narrowing.h`, `pipeline.cpp`)

- `prove_inlined_owner_statics(NarrowInput, InlinedProcVerdicts*)`: for each listed static still bound to its record, the
  hook whose old entry is `P`'s is judged by WP-25's comparator under the plan (earlier patches' code through `prior_code`).
  Unchanged: the pairing stands. Otherwise one CML3207 per static:
  `static data 'f::x' (...) in <obj> cannot be paired with the record 'x' at rva 0x3010 of its function: 'f' (rva 0x12d0)
  inlined 'f::<lambda_0>::operator()', a lambda's code, and a compiler records the statics of inlined code as records of the
  calling procedure under their own names, so the record may be that code's static and not this one; only an unchanged 'f'
  proves it is this one, and the code of 'f' changed (size-differs: new 140 bytes, old 135)` / `Leave 'f' unchanged while the
  program runs (edit other functions of the file), rename the static, or hot-restart.`
- The verdict per procedure is one function (`inlined_proc_verdict`) for both proofs; `prove_inlined_lambda_statics` takes the
  same optional `InlinedProcVerdicts*`, and the pipeline passes one map to both, so a procedure that holds a WP-53 pairing and
  a WP-57 pairing (s8) is judged once. The pipeline sets the flag on every plan and runs both proofs where the plan lists any;
  their refusals fail the module's reload as before.
- **The callee step** (`NarrowInput::follow_new_callees`, `old_proc_size`, `max_callee_pairs` = 64; set only by the two
  proofs): a REL32 of the judged code to a static function the patch defines and the planner made new (`PatchNewFunction`: a
  template instantiation over a closure) counts as the old code's target when
  - against the module file: the old target starts an old procedure (`PdbIndex::find_proc_by_rva`, start equal to the
    target) whose code size is the new function's length, and the new function compares equal with it by the same rules;
  - against an earlier patch's record (the caller is hooked and its record reaches the earlier patch's copy of the callee):
    the new function compares equal with the record kept for that address (`prior_code`);

  recursively, with the pairs (new function, old address) being compared counted as equal (a recursive function calls
  itself) and the pairs found equal remembered for the judgement. A pair that differs fails the whole judgement, so a pair
  assumed equal never survives a refusal. More than `max_callee_pairs` pairs cannot be judged ("more than N callee pairs
  would have to be compared"): refused. Logs `WP57-CALLEE caller=... callee=... old va=... verdict=equal|<reason> ...` (trace).
- Logs: `WP57-OWNER-PROOF static=... record rva=... proc=... (<step>) proven=unchanged|refused <why>` (trace) per static,
  `WP57-OWNER object=... listed=N proven=N refused=N skipped=N` (Info, only for an object that lists any; `skipped`: a later
  step re-decided the static, nothing to prove).

Hook narrowing does not follow callees: a function that calls a new static function stays hooked (`target-new`), so after
the first reload `P` runs the patch's copy, and the next reload compares `P` with that patch's record (the second case of
the callee step). The fixture scenario's second edit is that reload.

### s7, accepted by ruling

`[] { static int x = 5; return ++x; }` inlined into `f`, replaced by `f`'s own `static int x = 5`: the patch's `f`, with `x`
at the old record, is the old `f` byte for byte, so `f`'s new static keeps the deleted lambda static's value. In C++ terms it
is a new variable that a fresh start would initialise; the running program cannot tell the difference.

## What it still refuses (accepted, KNOWN_LIMITATIONS)

- Any edit of `P` itself, also when its lambdas are unchanged (s2, s4, s9, s11): s10 (R-54, the lambda kept with its
  signature and its static moved into `f`) and s11 (`f`'s own static and the same lambda, `f` edited) have the same old records
  and patches of the same shape; only the code tells them apart, and it changed.
- A `P` the comparator cannot judge (a relocation it cannot check, a constant holding pointers such as a `std::function`'s
  vtable, a reference to new data or a new guard), a new callee whose old target is not the start of an old procedure of its
  size, more than 64 callee pairs, a `P` not hooked, the old image not available.
- (Review of b1be388.) A listed pairing teaches no layout, so where it is the only pairing of its object section (no other
  static of the file with a record there), clang-cl's record-less guard of the static has no layout to be placed from: CML3600
  (s17). Any ordinary static of the file in that section (an anonymous-namespace counter, say) is enough.
- A new callee in a section that is not a COMDAT (no `/Gy`) compared with an earlier patch's copy of it: UnknownOldSize.
- Under cl, the record's position outside every inline site would prove it `P`'s own even with `P` edited: R-65.
