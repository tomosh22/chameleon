# WP-04: cml_pdb index

## What was built

`core/cml_pdb` is now a bounds-checked PDB reader and index. Public headers: `cml/pdb/pdb.h`
(umbrella), `index.h` (`PdbIndex`), `types.h`, `diag_ids.h`.

- **MSF container** (`src/detail/msf.*`): the PDB file is memory-mapped read-only
  (`CreateFileMapping`/`MapViewOfFile`, all share modes allowed; `mmap` on the POSIX hosts used for
  syntax checks). The super block and the whole stream directory are validated at open, so a stream
  read cannot leave the file afterwards. A stream whose blocks are consecutive is used in place (zero
  copy); a fragmented stream is copied once into a counted buffer. raw_pdb's `ValidateFile` is run
  first as a gate; everything after it is cml_pdb's own parser (see "raw_pdb" below).
- **Open API**
  - `PdbIndex::open_pdb(path, options)`.
  - `PdbIndex::open_for_pe(pe_path, options)`: reads the CodeView RSDS record of the PE (private,
    bounds-checked extractor in `src/detail/pe_codeview.cpp`; a comment there says it is replaced by
    `cml_pe` once WP-02 merges; `read_codeview_ref*` stay as the entry points), then looks for the
    PDB at the recorded path (a relative recorded path is relative to the image's directory), next
    to the PE, then in `OpenOptions::override_dirs` (by file name). An existing candidate with a
    different GUID/age is skipped; if no candidate matches, CML1411 names the mismatching one.
    Symbol-server support is out of scope: `OpenOptions::symbol_server` is the seam (it is only
    logged). Documented seam: add a step after the override directories.
- **Compiland table** (`Compiland`, one per DBI module): index, object file name, library name
  (set when the module record's second name, the archive, differs from the first), `S_OBJNAME`,
  module symbol stream and size, file count, `S_COMPILE3` (language, machine, frontend/backend
  versions, version string, decoded flag bits: edit-and-continue, no-debug-info, LTCG (`/GL`),
  no-data-align, managed, security checks (`/GS`), hotpatch, cvtcil, msil, sdl, pgo, exp-module) and
  `S_ENVBLOCK` as ordered key/value pairs with `cwd()`, `compiler()` (`cl`), `command()` (`cmd`),
  `source()` (`src`), `pdb()`; every one may be absent. `Compiland::optimization()` is a heuristic
  over `cmd` (S_COMPILE3 records no `/O` level at all, only `/GL`).
- **Build environment from either source**: `PdbIndex::build_env(i)` returns the `S_ENVBLOCK` pairs
  or, when there is none, the compiland's `S_BUILDINFO` resolved through the IPI stream
  (`LF_BUILDINFO` -> `LF_STRING_ID`, including `LF_SUBSTR_LIST` continuation) mapped onto the same
  keys (`cwd`, `cl`, `src`, `pdb`, `cmd`). This is lazy because `S_BUILDINFO` sits somewhere in the
  module symbols, not at their head. See the clang-cl evidence below: this is how clang-cl records
  its command line.
- **Files**: per-compiland list from the DBI source-info substream (as recorded, and normalised) and
  an inverted `file -> compilands` map (`compilands_for_file`). Normalisation (`normalize_path`):
  backslashes, duplicate separators collapsed, `.`/`..` resolved, `\\?\` stripped, ASCII
  lower-cased (non-ASCII is not case-folded). A relative recorded name is resolved against the
  compiland's `S_ENVBLOCK` `cwd` when that is known and absolute; otherwise it stays relative (and
  lookups with the same relative spelling still match it).
- **Symbols** (lazy, per compiland, parallel `load_all`): `S_GPROC32`, `S_LPROC32` (+ `_ID`,
  `_DPC`), `S_GDATA32`, `S_LDATA32` (function-local statics are found inside proc scopes and carry
  `parent_proc`/`parent_name`; scopes are tracked through `S_BLOCK32`, `S_THUNK32`, inline sites,
  `S_END`/`S_PROC_ID_END`/`S_INLINESITE_END`), `S_GTHREAD32`, `S_LTHREAD32`, `S_UDT`. A `SymbolView`
  carries kind, display name as recorded, section:offset, RVA, size (procs), type index, flags,
  compiland and parent. Globally: publics (`S_PUB32` with the code/function flag) and global data
  (`S_GDATA32`/`S_GTHREAD32` of the symbol record stream). Lookups: `find_public` (decorated),
  `find_global_data` (display name), `find_global` (publics then global data), `find_in_compiland`,
  `find_proc_by_rva` (via section contributions to the compiland, then a binary search in its procs;
  falls back to every compiland), `publics_at_rva`, `public_containing_rva`.
- **Sections**: section headers stream; `rva_from_section_offset`, `section_offset_from_rva`;
  section contributions (compact, sorted by RVA) with `compiland_for_rva` /
  `compiland_for_section_offset`.
- **Cache**: process-wide, keyed by (GUID, age) read from the PDB info stream. `open_pdb`/
  `open_for_pe` return a shared `shared_ptr<const PdbIndex>`. It holds `weak_ptr`s, so the cache never
  keeps an index alive, concurrent opens of one key build once (per-key mutex), different keys build
  in parallel. `PdbIndex::cache_size()`/`cache_clear()`.
- **Thread safety**: every const member is thread-safe. Lazy tables (publics, each compiland's symbols,
  the name and RVA lookup structures, the IPI table) are built at most once under internal
  synchronisation; failures are remembered and returned again.
- **Memory accounting**: all long-lived containers use a counting allocator; `memory_stats()`
  returns tracked bytes, tracked peak, mapped bytes and mapped peak.
- **Tools**: `cml_pdb_dump <pdb|pe> [--summary|--compilands|--compiland <stem>|--publics <s>|--file <p>|--rva <hex>]`;
  `cml_pdb_bench` (see below); `tests/bench/gen_pdb_project.py`.

## How to run

- Unit tests: `ctest -R unit.pdb` (target `cml_test_pdb`). Sources in `tests/unit/pdb/`:
  `pdb_builder.h` builds small valid MSF PDBs and PEs in memory (contiguous or interleaved/fragmented
  blocks, any block size) so most expectations are exact and compiler independent; `test_robust.cpp`
  truncates and corrupts them; `test_fixture.cpp` runs against the fixture `basic` PDB built by the
  cell's compiler.
- Dump a PDB: `cml_pdb_dump build/bin/fixture_basic.exe --compiland extras`.
- Benchmark: CI job `pdb-benchmark`; locally
  `python tests/bench/gen_pdb_project.py out --tus 900 --funcs-per-tu 1000`, build it with MSVC,
  then `cml_pdb_bench out/.../bench_project.pdb --min-size-mb 500`. `--smoke` skips the budgets
  (ctest `bench.pdb_smoke` runs it on the fixture PDB).

## Diagnostics (CML1400 to CML1499)

All are `cml::Diag` with a one-line message naming the file/module and a "what to do" sentence.

| Id | Raised when |
|---|---|
| CML1400 | file cannot be opened or mapped (missing, locked, OS error) |
| CML1401 | not a PDB: file empty, too small, or wrong signature |
| CML1402 | old MSF 2.00 PDB, invalid super block (block size, counts), or raw_pdb's super block validation fails |
| CML1403 | truncated: the super block describes more bytes than the file has |
| CML1404 | stream directory corrupt (block map, stream count, block index out of range) |
| CML1405 | DBI stream missing or invalid (signature, version, substream sizes) |
| CML1406 | DBI module table corrupt (record cut off, unterminated names) |
| CML1407 | PDB info stream missing or too short (no GUID/age) |
| CML1408 | PE has no debug directory / no CodeView `RSDS` record |
| CML1409 | PE image malformed (headers, sections, debug directory out of bounds) |
| CML1410 | no PDB found for a PE (message lists every path tried) |
| CML1411 | a PDB was found but its GUID/age differ from the PE's |
| CML1413 | a compiland's symbol stream is corrupt (returned by that compiland's queries only) |
| CML1414 | DBI section contribution table has an unknown version or a partial entry |
| CML1415 | the global symbol record stream is corrupt (returned by publics/global queries) |
| CML1416 | DBI source-info (file list) corrupt |
| CML1417 | compiland index out of range |
| CML1418 | a 32-bit offset/count in the index would overflow (names pool or stream above 4 GiB) |
| CML1419 | IPI stream / `S_BUILDINFO` data invalid (returned by `build_env`) |

CML1412 is unused. None of these is a by-design limitation for `docs/KNOWN_LIMITATIONS.md`, except
possibly: PDBs of 4 GiB or more are rejected (CML1418), and while the index is alive the PDB is
mapped, which can make the linker fail to overwrite it (see "Deferred").

## Evidence from CI (fixture `basic`, run 40149419776)

Produced by the `cml_pdb_dump of fixture_basic (evidence)` step (full text in each cell's
`logs-*` artifact, `pdb-dump.txt`). Toolchains seen: cl 19.51 (VS 18, MSVC 14.51.36231, windows-2025)
and clang-cl 20.1.8 with MSVC `link.exe`. Config shown: windows-2025 / msvc / RelWithDebInfo
(`/Zi /O2 /Ob0 /Gy /hotpatch`) and windows-2022 / clang-cl / Debug (`/Od`).

### S_ENVBLOCK versus S_BUILDINFO (needed by WP-05)

- **Neither cl nor clang-cl emitted `S_ENVBLOCK` into the compilands of the linked PDB.** The
  only `S_ENVBLOCK` in `fixture_basic.pdb` is in the CRT assembly objects and, when the linker is
  lld, the `* Linker *` module. This contradicts plan section 4.3 for the `/Zi` + `link.exe` case
  (the benchmark's `/Z7` PDB is not evidence either way; it was not dumped).
- **Both compilers record the build in `S_BUILDINFO`**, a module symbol pointing at an `LF_BUILDINFO` in
  the IPI stream with five `LF_STRING_ID` arguments: current directory, build tool, source file, PDB,
  command line. `PdbIndex::build_env()` resolves it onto the S_ENVBLOCK keys:

  | key | cl 19.51 | clang-cl 20.1.8 |
  |---|---|---|
  | `cwd` | `D:\a\chameleon\chameleon\build` (the ninja build dir) | same |
  | `cl` | `...\VC\Tools\MSVC\14.51.36231\bin\HostX64\x64\cl.exe` | `C:\Program Files\LLVM\bin\clang-cl.exe` |
  | `src` | absolute `...\tests\fixtures\basic\main.cpp` | absolute, same |
  | `pdb` | the compiler PDB, `...\fixture_basic_objs.dir\vc140.pdb` | empty string |
  | `cmd` | the **original driver command line** (`-Zi -O2 -DNDEBUG -std:c++20 -MT -EHs -EHc -GR -Ob0 -Gy -showIncludes -FS -c -I"..."`, all `-I` paths included) | the **cc1 command line** (`"-cc1" "-triple" "x86_64-pc-windows-msvc19.44.35229" "-emit-obj" ... "-D" "NOMINMAX" ... "-internal-isystem" ...`), not the `clang-cl` arguments |
  | `-gcodeview-command-line` | not applicable | already on: it is why `cmd` exists at all in clang 20 |

  For WP-05: the clang-cl command is cc1-style (`-cc1`, `-triple`, `-internal-isystem`, defines as
  `"-D" "X"` pairs) so the cl/clang-cl rewriter needs a cc1 parser, or the broker must use
  `compile_commands.json`. cl's recorded command is the real cl command line. Quoted tokens use
  `"..."` and embedded `\"` in both.
- S_COMPILE3 flags seen: cl `0x6001` = C++, hotpatch, `/GS`; clang-cl `0x4001` = C++, hotpatch (both
  fixtures are built with `/hotpatch`); `ltcg` is 0 in both. cl records the compiler version string
  as only `Microsoft (R) Optimizing Compiler` (the version is in the numeric frontend/backend
  fields, `19.51.36260.0`); clang records `clang version 20.1.8`. `machine` is `0xD0` (x64) for
  both. The optimisation level is not in S_COMPILE3; the heuristic over `cmd` gave `/O2` for the cl
  RelWithDebInfo cell and `/Od` for the clang-cl Debug cell (clang's cc1 `-O0`).

### File lists (inverted map) differ between the compilers

- **cl lists every file it opened**, headers included: `main.obj` has 114 entries, `extras.obj` 175
  (all of `windows.h`'s tree), `logic.obj` has `logic.cpp` and `logic.h`. Assertions on header
  membership (`logic.h` is included by logic and main, `extras.h` by extras and main) are made for cl
  only (`CML_TEST_COMPILER_IS_CL`).
- **clang-cl lists only files that carry line information**: `logic.obj` has just `logic.cpp`
  (`logic.h` is declaration-only), `main.obj` has `main.cpp` plus the two CRT headers that define inline
  functions (`stdio.h`, `corecrt_stdio_config.h`). A declaration-only or macro-only header never shows
  up. So the PDB cannot serve as the include graph for clang-cl objects; the plan's statement "no
  /showIncludes pass is needed" holds for cl only. clang-cl records `--show-includes` in cc1 args, so
  the broker's own depfile (`/showIncludes` output) is the dependable source (WP-05/WP-15).

### Names of statics, initialisers and templates (ADR-0010, for WP-07)

Module symbols carry *display* names; `S_PUB32` carries decorated names for external symbols only.
`extras.cpp` (anonymous namespace `s_counter`, `s_dynamic` with a dynamic initialiser, `add_one<T>`):

| construct | cl 19.51 (`/O2 /Ob0`) | clang-cl 20.1.8 (`/Od`) |
|---|---|---|
| anonymous-namespace static `s_counter` | `S_LDATA32` named `s_counter` (no namespace prefix) | `S_LDATA32` named `` `anonymous namespace'::s_counter `` |
| `s_dynamic` | `S_LDATA32` `s_dynamic`; plus a second `S_LDATA32` `s_dynamic$initializer$` (the `.CRT$XCU` slot) | `S_LDATA32` `` `anonymous namespace'::s_dynamic ``; no separate record for the `.CRT$XCU` entry |
| its dynamic initialiser | `S_LPROC32` `` `anonymous namespace'::`dynamic initializer for 's_dynamic'' `` | `S_LPROC32` `` `anonymous namespace'::`dynamic initializer for 's_dynamic' `` (closing quote differs: one quote) plus `S_LPROC32` `_GLOBAL__sub_I_extras.cpp` (the `.CRT$XCU` function) |
| `k_table` (const table) | `S_LDATA32` `k_table` | `S_LDATA32` `` `anonymous namespace'::k_table `` |
| template `add_one<int>` | `S_GPROC32` `add_one<int>`; public `??$add_one@H@@YAHH@Z` | `S_GPROC32` `add_one<int>`; public `??$add_one@H@@YAHH@Z` |
| template `add_one<long long>` | `S_GPROC32` `add_one<__int64>`; public `??$add_one@_J@@YA_J_J@Z` | `S_GPROC32` `add_one<long long>`; same public |
| static function `guarded_length` | `S_LPROC32` `guarded_length`, no public; its EH funclet is another `S_LPROC32` `` `guarded_length'::`1'::catch$0 `` far away (rva 472656) | `S_LPROC32` `guarded_length`, no public |
| anonymous-namespace function | `S_LPROC32` `` `anonymous namespace'::make_dynamic `` | same |

Consequences for the (decorated name, object file) key:

1. Statics and file-local functions have **no `S_PUB32`**, so the only bridge from the object file's
   symbol table (decorated names, e.g. `?s_counter@?A0x....@@3HA`) to the PDB is the *display name
   plus address*. Display names differ between cl and clang-cl for the same entity (namespace prefix
   on statics, `__int64` versus `long long`, one versus two closing quotes on the initialiser), so
   WP-07 must not compare display names across compilers or with the demangler's output as plain
   strings; compare per PDB, normalise, or use the RVA: every local symbol has section:offset, RVA and
   its compiland (`compiland_for_rva`), and an object's symbol of the same section offset within the
   contribution identifies the pair.
2. In the optimised cl cell `s_counter` is still present (cl does not fold it); an optimising clang-cl
   may turn an unmodified static into an `S_CONSTANT` in the global stream and drop the `S_LDATA32`
   (seen with clang + lld locally). `k_table` and `s_dynamic` survive.
3. Function-local statics are `S_LDATA32` inside the proc scope (`parent_name` = enclosing function).
   Example from cl: `_OptionsStorage` inside `__local_stdio_printf_options`; that one is an
   inline function's static (COMDAT), so it *does* have a public
   (`?_OptionsStorage@?1??__local_stdio_printf_options@@9@4_KA`, found with `publics_at_rva`),
   which a plain file-local static does not.
4. Template instantiations, inline functions and `std::` members are `S_GPROC32` (COMDAT) with a public
   at the same RVA; the display name is the C++ name with template arguments.

## Benchmark (CI job `pdb-benchmark`, windows-2022, MSVC 14.44, RelWithDebInfo build of `cml_pdb_bench`)

Generator: `tests/bench/gen_pdb_project.py --tus 900 --funcs-per-tu 1000 --headers 24 --seed 1
--debug-format Z7` (900 translation units x 1000 distinct functions, 24 shared headers with
inline functions and templates, local UDTs, anonymous-namespace statics, function-local statics,
dynamic initialisers), built with `cl /Z7 /Od /Gy`, linked `/DEBUG:FULL /OPT:NOREF /OPT:NOICF`. The
PDB is cached with `actions/cache` (key = `BENCH_ID` + hash of the generator). First build of the
600-TU variant took 121 s on the runner (the 900-TU one is about 1.5x that), so the whole job is far
inside the 25 minute target. Deviation from the brief: compiled with `/Z7`, not `/Zi`: `/Zi`
funnels every cl process through one `mspdbsrv`, which serialises 900 TUs on a shared runner; the
final PDB is still written by the linker with `/DEBUG:FULL`, and `--debug-format Zi` switches it
back. `S_ENVBLOCK`/`S_BUILDINFO` of this PDB were not dumped.

Result of the run on the head commit (PDB 544.0 MiB, 1131 compilands, 1704 distinct files,
2,061,082 section contributions, 908,262 publics):

| phase | ms (wall) |
|---|---|
| map | 0.1 |
| MSF directory | 0.6 |
| DBI header | 21.0 |
| module table + `S_COMPILE3`/`S_ENVBLOCK` heads | 2.4 |
| source-info lists + inverse file map | 26.0 |
| section headers + contributions | 41.7 |
| `open()` total | about 93 |
| publics + global data | 57.5 |
| all compiland symbols (8 threads; 395 ms CPU) | 99.5 |
| **total load** | **250.4** (budget for 544 MiB at 2 s per 500 MB x2 slack: 4352) |

Memory (counted allocations of cml_pdb's own containers + whole mapped file):
173.0 MiB + 544.0 MiB = 716.9 MiB = **1.32x** the PDB size (budget 1.5x). Index memory after `open()`
34.2 MiB, after publics 119.4 MiB (the symbol record stream, 908k publics, is the largest single
item: its names are kept in place), after all symbols 173.0 MiB. Peak working set of the process
552.7 MiB (only the touched pages count; the warm-up reads through a small buffer, not a mapping).
The margin to the budget is about 0.18x of the file size: a PDB whose module symbol area is a
larger share of the file than here (this one has hardly any type data to skip) would be tighter.
The earlier first-cut implementation was at 1.59x on a local 55 MB PDB (per-symbol hash tables,
unshrunk vectors, the DBI stream copy kept, 32-byte records); the fixes were compact records,
exact two-pass allocation, lazily built name/RVA indexes, dropping the DBI copy after `open()`, and
a 16-byte contribution record.

Locally (clang + lld-link, 80 TUs, 53 MiB PDB): load 97 ms in an unoptimised build, 1.22x memory.

## What was learned

- Both toolchains' linked PDBs carry **S_BUILDINFO, not S_ENVBLOCK** (see evidence). Plan section 4.3's
  statement needs fixing, and WP-05 must read the IPI stream (done here: `build_env`).
- clang-cl's DBI file list omits headers without line information; cl lists everything.
- Display names of the same entity differ between cl and clang-cl (table above).
- `S_GDATA32` records are in the global symbol stream (lld hoists them out of module streams
  entirely; link.exe keeps them in the modules too), so global data lookups use the global stream.
- Unmodified file-local statics may disappear into `S_CONSTANT` under clang optimisation.
- LLVM's `-fno-exceptions` libstdc++ does not honour `vector::shrink_to_fit`, so anything memory
  critical here sizes exactly instead of relying on it.
- MSVC STL's `string_view` stream operator needs `<ostream>` included before doctest stringifies it.

## raw_pdb

Only `PDB::ValidateFile` is used (super block, size against block count, free block map index), as a
gate in front of cml_pdb's own bounds-checked MSF/DBI/CodeView parsers. raw_pdb's stream classes
trust offsets from the file and assert, which is not acceptable for malformed input, so they are not
used. No raw_pdb source was modified. Risk note for WP-28 fuzzing: `ValidateFile` itself is trivial;
the attack surface is cml_pdb's own parsers, which are already exercised by truncation and
byte-flip tests in `tests/unit/pdb/test_robust.cpp` under ASan/UBSan on Linux (run locally with GCC; not in CI).

## Deferred, with reasons

- **Symbol server**: seam only (`OpenOptions::symbol_server`); out of scope for this WP.
- **PDB locked while mapped**: the index keeps the PDB mapped read-only for its whole life (also
  cached ones). The mapping uses all share modes, but a writer that truncates a mapped file (the
  linker rewriting the PDB in place) fails with `ERROR_USER_MAPPED_FILE`. The broker must drop its
  `shared_ptr` before relinking the target, or a copy mode (read the file into memory) must be added.
  Not done here because it changes the memory budget; flagged for WP-18/the broker.
- **`private RSDS extractor`** to be replaced by `cml_pe` after WP-02 merges.
- **`/DEBUG:FASTLINK` detection** (CML1101) belongs to WP-18; the index opens such a PDB but module
  symbols are then absent.
- **TPI/IPI type records** are not indexed (only IPI strings for build info). Type information is
  WP-07/later.
- **`SectionHdrOrig`/OMAP**: only the plain section header stream is used.
- **Non-ASCII case folding** in `normalize_path`.
- **compile_commands.json fallback** is WP-05; "non-reloadable" diagnostics WP-18. Here:
  `Compiland::has_env_block()`, `PdbIndex::build_env()` (`source == None`).
- Names pool and offsets are 32-bit: a single module's names or the global symbol stream above 4 GiB
  fail with CML1418.
- Memory counter covers cml_pdb's own long-lived containers; transient `std::string`s while opening
  (module heads) and the small `Compiland::env` vectors are not counted.
