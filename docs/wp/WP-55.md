# WP-55: reload and restart caches (R-58, R-62, R-63)

Branch `wp/55-caches`, one PR. ADR-0045, section WP-55. Review: medium. No new diagnostic id.

All three items keep WP-50's stamp-before-use rule: every input a cached result depends on is stamped before the scan
uses it, a result is never kept with a stamp taken after the use, and a lookup stamps every input again before anything
of the entry is used. The two TOCTOU fixes of the WP-50 delta review are unchanged.

## What was built

### R-63: a file over the scanner's size limit is an input, not a failed read

| Piece | File | Notes |
|---|---|---|
| Size limit | `include_scan.h` | `kScanMaxFileBytes` (8 MiB), the limit `disk_file_reader()` already applied, is public. |
| Recorder | `module_index.{h,cpp}` (`ScanInputRecorder::wrap`) | A read that fails for a file whose stamp (taken before the read) says it exists, is a file and is over the limit is not remembered as unreadable: the disk reader never reads such a file, so every read gives the same answer until its stamp changes. The file is an input with that stamp (a part that met it records it, see R-58). Only a failed read of a file under the limit (a sharing violation, an I/O error) makes the part that met it uncacheable (`unreadable:<path>`). A directory and a missing file are not failed reads, as before. |

Effect: Godot's generated `doc_translations.gen.cpp` (over 8 MiB) no longer makes every Godot scan
`WP50-SCAN-CACHE store=skipped reason=unreadable:...`. The file becomes one input with its stamp.

### R-62: WP-51's inline-site verdicts across reloads

| Piece | File | Notes |
|---|---|---|
| Cache | `bind_plan.h`, `src/inline_verdict_cache.cpp` | `InlineVerdictCache`: per (compiland, procedure index) the verdict `judge_inlinees` reached (risk, the R-57 evidence, closure tails, counts), with the procedure's RVA and name. Keyed by the PDB's identity (GUID and age): a lookup under another identity finds nothing, a store under another identity drops the old entries, a zero identity is never kept. A lookup whose entry names another RVA or name finds nothing. Only verdicts from inline sites that could be read are kept. Thread-safe. |
| Owner | `module_state.h` | `ModuleState::inline_verdicts`: one per module state, so it is dropped with the module (disable, unload, the agent's disconnect; a module loaded again or a hot-restart's process is a new state). |
| Planner | `bind_plan.cpp` | The cache lookup only: `inline_verdict(proc)` asks the cache before it reads, the first verdict's batch leaves out the procedures the cache answers, and `judge_inlinees` stores what it judged. The rules of WP-51 are not touched. `PlanInput::inline_verdicts` (optional). |
| Pipeline | `pipeline.cpp` | Passes the module's cache. `WP55-INLINE-CACHE module=... object=... kept=<verdicts from the cache> read=<verdicts read> entries=...` per unit that needed a verdict. |

Why a verdict from the cache is the verdict the planner would read: it is a function of the procedure's inline-site records
and the IPI/TPI records they name, all in the PDB of the loaded image, which does not change while the module is loaded.
The PDB may be released and mapped again (ADR-0017); it is the same file with the same identity. A relinked PDB
mapped again has another age or GUID, and nothing kept for the old identity is used.

## How to run

Nothing to switch on: the scan cache (set-option `cache_include_scan`, default true) and the verdict cache are used
whenever the module was indexed or planned before in the session. Evidence: the broker log's `WP50-SCAN-CACHE`,
`WP55-SCAN-RESCAN`, `WP50-INDEX ... cache=partial`, `WP50-RESTART ... index_scan_reused=...` and `WP55-INLINE-CACHE`
lines (docs/TROUBLESHOOTING.md, first steps item 5).

## What was learned

* The scanner's memo (WP-50) answered a remembered miss with `-1` and kept no id, so a walk that was answered from memory
  could not say what it depended on. The memo now keeps the file id; the answer is the same.
* A compiland's part of the include graph depends on exactly the paths its walks asked about: each one's existence and
  readability, and the contents of those read. The directory stamp stands for a path that did not exist, the file's own
  stamp for one that did. Over 8 MiB is a property of the stamp, not of the read.

## Deferred

* Reuse across a relink of the module (another module stamp): the compiland indices and the PDB's file lists may change,
  so nothing is reused; the whole module is scanned again, as in WP-50.
* A part reused from the cache is not stamped again after the scan (the lookup checked its inputs just before it was used,
  as for a WP-50 hit). An input that changes after the lookup is seen by the next lookup, because the entry keeps the
  stamps from before.

## After ci 46091387396 on d26fd78: racy stamps

The two review tests failed in 6 of the 14 Windows jobs. The index came back `warm`, and `before_scan_for_testing` was never called. Both tests edit app.cpp to the same size (`return 1` to `return 2`) and then move its time 2 s ahead. The first index runs between the two edits and takes only a few milliseconds. NTFS takes file times from the system clock tick (about 15.6 ms on these runners), so both writes can get the same time, and then the same time plus 2 s. The stored stamp then equals the new one, and the edit is invisible.

**This is a real cache bug, not only a test artefact.** A same-size edit that lands within one tick of the stamp is invisible to (size, mtime) in normal use too: an editor saving a one-character change right after the index read the file, for example. The stale graph then hits for the rest of the session.

Reproduced on Linux: I set app.cpp's time back to the first stamp's time after the second edit. Without the fix, the same assertions fail as on Windows (lines 463-472). With the fix, they pass.

**Fix (git's "racily clean" rule).**
- `stamp_scan_input` marks a stamp racy when the path's time is within `kScanRacyWindowSeconds` (2 s, which covers FAT's 2 s too) of the moment the stamp was taken, or later.
- A racy stamp also carries a content hash:
  - a file's hash is of the text the scan read (`ScanInputRecorder::wrap`);
  - a directory's hash is of its sorted names, taken with the stamp, before any use.
- `scan_input_holds` checks every racy stamp by content as well. It is used by the lookup, by `changed_scan_input` and by the re-check after the scan.
- In the result table, a racy stamp copied before the file was read gets the content the scan read. A reused part's racy stamp whose content differs from what the scan read is a `problem`, and the part goes to the second pass.
- Stamps older than 2 s are trusted on (size, mtime) as before, so a Godot-sized scan pays nothing extra.

The review tests are unchanged: they exercise exactly this case. New portable test in `test_include_scan.cpp`: `WP-55 (review): a same-size edit within the stamp's clock tick is caught: a racy stamp is checked by content`. It covers:
- a file edited to the same size with its time put back;
- a file created in a directory whose time is put back;
- a file last written an hour ago, which is not racy.

**Merged origin/main 391b28a** (WP-53, WP-54). The merge was clean.
- **Planning.** In WP-54's split pipeline, the cache is passed and `WP55-INLINE-CACHE` is logged in `ModuleReload::prepare(Staged&)`, once per planned unit of the module.
- **Abandon and roll-back.** Neither a cross-module abandon nor a roll-back touches `ModuleState::inline_verdicts`, and a `ModuleState` is only created at enable.

  A verdict depends only on the old PDB, so a verdict read by a plan that was later abandoned or rolled back is still valid.

## Convergence ruling on 6f0f0ae (ADR-0018)

**The same-tick hole was already on main.** WP-50's whole-module cache trusted (size, mtime) alone, both at a hit and in the re-check after the scan. A same-size edit within one timestamp tick of the stamp therefore went unseen on main as well. WP-55 closes it with racy stamps checked by content.
