# WP-10: Hook installer (agent side)

Plan section 4.8, ADR-0016 (heap, suspension rules), ADR-0020 items 4 and 5 (entry bytes, padding), diagnostic range
CML4300-4399 (ADR-0008).

## What was built

All code is in `agent/src/hook/`; none of it needs a third-party library.

| File | Content |
|---|---|
| `length_decoder.h/.cpp` | x64 instruction-length decoder, table driven (tables are built at compile time from opcode-range rules). Portable. |
| `hook_plan.h/.cpp` | Chooses strategy 1 or 2 from copies of the bytes around an entry, computes the RIP window, encodes `jmp rel32`. Portable. |
| `thread_set.h/.cpp` | Pre-sized thread table, `NtGetNextThread` enumeration, suspend / RIP capture / resume. Windows. |
| `installer.h/.cpp` | `Installer`: install, re-point, revert; all-or-nothing batches; registry of installed hooks and their original bytes. Windows. |
| `dispatch.cpp` | `Agent::handle_install_hooks` and friends: the InstallHooks request dispatcher. Windows. |
| `diag_ids.h` | CML4300-4316. |

Wire payloads (`core/cml_ipc/.../messages.h`, ids never renumbered, both now marked implemented):

* `InstallHooks` 0x0040, broker to agent: `u64 request_id, u32 flags, u32 count, count x {u64 old_entry, u64 new_entry, str name}`.
* `HooksInstalled` 0x0041, agent to broker: `u64 request_id, u32 status, str message, u32 attempts, u32 retries, u32 threads, u32 window_ms, u32 count, count x {u32 strategy, u32 status, u32 diag, str message}`.
* **Revert is folded into InstallHooks** (flag bit 0, `kInstallHooksRevert`; `new_entry` is ignored). Reason: it is the same operation on the same list, applied in the same stop-the-world window and answered by the same message; a second message pair would have duplicated every serialiser and every dispatcher branch. Unknown flag bits are rejected by the decoder.
* `InstallHooks` is a request type for `is_request_type` / `peek_request_id`, so the agent can answer an undecodable one (it replies with `HooksInstalled{status = CML5201...}`).
* Limits: 16384 hooks per message; reply text is carried only for the first 64 failed hooks, clipped to 600 bytes, so any reply fits one frame.

Dispatcher: `Agent::handle_install_hooks` (agent thread) calls `post_main_thread_work`. In synchronised mode the job is queued on `SyncQueue` and runs inside `cml::SyncPoint()` on the calling thread; in immediate mode it runs at once on the agent thread. The answer is queued and sent by the agent thread (`flush_replies`). `agent.cpp` gained three additive blocks (the dispatch line, the flush call, the rejected-InstallHooks answer); everything else is in `hook/dispatch.cpp`.

## How the hook is applied

Strategy choice (`hook_plan.cpp`), decided per function at install time:

1. **Padding + 2-byte** when the 6 bytes before the entry are all `CC`/`90`, the first instruction is at least 2 bytes (`40 57` = REX `push rdi` counts, 2 bytes), the entry address is even (2-byte aligned, so the 16-bit exchange cannot straddle a cache line) **and** the padding lies in executable memory (`VirtualQuery` of the first and last padding byte: committed, not guard, an EXECUTE bit; otherwise the jump would land on bytes the CPU cannot run). An odd entry or a non-executable padding page falls back to strategy 2 (`PlanEnvironment` in `hook_plan.h`; the installer fills it from the real address). `E9 rel32` goes into the 5 bytes before the entry, then `EB F9` at the entry via one 16-bit interlocked exchange.
2. **5-byte** otherwise: `E9 rel32` at the entry, written with one 64-bit compare-exchange when the 5 bytes lie inside one aligned 8-byte block, plain stores otherwise (everything else is stopped anyway). The RIP window is the entry up to the **end of the last instruction touched** (ADR-0020 item 4: `48 83 ec 28` is split by the jump, so the window is 4+ bytes, the stray tail bytes are never executed). A function shorter than 5 bytes is accepted only if the bytes between its end and byte 5 are `CC`/`90`; otherwise CML4301.
3. A call instruction that ends *inside* the overwritten range is refused (CML4304): a thread inside that callee would return into overwritten bytes. A call that is the last touched instruction is fine.
4. Any instruction the decoder does not cover inside the range is CML4300 (fail safe, bytes are quoted).

Procedure of a batch (`installer.cpp`):

1. Plan with all threads running (read bytes with `ReadProcessMemory`, which fails instead of faulting; strategy; range check +-2 GB; duplicates; overlapping regions; target and replacement must be executable). A single failure ends the batch before any thread is touched. Everything that allocates happens here.
2. `VirtualProtect` the (at most 2) pages of each hook to RWX, still before suspension. Restored after resume, in reverse order, each page to its own previous protection.
3. Stop the world: `ThreadSet::suspend_all` repeats the enumeration until a complete pass finds no thread it has not suspended (max 16 passes, 2 s budget, 4096-thread table). Compare every thread's RIP with every window. A thread inside a window: the offending threads alone are let run for about 1 ms (`offender_run_us`: yield on `SwitchToThread` and spin on `QueryPerformanceCounter`), suspended again and re-checked (up to 3 times, everything else stays stopped; the number of steps is bounded by `steps_per_attempt`); if that does not resolve it, everything is resumed, the installer yields (4 times) or sleeps 1 ms, and tries again. After **50 stops** the batch fails with CML4305 naming thread, function and RIP offset.
4. With no thread in a window: re-verify that the bytes are still the planned ones (else CML4312), write, `FlushInstructionCache`, resume.
5. Registry: the original bytes of the FIRST hook are kept; re-pointing rewrites only the 4-byte displacement (in the padding for strategy 1, at entry+1 for strategy 2) and never touches the recorded originals. Revert restores entry first, then padding.

### What runs while threads are stopped, and why each call is safe

Between the first `SuspendThread` and the last `ResumeThread` (`ThreadSet::suspend_all`, `Installer::attempt`, `apply_write`): no allocation, no logging, no locks of ours, no CRT call, no loader call. `heap::set_alloc_forbidden(true)` is set around the part that reads and writes code (a stray allocation aborts, tests check it is set), and cleared while an offender is let run.

| Call | Why it is safe |
|---|---|
| `NtGetNextThread` (resolved by `GetProcAddress` before any suspension) | system call that walks the kernel thread list and hands out a handle; no user-mode lock, no allocation. Used instead of a toolhelp snapshot, which allocates from the process heap in user mode. |
| `GetThreadId`, `GetExitCodeThread`, `NtQueryInformationThread(ThreadIsTerminated)` | thin system-call wrappers. |
| `SuspendThread`, `GetThreadContext(CONTEXT_CONTROL)` into a stack `CONTEXT`, `ResumeThread` | system calls. `GetThreadContext` on a thread whose suspension is in flight waits for it, so the RIP is the one it resumes from. |
| `CloseHandle` | `NtClose`; for handles that were only needed to find the next thread, and (after resume) the table's. |
| `SwitchToThread`, `GetTickCount64`, `QueryPerformanceCounter` | `NtYieldExecution`; reads of the shared user data page / the time stamp counter. |
| `_InterlockedExchange16`, `_InterlockedCompareExchange64`, byte stores | CPU instructions on pages made writable beforehand. |
| `FlushInstructionCache(GetCurrentProcess())` | `NtFlushInstructionCache`. |

`VirtualProtect` and `ReadProcessMemory` are deliberately called outside the window. This table is derived from how the Windows system DLLs implement these calls, not from a test that can prove the absence of a lock; the stress test below is the empirical check (a thread that is stopped inside `malloc`, `LoadLibrary`/`FreeLibrary` or `CreateThread` while the installer works would deadlock it).

There is no separate watchdog thread. A second thread resuming the world while the installer writes would race the writes. Instead every loop in the window is bounded (passes, steps, a 2 s deadline checked by `GetTickCount64`).

**The budget is enforced inside a pass**, not only between passes: `ThreadSet::expired()` is checked before every enumeration step (`NtGetNextThread`), before every `SuspendThread` and `GetThreadContext` attempt and between their retries, and by the installer before every offender step and after every offender re-suspension. On expiry the call returns `Timeout` at once, `Installer::attempt` resumes everything and the batch fails with **CML4309**. It is never reported as CML4305 (a thread that would not leave) or CML4307 (new threads kept appearing) and is not retried: the budget is spent. Tests: `ThreadSet` with a knob that expires the budget at the n-th check, for n sweeping the places where checks are (every result is `Ok` or `Timeout`, everything resumable and running afterwards), and the installer with the same knob (CML4309, one attempt, bytes unchanged, workers running again), and a spinner that never leaves with a 40 ms budget and an unlimited step count (CML4309, not CML4305).

**The one unbounded call.** `GetThreadContext` returns when the target thread has really stopped, and the kernel gives a caller no way to abandon that wait. The deadline is checked before each call, so a budget that is spent stops the pass at the next thread, but a single call cannot be interrupted. Nothing else in the window can block for an unbounded time.

**Set lookup.** The ids of the threads already in the set live in a pre-sized open-addressing table (power of two, load factor at most 1/2, allocated in `init`), so a pass is O(threads), not O(threads squared). `unit.agent_hook` stops 600 threads in one go and prints how long it took.

**The step-limit exit** of the enumeration (the guard against a kernel that keeps handing out threads) closes the temporary handle it was holding. Test: 60 forced step-limit exits with `GetProcessHandleCount` before and after (a leak shows as +60).

**Allocation in the window is caught by the tests, not just forbidden.** `unit.agent_hook` and `unit.agent_hook_stress` link `agent/src/operator_new.cpp`, the same replacement of `operator new/delete` that `cml_agent.dll` links, so in the tests every `new` / `delete` goes through the agent heap and `heap::set_alloc_forbidden` is really exercised (before this, the test executables used the CRT's `new` and the flag was never tested). `alloc_guard.h` installs, for the thread that owns the stopped window only (threads not yet stopped may allocate): a `heap::set_violation_hook_for_test` hook (agent heap) and, in Debug cells, a `_CrtSetAllocHook` (every `malloc` / `calloc` / `realloc` / `free` of the C runtime). Outside the negative tests a violation writes `WP10-ALLOC FATAL` and ends the process, so a test cannot pass with one. The negative test allocates (`new[]` and `malloc`) from the `test_in_window` callback and requires the hooks to fire; a positive control installs, re-installs and reverts three hooks with the hooks in counting mode and requires zero violations. The Release CRT has no allocation hook, so the RelWithDebInfo cells check the agent-heap path only; the C runtime path is checked in the Debug cells.

## Length decoder

Covered: legacy prefixes (66, 67, F2, F3, F0, segment overrides), REX; one-byte map: ALU (00-3F rows), push/pop, movsxd, push imm, imul imm, jcc rel8, group 1, test/xchg/mov/lea, nop/xchg/cdq family, string ops (with rep), mov imm (B0-BF incl. imm64), shifts, ret/ret imm16, mov imm (C6/C7), leave, int3/int imm8, x87 escapes (modrm only), loop/jrcxz, call/jmp rel, groups 3/4/5 (inc, dec, call, jmp, push); `0F` map: nop forms, endbr64 (`F3 0F 1E FA`), prefetch, SSE/SSE2 moves and arithmetic (movaps/movups/movdqa/movdqu/movq...), cmov, setcc, jcc rel32, bt family, shld/shrd, imul, movzx/movsx, xadd/cmpxchg, bswap, popcnt/bsf/bsr, fences, `0F 38` and `0F 3A` maps (all have ModRM; 3A has imm8), cpuid, rdtsc, syscall, ud2, `0F 01` group. ModRM/SIB/disp8/disp32/RIP-relative are computed from the ModRM byte. VEX, EVEX, XOP, moffs, I/O, far transfers, and anything undefined are **Unknown** (CML4300). `66` combined with a rel32 branch is also refused (rel16 or rel32 depending on vendor).

Verification:

* `test_length_decoder.cpp`: several hundred hand-computed vectors, including every ADR-0020 entry sequence, and the property that a window one byte short is "truncated", never a shorter instruction.
* Differential check (done locally on Linux, not part of CI): every instruction objdump reports for `libc.so.6` (385,673) and `libLLVM-17.so` (13,441,694) was fed to the decoder; whenever it answered it agreed on the length, 0 disagreements (the 6,275 + 10,321 refusals are VEX/EVEX and prefix-only fragments).
* CI evidence: `cml_lde_probe` decodes the first 16 bytes of every function in fixture `basic`'s PDB (the static CRT included). See "CI evidence".

## Diagnostics (CML4300-4316)

| id | message (names the function) | what to do |
|---|---|---|
| 4300 | instruction at `fn+N` (bytes ..) is not understood | report the bytes or exclude the function |
| 4301 | shorter than 5 bytes and no usable padding | `/FUNCTIONPADMIN` or a longer body |
| 4302 | new code more than 2 GB from the jump | bug: patch memory must be near the module |
| 4303 | code cannot be read / not executable / cut inside an instruction | check the address |
| 4304 | a call ends inside the overwritten bytes | exclude, or add padding |
| 4305 | thread N kept executing inside the first bytes after 50 attempts | wait for the application to leave the function |
| 4306 | cannot enumerate threads / more than 4096 | bug / limit |
| 4307 | enumeration passes keep finding new threads | stop thread creation, retry |
| 4308 | `VirtualProtect` failed | code-integrity policy |
| 4309 | threads stopped longer than 2 s | fewer functions per reload |
| 4310 | bad request (null, listed twice, replacement is the function, replacement not executable) | bug in the sender |
| 4311 | revert of a function without a hook | nothing to do |
| 4312 | bytes are not the recorded ones (another tool patched them) | remove the other tool |
| 4313 | not attempted: another hook of the request failed | fix that one |
| 4314 | a thread could not be suspended or inspected | bug |
| 4315 | more than 16384 hooks | split |
| 4316 | two hooks overwrite overlapping bytes | bug unless tiny functions are back to back |

CML4301 is the (renumbered) successor of the planned `CML4101` row in KNOWN_LIMITATIONS.md.

* `ctest --test-dir build -C <config> -R "unit.(agent_hook|ipc)" --output-on-failure`

### Repeat runs, the hang, and what they showed (review follow-up)

A temporary CI step ran `unit.agent_hook` and `unit.agent_hook_stress` repeatedly in every matrix cell (it is removed again). Results:

* At head `c3049c5`, 20 runs of each test in each of the 8 cells: `WP10-REPEAT <cell> unit.agent_hook runs=20 passed=20 failed=0` and `unit.agent_hook_stress runs=20 passed=20 failed=0` in all 8 cells (160 + 160 runs, none crashed or hung).
* The exit crash that was seen earlier on some Debug cells was **not reproduced** in these 320 runs, nor in the 8 x 10 + 8 x 10 runs at `250397c` (those counts are inferred from the step succeeding; the step exits non-zero on any failure). Its root cause was never established. The leading suspect is test threads still starting up or tearing down at process exit under the Debug runtime (the "threads created continuously" test now waits for every child); this is a hypothesis, not a finding.
* At `15b0604` the repeat step found two different problems, both in tests and not in the installer:
  1. `unit.agent_hook` hung for the whole 300 s once in windows-2025 msvc Debug and once in windows-2025 clang-cl Debug (`***Timeout 300.00 sec`, no output at all). The in-process hang watchdog printed nothing because it is one of the threads the installer stops, which is the evidence that the world was stopped and never resumed. Cause (inferred; not reproduced): tests added in the first review round allocated (`MESSAGE`, `std::vector`, `CHECK`) between `ThreadSet::suspend_all` and `resume_all`; with `operator new` now going through the agent heap, an allocation on that thread can wait for a heap lock held by a thread that is stopped. **Tests must not allocate or take a lock while the test thread has the world stopped**: they now copy results into locals and check after `resume_all`. The installer's own window code allocates nothing (`alloc_guard.h` fails the process otherwise).
  2. `unit.agent_hook_stress` failed `CHECK(retries >= 1)` once (windows-2022 clang-cl Debug, `retries=0` over 3834 stops): catching one of 16 workers in a 150-iteration loop was left to chance. The stress test now has a pinned thread that loops about a millisecond inside the slow function while it is unhooked, with a 1 ms gap between calls (without the gap a function that is never left is, correctly, CML4305). The assertion is unchanged.
* **Out-of-process hang watchdog.** Because of 1., `unit.agent_hook` and `unit.agent_hook_stress` start `cml_test_hang_watch.exe` (tests/unit/hang_watch) from `doctest_main.cpp`. It waits for the test process; 10 s after the in-process budget it prints, for every thread, the suspend count and the RIP as module+offset (`HANGWATCH: thread N suspend_count=K rip=0x... module+0x...`), writes a minidump (thread info, handle data, unloaded modules) to `CML_TEST_DUMP_DIR` and terminates the process with exit code 3. `test_hang_watch.cpp` proves it fires: a victim process suspends its own threads and hangs; the test checks the thread lines, the module+offset, the dump file and exit code 3.

## What was learned

* NtGetNextThread chains handles; an exited thread whose handle is still held stays in the kernel list, which is what makes the chain safe. The enumeration has a step budget and a no-progress check anyway.
* The RIP-in-window check as written in the plan (resume everything, retry) makes a busy 16-thread process fail often, because every retry re-randomises all threads. Letting only the offenders run for a moment while everything else stays stopped resolves nearly all conflicts in one stop.
* Local Wine smoke runs (mingw-w64 cross build) exercised the installer, the retry path and the dispatcher; Wine behaves differently from Windows on thread creation under suspension, so they are not evidence for the acceptance criteria, only for catching mistakes early.

## Deferred / limitations

* **A thread whose real resume point is inside a window but whose RIP is in ntdll's exception or APC dispatcher is not detected.** `GetThreadContext` reports the RIP of the dispatcher (`KiUserExceptionDispatcher`, `KiUserApcDispatcher`, `KiUserCallbackDispatcher`) while the thread is being delivered an exception, an APC or a callback, and the interrupted RIP lives in a context record on its stack. If that interrupted RIP lies in the overwritten bytes, the thread resumes there after the write. Compilers do not make a function's first bytes the resume point of an asynchronous event in practice, and the installer does not walk the stack to look; it is listed in `docs/KNOWN_LIMITATIONS.md` under "Documented behaviour".
* The broker side (`cml_core` session) still treats `HooksInstalled` as "not accepted from an agent"; accepting it and sending `InstallHooks` is WP-12. Nothing in `broker/` was touched.
* Jobs left in the SyncPoint queue when an agent is destroyed are leaked (a small struct each); `SyncQueue` has no cancel.
* A reply produced after the connection dropped is delivered to the next broker session if one connects before it is sent (answers queued while connected are discarded when a send fails). WP-12 must ignore unknown request ids.
* A branch from elsewhere in the function back into the first bytes (a loop whose target is inside the overwritten range) is not detected; compilers do not emit this for prologues.
* A thread that is created after the last enumeration pass and calls a hooked function within microseconds could see a half-written 5-byte jump when the entry is not inside one aligned 8-byte block and strategy 1 is not available. Strategy 1 and aligned strategy 2 writes are single atomic stores.
* ARM64, x86 and WOW64 are out of scope.
