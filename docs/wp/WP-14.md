# WP-14: File watcher and change detection

One branch (`wp/14-file-watcher`), one PR. Plan section 4.14, diagnostics CML5500-CML5549.

## How it works

1. The index of a module (WP-12) takes the xxh3 baseline of every source and header its compilands list. `ModuleIndex::tracked_files()` exposes those paths.
2. With `compile_on_save` on, the directories of those files are watched. An event for any path is turned into a key (lower case, backslashes) and collected; temporaries of editors never match a tracked file, and their last event says they are gone.
3. When a burst is over, the batch is checked: a tracked file whose last event says it exists, or an overflow, starts a reload. Nothing else does (a deleted tracked file is not a save).
4. **The confirmation by content hash is the reload's own sweep** (`SourceBaseline`, WP-12; no second baseline). Size and mtime prefilter, then xxh3 against the baseline: a formatter no-op or a touch hashes equal and finds nothing to compile (`patched = 0`, no patch, no event). Hotkey mode is the same sweep run by `reload`.
5. Saves while a reload runs: the reload is not started concurrently (`running_` check; the dispatcher thread waits 50 ms and retries on busy), and the events that arrive meanwhile coalesce into one batch, so exactly **one follow-up reload** runs.
6. Right after (re)arming, one synthetic event for a tracked file runs a catch-up sweep, so a save made between the baseline and the watcher starting is not lost.

### Atomic-save patterns (unit-tested on the event sequences ReadDirectoryChangesW produces)

| Editor | Sequence | Result |
|---|---|---|
| Visual Studio | write `x~RFnn.TMP`, rename `x` away to another `~RF` file, rename the temp to `x`, delete the old | `x` present, both temporaries gone |
| VS Code | in-place writes (truncate, content) | `x` present |
| Rider / IntelliJ | `x___jb_tmp___`, rename `x` to `x___jb_old___`, rename tmp to `x`, delete old | `x` present |
| vim (backup) | probe file `4913` added and removed, rename `x` to `x~`, new `x`, delete `x~` | `x` present |
| vim (nobackup) | probe `4913`, in-place writes | `x` present |

`tests/unit/watch/test_directory_watcher.cpp` does the same with real renames in a temporary directory (Windows CI only).

## Diagnostics

| Id | Meaning | What to do |
|---|---|---|
| CML5500 | (warning) a directory cannot be watched | saves there are picked up by the next `reload` |
| CML5501 | (warning) events were lost (buffer overflow or a watched directory vanished) | none: every tracked file is re-checked by hash |
| CML5502 | directory watching is not available on this host | use `reload` |
| CML5503 | the watcher could not start or none of the directories could be opened | check the source directories; use `reload` |
| CML5504 | (info) compile-on-save is on but no source directory is known yet | enable a module; watching starts when its index is ready |
| CML5505 | (warning) the reload started by a save failed | the reload's own diagnostic was published just before |
| CML5510-5512 | harness: `expect_event` timeout, `set_option` refused, `wait` failed | |

Watcher diagnostics are published as `diag` events with stage `watch`.

## Learned / deferred

- Baselines are taken eagerly by the index (WP-12), not lazily at first sight as plan 4.14 words it. A file that is not tracked is never reported. A save of a *new* header that no compiland lists yet is invisible until the PDB changes.
- Include directories that are system paths are not tracked (WP-12 default), so they are not watched either.
- Network shares and file systems that do not deliver change notifications are not covered; `reload` still works. Recursive roots may produce many irrelevant events; they are dropped by the tracked-file check.
- A directory whose handle is open cannot be deleted by other programs unless they share delete (the watcher opens with `FILE_SHARE_DELETE`).
- Not done: watching for a changed PDB or module, a GUI toggle (WP-17 area), `compile_on_save` persistence.
