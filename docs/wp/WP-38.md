# WP-38: VEX and EVEX in the hook length decoder; decoder fuzzing (R-04, R-41)

ADR-0042, branch `wp/38-vex-decoder`. Diagnostic range CML4317-4329: **no id was needed** (the outcome of an
undecodable entry is still CML4300, of a cut one CML4303).

**This reverses a WP-10 decision.** WP-10 wrote "no VEX, no EVEX": anything VEX-encoded was Unknown and the function
could not be hooked (CML4300). The reason was caution about a decoder nobody had checked against a reference. ADR-0042
reverses it together with that check: the decoder now knows VEX and EVEX, and every length it reports is compared
with a reference disassembler by a fuzzer and by a sweep over real code.

## The decoder

In 64-bit mode `C4` and `C5` are always VEX and `62` is always EVEX (never LES, LDS, BOUND), whatever the next byte is.

```
C5  [R vvvv L pp]                                   map 1 (0F)
C4  [R X B m-mmmm] [W vvvv L pp]                    map m-mmmm: 1 = 0F, 2 = 0F 38, 3 = 0F 3A
62  [R X B R' 0 0 m m] [W vvvv 1 pp] [z L'L b V' aaa]   the same three maps
opcode, ModRM (+ SIB, disp8 or disp32), imm8 where the opcode has one
```

* **ModRM** always, except VEX `0F 77` (vzeroupper, vzeroall). SIB and displacement exactly as for a legacy
  instruction: a VSIB is one SIB byte, an EVEX compressed displacement (`disp8*N`) is one byte.
* **imm8**: every map-3 opcode (the `/is4` forms carry a register number in it), and in map 1 `70`, `71`, `72`, `73`,
  `C2`, `C4`, `C5`, `C6`.
* **The tables** (`build_vex()`) hold one byte per opcode for each of the six maps: for which `pp` values (none, 66,
  F3, F2) the opcode is an instruction, whether an immediate follows, whether there is no ModRM. An opcode or `pp`
  the tables do not name is Unknown. Opcodes that exist in the legacy map but not under VEX (`0F 05`, `0F AF`,
  `0F 38 F0`, MMX forms without a prefix, ...) are therefore refused although the map byte is shared.
* **Unknown** by rule: a `66`, `F2`, `F3`, `F0` or any REX byte anywhere in front of the VEX/EVEX prefix (#UD on a
  processor; SDM vol. 2, 2.3.2 and 2.7.1); VEX maps 0 and 4..31, EVEX maps 0 and 4..7 (APX, AVX512-FP16); the EVEX
  payload bits that are fixed in these maps (bit 3 of the first byte, bit 2 of the second); zeroing (`z`) without a
  mask register; `L'L = 3` without `b`, or with a memory operand (it exists only as a rounding mode).
* **Allowed in front**: segment overrides and `67`. They are ordinary prefixes of the instruction; `67` sets
  `kInsnAddr32`, `64`/`65` set `kInsnSegFsGs`. `disp_offset`, `disp_size` and `kInsnRipRel` are filled as for legacy
  instructions.
* **Not looked at**: `VEX.L`, `W`, `vvvv`, the register-extension bits, the EVEX mask, broadcast bit and vector length
  (beyond the rule above), and which ModRM.reg / operand form a VEX opcode has. None of them changes the length. An
  encoding that is #UD only because of one of them gets the length of its opcode (see "Exceptions").

### Accepted encodings

VEX map 1: the AVX forms of SSE/SSE2/SSE3 (`10`-`17`, `28`-`2F`, `50`-`7F` with the prefixes each has, `C2`, `C4`-`C6`,
`D0`-`FE`), `77`, `AE` (vldmxcsr, vstmxcsr), the opmask instructions `41 42 44`-`47 4A 4B 90`-`93 98 99`.
VEX map 2: SSSE3/SSE4 forms, AVX2 (`16`, `36`, `45`-`47`, `58`-`5A`, `78`, `79`, `8C`, `8E`, gathers `90`-`93`),
vpermil/vtest (`0C`-`0F`), broadcasts (`18`-`1A`), vmaskmov (`2C`-`2F`), F16C (`13`), FMA (`96`-`9F`, `A6`-`AF`,
`B6`-`BF`), AES (`DB`-`DF`), GFNI (`CF`), BMI1/BMI2 (`F2`, `F3`, `F5`, `F6`, `F7`), AVX-VNNI and its INT8 / INT16
forms (`50`-`53`, `D2`, `D3`), AVX-IFMA (`B4`, `B5`), AVX-NE-CONVERT (`72`, `B0`, `B1`), SHA512 (`CB`-`CD`), SM3 / SM4
(`DA`).
VEX map 3: `00`-`02`, `04`-`06`, `08`-`0F`, `14`-`19`, `1D`, `20`-`22`, `30`-`33` (kshift), `38`, `39`, `40`-`42`,
`44`, `46`, `4A`-`4C`, `60`-`63`, `CE`, `CF`, `DE`, `DF`, `F0` (rorx).
EVEX maps 1 to 3: AVX-512 F, CD, BW, DQ, VL, IFMA, VBMI, VBMI2, VNNI, BITALG, VPOPCNTDQ, BF16, VP2INTERSECT, and the
EVEX forms of VAES, VPCLMULQDQ, GFNI.

**Not covered (Unknown):** XOP, 3DNow!, FMA4, AMX, the Knights Corner / Knights Mill / AVX-512 PF / ER sets,
AVX512-FP16 (maps 5 and 6 and its few map-3 forms), APX (map 4), AVX10.2 additions. `cml_lde_diff` lists what the
reference decodes and the decoder does not (`WP38-DIFF-UNKNOWN`).

### Legacy maps: tightened (a deviation from ADR-0042; what it costs)

ADR-0042 asked for VEX and EVEX. The comparison rule it also asks for covers every `Ok`, and the legacy part of the
decoder said `Ok` to a great many byte sequences that are not instructions: every opcode of `0F 38` and `0F 3A` under
every prefix, every x87 ModRM byte, any prefix on any SSE opcode, lock on anything. ADR-0042 point 3 gives the choice
between refusing such bytes and listing them as exceptions; they are refused. This changes what the decoder of the
already-shipped hook installer accepts, so here is exactly what changed and what it can cost.

**(a) What was Ok on main and is Unknown now.** Complete, generated list: `docs/wp/WP-38-legacy-delta.md`. In classes:

| Class | Example | Why it is not an instruction |
|---|---|---|
| lock on an instruction that cannot take it, or with a register destination | `F0 8B 01`, `F0 FF C0`, `F0 90` | #UD (SDM, LOCK prefix) |
| `0F 38` / `0F 3A` opcodes that do not exist, or not with that prefix | `0F 38 50 C1`, `0F 38 17 C1` (ptest needs 66), `0F 3A 00 ..` | SDM tables A-4, A-5 |
| SSE opcodes of `0F` in a mandatory-prefix form that does not exist | `F3 0F 28 C1`, `0F 6C C1`, `0F B8 C1`, `0F F0 01` | SDM table A-3 |
| An operand form the opcode does not have | `8D C1` (lea reg), `0F 2B C1`, `0F 50 01`, `0F C3 C1`, `0F 38 F0 C1`, `66 0F 73 19 08` | memory-only / register-only |
| Empty slots of the x87 escapes | `D9 09` (D9 /1), `D9 D1`, `DB 21`, `DD 29`, `DF E1` | SDM tables A-7..A-22 |
| Empty slots of groups 7, 9, 12-15 | `0F 01 CC`, `0F C7 01`, `0F AE C0`, `66 0F 71 C8 08` | SDM table A-6 |
| Segment registers that do not exist or cannot be loaded | `8C F0`, `8E C8` (mov cs) | #UD |

The same enumeration that produced the list (26 prefix forms x 4 maps x 256 opcodes x 256 ModRM bytes) asked Zydis
about every combination main accepted: of 5,898,112 accepted on main, 4,174,116 are refused now, and **Zydis decodes
none of them**. Nothing that is an instruction was lost: a first version of this work also dropped a few real but
exotic instructions (undocumented x87 aliases such as `ffreep`, system instructions of group 7 behind a stray prefix,
Key Locker, RAO-INT, hreset, pcommit); they are accepted again, so that the property holds without an asterisk.
Where both decoders say Ok the length is unchanged everywhere.

**(b) Function entries: main next to this branch.** `LDE-OUTCOME` of `cml_lde_probe` for every fixture module in every
`ci` cell and for the corpus cells is in the table under "Evidence": `refused_unknown_opcode` and `refused_other` stay
0 and `refused` falls to 0 (it was all `refused_vex`).

**(c) What WP-36's linear sweep can lose.** WP-36 decodes whole function bodies with this decoder and refuses the
reload (CML3101) when it meets Unknown before a relocation site. Two things bound the effect of the tightening:

* By (a), an instruction the reference can decode is never newly Unknown. A sweep can newly stop only at bytes that
  are not an instruction, i.e. where it has lost the instruction boundaries or runs through data in a code section.
  On main such bytes got a guessed length and the sweep went on from a made-up boundary; stopping there is the
  safer outcome for a planner that is about to patch a displacement.
* Measured, position by position, on four real code sections with both decoders (15.4 million positions: libLLVM-18,
  glibc, libm, libcrypto): main's decoder said Ok and this one does not at 782 positions, all of them in libcrypto's
  lookup tables inside `.text` and none decodable by the reference; 0 positions in the three others; 0 length
  differences. In the other direction this decoder accepts 136,599 positions main refused (the VEX and EVEX code).
* In CI, `cml_lde_diff sweep` lists every kind of instruction the decoder refuses in the bodies of the 16 Windows
  modules (`WP38-DIFF-UNKNOWN <mnemonic> count=.. example=..`, see "Evidence"): what is there was already refused on
  main.

So WP-36 loses nothing on code a compiler emitted; it gains the functions that contain VEX or EVEX instructions before
a relocation site, which main's decoder stopped at.

Table size: about 5.7 KB of constant data (before: 2 KB). No allocation, no OS dependency, nothing third-party.

## The reference check

**Zydis** (https://github.com/zyantific/zydis, **MIT**), release v4.1.1, commit
`a2278f1d254e492f6a6b39f6cb5d1f5d515659dc`, with its dependency **zycore-c**
(https://github.com/zyantific/zycore-c, **MIT**), v1.5.2, commit `0b2432ced0884fd152b471d97ecf0258ff4d859f`.
`tests/fuzz/fetch_zydis.ps1` fetches exactly these commits at run time and fails otherwise; `fuzz.yml` passes the
checkout to CMake as `CML_ZYDIS_DIR`. Zydis is linked into `cml_fuzz_lde` (in such a tree) and `cml_lde_diff` and into
nothing else; it is not in the repository, not in `third_party/`, not in the agent, the broker or the package. The
decoder's tables were written from the SDM; Zydis was used to find where they were wrong or incomplete, and each
finding was then checked against the manual.

Zydis is configured for 64-bit mode with its defaults, except that MPX decoding is off (with it Zydis takes
`0F 1A`/`0F 1B` for the MPX instructions and rejects bound registers 4..7; on current processors these opcodes are the
NOPs the decoder takes them for).

**The rule** (`lde_reference.h`, `Reference::compare`): whenever the decoder says Ok, Zydis must decode the same bytes
to the same length, the same displacement offset and size, the same RIP-relative property, and the prefix flags must
be the prefixes that are there. Whenever the decoder says Truncated, Zydis must not find an instruction inside the
bytes. Anything else is a mismatch, and a mismatch fails the run.

### Exceptions (Zydis rejects what the decoder accepts)

One class, checked mechanically for every such input, never by a list of opcodes:

> The instruction is VEX- or EVEX-encoded, Zydis rejects it, and Zydis **accepts a sibling**: the same lead byte,
> map, `pp` and opcode (without the segment / address-size prefixes in front, which never decide whether an encoding
> is an instruction), with other values of the fields the decoder does not look at (register
> extension bits, `W`, `vvvv`, `L` / `L'L`, EVEX mask, no zeroing, no broadcast, ModRM.reg, and the operand as it is,
> as a register, as `[rax]` or as `[rax + index]`). On **every** sibling Zydis accepts, both decoders must agree
> completely. If Zydis accepts no sibling the opcode is unknown to it: mismatch.

**What is still guaranteed for such an encoding.** Its length is computed from the same table entry (map, `pp`,
opcode: ModRM or not, imm8 or not) and by the same ModRM / SIB / displacement rule that give exactly Zydis' length,
displacement and flags on every sibling Zydis accepts; the check fails if a single accepted sibling differs. So the
decoder treats the rejected encoding like its valid neighbours, and it is right about all of those. What is not
guaranteed is that a processor would execute it: it would raise #UD.

**Why such an encoding cannot be the first instruction of a real function** (or any instruction of one): it raises
#UD when executed, so a compiler or assembler never emits it as code, and a function that began with it would fault
on its first call. The bytes can occur only as data that a sweep mistakes for code, which is no different from any
other data that happens to decode as instructions. `cml_lde_diff` counts the exceptions in its sweeps over compiled
code (`exceptions=` in the `WP38-DIFF` lines, see "Evidence").

Reason for the class: such an encoding is #UD on a processor only because of a field that does not enter the length: a vector
length or `W` the instruction does not have, an operand form it does not have (register where only memory exists, a
group slot that is empty, a gather without SIB), a register number out of range or used twice, a mask that is
required or forbidden. The decoder gives it the length of its opcode; a processor never executes it. Making the
decoder refuse them would mean per-instruction tables of `L`, `W`, operand form and register rules, which is a
disassembler, not a length decoder, and every mistake in such a table would be a refused real instruction.

In the walk over the encoding space the exceptions split by Zydis status into `DECODING_ERROR` (no such form),
`BAD_REGISTER` and `INVALID_MASK` (numbers under "Evidence"). In the sweeps over compiled code there are none.

There is **no exception for legacy-encoded instructions**: the decoder refuses what Zydis rejects there.

### fuzz_lde

Input: bytes at a function entry. Checked in every build (the replay in each `ci` cell, libFuzzer + ASan in `fuzz.yml`):

* no read past `available`: every prefix of the input is decoded from a heap block of exactly that size (ASan) and
  from two stack copies that differ behind it (any build);
* `Ok` means length 1..15 within the bytes, a displacement of 0, 1 or 4 bytes inside the instruction, `kInsnRipRel`
  only with a disp32, at most one control-flow kind; `Unknown` and `Truncated` carry nothing;
* the verdict does not depend on what follows: shorter than the length is `Truncated`, the length or more is the same
  `Ok`; an `Unknown` stays `Unknown` when more bytes are visible;
* `plan_hook()` on the same bytes never claims more than it was given.

With `CML_ZYDIS_DIR` each decoded position is also compared with Zydis. The process prints
`WP38-FUZZ reference=zydis inputs=... positions=... ok=... agree=... exceptions=... disagreements=0` when it ends
without a finding; `fuzz.yml` requires that line for the `lde` cell.

**Found by the fuzzer.** The first run in `fuzz.yml` (run 45413405832, job 138513021594, 4.09 million executions)
stopped at `26 26 26 26 26 26 26 26 26 3E C4 E2 6D 92 33`: ten segment prefixes, then a VEX gather whose ModRM byte
asks for no SIB byte. The decoder says 15 bytes; Zydis rejects it (a gather needs a SIB). That is the exception class
above, but the check built the siblings with the prefixes, and the one sibling Zydis accepts (with a SIB byte) was 16
bytes long. The decoder was right; the comparison was wrong. Siblings are now built without the legacy prefixes, the
input is in the corpus (`found_prefixed_gather_without_sib.bin`), and `cml_lde_diff enumerate` walks every VEX / EVEX
opcode behind 5 to 12 allowed prefixes.

### cml_lde_diff

`sweep <modules>`: a linear sweep from every function entry (PDB procs and function publics) to the function's end,
every position compared; where the decoder says Unknown, the reference's length carries the sweep on.
`enumerate`: every legacy opcode of the four maps under 40 prefix combinations with every ModRM byte, every VEX (32
map numbers) and EVEX (8) map / pp / opcode / ModRM with random payload bits and occasional reserved bits, prefix runs
in front of VEX/EVEX, and random bytes: 198 million cases, deterministic. `raw <files>`: the sweep over files that are
only code (used on Linux with `objcopy -O binary --only-section=.text`).

`cml_lde_probe <exe>` prints `LDE-VEX <function> rva=... bytes=<16 bytes> lens=... plan=...` for every function whose

## The AVX2 stress acceptance

`unit.agent_hook_stress` (16 workers + the pinned thread, 60 s) hooks 17 functions per batch now. Eight begin with a
VEX instruction:

| Target | Entry | Padding | Strategy |
|---|---|---|---|
| `avx2_float`, `avx2_double` | compiled (`float f(float)`, `double f(double)`), `/arch:AVX2`, optimised in every configuration: `C5 FA 58 05 ..` vaddss / `C5 FB 58 05 ..` vaddsd xmm0, xmm0, [rip+constant] | the linker's | reported |
| `vex_c5_padded` | `C5 F9 6E C1` vmovd xmm0, ecx | 8 x CC | padding + 2-byte |
| `vex_c5_no_padding` | same | none | 5-byte (ends inside the second VEX instruction) |
| `vex_c4_no_padding` | `C4 E1 79 6E C1` (5 bytes) | none | 5-byte |
| `vex_zeroupper_no_padding` | `C5 F8 77` then a 6-byte `lea` | none | 5-byte |
| `vex_ymm_padded` | `C5 FD EF C0` vpxor ymm0 | 16 x CC | padding + 2-byte |
| `vex_slow_loop_no_padding` | two VEX instructions, then a loop | none | 5-byte |

The entry bytes are read from memory before anything is hooked; a target that does not begin with `C4`/`C5` fails
the test (the compiler decides what a compiled function starts with). A machine without AVX2 fails the test with a
message; it is not skipped. Evidence line: `WP38-STRESS-VEX cpu_avx2=1 targets=8 padding=P five_byte=F compiled=2
<name>[<first 8 bytes>]=<strategy> ...` in the same evidence file as `WP10-STRESS`.

`tests/unit/agent_hook/avx/CMakeLists.txt` turns that directory's Debug flags into optimised ones (`/Od` to `/O2`,
no `/RTC1`): at `/Od` clang-cl starts every function with a stack adjustment, so the entry would not be VEX.

## What was learned

* **The legacy decoder was sound where it mattered and loose elsewhere.** Before any change the comparison found no
  length disagreement in 12 million legacy cases, but 7.2 million cases where the old decoder said Ok for bytes that
  are no instruction (all of `0F 38`/`0F 3A`, prefixes on SSE opcodes, x87 holes, lock on anything). None of that can
  be reached in compiled code, but "whenever we say Ok the reference agrees" needs it gone.
* **For the length only (map, pp, opcode) matters under VEX/EVEX.** The six tables are 1.5 KB. Everything else that
  makes an encoding valid is register and form rules; the sibling check lets the comparison stay strict without
  copying those rules.
* **vzeroupper is the trap that matters in practice**: the MSVC STL's vectorised helpers end with it and several
  begin with it. With a ModRM byte it would swallow the first bytes of the next instruction.
* **A wrong length inside the first 5 bytes is less dangerous to the installer than WP-10 assumed** (a thread's RIP
  is always on a true instruction boundary, and every boundary below 5 is inside the checked window whatever the
  decoder thinks), but the decoder's other users are not so forgiving: the planner's short-function and
  call-in-window rules, and WP-36's sweep to a relocation site, need exact boundaries.
* The opmask instructions of AVX-512 (`kmov`, `kand`, `kshift`...) are VEX-encoded, not EVEX.
* clang's `/arch:AVX2` selects a processor model without AES and PCLMULQDQ; the module's crypto function names the
  features itself.
* **What a compiler puts at an entry is the compiler's business.** For `int f(int)` computed in floating point,
  clang starts with `vcvtsi2ss`, cl with `mov [rsp+8], ecx` (it converts from the home slot). With the argument in
  `xmm0` (`float f(float)`) both start with `vaddss xmm0, xmm0, [rip+..]`. The stress test checks the bytes instead
  of trusting this.
* **cl's optimiser has its own limits with AVX-512 intrinsics.** cl 14.44 and 14.52 stop with C1001 on a function
  that chains `_mm512_mask_blend_epi8` and `_mm512_maskz_mov_epi8` (and on the thirteen-statement shuffle function
  that contained them), at `/O2` only; each statement compiles alone. The AVX-512 module code keeps those one per
  function. Found with a throwaway workflow on a scratch branch (`probe/wp38-cl-ice`, runs 45423581557, 45425792728
  and 45430337194; not part of the pull request) that compiled the statements one by one.
  cl also has no `_andn_u32` / `_andn_u64` and takes only 0..7 as the rounding argument of `_mm256_cvtps_ph`.

## Deferred / limitations

* Not covered, by decision or by choice: see "Not covered" above. A function that begins with one of those is still
  CML4300. FMA4 and XOP exist only on old AMD processors; AMX, FP16 and APX code is not emitted by `/arch:AVX2` or
  `/arch:AVX512`.
* The exception class means the decoder gives a length to some VEX/EVEX encodings a processor rejects. That is a
  statement about bytes that are never executed; it does matter to a user of the decoder that sweeps data.
* The differential check runs in `fuzz.yml` (nightly, on dispatch, and on pull requests that touch the decoder, its
  tests or `tests/fuzz`), not in `ci`: `ci` has no Zydis. `ci` runs the hand-derived vectors, the seed replay with the
  invariants, the probe over 13 modules and the stress test.
* EVEX code is decoded and compared but never executed by a test (the runners do not promise AVX-512); the stress
  test executes VEX code only.
* `KNOWN_LIMITATIONS.md` still says VEX prologues are refused; the new text is proposed in the pull request (the
  orchestrator owns that file).
