**Why the host is changed at all.** A plugin can only enable itself through the agent the host created (a second agent
in one process would be a second "process" for the broker). Godot has no hook for that, so the host gets two exports,
`cml_corpus_host_agent()` and `cml_corpus_host_marker()`, appended to the corpus support file of this cell's copy of the
checkout. That is the host's part of a plugin architecture that uses Chameleon; Godot's patch, its build script and the
cache key are unchanged, and the cell `godot / msvc` never sees the change (this cell restores the cache and does not
save it; scons recompiles one file and relinks the editor here).

**Why `--script` and not `--editor`.** In the editor (`Engine::is_editor_hint()`), Godot loads a GDExtension from a
temporary copy of the DLL with a renamed PDB, and loads it when its filesystem scan finds it, which the driver cannot time.
Running the project's script with the editor binary loads the DLL itself, exactly when the driver says so.

### Driver changes in `run_corpus.ps1` (generic needs)

* `ValidateSet` gains `godot-gdextension`; `project.json` may name `base_project`: the repository, tag, commit, patch and
  support directory are then read from that project's `project.json` and the checkout is `src-<base>` (here `src-godot`,
  so the cached Godot tree is reused, and the pin cannot drift from the files the Godot cache key hashes).
* `project.json` may name `extra_modules` (`file`, `min_functions`); `build.ps1` reports where it built them in
  `$script:ExtraModules`. Each gets `check:<file>` and `decode:<file>` (the same checks as the executable), and skip rows
  when the build failed, so the matrix has the same rows in every run.
* Edit kinds (an entry of `edits` without `kind` behaves as before):
  * `signal`: writes `write.text` to `write.file` (to a temporary file renamed over it, so the application never reads
    half a command; main.gd also ignores `loaded` without a generation), then waits for every `expect` regex, for
    `expect_grows` (a marker whose count rises above the newest CORPUS line before the step), and for `wait_module` (a module
    of the process, by path regex, enabled with its index `ready`, from `status`); `absent_before` fails the step when such a
    module is already listed;
  * `check`: the same without writing;
  * `restart`: hot-restart through `restart {pid, timeout_ms, registration_timeout_ms}`; asserts `expect_diag` (response
    or diag events), `expect_not_enabled` (path regex in `not_enabled`), `expect_reapplied` (no `reapply_error`,
    `reapplied_files` and `patched` at least 1); follows the new pid and waits for its AGENT and CORPUS lines.
* On failure the tail of `app.stdout.txt` is printed too (main.gd writes its load/unload results there).
* An entry of `expected_failures` may give `match`, a regex over the error's message (`$_.Exception.Message`, untruncated
  and unwrapped; the displayed detail stays cut at 1500 characters); a step that fails otherwise fails the cell
  (`expected to fail with /.../ (...), failed otherwise`). The same lines and semantics as WP-41's (PR #69), so whichever
  merges second keeps one implementation. Used by F-42.1..F-42.3; the older entries have none and behave as before.

### Findings

None is fixed here (product code, ADR-0043: a finding for the orchestrator). Each one has a reduced repro,
`tests/corpus/repro/f42_plugin_reload/` (host.c + plugin.c), and is asserted by the corpus.

**F-42.1. After the plugin is freed and loaded again it runs its original code, and nothing says so.** Edit, `reload`
(accepted, `plugin_tick_v2` runs), `FreeLibrary` + `LoadLibrary` of the same DLL. The broker sees it
(`ModuleUnloaded` at 95698 ms, `ModuleLoaded` at the same base at 97539 ms, broker.log), drops the module's state
(`ReloadService` sync: "disabled, unloaded, or reloaded at another address") and builds a new index whose source baseline
is the files as they are now, i.e. with the accepted edit. So the new instance runs the original code
(`plugin_tick_v2:133` frozen for 30 s while `plugin_tick` went from 180 to 1082), the source says otherwise, and a `reload`
finds no changed file: the edit is lost until the file is edited again. **What the user sees: silent old code.** No
warning or diag event in the broker log or on the control pipe between the unload and the next reload (the only
`[warn]` lines of the run are CML3357, CML5212 and CML5809 elsewhere). Possible direction (not made): treat a module that
comes back with the same path like the hot-restart case, i.e. carry the old baseline's originals over
(`session_snapshot()` / `restore()`, WP-21) and re-apply, or at least warn with the files whose patches were lost.

**F-42.2. The first reload of the plugin after it was loaded again fails with CML3350 (LNK1104).** Right after F-42.1 an
edit of the plugin is refused: `linking 'patch_1_1' failed (exit code 1104): LINK : fatal error LNK1104: cannot open
file '...\session\corpus_plugin.dll\p3404\g1\patch_1_1.dll' (1 of 2 modules failed)`. Root cause: the work directory is
`<session>/<module name>/p<pid>` and the patch directory `g<patch_counter>` (`pipeline.cpp`, `make_work_dir`,
`apply_unit`); `patch_counter` lives in the `ModuleState`, which F-42.1's re-creation starts at 0 again, so the first patch
of the new instance is written to the path of the freed instance's first patch DLL, which is still loaded in the process
(patch DLLs are never unloaded). **What the user sees: a diagnostic** (CML3350, error, stage `link`); the process is not
affected and the edit is not applied. Because the counter also counts failed attempts and never goes back, the next
reload uses `g2`: in general the first N reloads fail, N being the number of patches of the earlier instance (not shown by
this run, which tries once). A hot-restart is not affected (new pid, new directory: `edit:plugin-function-after-restart`
linked `p1980\g1`). Possible direction (not made): a per-instance part in the directory (base address or a counter kept
per pid and module path, not per `ModuleState`).

**F-42.3. After a hot-restart, the edits of a module the application enables late are not re-applied when it is
enabled.** The restart reports the plugin as not enabled (CML5809, "It may not be loaded yet; enable it from the
application once it is.", `not_enabled` in the result) and re-applies the host's file only (`reapplied_files=1`,
`changed_files: [...gdextension.cpp]`). When the new process then loads the plugin and enables it (as CML5809 says), its
index starts from the edited files: `plugin_tick_v2` never shows up in the new process until the file is edited again
(`edit:plugin-function-after-restart` brought it back). The carried baselines are only applied to modules enabled while
the restart runs (`restart.cpp`, the loop over `new_snap.enabled`), then dropped. **What the user sees: CML5809 at the
restart, then silent old code** for that module; no diagnostic says that its edits were not re-applied, and the restart
result does not list them. KNOWN_LIMITATIONS says lazily loaded modules "are reported (CML5809) and not enabled again";
it does not say that their edits are lost. Possible direction (not made): keep the carried baseline for a module that was
not enabled in time and apply it (and re-apply) when the module is enabled, or name the files in CML5809.

Proposed KNOWN_LIMITATIONS text (for the orchestrator): *A module that is freed and loaded again (FreeLibrary +
LoadLibrary) runs its original code: the edits patched into the earlier instance are not re-applied and no diagnostic says
so (F-42.1); its first reload afterwards can fail with CML3350/LNK1104 (F-42.2). After a hot-restart, a module enabled after
the restart finished (CML5809) does not get the session's edits either (F-42.3). Edit the file again (or restart with the
module loaded) to bring them back.*
