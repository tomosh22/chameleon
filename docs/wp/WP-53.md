# WP-53: a new static of an inlined lambda never takes its caller's deleted static (R-61; ADR-0045)

Branch `wp/53-inlined-mirror`, one PR. Review: high (bind planner). Diagnostic: CML3207 (no new id).

## Round 1: spike (evidence before code)

R-61 is the mirror of R-54 (WP-51). Under clang-cl /O2 a lambda inlined into `f` records its static as a plain record of
`f`. An edit that deletes `f`'s own `static x` and declares `static x` in the lambda leaves the old image with one record
`x` in `f`, and WP-40's in-caller pairing (the closure step's "inlined records", then pass B's layout or place step) binds
the lambda's new static to it: the lambda takes `f`'s live object and its initialiser never runs.

### clang-cl -O2: what the old image records

`f`'s procedure, as `llvm-pdbutil` prints it (c1 against c3; offsets dropped):

```
c1 (the lambda's x)                         c3 (f's own x, lambda without statics)
S_GPROC32 `f`                               S_GPROC32 `f`
  S_INLINEES  0x1011 (operator())             S_INLINEES  0x100F (operator())
  S_LDATA32 `x`  type Obj  0003:0016          S_LDATA32 `x`  type Obj  0003:0008
  S_INLINESITE inlinee 0x1011 (operator())    S_INLINESITE inlinee 0x100F (operator())
S_END                                       S_END
```

The two are the same shape: one plain record of the name in `f`, one inline site of `f::<lambda_0>::operator()` (the
closure the patch's static names). The patch objects are the same shape too (the new `x` is a record of `f`, its symbol
`?x@?1???R<lambda_0>@?0??f@@YAXXZ@...`). Why, in LLVM's CodeView writer (`collectLexicalBlockInfo`): a scope that is not
a `DILexicalBlock` (the function itself, every inlined call operator) is "ignored" and its function-local globals are
appended to the parent's list; the inlined scopes are children, so the caller's own top-level statics come first and every
inlined scope instance appends its statics again. Hence:

- **Count per name.** One own static: one record. A static of an inlined scope: one record **per inlined instance** of
  that scope (c2: two call sites, two records `x` at one address). One call site (c1, c8, the fixture, Godot's `SNAME`
  pattern) gives one record, exactly like an own static. The count tells them apart only when the lambda was inlined more
  than once. (It also makes WP-40 refuse c2 today: `inlined=2 old=2 patch=1 refused=lambdas-changed`, a pre-existing
  over-refusal, see "Found on the way".)
- **Order.** The own statics of `f`'s top-level scope come before the inlined ones (c9: own `x` at 0003:0008 first, the
  lambda's at 0003:0024 second; WP-51's `e_main` the same). With one record there is nothing to order.
- **Type.** The record's type against the static's: refutes only a changed type (c6; pass B's place step already refuses
  it). Moving `static Obj x` into the lambda keeps the type.
- **Inline sites (WP-51's `proc_inlinees`).** They show whether `f` inlined the static's closure at all (c4: no inline
  site, so the record cannot be the lambda's). When it did (c3, c5, c7, c10, and every WP-40 case) they say nothing about
  which statics the closure had: the record is not in the site's scope.
- **The closure's other statics.** c5: the lambda's old `y` is a record of `f` as well; nothing ties `x` to the closure
  or not.
- **The patch's structure.** In R-61 the patch's `f` no longer declares `x`; in WP-40's case it does not either. The patch
  is the same in both; what differs is only the old source, which the records do not keep.
- **Section layout.** It only says that the old object had *a* variable at that offset. In c10 the layout of R-61's patch
  is the old layout exactly (`s_count`, then `x` and its guard), so the guard is placed and the reload goes through.

Conclusion for clang-cl: **no record of the old image or the patch proves that a single record of `f` is an inlined
lambda's static.** The only thing that distinguishes c1 from c3 is the code.

What main's planner does with them (clang 18, local):

| Case | main | Right answer |
|---|---|---|
| c1, c8, c11 (WP-40) | bound by layout (`compiland-static-rva`), guards by layout | bind |
| c2 (WP-40, two call sites) | CML3207 `lambdas-changed` | bind (pre-existing over-refusal) |
| c3, c4, c5, c12 (R-61) | `x` **bound by place** (`compiland-static-procedure`) to `f`'s own record; refused only because its guard found no layout (CML3600: R-61 changed the order the globals were created in, so `s_count` moved) | refuse (CML3207) |
| c6 (R-61, type changed) | CML3207 (place step: another type) | refuse |
| c7 (R-61, constant-initialised) | **accepted**: the lambda's `x` bound to `f`'s old `x` | refuse, or see below |
| c9 | CML3207 (count) | refuse |
| c10 (R-61, own `x` in a block) | **accepted**: `x` bound by layout, its guard by layout onto `f`'s old guard | refuse |

So R-61 is real and silent under clang-cl wherever the layout survives the edit (c10) or no guard is needed (c7); the
CML3600 of c3/c4/c5/c12 is luck (the order of global creation changed with the edit).

### cl /O2: what the old image records

clang-cl 19.1.5 with link.exe (CI) writes the same shapes as clang 18 with lld and plans the same (c7 and c10 accepted with
the wrong pairing, c3/c4/c5/c12 refused by CML3600 only, c11/c1/c8 bound, c2 refused).

cl 19.44 (CI) is different, and decisive. It records an inlined lambda's static **and its guard inside the
`S_INLINESITE` scope of the closure's call operator**; the function's own statics (and their `$TSS0`) come after the inline
sites, directly in the procedure:

```
c1 (the lambda's x)                              c3 (f's own x, lambda without statics)
S_GPROC32 `f`                                    S_GPROC32 `f`
  S_INLINESITE inlinee 0x1012 (operator())         S_INLINESITE inlinee 0x1012 (operator())
    S_CALLEES _Init_thread_header, make, ...       S_INLINESITE_END
    S_LDATA32 `x`      Obj  0003:2776              ...
    S_LDATA32 `$TSS0`  int  0003:2784              S_LDATA32 `x`      Obj  0003:2776
  S_INLINESITE_END                                 S_UDT `f::__l2::<lambda_1>`
  ...                                              S_LDATA32 `$TSS0`  int  0003:2784
  S_UDT `f::__l2::<lambda_1>`                    S_END
S_END
```

The inlinee is `LF_MFUNC_ID operator()` of class `.?AV<lambda_1>@?1??f@@YAXXZ@`, which is the scope the patch's static
names (`?x@?1???R<lambda_1>@?1??f@@YAXXZ@...`). c9 has both: the lambda's `x` inside the site, the own `x` after it; c2
has the lambda's `x` once inside each of the two sites; c8/c11 one per site of three different closures. No S_GPROC32 for
the call operator: the patch object has one (`S_LPROC32_ID ??R<lambda_1>@...`, a COMDAT), and `/OPT:REF` discards it
because every call was inlined. Without `/OPT:REF` (link's default under `/DEBUG`, as in the CI fixture
`planner_pairing_o2`) the procedure stays and WP-40 saw the static twice, in the call operator and in the caller at one
address: the "same-variable" case the closure step pairs. So under cl the record's position proves which lambda it is.

What main's planner does with the cl images: every case is refused, WP-40's as well (CML3207: "1 of the old records named
'x' are in the procedure of 'f' itself (the compiler inlined the lambdas), which does not say which lambda each belongs
to"): cl puts no layout the planner can use, and pass B's place step refuses a record "declared inside an inlined call"
(`plain_scopes == false`). R-61 is therefore safe under cl today, and WP-40's in-site case is an over-refusal under cl
with `/OPT:REF`.

### The code: WP-25's comparator on the procedure that holds the record

The driver runs `narrow_hooks` on the plan (the old image on disk, the patch object, the plan's decisions). The
clang-cl column holds for clang 18 + lld (local) and clang 19.1.5 + link.exe (CI) alike:

| Case | `f` judged (clang-cl) | Plan on main (clang-cl) |
|---|---|---|
| c11 (WP-40, `f` unchanged) | `unchanged` | accepted, bound |
| c1, c8 (WP-40, `f` edited) | `bytes-differ` | accepted, bound |
| c2 (WP-40, two sites) | `size-differs` / `bytes-differ` | CML3207 |
| c3, c5 (R-61) | `bytes-differ` | CML3600 |
| c4, c12 (R-61) | `target-new` (the guard CML3600 refused) | CML3600 |
| c6 (R-61, type) | `size-differs` / `bytes-differ` | CML3207 |
| c9 (R-61) | `size-differs` | CML3207 |
| c10 (R-61, block) | `size-differs` | **accepted, wrong pairing** |
| c7 (R-61, constant-initialised) | `unchanged` | **accepted, wrong pairing** |

"Unchanged under the plan" means: the patch's `f`, with the lambda's static at the old record's address and its guard where
the plan put it, is byte for byte the old `f` with the same targets. The old `f` then used that record exactly as the new
`f` uses the lambda's static (initialised, guarded, read and written at the same points), so the running program cannot
tell the binding from "nothing changed": the pairing is proven in the only sense that matters at run time. This is the
proof WP-40 already uses for `$S<n>` bitmask guards (`prove_bitmask_guards`) and WP-46 for hashed lambdas.

c7 is the one R-61 edit it accepts: an R-61 edit whose code is the old code (a constant-initialised static moved into a
lambda that only touches it). Binding it keeps `x`'s value, as for any unchanged function; refusing it would refuse an
edit that changed nothing at run time. **Ruled: accepted** (below). The alternative was to refuse every R-61
shape including the code-identical one (then nothing in the image distinguishes it from WP-40 with `f` unchanged, c11, and
WP-40's fixture case would have to be refused as well).

## Round 1 proposal (kept for the record)

The proposal handed back with round 1: (1a) cl's twin record, (1b) cl's inline-site position, (2) the code of `P`;
otherwise CML3207. A record directly in `P` is never taken for a lambda's static on its own: under cl that is where the
function's own statics are, under clang-cl it is where both are. Alternatives considered and rejected:

- Telling the compilers apart (S_COMPILE3) and trusting "a record directly in `P`" under clang-cl: that is exactly R-61.
- Refuse every inlined-record pairing under clang-cl: sound, but WP-40's fixture case (c11, `mark_3`) would be refused too.
- Bind when the record is duplicated per inline site: proves "an inlinee's static" only for a lambda inlined twice or more,
  and not whose.
- Look at the inline sites' code ranges for the guard's initialisation: optimised code moves across inline boundaries and
  constant-initialised statics have no initialisation code; not a proof.

## The ruling (ADR-0045)

0. Check first that WP-51's inline-site reader is not blind under clang-cl + link.exe (round 1's observation). Below: it
   is not; the observation was a mistake of the spike's report.
1. Rule (1a) + (2): a lambda's static paired with a record directly in its caller's procedure `P`, with no call-operator
   record at that address, is refused (CML3207) unless cl's twin record exists (the closure step, unchanged) or the
   pipeline proves `P` unchanged with WP-25's comparator under the plan. Anything the comparator cannot judge is refused.
2. c7 (an R-61 edit with identical machine code) is accepted through (2): the running program cannot tell the difference.
3. (1b) (cl's inline-site position) is deferred to the roadmap: it removes an over-refusal main already has, it fixes
   nothing unsafe. The build tree's original `.obj` checked against the section-contribution CRCs is a roadmap item too.
4. Logs: `WP53-INLINED-PROOF` per static at trace; one `WP53-INLINED object=... listed=.. proven=.. refused=..` per planned
   object at Info, only when listed > 0 (no line: 0).
5. Unit tests on the spike's real inputs; `spike/wp53/` removed from the branch.
6. c2 and WP-40's count rule stay as they are.

## Item 0: WP-51's reader under clang-cl + link.exe is not blind

Round 1 said that under clang-cl + link.exe the driver's `proc_inlinees` listed no inlinee for `f`. That was wrong: the
grep that produced the summary (`^  rec|^ERROR|WP40-INLINED`) did not include the driver's `inlinee` lines. A second CI
run (46088946877, job 140805065465, head 50ee4a6) printed `proc_inlinees`' result for every procedure of every case,
including its error when there is one:

- clang-cl 19.1.5 + link.exe, c1: `proc_inlinees sites=1 inlinees=1 complete=1`, `inlinee 'operator()' class='f::<lambda_0>'
  unique='.?AV<lambda_0>@?0??f@@YAXXZ@' sites=1 depth=1`; c11 and c8: `sites=3 inlinees=3`; c2: `sites=2 inlinees=1`; c4
  and c12 (no lambda in the old `f`): `sites=0 inlinees=0`, which is right. The first run's log (46087905878) has the same
  inlinee lines.
- cl 19.44 + link.exe: the same counts.
- No error anywhere, no case where llvm-pdbutil shows a site and the reader lists none.

The corpus's clang-cl cells link with lld-link in any case: the broker logs of run 46052330588 (Jolt and ImGui clang-cl)
read `linker detection ... PDB: '* Linker *' compiland: ... version="LLVM Linker" ... exe="C:\PROGRA~1\LLVM\bin\lld-link.exe"`
(CMake picks the lld-link next to clang-cl). No reader change, no further test: there is no hole.

## Round 2: what was built

### Planner (`broker/cml_core/src/bind_plan.cpp`, `bind_plan.h`)

`BindPlan::inlined_lambda_statics` (`InlinedLambdaStatic`: the static, the old record's RVA, the procedure `P` that holds
the record and its entry RVA, the step that paired it). At the end of pass B, next to WP-51's sweep and before the guards
are settled, every static of a call operator (a guard too) whose pairing is with an inlined record (`is_inlined_record`: the
record's procedure is the lambda's enclosing function or outer call operator) is listed, unless cl's twin exists: a record at
the same address in a call operator of the static's OWN closure (its type's unique name, rule (d)'s pairing applied, begins
the static's decorated scope), in another procedure than the paired record's (`own_closure_twin`; `WP53-TWIN`, trace; a
record of another closure's call operator is logged `WP53-NOT-TWIN`). The call operators' data records are indexed by RVA
once per compiland. Log `WP53-LISTED` (trace). The
pairing itself is unchanged: WP-40's counting, the layout and the place step still choose the record. Nothing in the steps
WP-52 edits.

### Proof (`broker/cml_core/src/hook_narrowing.cpp`, `pipeline.cpp`)

`prove_inlined_lambda_statics(NarrowInput)`, called by the pipeline right after `prove_bitmask_guards`: for each listed
static still bound to its record, the hook whose old entry is `P`'s is judged by WP-25's comparator under the plan (one
verdict per procedure, earlier patches' code included through `prior_code`). Unchanged: the pairing stands. Anything else
(changed, `P` not hooked, the old image unavailable, not comparable) gives a CML3207 per static:

`static data 'f::<lambda_0>::operator()::x' (...) in <obj> was paired with the record at rva 0x3010 of 'f', which inlined
its lambda; a compiler records the statics of an inlined lambda there and the function's own statics alike, so only an
unchanged 'f' proves the record is this lambda's (it may be a static the edit deleted from 'f'), and the code of 'f'
changed (size-differs: new 135 bytes, old 153)` / `Leave 'f' unchanged while the program runs (edit other functions of the
file), rename the static, or hot-restart.`

Logs: `WP53-INLINED-PROOF static=... record rva=... proc=... by=... proven=unchanged|refused <why>` (trace),
`WP53-INLINED object=... listed=N proven=N refused=N skipped=N` (Info, only when the plan lists any; `skipped`: listed
statics a later step re-decided, so there was nothing to prove; listed = proven + refused + skipped).

### c7, accepted by ruling

An R-61 edit whose machine code is the old code (c7: `static int x = 5` moved from `f` into a lambda that only adds to it):
the patch's `f`, with the lambda's `x` at `f`'s old `x`, is byte for byte the old `f`, so the pairing is proven and the
lambda's static keeps the value of `f`'s deleted one. The running program cannot tell the difference. In C++ terms the
lambda's static is a new variable and a fresh start would initialise it; the reload does not.

The same holds for any R-61 edit that leaves `f`'s machine code as it was once the lambda's guard is placed on `f`'s old
guard: c13 (c12 with the layout kept) is accepted. c4 and c12 are refused only because their edit changed the order the
globals were created in, so the guard found no layout (CML3600) and the comparator saw a reference to a new guard
(`target-new`).

## What it refuses that a perfect rule would allow

- **WP-40's case with `P` edited** (c1, c8): a lambda inlined into `f`, its static recorded only in `f`, and the user edits
  `f` itself. Under clang-cl that is every such edit; under cl with `/OPT:REF` main refuses it already (1b would allow it).
  This is the `SNAME("x")`-in-an-edited-function pattern; it is not in the Jolt or ImGui clang-cl cells.
- Functions the comparator cannot judge (an unverifiable relocation, `P` not hooked, the old bytes unreadable).
- Not new: c2 (two call sites) stays refused by WP-40's count.

## Review of bb63263 (fix round 1)

| # | Finding | Fix |
|---|---|---|
| 1 | Any data record at the same RVA in a procedure named `operator()` counted as cl's twin, so an outer lambda's static also inlined into another lambda left an R-61 pairing unlisted and unproven | A twin is a record in a call operator of the static's own closure (by the type's unique name, after rule (d)), in another procedure than the paired record; the call operators' records are indexed by RVA once per compiland (`own_closure_twin`). Unit test in `test_inlined_lambdas.cpp`; fails on bb63263 (`listed 0`) |
| 2 | c4 and c12 were claimed to show the refusal independent of the globals' order, but are refused only through the guard (`target-new`) | The test and this file say so; c13 (the guard placed, `f` unchanged) asserts the actual outcome: accepted |
| 3 | `WP53-INLINED` did not add up when a listed static was re-decided before the proof | `skipped=N` |
| 4 | `test_inlined_mirror.cpp` dereferenced `listed()` unchecked | `REQUIRE(... != nullptr)` first |

The comparison of the twin's closure uses the procedure's type (as WP-51's `closure_of` does), not `comp_norm`: the
canonical display name drops the lambda numbers, so `f::<lambda_0>::operator()` and `f::<lambda_1>::operator()` compare
equal. Checked with clang 18 on the shape of finding 1 (o kept and inlined into k, the edit moves `x` into an inner lambda
of o): there WP-40's closure step already declares the inner static new ("no lambda of its function had a static of this
name"), so the loose check was reachable only where the closure step leaves the static to the layout, as in the unit test
(one of the call operators' types cannot be read).

## Deferred (roadmap, by ruling)

- **(1b) cl's inline-site position:** under cl with `/OPT:REF` the lambda's static and its guard sit inside the
  `S_INLINESITE` of the closure's call operator, which proves them (round 1). Needs `proc_statics` to report the inlinee of
  the innermost site around a record and the place step to pair such records; removes an over-refusal, fixes nothing
  unsafe.
- **The build tree's original object:** it names every static exactly at its section offset and can be proven to be the
  linked one by the DBI section contributions' data CRCs (lld and link.exe fill them); it would settle R-61, R-54/R-59 and
  R-57 by name, but reads a file outside the old image and fails once the user rebuilds.

## Found on the way (not changed)

- WP-40 counts clang-cl's per-site duplicate records (c2): a lambda inlined at two call sites is refused (`inlined=2 old=2
  patch=1`). Counting distinct addresses would fix it; kept by ruling.
- Under cl with `/OPT:REF`, WP-40's inlined lambda statics are refused (CML3207) because nothing reads the inline site they
  sit in (1b).
- WP-40's doc says cl "emits the call operators as well": true only while the linker keeps the unreferenced COMDAT
