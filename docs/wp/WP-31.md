# WP-31: Visual Studio extension

ADR-0038 (directory `integrations/vs/`, diagnostics CML5994-5997, workflow `.github/workflows/vs.yml`). Plan: commands, output pane, automatic
debugger re-attach after hot-restart. Acceptance: manual checklist (below) plus the automated proxies, and the `.vsix` as an artefact.

## How the re-attach works, and the timing

1. `VsDebuggerAttach` is an `IDebugEventCallback2`. On `IDebugProgramCreateEvent2` it records `pid -> engine names` (`IDebugProgram2.GetEngineInfo`);
   on `IDebugProcessDestroyEvent2` it forgets the pid. Every change calls `ReattachCoordinator.Observe()`.
2. The broker terminates the old process **before** it announces the new one, and Visual Studio ends the debug session of a process that exits. So
   at the time of `restarted` the debugger is no longer attached to `old_pid`. The coordinator therefore remembers every process it saw debugged, and a
   process that disappears stays remembered for 5 minutes (`GoneProcessMemory`, longer than the restart budgets). Hot-Restart from the menu also calls
   `Observe()` first.
3. `restarted {old_pid,new_pid}`: setting off, nothing to do (log line). Debugged old pid unknown: nothing. New pid already debugged: nothing. Otherwise
   attach `new_pid` with the same engines, up to 3 attempts 300 ms apart, then CML5997. The event and the answer of the menu command can both report the same
   restart; a pair is handled once.
4. Attach: `DTE.Debugger.LocalProcesses` -> `Process2.Attach2(engine names)`. If the engines are refused it falls back to `Process.Attach()` (the
   debugger chooses) and logs it.

**The race (what is and is not solved).** The extension attaches when `restarted` arrives. That event comes at the **end** of the restart: after the new
process registered, its modules were enabled again, its PDB index was built and the session's edits were re-applied. The new process has been running all
that time, so breakpoints in code that runs at start-up (before `main` reaches the first tick) can be missed. The extension cannot do better with the
current shapes: the pid of the new process is first known to clients in `restarted`.
**Requested additive fields** (not implemented; they are in `broker/` and the agent, outside this package): `restart {hold_new: true}` makes the broker
create the new process suspended (`CREATE_SUSPENDED`), publish an event `{"event":"restarting","old_pid","new_pid"}` right after `CreateProcessW`, and wait
(bounded, e.g. `hold_ms`, default 10 s) for a command `restart-resume {new_pid}` (or the timeout) before it resumes the main thread. The extension would then
attach inside that window and resume, so breakpoints bind before the first instruction. Capability name suggestion: `restart-hold`. Until then the
checklist below uses a breakpoint in code that runs repeatedly (the fixture's tick loop).

## Automated acceptance (CI, `vs.yml`, windows-2022)

* Unit tests (`tests/Chameleon.Control.Tests`, 53 tests, run on Windows in CI; they also pass on Linux): framing, pipe names, the client against a fake broker on a
  real named pipe (events between answers, timeouts, pipe loss, garbage lines), the session (status then subscribe, event lists, missing capabilities, older
  broker, no broker, keep trying, reconnect, auto-reconnect off, disconnect), the re-attach decisions against a fake debugger (attached to the old pid -> attach
  the new one; not attached -> nothing; engine list kept; failure -> CML5997 after the attempts; setting off; duplicates; the old process already gone;
  memory expiry), diagnostic location parsing, event formatting, the diagnostic ids.
* Integration test (`tests/Chameleon.IntegrationTest`): a real `cml_broker` and fixture `basic` built in the job. It runs `status`, `subscribe`, a scripted
  edit of `logic.cpp` and `reload` (the `patch_applied` event, the fixture prints `value=2`), `revert last` (`patch_reverted`, `value=1`), `reload` again and
  `restart` (the `restarted` event, a new pid that is running and ticking in the same output), and then checks that a fake debugger "attached" to the old pid was asked
  to attach the new pid with the same engines. It prints `WP31-IT ...` lines, for example
  `WP31-IT restart=ok old_pid=5444 new_pid=7856 restarted_event=1 new_pid_alive=1 new_pid_ticking=1`.
* `build.ps1 -Configuration Release` builds the VSIX; it is uploaded as artefact `chameleon-vsix` (`Chameleon.Vsix.vsix`).

What is **not** automated: loading the VSIX in Visual Studio, the menu, the Output pane, the Error List and the real debugger attach (`Attach2`).
Those are the manual checklist.

## Manual checklist (needs Visual Studio 2022 or 2026 and a built Chameleon tree)

Prepare: build Chameleon (`cmake --build build`), so that `build\bin` holds `cml_broker.exe`, `cml_agent.dll` and `fixture_hot_restart.exe` (or `fixture_basic.exe`).
Install `integrations\vs\out\Chameleon.Vsix.vsix` (double click, restart Visual Studio).

1. Tools menu: **Chameleon** with Reload, Hot-Restart, Revert Last, Revert All, Connect, Disconnect, "Re-attach debugger after hot-restart" (checked) and
   Show Output. Reload, Hot-Restart and the Reverts are greyed out while not connected. Tools > Options > Chameleon > General shows the settings, including
   "Re-attach debugger after hot-restart".
2. Open the Output window, pane "Chameleon": "Chameleon for Visual Studio is ready ...". With no broker running the pane says CML5994 once (with its "what to do"
   sentence) and nothing more while it waits. The Error List shows the same entry.
3. Open `tests\fixtures\hot_restart` (or any project that uses the agent) as a CMake folder or solution, build it with the Chameleon flags
   (`docs/BUILD_REQUIREMENTS.md`). Start it **under the debugger with F5** (debug the exe `fixture_hot_restart.exe --agent`). Launch it so the agent finds a broker
   (the agent starts `cml_broker.exe` itself when it sits next to the exe).
4. Within a few seconds the pane prints `broker: connected` (the pane's line "connected to ..." lists the capabilities) and Reload/Hot-Restart/Revert become enabled.
5. Set a breakpoint in `compute_value()` (`logic.cpp`) or a line in the tick loop of `main.cpp`. It hits; continue (F5).
6. Edit `logic.cpp` (change the returned value), save, **Tools > Chameleon > Reload**. The pane shows `patch applied: module ...` and `reload ok: patched 1 ...`; the
   program prints the new value; the breakpoint still hits.
7. Introduce a compile error in `logic.cpp`, Reload. The pane shows a line `C:\...\logic.cpp(12,5): error CML....`; **double click it** to jump to the line.
   The same entry is in the Error List; double click opens the line. Fix the error, Reload: the Error List entries are cleared.
8. **Hot-Restart** (the heart of this package). With the debugger still attached and the breakpoint set:
   a. Tools > Chameleon > Hot-Restart. The pane prints `hot-restart (pid N) ...`.
   b. The old process ends (Visual Studio may show "The program ... has exited" in the Output pane for Debug).
   c. The pane prints `process restarted: pid N was replaced by pid M`, then `debugger re-attached to pid M (it was attached to pid N)`.
   d. The Debug toolbar is in debug mode again (Debug > Windows > Processes shows pid M); the breakpoint is bound (solid red) and **hits in the new process**.
      Check the engines in Debug > Attach to Process (the same engine as before, e.g. Native).
9. Repeat step 8 twice (the re-attach works for the new pid again).
10. Turn the option off (Tools > Chameleon > "Re-attach debugger after hot-restart" loses its check mark; the pane says "now off"), Hot-Restart: the pane says
    "automatic re-attach is off ... attach to pid M by hand", the debugger stays detached. Turn it on again.
11. Failure message: with the option on, start the debugger as a normal user and run the application **elevated** (or protect the process another way), Hot-Restart: the pane
    and the Error List show CML5997 with "Attach by hand with Debug > Attach to Process (pid M) ...".
12. No debugger: stop debugging, run the program without the debugger, Hot-Restart: no attach, no error (`reattach: the debugger was not attached to pid N` is only in the
    log, which is the pane's "debugger:" lines).
13. **Revert Last** and **Revert All**: the pane prints `revert (last) ok ...`; the program's value goes back.
14. Stop the broker (close the application). The pane prints CML5995, and later (if "Reconnect automatically" is on) `broker: connected` when a new
    one is up. **Disconnect** stops trying; **Connect** starts again.
15. Uninstall (Extensions > Manage Extensions) removes the menu.

## Decisions

* **Logic in a plain library.** `Chameleon.Control` targets netstandard2.0 and has no Visual Studio reference; the shell is about 500 lines of glue. The VSIX project
  is classic (non-SDK) style because the VSIX tooling expects it.
* **Newtonsoft.Json** (MIT) for JSON, because Visual Studio ships it; System.Text.Json would bring assembly-binding trouble inside the IDE.
* **`exception` events are opt-in** (`Show exception events`, off). The brief lists them, but subscribing to `exception` makes the agents hold a faulting thread
  until a client answers (WP-20), which would stall a program that is under the Visual Studio debugger, and the extension has no dialog to answer with.
  With the option on the pane shows the event and says to answer with `cml_ui` or `exception-action`.
* **`restarted` is subscribed when the broker advertises `restart`**; if a broker refuses an event name the subscription is repeated with the default set.
* **Which process a command names**: a process the debugger is attached to and the broker knows (from `status`), else none (the broker then takes the only
  connected process, or answers CML5801).
* **Diagnostic ids.** CML5994 no broker, CML5995 connection lost or no answer, CML5996 unsupported broker or missing capability, CML5997 re-attach failed (all four
  re-attach failure reasons use this id and put the reason in the message).
* **Missing `subscribe`**: the extension stays connected for commands, CML5996 says the pane and re-attach are off.
* **No server-identity check.** The C++ clients verify that the pipe server runs as the same user (CML5209). The pipe's DACL already admits only the current user;
  the extension does not repeat the check.

## Deferred / limitations

* Early attach (see "The race"): needs the broker fields requested above.
* Only processes seen through debug events are known as debugged. If the package loads after a debug session started (it auto-loads in the background at
  start-up, so this is rare), that session is not known until the next attach; a restart then does nothing for it.
* A process that leaves the debugger by Detach stays remembered for 5 minutes; a hot-restart of that pid in that window re-attaches. A restart started from `cml_ui`
  (not from this menu) is still handled, because the event is what triggers it.
* Several debugged processes restarted at once are handled one after the other.
* Attach goes through the automation model on the UI thread and takes about a second.
* Engine names come from `IDebugProgram2.GetEngineInfo` and go to `Attach2`; if Visual Studio refuses the names the debugger picks the engines (logged).
* The Error List shows at most 200 Chameleon entries (it is cleared at the next `patch_applied`).
* Visual Studio 2026 and the Visual Studio Marketplace are not covered (no signing, no publisher account).
