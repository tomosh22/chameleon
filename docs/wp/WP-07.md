# WP-07: Bind planner

## What was built

All in `broker/cml_core` (portable, no Win32; unit-tested on Linux with synthetic inputs and in CI on the real fixtures).

| Header | Content |
|---|---|
| `cml/core/bind_plan.h` | `PlanInput`, `plan_bind()`, `BindPlan` (decisions, hooks, thunks, placeholders, new functions/globals, initialisers, fix-ups, warnings), `make_fixup_triples()`, `layout_from_pdb()`, `to_json()` |
| `cml/core/symbol_registry.h` | `SymbolRegistry` and `ProcessModules` interfaces, `InMemorySymbolRegistry`, `InMemoryProcessModules` (the fake for tests) |
| `cml/core/bind_names.h` | a small MSVC-name reader (`display_name`, `base_identifier`, `enclosing_function`, `last_component`) and recognisers for compiler-generated symbols |
| `cml/core/bind_diag_ids.h` | CML3101, CML3102, CML3200..CML3212 |

The planner links, loads and hooks nothing. It does not touch `agent/`, `core/cml_toolchain` or `core/cml_ipc`; output types are plain data so WP-12 can wire them to WP-08/09/10.

### Decisions (plan 4.5)

| Symbol in the new object | Decision (`DecisionKind`) |
|---|---|
| defined function, in the old image | `PatchHooked`: `HookEntry{new symbol, old VA/RVA, old size}` |
| defined function, not in the old image | `PatchNewFunction`: listed in `new_functions` (to register after load) |
| defined data (external or static, guard variables included) in the old image | `BindOldData`: every relocation to it becomes a fix-up, the patch's copy is dead |
| defined data not in the old image | `PatchNewData`: `new_globals`, with the initialisers that run for it |
| vtables `??_7`, RTTI `??_R`, `??_C@`, `__real@`/`__xmm@`, cl's `$...` locals, `.pdata/.xdata/.rtc$/.CRT$`, dynamic-initialiser and atexit stubs, EH funclets | `PatchFresh` |
| undefined function | `BindOldFunction`: `ThunkEntry` (binding.obj thunk + `__cml_slot_<name>`) |
| undefined data | `BindOldData`: `PlaceholderEntry` (8-byte placeholder named exactly the symbol) |
| `__ImageBase` | `LinkerProvided` |
| weak external nothing resolves | `WeakDefault` (the object's default symbol is used) |

"In the old image" = the registry (symbols of earlier patches), else the module PDB: publics for externals, the compiland's `S_LPROC32`/`S_LDATA32` records for statics (below). A defined symbol found in the registry is hooked/bound to the earlier patch's definition, so patching the same TU twice does not duplicate globals.

Function vs data comes from the PDB (public with the function flag or in an executable section), never from the object's DTYPE (ADR-0020 #3); for defined symbols from the defining section.

### Resolution chain for undefined symbols

1. `SymbolRegistry::find`.
2. The compiland's own statics (`S_L*`), **only for names that can denote a TU-private entity** (anonymous-namespace marker `?A0x...` or function scope `?<n>??`). An ordinary external `?g_tick@@3HA` is never matched to a local static called `g_tick`.
3. PDB publics, then PDB global data by display name (C names).
4. `__imp_X`: the PDB public `__imp_X` (found in step 3, reported as `import-slot-pdb`), else `ProcessModules::iat_slot(module, X)` (`import-slot-module`).
5. `ProcessModules::find_export` of other loaded modules; for `__imp_X` that the module does not import, the export `X` fills a synthesized import slot (a placeholder named `__imp_X`, a `Slot` fix-up writes the export's address, references are not retargeted).

Nothing found: **CML3200** naming the symbol (display and decorated) and the referencing function (found from the first relocation: the COMDAT leader, or the symbol that contains the offset, following associative sections to their parent).

### Statics (ADR-0010)

Statics have no `S_PUB32` and the PDB records display names. The bridge, per group of statics with the same (function/data, base identifier, enclosing function):

1. candidates = the TU compiland's records of the right kind whose last name component equals the identifier (`last_component("`anonymous namespace'::s")` = `s`), function-locals filtered by `parent_name`;
2. one object static and one record: matched by **name + compiland**;
3. several: first by **RVA in the unchanged section layout** (a unique match in a non-COMDAT section gives `old RVA - section offset`; matches that disagree void it), then by **position** (object order = link order = RVA order), else **CML3207**, never a guess;
4. compiler-generated **guard variables** (`?$TSS<n>@...`), which have no PDB record, are placed with the same section delta and accepted only if the RVA lies in the compiland's contribution; otherwise the guard is new and **CML3211** warns.

A static that has no record at all is new (that is how new statics look). The evidence for what cl and clang-cl really record is in the CI logs, see below.

### Fix-ups (plan 4.6, ADR-0024, ADR-0025)

`Fixup{section_index, offset, kind, addend, target_va, target_rva, symbol}` for every relocation in a linked section whose target is `BindOldData`:

* `REL32..REL32_5`, `ADDR64`: the in-place addend `A` is read from the object's section bytes; the final value is computed later.
* calls/jumps to `BindOldFunction`: no fix-up, the linker resolved them to the thunk. `ADDR64` to a bound function is retargeted to the real address (function-pointer identity). `ADDR32NB` to a thunk is legal.
* `ADDR32NB` to old data: **CML3101**. `SECREL`/`SECTION` against a bound symbol, or a defined `.tls` symbol: **CML3102**. Any other kind (`ADDR32`, `SREL32`, ...): **CML3202**. A needed fix-up in a section without locator (associative, not linked): **CML3204**. A site outside the section data: **CML3208**.
* `Slot` fix-ups: one per thunk (`__cml_slot_<name>` receives the old function's address) and per synthesized import slot.

`make_fixup_triples(plan, PatchLayout)` is the pure function: `target = S + A`; REL32 family `value = target - (site + 4 + N)` range-checked to int32 (**CML3205**, nothing is written), `ADDR64` `value = target`, `Slot` `value = old address`. `layout_from_pdb()` fills the layout from the patch PDB using the `SectionLocator`s of `add_anchors()` (section start = locator RVA - locator offset) and the `__cml_slot_*` publics.

### Initialisers

`.CRT$XC*` tables are scanned: a cl `??__E<global>` runs only if `<global>` is a new global (a bound global's initialiser is skipped); clang's TU-wide `_GLOBAL__sub_I_<file>` runs only if the TU has new globals, with **CML3210** when it also holds bound data (it would re-run their initialisers; cannot be split). Each entry carries (table section, offset) because the initialisers are static functions, hence not in the PDB: read the pointer from the loaded patch.

### Trace logging

Every decision (`bind: sym=... decision=... source=... addr=... reason=...`), every fix-up, the compiland choice, initialisers and layout lookups are `CML_LOG(Trace)`; a unit test checks that every decision has a line.

## How to run

* Unit tests: `ctest -R unit.bind` (`cml_test_bind`: names, every table row, every chain step, statics, negatives, triples, golden JSON, trace) and `ctest -R unit.bind_fixtures` (MSVC cells only).
* Local, any host: configure with `-DCML_ALLOW_NON_WINDOWS=ON` and build `cml_test_bind`; `CML_UPDATE_GOLDEN=1 cml_test_bind` rewrites `tests/unit/bind/golden/*.json`.
* Fixtures: `tests/unit/bind/edited/` copies every M1 fixture at configure time, applies its `edits/*.edit` with `git apply -p1 --ignore-whitespace`, and compiles the edited TU with the fixture's flags (`bind_edit_<fixture>`). `unit.bind_fixtures` plans each against the original fixture exe's PDB. Output: `<build>/test_work/bindplan/{summary,evidence}.txt` and `<fixture>.plan.json`; CI prints the summary in the step "WP-07 bind plan evidence".

## Golden files: why they are not identical across toolchains

* `tests/unit/bind/golden/{basic_like,statics_like,new_things_like}.json`: complete plans of synthetic scenarios (WP-06 writer objects against WP-04 builder PDBs). Fully deterministic, one file for all cells.
* `tests/unit/bind/golden/fixtures/<fixture>.json`: the real fixtures. A full plan cannot be identical: the set of STL instantiations, `/RTC1` helpers, EH handlers (`__CxxFrameHandler3/4`), RVAs and lambda numbering (`<lambda_0>` vs `<lambda_1>`) differ between cl and clang-cl and between Debug and RelWithDebInfo. The files therefore pin the **source-level decisions by display name** (`Square::area` hooked, `(anonymous namespace)::g_fn` bound to the old storage via the compiland, `new_helper` new, ...), what must not happen, and minimum counts; the complete per-cell plan is written as an artifact. Per-compiler entries use `"when": "cl"`.

What this settled:

* **Name + compiland works** for file-statics, `static const` tables and function-local statics (record kind `S_LDATA32`, display name = the identifier, `parent_name` = the enclosing function; the anonymous-namespace prefix differs, cl records none, clang records `` `anonymous namespace'::``, so only the last component is compared). Static functions are `S_LPROC32` with the plain name.
* **The guard variable `$TSS0` is a record for cl** (`LDATA32 '$TSS0'`, parent `statics_value`) **but not for clang-cl.** The planner matches by name first and falls back to the unchanged-layout inference (`compiland-layout`, one `.bss` section whose other statics all agree on `old RVA - section offset`) only when there is no record. It is never guessed when the layout changed (CML3211, unit-tested).
* **clang-cl names internal-linkage data and some functions with the plain identifier** (`k_weights`), not a mangled name.
* **cl's local entities are spelled with quotes and block numbers** in the PDB (`` `lambdas_init'::`2'::<lambda_1>::operator() ``) and its lambdas with a content hash, while the decorated name has a counter (`<lambda_1>`; clang counts from 0): normalised before comparing the qualified name; the last component alone is ambiguous (`std::function::operator()` also exists).
* **Member functions of local classes (lambdas) are top-level procs** in the PDB although the decorated name has a function scope; that scope filters data only.
* Funclets appear as PDB procs too (`` `statics_value'::`1'::dtor$0 ``); they are never hooked (`PatchFresh`).

### Other findings that changed the design (all found by CI, none by reading)

1. **SECREL.** Every thread-safe function-local static reads the CRT's TLS variable `_Init_thread_epoch` with `IMAGE_REL_AMD64_SECREL` (first CI run: `CML3102 ... reference to '_Init_thread_epoch' from 'statics_value'`, all 8 cells). Rejecting it would reject every function-local static. New fix-up kind `SecRel32`: value = offset of the target inside its image section (from the old PDB) + addend, module targets only; `_tls_index` is an ordinary bound data symbol. `SECTION`/`SECREL7`, a defined `.tls` symbol, or SECREL against a non-module target stay CML3102.
2. **ADR-0024 needs an amendment: associative sections do sometimes need retargeting.** cl puts EH funclets in `.text$x` associative COMDATs; the funclet of a function-local static resets the guard (`$TSS0`), a bound static (`CML3204 ... sits in section '.text$x' which has no locator`, cl cells). The plan therefore lists `locator_sections` and `associative_locator_sections`; `coff::AnchorOptions::anchor_associative` (new, `core/cml_coff`, additive) gives exactly those sections a locator. Cost: if the parent COMDAT is discarded as a duplicate by the linker, an anchor in the child is left undefined (lld-link errors), hence "only on request".
3. **A patch may call CRT functions the old image never linked.** `new_global` needs `strlen` (`std::string(const char*)`); the old fixture has no call to it (`CML3200 unresolved external symbol 'strlen' referenced from 'std::_Narrow_char_traits<char, int>::length'`). Resolution step (5), exports of other loaded modules, is what resolves it (ntdll exports it); the fixture test passes the exports of the system DLLs loaded in the test process as `ProcessModules`. WP-12's real `ProcessModules` must therefore cover ntdll/ucrtbase. Anything in no loaded module stays a hard error.
4. **Static function template instantiations** (`std::forward<lambda>`, `std::move<lambda>`, ...) have internal linkage when the argument is a local type; they share a base name with unrelated instantiations and the PDB spells their arguments differently. They are not matched (not hooked, no warning); overloaded static functions that cannot be told apart are CML3213 (not hooked), static data that cannot be told apart is CML3207.
5. `cl /RTC1` emits per-function `$rtcName$n`, `$rtcVarDesc`, `$rtcFrameData` data; `_Avx2WmemEnabledWeakValue` (an STL COMDAT variable) is bound to the old image like any inline variable; clang's TU-wide `_GLOBAL__sub_I_logic.cpp` is the only initialiser for `new_global` there and runs because the TU has a new global (CML3210 only when the TU also binds writable non-COMDAT data).
6. Hook counts are large for STL-heavy TUs (`new_global`: 55..83): the planner hooks every defined function present in the old image (plan 4.5); `HookEntry::old_size` is filled so that WP-10/WP-12 can skip too-short functions, and narrowing to the functions whose code really changed is WP-12's job.

Not verified in logs (inferred): that cl and clang-cl agree on the layout of statics in Release for programs bigger than the fixtures; the `windows-2025` cells print the same BINDPLAN lines as `windows-2022` (they passed the same assertions, only windows-2022 cl Debug and clang-cl RelWithDebInfo logs were read in full).

## What was learned

* A planner that only reads the object cannot decide anything about statics; the PDB bridge (above) is the substance of this WP and the part least predictable from documentation.
* "Every decision is logged at trace" is cheap and was essential: the CI evidence file is the same decision list.
* Writing the goldens as source-level decisions rather than whole plans kept the expectations stable across the 8 cells after the first iteration (it took several CI iterations because each compiler had one more surprise).

## Deferred

* Section-relative references (private symbols, `CML3212` warning) are detected but not remapped; neither compiler produced one for the fixtures.
* `ADDR64` to a hooked function is not retargeted to the old (hooked) entry, so `&f` taken in a patch differs from `&f` taken by old code (vtables and std::function are unaffected).
* CML3103 (type layout change) needs type information; stays with WP-18.
* TLS defined in a patched TU (WP-24).
* `layout_from_pdb` is unit-tested on a synthetic patch PDB; it meets a real linked patch only in WP-09/WP-12.
* The reported counts include STL instantiations; a "changed functions only" filter belongs to the pipeline (WP-12).
