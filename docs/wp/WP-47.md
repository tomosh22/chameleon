# WP-47: a refused multi-compiland reload applies nothing (R-52; ADR-0044)

Branch `wp/47-atomic-reload`, one PR. Diagnostic range of ADR-0044: CML3650–3669. Used: **CML3650**, **CML3651**, **CML3653**,
**CML3655** (warnings) and **CML3652**, **CML3654** (errors), `broker/cml_core/include/cml/core/atomic_reload_diag_ids.h`. Review: high (pipeline, hooks).

## The defect (F-41.4)

`pipeline.cpp` planned and applied the recompiled compilands of a module one at a time (`for (Unit& u : units) apply_unit(...)`)
and stopped at the first refusal. The compilands before it stayed patched while the reply was `ok:false`, and the edited file was
not re-baselined, so the process ran the edit in some translation units and not in others (corpus: a `patch_applied ...
generation 7` before the CML3214 of a later batch in jolt cl `header-fanout-update-context` before WP-46; the same before a
CML3214 / CML3601 in raylib clang-cl `edit:header-inline-raymath`). The unit test `patches applied before a later compiland
failed still count in the generation` asserted that behaviour; it is replaced by the tests below.

## What was built

| Piece | File | Notes |
|---|---|---|
| Two-phase reload of a module | `broker/cml_core/src/pipeline.cpp` | `run()` prepares every compiland (`prepare`: plan, the WP-40/46 code proofs, narrowing, anchor, binding object, reservation, `link`: link, fix-ups, pre-applied SECREL, and what applying it adds), then applies them in order (`apply`: LoadPatch, ApplyFixups, RunInitializers, InstallHooks, `commit`). `Staged` holds one compiland between the two. |
| The overlay | `pipeline.cpp` (`OverlayRegistry`, `staged_is_hooked`, `staged_code_running_at`) | A compiland is planned as if the ones staged before it were applied, as the sequential pipeline did with them really applied: their new functions and globals resolve through the registry overlay (a header's new inline function, a function a second file calls), their hooks and WP-25 code records are seen by the narrowing and the proofs (a header inline function each TU has a copy of is hooked once; the next TUs' copies compare equal to the staged patch and add nothing). Nothing staged is written into the module's state before it is applied, so the exception service (`snapshot_hooks`) and `status` never see a patch that is not loaded. |
| Refusal | `refused()` | Any failure while preparing (plan, proof, link, fix-ups, the deadline) applies nothing: the slices of the reservation the staged compilands were linked into are given back (newest first), no file of the reload is re-baselined, no `patch_applied`. The reply keeps the refusal's own id (CML3400, CML3214, CML3601, CML3350, ...); for a reload of several compilands its message ends with `(compiland 3 of 3, tu_c.cpp); nothing of this reload was applied` and the warning **CML3650** is published. |
| Roll-back | `after_apply_failure()` | A failure while applying compiland *k* (the agent refuses LoadPatch / ApplyFixups / RunInitializers / InstallHooks, the agent's or the broker's injected stage, the deadline before a load) first does what it did before (its own patch is unloaded); then the compilands this reload applied before *k* are rolled back with the WP-22 revert: the reload's batch is recorded and `revert_module(..., Last, only_reload = this reload)` undoes it (re-point to an older patch or restore the original bytes, quiet; un-commit the images; registry, hook table, code records and generation back). The roll-back has its own budget (at least 10 s, the reload's deadline may be what failed). **CML3651** (warning) says so and the reply's message ends with `the N compiland(s) this reload had applied were rolled back`. If the revert fails too the reply is **CML3652** (both diagnostics in the message), the batch stays recorded for a later `revert`, and its files are not re-baselined. |
| Unconfirmed hooks | `keep_unconfirmed()` | CML5309 (no HooksInstalled in time, synchronised mode) and CML4656 (the agent could not take its hooks out again): that patch may still become live, so it is not rolled back and nothing after it is applied (more requests would queue behind the unconfirmed one, each waiting for `SyncPoint()`). Recorded as before (hook table, code records, batch); **CML3653** (warning) for a reload of several compilands. |
| `patch_applied` | `commit()`, `run()` | Collected per applied compiland and published when the reload of the module is done; never for a compiland that was rolled back. |
| Relink after a taken range | `relink()` | The relink at another base on CML4203/4205 now happens while applying. The compilands staged after it were planned against its addresses (registry entries, hook targets, code records), so their slices are given back and they are prepared again after the relink. |
| Re-baselining | `run()` | A file is re-baselined when every compiland it maps to is live: applied, or unchanged against the running code, where "unchanged" counts only when that comparison did not rely on a staged compiland that was then not applied. |
| Harness | `tests/harness/src/scenario.*`, `runner.cpp` | `expect_event` takes `absent = true`: no event of that name may arrive (the events not consumed yet are read, then the step waits `within_s`). Fails with CML5510. |
| Fixture / scenario | `tests/fixtures/atomic_reload`, `tests/harness/scenarios/atomic_reload.toml` | See "How to run". |

### Diagnostics (CML3650–3669)

| id | severity | meaning | what to do |
|---|---|---|---|
| 3650 | warning | one compiland of several was refused while preparing: none was applied | fix what the refusal names, reload |
| 3651 | warning | applying failed after earlier compilands of the reload were applied: they were rolled back | fix what the failure names, reload |
| 3652 | error | applying failed and the roll-back failed too: the process runs a part of the edit | `revert` (scope last), or restart |
| 3653 | warning | hooks not confirmed in time (CML5309) or not taken out again (CML4656): the reload stopped there, the rest is not applied | reach `SyncPoint()`, reload, or `revert` |

## High-review round (on 566235c)

1. **A roll-back the agent does not confirm is not CML3651.** `revert_module` succeeds also when a hook change gets no answer in
   time (CML5852) or an image is not un-committed (CML5855); the reload then returns **CML3654** (error, both diagnostics in the
   message), not CML3651, and re-baselines and announces nothing. The review asked to keep the batch recorded as well, so that a
   later `revert` can retry. It is not kept: after those warnings `revert_module` has already committed the roll-back to the
   broker's state (WP-22's rule for CML5852: the agent applies the queued change at the next `SyncPoint()`), so the hooks are no
   longer the batch's. Recording the batch again would make a later `revert` send restores for functions the patches no longer
   hook, which the agent refuses (CML5851), and for CML5855 the hooks are confirmed back already; only the un-commit failed, which
   `revert` has no step to retry. Tests: a revert timeout (the roll-back's InstallHooks gets no answer) and an agent that refuses
   the un-commit.
2. **The agent lost while applying** emits **CML3655** and the suffix "N compiland(s) of this reload were applied before it, M were
   not"; no file of the reload is re-baselined and no `patch_applied` is published (the applied ones stay recorded as the batch).
   Test: the second LoadPatch closes the link.
3. **Memory.** A staged compiland drops its COFF object, plan, narrowed hooks and link inputs as soon as it is prepared
   (`release_prepared`); what the apply and the overlay need (fix-ups, hook table, code records, registry entries) stays. A relink
   prepares the compiland again from its object file. The reply's `patches[].objects_held_peak` (new) is the most objects the
   reload held at once: 1, also across a relink (unit test). The peak working set of a 200-compiland fan-out was not measured on
   Windows in this round.
4. A failure of a compiland prepared again after a relink is named by that compiland ("(compiland 2 of 2, main.cpp)", "when
   compiland 2 was prepared again after compiland 1 was relinked at another base"), and the CML365x warnings name it too.
5. CML3652 says the batch stays recorded (and advises `revert`) only when it does; after CML5856 (the module went away) it says
   the module's patch list was dropped.

## Decisions taken here (confirmed by the orchestrator: per-module scope, R-56 for cross-module; no roll-back after CML5309/4656; ReserveRange while preparing)

* **Scope: one module.** The reload service still runs the modules (and processes) of one reload one after the other, and a
  module whose compilands are all applied stays applied when another module of the same reload is refused (unchanged: "(n of m
  modules failed)"). The R-52 evidence is all within one module (Jolt and raylib are static libraries in the exe). A refusal of
  the plugin DLL's compiland after the exe's compilands of the same header edit were applied is still possible. Extending it to
  every module of a process needs a two-phase PatchPipeline API; proposed as a follow-up.
* **CML5309 / CML4656 do not roll back.** Rolling back an unconfirmed install would queue a revert behind it (both applied at
  the next `SyncPoint()`); the scenario `sync_point_late` relies on the late install taking effect. The reload stops there.
* **Load belongs to the apply phase** (as ADR-0044 says), so a range taken at load time re-prepares the compilands after it.
* **ReserveRange is sent while preparing** (once per module, as before): reserved address space is not a change of the
  program's behaviour. LoadPatch is the first request that maps anything.
* **The reply keeps the refusal's id**; CML3650 is the separate warning, so scenarios and clients that expect CML3400 / CML3214
  keep working.

## How to run

* Unit (portable, also on Linux with `-DCML_ALLOW_NON_WINDOWS=ON`): `ctest -R unit.broker_core`, the `atomic reload (WP-47)`
  cases in `tests/unit/broker/test_reload.cpp`, one per failure point: plan (CML3200), link (CML3350), the code proof (the `$S1`
  bitmask of a function the patch does not hold, CML3600, `Rig(..., bitmask_world = true)`), apply (the agent's hook-install stage
  CML4652, and the broker's send-patch stage CML5969 armed between the two compilands), the failed roll-back (CML3652, then
  `revert`), unconfirmed hooks (CML5309 + CML3653), the overlay (a second compiland's code equal to the staged first one loads
  nothing; a second compiland bound to the staged first one's new function), and the relink at another base that prepares the
  second compiland again against the first one's new addresses. Each would fail on main (eight of the ten do; the other two
  check single-compiland reloads are unchanged).
* Harness: `ctest -R unit.harness` (`test_wp47_scenarios.cpp`: the `absent` key, the scenario's shape).
* Scenario: `cmltest --scenario tests/harness/scenarios/atomic_reload.toml ...`. Fixture `atomic_reload`: `scale.h` (no code:
  `kScale`, `CML_EXTRA_TLS`) is included by `tu_a.cpp`, `tu_b.cpp`, `tu_c.cpp`; `TICK a=11 b=101 c=1001`. Edit `scale_2_tls`
  (kScale 1 → 2, and a new `thread_local` in `tu_c.cpp`, the third compiland): the reload is refused with CML3400, no
  `patch_applied` arrives (`expect_event ... absent = true`), `a=11 b=101 c=1001` go on. Edit `stacked/no_tls` (the
  `thread_local` gone, kScale stays 2): the reload patches all three (`patched = 3`), `a=22 b=202 c=2002`, and the main thread's
  `thread_local` frame counter never went back (`expect_monotonic frames`). Before WP-47 the first reload would have left
  `a=22 b=202 c=1001`.
* Corpus: the job logs print `events: ...` per reload; F-41.4 is a `patch_applied` before an error `diag` of the same reload.

## What was learned

* The sequential pipeline's dependence of one compiland on the previous one was real and had to be kept: a header's inline
  function is hooked by the first TU and dropped by narrowing in the others only because the first one's patch is what they are
  compared with; a new function defined by one TU and called by another resolves through the registry. Planning all first is
  correct only with that state staged (the overlay), not with the module's state alone.
* The relink at another base is the one place where a staged address changes after later compilands were planned against it.
* The WP-22 revert already had every piece a roll-back needs (LIFO re-pointing, registry undo, generation, un-commit, one
  deadline, its own error paths); the roll-back is a batch that is recorded and reverted at once.

## Deferred

* Atomicity over the modules (and processes) of one reload (above).
* A compiland that is unchanged against a staged compiland that is then refused is not re-baselined: the next reload compiles
  it again (correct, a little slower).
* Initialisers that ran in a rolled-back compiland are not undone (as for any failure after RunInitializers, WP-12); the
  rolled-back patch DLLs stay loaded and inert (as after `revert`, WP-22).
* After a relink, the warnings of the compilands that are prepared again are reported twice in the reply.
