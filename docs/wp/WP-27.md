# WP-27: Performance budgets

One branch (`wp/27-perf-budgets`), one PR. All measurements run in the existing `pdb-benchmark` CI job (windows-2022, MSVC,
RelWithDebInfo); the other 13 jobs are unchanged. Only absolute budgets fail the job.

## The budgets and how each is taken

| Budget | CI threshold | How it is measured |
|---|---|---|
| PDB index 2 s per 500 MB | 2 x (4 s per 500 MB, scaled to the file size) | `cml_pdb_bench` on the 544 MiB generated PDB: `open()` + publics + every compiland's symbols; OS cache warmed first (unchanged from WP-04). |
| compile -> applied excluding compiler time, 2000-line TU: 1.5 s | median 3.0 s | Scenario `perf`: five edit + `reload` rounds on fixture `perf`. Per reload the broker returns `timing_ms` (sweep, compile, plan, anchor, link, load, fixups, init, hooks, total). The figure is `total - compile`; the threshold applies to the median over the five reloads, the maximum is reported. |
| Broker idle CPU 0.5 % | 1 % | Same scenario, before the reloads: one connected fixture, `compile_on_save` on (the file watcher is active), 5 s settling, then 60 s observed. CPU = kernel + user time of the broker process (`GetProcessTimes`) over the wall time, as a percentage of ONE core (stricter than a share of the whole machine). The fixture is checked alive every second. |
| Broker memory 1.5 x PDB | 1.5 x (no slack) | `cml_broker_mem` on the 544 MiB PDB: peak private bytes (`PeakPagefileUsage`, peak commit) of a process that hosts only the broker's `ModuleIndex`. |

Stage mapping for the reload budget: "detect" and "PDB" are the `sweep` stage (it includes mapping the PDB again after
ADR-0017's release); "compile" is reported and excluded; "plan" = `plan`; "link" = `anchor` (binding object) + `link`;
"pre-apply" = `fixups`; "load" = `load`; "hook" = `init` + `hooks`. The PDB stage is not timed separately by the pipeline
(no pipeline change was needed); it is part of `sweep`.

## Guards against a budget that passes without measuring

* `perf_report` fails when any recorded reload lacks a numeric, non-negative stage member, or has `total < compile`
  (`validate_timings`); nothing is treated as 0.
* `perf_idle` checks both `GetProcessTimes` calls and fails on a failure or a CPU time that goes backwards, and it fails
  cleanly when settling plus the observation do not fit in the scenario's remaining time.
* The trend baseline is the newest completed `main` push run that has a `perf-results` artifact; a zero baseline (idle
  CPU) warns when the metric rises by more than its noise floor (0.05 percentage points).

## What was learned

* A reload of a 2000-line TU is dominated by the compiler (230 ms of 270 ms); everything the broker does is 30-100 ms, link
  being almost all of it. The first reload is the slowest link (100 ms, cold).
* The idle CPU reads 0 because `GetProcessTimes` has scheduler-tick resolution (about 15.6 ms): over 60 s the broker did
  not accumulate one tick. The measurement can therefore only catch a broker that wakes up often or does real work; 1 % of
  60 s would be 600 ms.
* The broker's peak private bytes during the index are 0.49 x the PDB (cml_pdb allocations about 214 MiB plus transient
  structures); after the index and sweeps it is back at 2 MiB because `release_pdb()` drops the index.

## Deferred / limitations

* **No reload inside the large PDB.** The generated benchmark project is a plain program with no agent, so there is no
  process to patch and "index plus one reload of a TU in it" was not feasible. What was measured is the index plus two sweeps
  (a sweep maps the PDB again after a release). The memory of a real reload is covered only at small scale (10.6 MiB peak in the
  `perf` session, PDB of the fixture).
* **Source baseline on the large PDB is always present.** The benchmark PDB is cached but its sources are generated only on a
  cache miss, which made the number depend on the cache. The memory step now regenerates `bench-src` (the generator is
  deterministic and writes the same paths) when it is missing, and `cml_broker_mem --min-tracked-files 900` fails when fewer
  files are tracked. So every run measures the index WITH the source-hash baseline. `scan_includes` stays off (it follows
  `#include` through system headers; not part of the budget).
* **Large-PDB figure is a `ModuleIndex` host, not the full broker.** `cml_broker_mem` hosts only the broker's `ModuleIndex`.
  To catch growth outside it, `perf_report` also asserts the real broker's peak private bytes in the `perf` session
  (about 12 MiB) against 1.5 x the fixture module's PDB size plus a fixed 32 MiB process baseline (the broker's runtime, pipes
  and logs cost that whatever the PDB; 1.5 x a small PDB alone would be below any process).
* **Memory definition.** Peak private bytes are asserted (0.49 x). The PDB mapping is file-backed and reclaimable by the OS,
  not memory the broker owns, so private + mapped (1.49 x, the way `cml_pdb_bench` counts) is printed as information only.
* **Runner noise.** Single runs on shared runners; the thresholds carry the ADR-0009 2 x slack on time and CPU. The trend
  comparison starts with the first successful `main` run that uploads the `perf-results` artifact; until then the summary says
  there is nothing to compare with.
* **Idle CPU resolution** as above; a finer measure (`QueryProcessCycleTime`) was not needed.

## How to run

```
cmake --build build --target cml_pdb_bench cml_broker_mem cmltest cml_broker cml_agent
build/bin/cml_pdb_bench.exe bench_project.pdb --min-size-mb 500 --json pdb.json
build/bin/cml_broker_mem.exe bench_project.pdb --factor 1.5 --json mem.json
CML_PERF_JSON=perf-reload.json build/bin/cmltest.exe --scenario tests/bench/scenarios/perf.toml --build-dir build --generator ninja --config RelWithDebInfo --cxx cl --require-all-capabilities
pwsh tests/ci/perf_results.ps1 -PdbJson pdb.json -MemJson mem.json -ReloadJson perf-reload.json -Out perf-results.json
```

`tests/fixtures/perf/gen_perf_tu.py` regenerates the TU and the edits.
