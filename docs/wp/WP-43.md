**An arming never carries over (review finding 2).** A restart or revert stage is armed for the **next** restart (revert) of its process
only, with count 1 (a larger count is CML5960). At the end of that operation every stage of its group still armed for the process is
disarmed, in the broker (`FaultInjector::disarm_group`) and in the agent (`ArmFault` with count 0, for the agent stages inject-failure armed
there, `finish_injection`), whether it fired or not; the answer lists the stages that did not fire as `injection_disarmed` and the broker
logs a warning. So `restart-hold` armed before a restart without `hold_new`, `restart-reenable` when nothing is missing, `restart-reapply`
when nothing is re-applied, `revert-repoint` before a revert that only restores (and the reverse) end with that operation. A restart or
revert stage cannot be armed while such an operation runs (CML5978). The broker's undo of a re-pointing first disarms `revert-repoint` in
that agent, so it is never injectable (review finding 5). Tests: `an armed restart stage that the restart does not reach is disarmed at its
end, never carried over`, `an arming for another process is left alone ...`, `a restart stage cannot be armed while a restart runs`,
`revert injection (WP-43): an armed revert stage the revert does not reach is disarmed in the agent at its end`.

`re-enable` is a broker stage although the agent handles the request: an agent stage is armed in the agents that are connected, and
the new process's agent does not exist when the stage is armed. Registration likewise.

Agent rules: the two installer stages are one more `fault::consume(stage)` (lock-free atomic) plus a constant table read inside the
window; the diagnostic text is built after the threads run again (`batch_diag`), as for `hook-install`. `Installer::install` keeps its
`bool injectable` overload; new overloads take the stage (`Stage::Count` = none). The broker's undo of a re-pointing is a quiet request
and could in principle consume `revert-repoint`, but it is only sent after a re-pointing succeeded, i.e. when that stage was not armed.

### The second start attempt (new behaviour, what is and is not retried)

`RestartableProcess::relaunch()` must not leave a process behind when it fails: if an attempt created a process and a later step of it
failed, the host terminates that process and `relaunch_created_process()` answers true. The coordinator retries **only** when the first
attempt created no process (`relaunch_created_process()` false, or the injected `restart-relaunch` failure, which takes the place of the
attempt); otherwise the restart ends with CML5807 "the new one was created but could not be started (...), so it was terminated and no
second attempt is made". In the Windows host every failure of `relaunch()` comes before `CreateProcessW` succeeded (the attribute list,
`CreateProcessW` itself), so it always answers false; after `CreateProcessW` nothing in `relaunch()` can fail (the watchdog is optional).
Failures of later steps of the restart are never retried: a failed resume of a held process terminates it (CML5817, as in WP-34); the
registration, re-enable and re-apply leave the process running. Tests: `a real failure of the first start is tried once more (CML5822)`
(no process: two calls), `an attempt that created the new process and then failed is never repeated` (one call, the host terminated it).

### Unfinished restarts (new behaviour)

A restart that ends after the old process is gone without finishing its work in the new one (registration not in time, CML5808; the
injected CML5975; modules not enabled, CML5809) remembers, for the new pid, the modules it did not enable and the source baselines it
did not restore (at most 16 processes). The next `restart` of that process adds those modules to what it enables again and merges the
baselines (the older originals win: they describe the original binary; the newer stamps stay). The record is kept when that restart is
refused before the termination and dropped once the process is terminated. Without this, a process left running by a failed restart
lost its modules and the session's edits for good (the fixture does not enable its module when relaunched).

What the user sees: the restart's answer is CML5808 (or the injected CML5975, or CML5821 at shutdown; the message of CML5808/CML5975
ends "its next `restart` enables its modules and re-applies the session's edits"), or the restart succeeds with `not_enabled` and the
warning CML5809 per module ("... its next `restart` ..." when the request was not sent). The new process runs the original code without
those modules until then. The next `restart` of that process completes it: the modules are enabled again and the edits re-applied
(`patched` in its result). The log says "remembering for process N ..." and "carried over again".

The record can never apply to another process: it holds the restart token of the process it is for, and a process with the same pid
but another token (a reused pid) drops it; it is also dropped when that process's agent disconnects **and the process has exited**
(`ReloadService::detach` -> `process_gone`, `ProcessHost::has_exited`: no such process, or its handle is signalled). A pipe that broke while
the process runs keeps the record (the agent reconnects with the same token). Tests: `... dropped when that process has exited, not when
only its pipe dropped`, `... never applies to another process with the same pid` (fails without the token check, checked locally).

### The intermittent SIGSEGV in `unit.agent_hook` (WP-42 ci job 138898816837)

`WP10-REPEAT windows-2022 msvc Debug unit.agent_hook runs=19 passed=18 failed=1`, `test_dispatch.cpp(947): TEST CASE: hot-restart: launch
parameters that do not fit one message are refused with an answer, before any hook runs` / `test case CRASHED: SIGSEGV`. It is a bug of
the test, not of the agent's restart path:

* `ScopedVar` kept the `const wchar_t*` it was given as the variable's name.
* That test declared `std::vector<std::unique_ptr<ScopedVar>> big;` **before** `std::vector<std::wstring> names;` and built each ScopedVar
  from `names[i].c_str()`. Locals are destroyed in reverse order: `value` (the 60 000-byte string), then `names`, then `big`. So every
  `~ScopedVar()` called `SetEnvironmentVariableW(name_, nullptr)` with a pointer into freed memory: a use-after-free.
* The test executable routes `operator new` to the agent's private heap (agent/src/operator_new.cpp). What the freed 28-byte name blocks
  contain afterwards depends on the heap's layout: free-list metadata (encoded with a per-process random key) overwrites the first
  characters, and when the frees of `value` and the names coalesce into a free range above the heap's decommit threshold, the pages are
  decommitted. Reading the name from a decommitted page is the access violation; on the other runs the read finds a terminator in the
  garbage, the call fails quietly and the twelve 30 000-character variables stay in the environment for the rest of the process. The crash
  happens in the test case's own destructors, which is why doctest names this test case.
* Why not the agent: the restart handler's path for this input is deterministic (the environment field is over `kMaxWideUnits`, so
  `encode_frame` fails before any byte of it is written, and the refusal is a short message); it runs on the agent thread, which
  `stop_and_wait_for_calls()` joins before any local is destroyed.

Fix (`tests/unit/agent_hook/test_dispatch.cpp`): `ScopedVar` owns a `std::wstring` copy of the name; the test declares `names` before
`big`, and now checks after `big.clear()` that each variable is gone (`GetEnvironmentVariableW` -> `ERROR_ENVVAR_NOT_FOUND`), which failed
silently before whenever the freed name was garbage. A deterministic reproduction of the access violation itself would need page heap
(Application Verifier), which the CI image does not enable; the mechanism above is from the code. `ScopedEnv` in `tests/unit/agent` already
owns its name.

## Learned

* The R-40 race (item 3) was a window between two lock sections, not a missing lock; a deterministic test needs a trace point at the
  decision. The test pins the invariant ("resumed:true never next to CML5813") at the only place the window could reopen.
* Replacing the coordinator to swap the host was the root of item 6 and of a second stranding: `cancel()` reached only the new
  coordinator. Keeping one coordinator fixes both.
* "A new process running" after an injected failure is not enough for the hot_restart fixture: without the unfinished-restart record a
  following restart "succeeds" with no module and no edits.

## Deferred, and why

* No broker-side revert stage: the revert's broker-side steps cannot fail on their own (state roll-back); the injectable points are in the agent. CML5978 is the refusal to arm a restart or revert stage while one runs.
* Unfinished restarts are not finished when the process registers late by itself; only its next `restart` does the work (finishing on
  registration would need a background job in the broker, with its own shutdown story).
* A restart whose PDB index of a module is not ready in time (CML5810 "index not ready") does not record its baseline as unfinished: by
  the next restart that index is normally ready with a baseline of its own.
* The watchdog itself has no injection stage (it guards against a broker that is killed, which `integration.restart_hold_broker_killed`
  covers).
* A real Visual Studio attach to a suspended process is still checked only by the manual checklist of WP-34.
