# WP-24 — Thread-local variables

Status: implemented; acceptance is the Windows CI matrix (scenario `tls_read_write`).

## What was built

* **Existing TLS binds to the old storage.** A `thread_local` the old image has (defined in the patched TU, or in
  another TU) is a bind-to-old data symbol. The patched code addresses it with the usual x64 sequence
  (`_tls_index`, `gs:[58h]`, `SECREL var`); `_tls_index` is ordinary bound data, and each
  `IMAGE_REL_AMD64_SECREL` against the variable is a `SecRel32` fix-up whose value is the variable's offset inside
  the old module's `.tls` section (+ the in-place addend). The broker pre-applies it into the patch DLL file
  between link and `LoadPatch` (ADR-0030, `patch_image.cpp`); no wire kind, no agent change.
* **Where the offset comes from (CI finding).** `S_PUB32` of a thread-local does **not** carry its offset in `.tls`.
  First CI run, cl RelWithDebInfo: the public of the namespace-scope `t_counter` resolved to section offset
  `0x10d54` while the function-local static next to it (S_LTHREAD32) was at `0x8`; the patched code then read and
  wrote a wrong per-thread location (`main_ns=1127953467`, in Debug an access violation). External TLS is
  therefore placed from the global stream, `S_GTHREAD32` (`PdbIndex::find_global_data`, by display name), for
  defined and for undefined references alike (this also covers the CRT's `_Init_thread_epoch`). Statics use the
  compiland's `S_LTHREAD32` records as before (ADR-0010 matching).
* **New TLS is rejected: CML3400** (`kNewThreadLocal`, planner error): "`'<name>' is a new thread_local: <obj>
  defines it but the old image has no such thread-local variable; patch-local thread-local storage is not
  supported.` What to do: hot-restart, or move the new thread_local to an unchanged source file." The reload is
  refused; the app keeps running the previous patch.
* **CML3401** (`kThreadLocalInit`, planner warning): the patched TU carries TLS dynamic-initialisation tables
  (`.CRT$XD*`) or references `__tlregdtor` / `__dyn_tls_*`. The old image's initialiser and destructor stay in
  effect: existing threads keep their values, new threads run the OLD initialiser, a changed initialiser is not run.
  (The planner cannot tell whether the initialiser changed, so it warns whenever the tables are present.)
* **CML3102 narrowed** to the TLS shapes that stay unsupported: `IMAGE_REL_AMD64_SECTION` / `SECREL7` against bound
  data, SECREL against a non-module target (e.g. a registry symbol of an earlier patch), and any non-SECREL
  reference (REL32/ADDR64) to a defined thread_local (the address of a thread-local is per thread).

## The patch DLL's own `.tls`

The patch is linked `/NOENTRY /NODEFAULTLIB`: nothing defines `_tls_used`, so the linker emits no TLS directory.
If the object defines the variable, its copy sits in the patch DLL's `.tls` section, but the loader ignores a `.tls`
section without a TLS directory, no thread gets a block for it, and every access in the patched code is retargeted
to the old template offset. It is dead data, harmless. Evidence: the patch loads and runs on both threads
(the fixture's worker thread existed before the patch and keeps counting; a thread created afterwards would use the
old template, since the patch registers nothing). No TLS callback and no second initialiser table is ever
registered: `.CRT$XD*` of the patch is never walked (the patch has no CRT; `find_initialisers` only runs
`.CRT$XC*`).

  even though the public carries a different offset (`.tls` is the 4th image section, not the first); undefined
  `_Init_thread_epoch`; function-local static via `S_LTHREAD32`; new external and new static TLS (CML3400);
  REL32 to TLS (CML3102); dynamic TLS init table (CML3401).
* Changed existing assertions: `test_negative.cpp` (a defined `.tls$` symbol the old image lacks: CML3102 →
  CML3400) and `test_scope.cpp` (finish_errors test: first collected error CML3102 → CML3400). Reason: a new
  thread_local is now CML3400; CML3102 keeps the unsupported reference shapes.
* Fixture `tls` + scenario `tls_read_write` (main thread and a worker thread, namespace-scope and function-local
  `thread_local`; STEP 1 → 5 keeps both threads' values and grows by 5; a stacked edit that adds a `thread_local`
  is refused with CML3400, the app keeps running). `unit.bind_fixtures` plans the edit against the real PDB
  (golden `golden/fixtures/tls.json`, `FIXUP-SECREL` evidence lines); `unit.link_patch` links it with both linkers.

## Deferred / limitations

* New `thread_local` variables (patch-local TLS needs `.tls` registration): CML3400, hot-restart.
* A changed TLS dynamic initialiser/destructor does not take effect (CML3401 warns).
* `IMAGE_REL_AMD64_SECTION` against TLS stays CML3102 (not emitted in code sections by cl or clang-cl).
* A thread_local the old image's PDB has no `S_GTHREAD32`/`S_LTHREAD32` record for (for example stripped records)
  is reported as new (CML3400).

## The TLS invariant and the review (PR #39)

One invariant in `build_fixups` covers the silent-corruption class: **a SECREL against data of the old image must resolve
inside the old module's `.tls` section from a thread-local record** (`S_GTHREAD32` via `lookup_thread_global`, or the
compiland's `S_LTHREAD32`/layout match), **and no other relocation (REL32/ADDR64/ADDR32NB) may target an address inside
`.tls`**. Either violation is CML3102 with a precise message. A SECREL target is never resolved through publics: an
undefined symbol referenced by SECREL that has no thread-local record fails (CML3102) instead of falling back.
