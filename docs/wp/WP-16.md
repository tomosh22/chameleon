One branch (`wp/16-multi-module-process`), one PR. Diagnostic range CML5600-5649 (ADR-0031): none needed, no new failure mode.

## How the scenarios work

* **`exe_plus_dll`** (one process, two modules, one reload): the DLL's `lib_scale` goes 3x to 30x; the exe calls it through its import slot, the old entry carries the hook, so no IAT rewrite is needed (`dll=6` to `dll=60`). The exe's `exe_callback` goes `x+1` to `x+100`; the DLL calls it through a function pointer to the old entry (`cb=6` to `cb=105`). The exe's `exe_import_user` goes `lib_offset(x)*2` to `*3`: the new code reads the DLL's IAT slot `__imp_lib_offset`, resolved by the planner through `ProcessModules` (`imp=10` to `imp=15`). Asserts `patched=2`, `modules_patched=2`, `processes_patched=1`, `compiled=2`. The exe and the DLL are separate modules with their own registry, index, patches and hooks.
* **`two_processes`** (two processes, one broker): server and client enable the same DLL. One edit, one reload: `patched=2`, `processes_patched=2`, `compiled=1`, `compile_reused=1`; both processes print the new value, and `calls=` (state in each process's old image) never goes down in either.
* **`relink_other_base`** (FU-15): `fixture_exe_plus_dll --force-load-collisions 1` sets `CML_TEST_FORCE_LOAD_COLLISIONS=1`; the agent's `PatchLoader::try_load_candidate` then takes the image range itself right after releasing it (what another thread allocating there would do), so the real `LoadLibraryExW` fails (CML4203), the broker relinks at the next base and loads again. Asserts `load_attempts=2` and that the patch is live.

## Decisions

* **Where FU-15's occupation happens.** A fixture cannot take address space the agent already owns, and taking it before the reservation only moves the reservation. The agent therefore takes the range in the window between release and `LoadLibraryExW` when an environment variable asks for it. This is a test-only code path in the agent (outside this package's listed area; declared in the PR). The agent logs a warning at start when the variable is set; a failed reservation does not use up a collision. It is off unless the variable is set, costs one environment lookup per process otherwise.
* **Cache lifetime = one reload.** A longer-lived cache would need source hashes in the key. The cost of the short lifetime is nil in the multi-process case (all processes are compiled within one reload).
* **Cache is keyed by command line, not by module.** An exe and a DLL compiled from one recorded command line also share the result.
* **Per-process baselines stay per process.** Each `ModuleState` has its own source baseline and sweep, so every process detects the edit independently; sharing the PDB index between processes of one file would save memory but is not needed for correctness (not done).

## How to run

`build\bin\cmltest.exe --scenario tests\harness\scenarios\two_processes.toml --build-dir build --generator ninja --config Debug --cxx cl` (same for `exe_plus_dll`, `relink_other_base`). CI runs every `tests/harness/scenarios/*.toml` with `--require-all-capabilities`.

## Deferred

* A process started after an edit does not receive it (documented in `docs/KNOWN_LIMITATIONS.md`).
* Sharing one PDB mapping between processes that run the same module file.
* A compile cache that survives several reloads (needs content hashes in the key).
