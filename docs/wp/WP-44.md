# WP-44: failure injection in the crash handler and the watcher; persistent arming (R-42 rest, R-49, R-51)

ADR-0043 (amended for R-51). Branch `wp/44-injection-rest`. Diagnostic ids CML4661-4664 (agent stages; CML4665-4699 stay free) and
CML5979-5984 (broker). No new agent message type, no new control capability, `agent_abi_version` unchanged.

## What was built

### R-42: the crash handler's and the watcher's stages (appended to `cml/ipc/fault_stages.h`)

Three new groups. The mechanism is WP-28's and WP-43's: `inject-failure` arms a broker stage in `FaultInjector` or an agent stage through
`ArmFault`; the stage takes its normal error path; a stage of a group with an end-of-operation cleanup applies to the next matching
operation only, whether it fired or not, and what is left at its end is disarmed and listed as `injection_disarmed`.

| Stage | Side | Id | Group | Where it fails | What the application has afterwards |
|---|---|---|---|---|---|
| `exception-hold` | agent | 4661 | exception | the vectored handler, for a fault it would hold: passed on (one lock-free decrement in the handler, like the slots-full path CML4403) | the fault as without Chameleon: the application's own handler or the system sees it. The agent logs CML4661 |
| `exception-report` | broker | 5979 | exception | `ExceptionService::on_exception`: the `exception` event is not published, a `diag` CML5979 (error) is | the thread stays held and pending: `exceptions` lists it, `exception-action` answers it |
| `exception-continue` | agent | 4662 | exception-action | `ExceptionGate::resolve` once the thread is claimed: refused before anything is computed | the thread stays held; the next action works |
| `exception-leave` | agent | 4663 | exception-action | the same, for `leave` | the same |
| `exception-reexecute` | agent | 4664 | exception-action | `ExceptionGate::resolve_reexecute`, before the plan is looked at | the same; `reexecute` stays offered |
| `watch-debounce` | broker | 5980 (warning) | watch | the debounced batch is lost: the watcher does what it does after lost events (every tracked file is re-checked) | the save is patched anyway |
| `watch-change-detection` | broker | 5981 | watch | the check which saved files are tracked: the batch is dropped | the old code; the next save or `reload` picks the change up |
| `watch-reload` | broker | 5982 | watch | the reload the save starts, before it runs; the watcher's own CML5505 follows | the same |

What the "operation" of each group is:

* **exception**: the next fault the crash handler would hold (for `exception-hold`) or the broker hears of (for `exception-report`). It
  always reaches its stage, so there is nothing to disarm at its end. Because a held fault passes the hold before the report, the group
  keeps **one arming at a time**: arming `exception-report` disarms `exception-hold` in the agents it applies to, and the reverse.
* **exception-action**: the next `exception-action` command for a held thread of the process. `ExceptionService::action` counts it as
  running (under the R-51 gate below), runs `finish_injection` at its end and lists unused stages (`leave` armed, `continue` sent) as
  `injection_disarmed` in its answer. `ignore` has no stage: it is what happens without Chameleon.
* **watch**: the next batch of saves that touches a tracked file, or reports lost events. A batch that touches no tracked file is not an
  operation (editor temporaries would otherwise use armings up). The batch counts as running (it starts under the R-51 gate, like
  restart, revert and exception-action), so a watch stage cannot be armed while one runs (CML5978). At its end every watch stage still
  armed is disarmed and reported with the warning CML5983 naming it (the watcher has no command answer to carry `injection_disarmed`). A
  watch stage takes no `pid` (CML5960): the watcher is not per process. `watch-debounce` takes the real lost-events path, so the
  watcher's own warning CML5501 follows CML5980.

Agent rules: the handler's stage is one `fault::consume` (a lock-free CAS on a constant-initialised counter) plus one atomic increment
and the existing `SetEvent` of the notify event; no allocation, lock or log in the handler. The agent thread logs CML4661 at its next wake
(`flush_exceptions`, next to CML4403). The action stages run on the agent thread, after `claim_open` (so only an action for a thread that
is held uses an arming up); the claim is given back (`finish_claim(None)`), so the thread stays held.

### Persistent arming

`inject-failure {stage, persist:true}` also writes the arming to `<broker log>.fault-injection.json` (`cml_broker --log FILE` sets
`ServerOptions::fault_state_file`); a broker that starts with that file arms those stages again (`FaultInjector::load_state`, logged at
info). Without `--log` there is no place for it: CML5984. The answer carries `persist`.

* The file mirrors what is armed with persist: a broker stage that fires (its count is kept as what is left), is disarmed at the end of its
  operation, or by `{"stage":"none"}` leaves the file; `none` removes it. It is written beside and renamed over, so a killed broker leaves
  the previous state.
* An agent stage is armed in the agent process, which outlives a broker restart on its own. What is persisted for it is the broker's
  record that the end of the stage's operation must disarm it there (groups restart, revert, exception-action). For an agent stage of
  another group the broker keeps nothing, so `persist` is refused there (CML5960).
* The records of a process are dropped only once it has exited (the process host says so, with the R-51 re-check). A pipe that breaks
  while the process runs keeps them, and a broker that shuts down (`ReloadService::cancel()`, then every connection detaches) never drops
  them: the persisted ones are still in the file for the next broker.
* `{"stage":"none","pid":N}` disarms the broker stages armed for N and N's agent records with their persisted entries; armings without a
  pid (they apply to every process, the watcher's included) and other processes' stay. For a pid without a connected agent it clears
  N's records only when the process host confirms that N has exited; a live process that is only disconnected keeps them (its agent is
  still armed) and the command is refused with CML5961, as before. Without a pid everything goes and the file is removed.
* A file that cannot be used (not JSON, another version, an entry naming no stage of its side, a bad count or pid) arms nothing, is
  renamed to `<file>.bad` and reported (CML5984 warning in the log).

## How to run

* `ctest -R "unit.(broker_core|harness|ipc|pe|agent_exception)"`. The new broker cases are named `... (WP-44) ...` and `... (R-51 n) ...`
  (`test_restart.cpp`, `test_reload.cpp`, `test_exceptions.cpp`, `test_save_watcher.cpp`; portable, `-DCML_ALLOW_NON_WINDOWS=ON` runs them
  on Linux). The agent stages are child scenarios of `unit.agent_exception` (Windows): `exception_hold_injected`, `action_injected`,
  `reexecute_injected`.
* `cmltest --scenario tests/harness/scenarios/{crash_inject,crash_reexecute_inject,watch_inject}.toml ...` (CI runs every scenario with
  `--require-all-capabilities`).
* Persistent arming by hand: `cml_broker --headless --log b.log`, `inject-failure {"stage":"link","persist":true}`, stop the broker, start
  it again with the same `--log`: the log says "the stage 'link' is armed again from b.log.fault-injection.json (persist)".

## Learned

* WP-43's cleanup had the right rule but the wrong lifetime: the rule "disarm at the end" only holds if "the end" is still inside the
  operation for everybody else. Moving the lock acquisition one frame up (into the function that also runs the cleanup) was smaller than a
  scope guard in the impl, and keeps the impls' diagnostic order.
* The handler-side stage had to be placed after every "acts only when" check, or an unrelated fault (another module, a debugger attached)
  would use the arming up.
* The watcher's sweep when it starts watching is a batch that touches a tracked file; a scenario must let it pass before it arms a watch
  stage.

## Deferred, and why

* `exception-hold` is seen by the broker only through the agent's forwarded log (the broker has no message for "a fault was passed on",
  and no new message type was allowed); the scenario checks the application's own handler instead (`PASSED_ON`).
* `ignore` has no stage (it is the behaviour without Chameleon).
* No `exception-report` cleanup: the stage fires at its operation by construction. The "one arming of the group at a time" rule covers
  the only way an arming could have been skipped (a hold that passes the fault on).
* The persisted record of an agent stage of the reload group is not kept (WP-28's reload stages have no end-of-operation cleanup; the
  agent keeps its own counter).
* A stale state file from a long-dead broker re-arms its stages at every start until they fire or `none` is sent; the start logs each one.
* Records of a process whose exit the broker did not see (a slow exit, a broker that stopped) stay until a global `{"stage":"none"}` (or
  `none` with the pid once the host confirms the exit).
* Broker-side armings made for a pid carry over to a new process that reuses that pid.
* `none` (with or without a pid) sent while a cleanup operation runs (restart, revert, exception-action, a watch batch) can clear that
  operation's records before its `finish_injection`, which then does not list them as `injection_disarmed` (pre-existing since WP-43).
