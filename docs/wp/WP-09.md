# WP-09: Linker driver

## What was built

All in `core/cml_toolchain` (new headers `link_patch.h`, `link_diag_ids.h`; sources `link_patch.cpp` (portable) and `link_win.cpp` (Windows)). No change to `agent/`, `core/cml_ipc`, `broker/`. The only shared files touched: `core/cml_toolchain/CMakeLists.txt`, `toolchain.h` (two includes), `tests/unit/toolchain/CMakeLists.txt`, and `.github/workflows/ci.yml` (additive: the step "WP-09 link evidence (linker driver)" in the matrix job, placed LAST so its output is the tail of the job log, and the same step in `vs-generator`).

| Part | API (`cml::toolchain`) |
|---|---|
| 1. Which linker | `detect_module_linker(pe_path, pdb_options, DetectLinkerOptions)` reads the module's PE and PDB, releases the PDB index before returning, and returns `LinkerDetection {family, from_pdb, from_pe, version, overridden, evidence[], warnings[]}`. Pure parts: `read_pe_linker_facts(bytes)`, `read_pdb_linker_facts(PdbIndex)`, `decide_linker_family(PeLinkerFacts, PdbLinkerFacts*, options)`. User override: `DetectLinkerOptions::override_family`; user binary: `ResolveLinkerOptions::explicit_path`. |
| 2. The command | `build_link_command(LinkCommandSpec)` -> argument vector; `check_extra_link_args()`; `format_base_argument()`; `needs_response_file()`, `render_response_file()` (UTF-16LE + BOM, one quoted argument per line); `summarize_link_output()` (errors, warnings, unresolved symbols for both linkers' formats). |
| 3. Link and read back | `resolve_linker(family, options)` (Windows), `link_patch(LinkPatchRequest, LinkTrace*)` (Windows) = build + run (`run_process`, cancellation, timeout) + `read_linked_patch(ReadPatchRequest)` (portable). |
| Output | `LinkedPatch {dll_path, pdb_path, base, image_size, sections[] (object, section index, kind, locator symbol, symbol RVA, section RVA), slot_rvas, thunk_rvas, data_rvas, function_rvas, link_ms, pdb_read_ms, linker_family/path/version, warnings}`; `LinkedPatch::find_section(object, section)`. |

Inputs from WP-06 are used as they are: `PatchObjectInput {path, locators}` takes the `std::vector<SectionLocator>` that `coff::add_anchors()` returned, `LinkPatchRequest::bindings` takes the `coff::BindSymbol` list that `coff::make_binding_object()` was made from. The driver contains no planner.

### The command (plan 4.6 as finalised)

```
<linker> /nologo /DLL /NOENTRY /NODEFAULTLIB /MACHINE:X64 /DEBUG:FULL /INCREMENTAL:NO /OPT:NOREF /OPT:NOICF
         /FUNCTIONPADMIN /FIXED /DYNAMICBASE:NO /BASE:0x<base> /PDB:<pdb> /OUT:<dll> [extra args] <objects...> [binding.obj]
```

- `/OPT:NOREF /OPT:NOICF` are always passed (ADR-0024 precondition). `check_extra_link_args()` refuses with **CML3360** `/OPT:REF`, `/OPT:ICF`, `/OPT:ICF=n`, any comma list containing them (`/OPT:NOREF,ICF`), `/OPT:SAFEICF` (also in lists), `/PROFILE`, `/DEBUG:NONE`, `/DEBUG:FASTLINK`, `/FORCE*`, `/INCREMENTAL` other than `:NO`, `/DYNAMICBASE` other than `:NO`, `/FIXED:NO` (`/RELEASE` is fine); with **CML3361** the options the driver owns (`/OUT /PDB /BASE /DLL /ENTRY /NOENTRY /MACHINE /DEBUG /FUNCTIONPADMIN /FIXED /NODEFAULTLIB /NOLOGO /DRIVER /DEMANGLE`). Spelling `-OPT:ref` and `@response` files in the extra arguments are handled (the file is expanded first). A forbidden flag never starts the linker (asserted: `trace.command_line` is empty).
- Long command lines (> 30000 characters, or `force_response_file`) go into `<out_dir>\<name>.rsp`, written by the driver as UTF-16LE with BOM (both linkers read it; the WP-05 runner's own `@file` is UTF-8 and is not used here). The file is kept next to the output.
- The family decides one argument only: lld-link also gets `/demangle:no` (after `/OUT`) so that its diagnostics carry decorated names like link.exe's; `summarize_link_output()` extracts the name the same way for both. Otherwise both get the identical command line (unit-tested, and the CI links under both).
- Paths: `out_dir`, every object, `binding.obj`, the padding object, `/OUT`, `/PDB` and the response file are made absolute and lexically normal before the command is built (cwd = the absolute `out_dir`). `@file` entries of `extra_args` are resolved against the PROCESS cwd and passed as absolute paths, so the file that is checked for forbidden options is the file the linker reads. `ProcessSpec::max_command_line` is `LinkPatchRequest::max_command_line`, the same measure as `needs_response_file()`, so `run_process` never wraps a second time (tested at the exact boundary).

### Deciding the linker family

Evidence from CI (clang-cl 20.1.8 + lld-link 20.1.8, cl 19.44/19.51 + link.exe 14.44/14.51), quoted in the Evidence section:

| Source | link.exe | lld-link |
|---|---|---|
| PE `MajorLinkerVersion.MinorLinkerVersion` | 14.44 / 14.51 (the toolset) | 14.0 |
| PE Rich header (between DOS stub and `PE\0\0`) | present | absent (not evidence by itself) |
| PDB `* Linker *` compiland, S_COMPILE3 version string | `Microsoft (R) LINK` | `LLVM Linker` |
| PDB `* Linker *`, S_ENVBLOCK `exe` | the 8.3 path of link.exe, e.g. `C:\PROGRA~1\MICROS~2\2022\ENTERP~1\VC\Tools\MSVC\1444~1.352\bin\Hostx64\x64\link.exe` | `C:\Program Files\LLVM\bin\lld-link.exe` |

This corrects WP-04's note that only lld-link writes an S_ENVBLOCK into `* Linker *`: **link.exe writes one too** (`env_block=yes` in the msvc cells), so the block alone identifies nothing. Priority: `exe` name, then the version string, then the PE. A Rich header is positive evidence for link.exe; a MISSING Rich header is not evidence of anything. lld-link is concluded without the PDB only when the PE says linker version 14.0 with no Rich header, no PDB could be opened and the user did not override: that is returned together with a CML3366 warning that says "inferred". Otherwise CML3365. The PE must be PE32+ (loaded with `cml_pe`, whose diagnostic, e.g. CML1303 for PE32, is returned). PE and PDB are cross-checked: a disagreement gives the warning **CML3366** and the PDB wins; a PDB that cannot be opened is a warning and the PE decides. Neither: **CML3365**. A user override wins and is reported (`overridden`, the evidence is still collected). The decision is about the linker that built the MODULE; `resolve_linker()` then finds a binary of that family (explicit path, then `search_dirs` such as the directory of the recorded compiler, then `VCToolsInstallDir` / `C:\Program Files\LLVM\bin`, then PATH) and runs every candidate through `detect_tool`, so Git for Windows' coreutils `link.exe` cannot be picked up. Not implemented because not needed: matching the linker VERSION to the module's (the installed linker is used; its version is in `LinkedPatch::linker_version`).

### ADR-0017 (PDB mapping lock) and `cml_pdb`

`cml_pdb` maps the PDB read-only for the lifetime of the `PdbIndex`; a linker cannot overwrite a mapped PDB. Both places where this driver opens a PDB (`detect_module_linker` for the module, `read_linked_patch` for the patch) use `use_cache = false`, keep the index in a local scope, copy out plain strings and integers, and destroy it before returning. `LinkedPatch` holds no index. Evidence that this works: `unit.link_patch` links `basic` six times (warm-up + 5 timed) to the SAME `patch_1.pdb` path with `read_linked_patch()` inside every link; a mapped PDB would fail the next link. The module's PDB is not held open anywhere in the driver, so a later relink of the module (hot-restart) is not blocked by `detect_module_linker`. Callers that open the module PDB themselves (`unit.link_patch` keeps the fixture's open for classification) must release it before relinking the module (ADR-0017). Patch DLLs: use a new `name` per patch generation (a DLL loaded in the target cannot be overwritten either; the driver deletes stale outputs before linking and ignores errors doing so).

## How to run

`ctest --test-dir build -R "unit\.toolchain"` (portable tests of command construction, refusals, response files, output summary, family decision from synthetic PE and PDB facts: 75 test cases in `unit.toolchain`, they also run on Linux with `-DCML_ALLOW_NON_WINDOWS=ON`) and `ctest --test-dir build -R unit.link_patch` (Windows only, about 5 seconds: the acceptance below). The acceptance writes `<build>/test_work/link_patch/evidence.txt`; CI prints the filtered lines in the last step of each matrix job ("WP-09 link evidence (linker driver)") and keeps the complete file as `ci-logs/wp09-evidence.txt` in the `logs-*` artifact. It needs `link.exe` and `lld-link.exe`; when the "other" linker is missing it prints `LINK-SKIP` and carries on with the mirrored one.

## Acceptance

`unit.link_patch` (`tests/unit/toolchain/test_link_fixtures.cpp`), for each of the 7 M1 fixtures, in the cell:

1. `detect_module_linker(fixture.exe)` must equal the linker CMake used for the fixture (`CMAKE_LINKER`) and give no warning.
2. The fixture's `edits/*.edit` is applied with the harness's `apply_patch_to_tree(..., strip=1)` to a scratch copy of the sources; the changed `.cpp` is compiled with the command recorded in the module PDB (WP-05: `record_from_build_env` + `compile_tu`), with the source path replaced by the edited copy.
3. The object is anchored (`ObjectModel::from_object` + `add_anchors`), a stand-in bind plan (TEST CODE ONLY: each undefined external is a function thunk when the module PDB says it is code (flag or executable section), else a data placeholder; relocation context only when the PDB does not know the symbol) feeds `make_binding_object`.
4. `link_patch()` with the mirrored linker and again with the other one. Both must succeed. Then: every section locator is placed inside the image, `slot_rvas/thunk_rvas/data_rvas` have one entry per bind symbol, `function_rvas` one per new function; each thunk is read back from the DLL (`FF 25` + rel32 lands exactly on its `__cml_slot_<name>` which lies in a writable section) and each data placeholder lies in a writable section.
5. Prints `LINK <fixture> linker=<family> ok locators=N/N slots=N/N ms=<t>`.

Also asserted: `basic` median link time under 300 ms in RelWithDebInfo (5 timed links after a warm-up, same output path every time); `/OPT:REF` and `/OPT:ICF` never reach the linker; the user override of the family; an explicit linker path of the wrong family is refused; failures are diagnosed (no `binding.obj` gives **CML3356** naming the symbol; a missing object gives **CML3350** with the linker's own message); `/IGNORE:4001,4254,4281` is accepted by both; a forced response file links.

### Link times and the Q2 recommendation (plan 13 Q2: should lld-link be the default patch linker even for cl-built modules?)

`LINK-TIME fixture=basic`, median of 5 links after a warm-up, in ms (link.exe vs lld-link on the same objects; the link includes process creation; `basic` = anchored `logic.obj` + `binding.obj`, `/DEBUG:FULL`, PDB written):

| cell | objects | link.exe | lld-link |
|---|---|---|---|
| windows-2022 msvc Debug | cl | 34 | 46 |
| windows-2022 msvc RelWithDebInfo | cl | 33 | 38 |
| windows-2025 msvc Debug | cl | 34 | 43 |
| windows-2025 msvc RelWithDebInfo | cl | 32 | 38 |
| windows-2022 clang-cl Debug | clang-cl | 30 | 46 |
| windows-2022 clang-cl RelWithDebInfo | clang-cl | 32 | 36 |
| windows-2025 clang-cl Debug | clang-cl | 26 | 30 |
| windows-2025 clang-cl RelWithDebInfo | clang-cl | 30 | 34 |

**Recommendation: keep mirroring the module's family; do not make lld-link the default.** Not decisive for lld-link: on these inputs link.exe is faster in all 8 cells (by 4 to 16 ms), and lld-link's speed advantage only appears for large links, which patches are not. Both are far below the 300 ms budget (`basic` median 26 to 46 ms in every cell), so speed is no reason to deviate from the module's family; mirroring also keeps the patch PDB in the format the module's debugger and the user's symbol settings already expect (cdb reports `(private pdb symbols)` for link.exe PDBs, `(pdb symbols)` for lld-link PDBs, WP-03). The one reason to prefer lld-link would be a link.exe-only failure; none was seen: all 7 fixtures link under both linkers in all 8 cells. The driver supports either linker for any module (`detect_module_linker` override), so the orchestrator can change the default by configuration. The inverse risk is real: lld-link 20.1.8 crashes in one case (below).

### `/IGNORE:4001,4254,4281`: keep or not? Decision: not passed by default

Evidence: `LINK-NOIGNORE fixture=basic linker=<x> output_lines=0 warnings=0 errors=0` for both linkers in every cell (the linker prints nothing at all), and `LINK-IGNORE ... accepted /IGNORE:4001,4254,4281 exit=0` (both linkers accept the list, so it stays available as `LinkCommandSpec::ignore_warnings`). LNK4001 (no object files), LNK4254 (merged sections with different attributes) and LNK4281 (base address below 4 GB with ASLR) cannot occur with this command: objects are always given, nothing merges sections, `/DYNAMICBASE:NO` is on. Hiding warning numbers by default would only hide new information. In fact the one warning seen is useful and would be hidden by a blanket list if 4210 were added: **link.exe LNK4210 ".CRT section exists; there may be unhandled static initializers or terminators"** for `lambdas` and `new_global` (objects with dynamic initialisers in `.CRT$XCU`); lld-link says nothing. The driver turns every linker warning into a `Diag` with **CML3357** in `LinkedPatch::warnings`; the real consequence (the patch has no CRT startup, so its initialisers do not run unless the broker/agent runs the `.CRT$XCU` table) belongs to whoever implements new-global handling (WP-12/WP-20), not to the linker flags.

## What was learned

- **lld-link 20.1.8 crashes (access violation, exit -1073741819, "PLEASE submit a bug report") on this exact input: ONE anchored clang-cl object, no second object, `/DEBUG:FULL` and `/NODEFAULTLIB`.** The CI probe (`LLD-PROBE`, same result in all four clang-cl cells; `new_function` has nothing to bind so there was no `binding.obj`): crashes with `as_is`, without `/FUNCTIONPADMIN`, without `/NOENTRY` (+`/ENTRY`), without `/FIXED /DYNAMICBASE:NO`, with `/OPT:REF /OPT:ICF`; does NOT crash with the original (unanchored) object, without `/DEBUG:FULL`, without `/NODEFAULTLIB`, or when any second object is linked (`with_pad_binding_obj`, `original_with_pad_binding_obj`). The cl-built object of the same fixture links fine with lld-link. Workaround, now part of the driver: a patch that binds nothing still links a binding object that holds one data placeholder (`make_padding_binding_object()`, symbol `__cml_binding_pad`); `link_patch()` adds it by itself when `binding_object` is empty (`LinkTrace::padding_binding_object`, printed as `padding_binding=yes`). Callers that call the linker some other way must do the same.
- Without `/demangle:no` the two linkers name unresolved symbols differently: link.exe `LNK2019 ... unresolved external symbol "int __cdecl helper(int)" (?helper@@YAHH@Z)`, lld-link `undefined symbol: int g_tick` (demangled; seen in the CI run on head 7796432: `unresolved symbol 'int g_tick'` vs `'?g_tick@@3HA'`). The driver now passes `/demangle:no` to lld-link and extracts the decorated name the same way for both.
- Linker exit codes: link.exe fatal errors exit with their LNK number (1181), lld-link with 1; do not interpret them.
- `link_ms` is 26 to 53 ms per link for these inputs; reading the patch PDB and the DLL header back costs 0.2 to 0.8 ms (`pdb_read_ms`). The 300 ms budget leaves plenty of room for larger TUs.
- Image size of the patches: 16384 to 24576 bytes; `base` read back from the DLL always equalled the requested `/BASE` (`CML3375` otherwise).
- cl's `new_function` link has 2 locators (RelWithDebInfo; 4 in Debug), clang-cl's 5: the locator count is compiler dependent (clang emits more sections), which is why the test compares against the locators `add_anchors` returned, not against a constant.

## Diagnostics (CML3350..CML3375, ADR-0008; `link_diag_ids.h`)

| id | meaning | what to do |
|---|---|---|
| CML3350 | linker ran and reported errors (first error line in the message) | read the linker output (`LinkTrace::output`) |
| CML3351 | no usable linker of the requested family / explicit path wrong | install the tools or set the path |
| CML3352 | linker process could not be started | check the path |
| CML3353 | link cancelled | - |
| CML3354 | link timed out | check for a hung `mspdbsrv.exe` |
| CML3355 | exit 0 but DLL or PDB missing | see the output |

| CML3357 | linker warning (warning) | usually harmless; LNK4210 means unrun static initialisers |

| CML3367 | module PE unreadable / its PDB could not be opened (warning) | check the files |

## Deferred (with reasons)

- "Retry with another reservation" when `/BASE` is unavailable (plan 4.6): `/FIXED /BASE` never fails at link time; unavailability shows when the DLL is loaded, which is WP-08/WP-12. `link_patch()` takes the base as input and is cheap (about 30 ms), so a retry is a second call.
- Running the `.CRT$XCU` initialisers of a patch (LNK4210 above): WP-12/WP-20.
- Cross-checking the located sections against the PDB's section contributions: done by WP-06 (`unit.coff_link`); the driver only checks that every locator is a public and inside the image.
- Matching the installed linker's version to the module's: the module's linker version is reported (`LinkerDetection::version`), the installed one is used.
- `/bigobj` patches (66000-function objects) were not linked here; `unit.coff_link` covers bigobj locators.
- Multiple objects per patch are supported by the API (`objects`, per-object tags are the caller's responsibility, CML3308), but the acceptance links one edited TU per fixture (all M1 edits touch one file).
