### Decoder corpus (plan section 11)

`cml_lde_probe` runs `plan_hook()` over every function entry of the PDB. Outcomes: *padding* (6 bytes of padding, 2-byte entry write), *five_byte* (whole instructions overwritten at the entry; nothing is ever relocated in this design, ADR-0020, so there is no "hookable by relocation" class), *refused*.

| Module | functions | padding | five_byte | refused (CML4300, VEX) | refused other |
|---|---|---|---|---|---|
| raylib cl / clang-cl | 4811 / 4476 | 4807 / 4472 | 4 / 4 | 0 / 0 | 0 |
| ImGui cl / clang-cl | 3350 / 3162 | 3346 / 3158 | 4 / 4 | 0 / 0 | 0 |
| Godot editor (cl) | 512467 | 512226 | 21 | 220 | 0 |
| fixture PDBs (cl, from the `ci` workflow) | 3628-5301 each | about 97 % | 17 | 5-212 | 0 |

No crash and no refusal of a non-VEX instruction in any module. Every CML4300 refusal begins with a VEX prefix (`C4`/`C5`: `vmovdqu ymm`, `vpermq`, `vzeroupper`, ...): the MSVC STL's vectorised algorithms (`__std_minmax_*`, `__std_find_*`, `_Load_avx_256_*`) linked into the fixtures and into Godot. That is the documented limitation of the decoder ("no VEX, no EVEX", CML4300 in KNOWN_LIMITATIONS, WP-10), not a bug of the corpus, so the probe counts it as `refused_vex` and the ctest / driver fail only on other unknown opcodes. Teaching the decoder VEX/EVEX would be a small change (prefix payload 1/2/3 bytes, map 1-3, ModRM always except `0F 77`, imm8 for map 3 and a few map-1 opcodes) but it reverses a documented decision and four `test_length_decoder.cpp` assertions that pin "VEX is unknown", so it is left to the orchestrator. Application code built with `/arch:AVX2` would have VEX at the entry of many leaf functions.

## Findings

No fix was made in this package. Each finding is asserted by the corpus (so it turns the cell red if it changes) and has a reduced repro in `tests/corpus/repro/`.

**F-1. Members of a static library are never reloaded, and nothing says so.** `ModuleIndex::is_source_compiland` rejects every compiland whose PDB module names an archive. raylib built through its CMake static library: `reload: sweep of raylib_game.exe: 6 files checked, 0 changed` for an edit of `rcore.c`; Godot links `core/`, `scene/`, `main/`, `servers/`... from per-directory `.lib` files, so only `platform/windows/*` and files compiled straight into the exe are reloadable: the reload answers `ok`, `patched: 0`, `changed_files: []`, no diagnostic. Large projects are normally built from libraries, so this decides how useful the tool is on them. Pinned by `corpus F-1` in `test_audit.cpp`, repro `repro/f1_static_library/`. Orchestrator decision needed: (a) accept library members whose recorded command line and source files exist, (b) keep the rule and warn at enable time ("N compilands come from archives and cannot be reloaded") and/or answer `reload` with a warning when a tracked-nothing edit is made. Proposed KNOWN_LIMITATIONS row: *Code linked from a static library is not reloaded; the reload patches nothing and reports no error. Link the sources directly into the module (OBJECT library) or hot-restart.*

**F-2. `CML3101` for any edit of a cl translation unit that indexes a global array by a variable.** raylib `rcore.c` under cl: `'PlayAutomationEvent' references 'CORE' in raylib_game.exe image-relatively (ADDR32NB)`. The whole TU is refused, whichever function was edited, and a header included by it (here `raymath.h`) is refused with it. The diagnostic is the documented one, but the pattern (`lea rcx, __ImageBase` + `[rcx+rax*4+sym@IMGREL]`) is ordinary code, so in practice it excludes many TUs. Possible direction (design change, not made): resolve the patch's `__ImageBase` for such sites to the old image base. Repro `repro/f2_global_array_index.c` (the reduction is the expected shape; the log names the symbol, not the instruction).

**F-3. clang-cl: the reload of raylib `rcore.c` is accepted and the process then crashes.** Reload `ok` (72 hooks, `new_globals: 21`), 3 ms later `0xC0000005` read of `0x20` at `raylib_game.exe+0x11cf80` = `glfwWindowShouldClose+0x10` of `rglfw.c` (symbolised by the driver from the exe's PDB), i.e. a null `GLFWwindow*` coming from the patched `WindowShouldClose`. Hypothesis, not proven: the 21 "new globals" include `static PlatformData platform` of the included `rcore_desktop_glfw.c`, so the patch reads a zero-filled copy. The last commit adds `log_level trace` for raylib and prints the planner's `bind: sym=` decisions for statics when a crash is logged; that output was not available when this was written. The clang-cl cells assert this as `xfail` (`edit:header-inline-raymath`, `still-running-final`). This is the one finding that is a Chameleon bug (a crash after an accepted reload); next step is to read the trace output of the next raylib/clang-cl run and fix the static matching for C translation units in `bind_plan.cpp` (planner range CML3500-3549 is available), or refuse the reload.

**F-4. `CML3214` refuses every TU that sees overloaded `static` functions.** Dear ImGui's `imgui_internal.h` declares `static inline float ImFloor(float)` and `static inline ImVec2 ImFloor(const ImVec2&)`; every library TU of ImGui includes it, so only the example `main.cpp`, the dx11 backend and (clang-cl) the win32 backend are reloadable. Needs the TPI (types) in `cml_pdb`, which the PDB reader still lacks (KNOWN_LIMITATIONS CML3214). Repro `repro/f4_static_overloads.cpp`. Suggested wording for the CML3214 row: *Frequent in real code: any `static`/`static inline` overload set in a header disables reloading of every TU that includes it.*

**F-5 (VEX decoder gap, above)** and **F-6**: an empty function called from a loop is not a usable edit target (the optimiser drops the call; the ImGui example function got a counter), and a 1-3 byte function with `/hotpatch` hooks fine.

Other observations: after a refused reload the file stays changed, so every later reload retries it (the driver restores the file); the broker accepted `reload` with `patched: 0` for an untracked file without a warning (F-1).
