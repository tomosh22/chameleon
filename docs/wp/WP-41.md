### Generic driver changes: `entry_vex` and `match`

An edit may name a function with `entry_vex` (a substring of exactly one decorated public of the PDB). Before the edit the
driver looks the public up with `cml_pdb_dump --publics`, maps its RVA to the file offset through the image's section table,
and fails the edit unless the first byte at the entry is a VEX or EVEX prefix (`C4`, `C5`, `62`; in 64-bit code these bytes
are always prefixes). The bytes are quoted in the step detail. So "the edit hooks a function that starts with a VEX
instruction" is read from the built image, not assumed from the source.

An expected failure may carry `match`, a regex over the step's exception message: the step then counts as `expected-fail`
only when it fails that way; any other failure stays `fail` ("expected to fail with /re/ ..., failed otherwise"). Every
Jolt `xfail` is tied to its diagnostic this way. (WP-42 added the same key with the same semantics in its PR #70; the
second to merge keeps one implementation.)

`trace: true` in `jolt/project.json` (an existing key, as raylib has it) puts the planner's per-symbol decisions into
`broker.log` (uploaded with the cell's artefact) for the follow-up package of F-41.1 and F-41.2.

**CML5551 and the 64-compiland cap.** With the unity build a header can reach at most the 18 Jolt batches plus the two other
targets' unity sources (20 compilands), so no edit of this project can exceed `max_affected_compilands` (64). Without the
unity build it could: a dependency scan of a non-unity build of the same configuration (Linux, clang 18, `ninja -t deps`,
144 Jolt objects) finds 31 headers outside the precompiled header with more than 64 including objects, among them
`Jolt/Core/Reference.h` (124), `Jolt/Core/RTTI.h` (114) and `Jolt/Geometry/Triangle.h` (103); `PhysicsUpdateContext.h` has 14
and `Body.h` 38. So a reload after an edit of `Reference.h` would answer CML5551 in a non-unity build and goes through here.
The headers of the precompiled header (32, e.g. `Vec4.inl`, in every object) are refused with CML5550 first.

## Findings

None is fixed here (bind planner; ADR-0043: fixes are separate decisions). Each is asserted by the Jolt cells with `match`
and has a reduced repro (sources, not yet run on Windows: the reductions follow the diagnostics and may need correcting, as
WP-26's F-2 did).

**F-41.1. Statics of Jolt's RTTI overloads: CML3207 (cl and clang-cl).** Jolt's `JPH_IMPLEMENT_RTTI_*` and
`JPH_IMPLEMENT_SERIALIZABLE_*` (`Jolt/Core/RTTI.h:281`) define, for each class, an overload of the free function
`GetRTTIOfType(Class *)` holding a guarded `static RTTI rtti(..., lambda, lambda, ...)`. A unity batch holds several of these
overloads (7 in batch 8, which contains `SphereShape.cpp`). The reload of such a batch is refused:
`CML3207 static data 'JPH::GetRTTIOfType::$TSS0' (?$TSS0@?1??GetRTTIOfType@JPH@@YAPEAVRTTI@2@PEAVSphereShapeSettings@2@@Z@4HA)
matches 7 records named '$TSS0' in compiland 10 but the patch object defines 7 of them: the statics named '$TSS0' of
'JPH::GetRTTIOfType' cannot be matched by their place in the function: the guard variable ... of static 1 of 1 has no record
in the old image, so it cannot be bound to the old guard and the static would be constructed a second time` (cl; clang-cl the
same for `rtti`). Hypothesis, not proven: the statics of an overloaded function are grouped by the undecorated function name,
so the seven overloads' statics form one group. The refusal is safe (nothing applied, the application keeps running). Most
of Jolt's batches contain two or more RTTI macros, so most library edits under clang-cl end here. Repro
`repro/f41_1_f41_2_rtti_overloads.cpp`. Proposed KNOWN_LIMITATIONS row: *CML3207: a translation unit (or unity batch) with
several overloads of one function that each hold a guarded local static (e.g. Jolt's `GetRTTIOfType`) cannot be reloaded.*

**F-41.2. cl: the lambdas of a recompiled unity batch: CML3214.** Under cl every edited Jolt batch with lambdas is refused:
`CML3214 ambiguous overloads of static '<lambda_4322d7cb51a11be9bf52eb9e3fa2a650>::operator()' ... in unity_2_cxx.obj; cannot
tell which old function each new one replaces (4 in the patch, 54 records named 'operator()' in compiland 4): the lambdas of
the enclosing function are not the same as in the old image (54 call operator(s) there, 4 in the patch); a lambda's
compiler-assigned number is its only identity, and the numbers may have shifted` (batch 12: 39 / 90, batch 14: 15 / 76, batch
1: 5 / 19). clang-cl reloads batch 2 with the same edit, so this is the cl naming of closures (`<lambda_HASH>`). What to find
out first: whether cl's `<lambda_HASH>` names change between two compiles of a translation unit when another function of it
changes, and why the old compiland has many more `operator()` records than the patch defines. Repro (the RTTI lambdas)
`repro/f41_1_f41_2_rtti_overloads.cpp`. Proposed KNOWN_LIMITATIONS row: *CML3214 (cl): a translation unit with lambdas may be
refused after an edit elsewhere in it; under unity builds this covers most batches.*

**F-41.3. clang-cl: the destructor of a local class: CML3214.** `CML3214 ambiguous overloads of static
'JPH::PhysicsSystem::ProcessBodyPair::ReductionCollideShapeCollector::~ReductionCollideShapeCollector' ... in unity_12_cxx.obj;
cannot tell which old function each new one replaces (1 in the patch, 2 records named '~ReductionCollideShapeCollector' in
compiland 4): 1 new and 2 old functions have the same signature`. The class is local to `PhysicsSystem::ProcessBodyPair`,
derives from a base with `virtual ~CollisionCollector() = default;` and has a member with a non-trivial destructor. What to
find out: what the second old record is. Repro `repro/f41_3_local_class_destructor.cpp`.

What works on library code: under clang-cl, `BodyInterface::IsActive` in batch 2 reloads (1 unity compiland of 8 TUs,
88 hooks) and its marker runs; the header inline function and the template of the support library reload in both cells
(2 compilands); the PCH header is refused with CML5550 and a new `thread_local` with CML3400 in both.

## Deferred

* **F-41.1..F-41.3** (bind planner): a follow-up package (orchestrator: after WP-40). The Jolt cells carry the trace-level
  planner log for it.
* **LLVM (named in R-06): deferred; a cold clang build with `/Zi` does not fit the corpus job.** Sourced number: LLVM's own
  port of its Windows pre-merge build to GitHub-hosted Windows runners (llvm-commits, PR #82093, February 2024) measured the
  build step of `LLVM_ENABLE_PROJECTS=clang;lld;llvm` at **183 minutes** (and 359 minutes, a timeout at the 6-hour job limit,
  for the seven-project set), without `/Zi`. These are the same 4-processor standard runners (`runner: 4 logical
  processors` in our cells). Counted from the `llvmorg-21.1.0` tree: an X86-only clang build compiles about 2,961 `.cpp`
  files (1,789 in `llvm/lib` without targets, 92 X86 and common target files, 96 TableGen, 980 in `clang/lib`, 4 in the
  driver; about 4,006 with every target). `/Zi` adds compiler-PDB writes through `mspdbsrv` and a `/DEBUG:FULL` link of
  `clang.exe` with a multi-gigabyte PDB. Estimate: **3 to 5 hours cold**, against the corpus job's limit of 90 minutes (175 for
  Godot) and the 6-hour GitHub limit, before any reload is run, and the build tree would need a cache far beyond Godot's. For
  comparison, this project's Jolt build (153 TUs, unity, PCH) takes 17-21 s on the same runners. Godot (the existing large
  scons project with static libraries) already covers the "large codebase with static libraries" part of R-06 at
  24-32 minutes cold. Options if LLVM is wanted: a larger runner, a self-hosted runner, or a pre-built cached tree.
* The non-unity variant of this project (where `Reference.h` would reach 124 compilands and CML5551) is not a cell; the
  dependency counts are from a Linux scan (above).
