## Wire protocol

All messages follow the WP-11 frame format. `kMessageVersion` stays 1. The broker chooses request ids;
the answer repeats them.

| id | Message | Direction | Answered by |
|---|---|---|---|
| 0x0020 | `ReserveRange` | broker -> agent | `ReserveRangeResult` |
| 0x0021 | `ReleaseRange` (`mode` 0 = give reserved space back to the OS, 1 = unload the patch at `base` and return its range to the reserved state) | broker -> agent | `Reply` |
| 0x0030 | `LoadPatch`: 1..5 candidates (`path`, `image_base`, `image_size`, `fixups`) and the initializer RVAs | broker -> agent | `PatchLoaded` |
| 0x0022 | `ReserveRangeResult`: status (0 or CML42xx), message, the blocks actually reserved (appended id; 0x0020/0x0021 are unchanged) | agent -> broker | - |
| 0x0031 | `PatchLoaded`: status (0 or CML42xx), message, `image_base`, `image_size`, `candidate_index`, `attempts`, `fixups_applied`, `initializers_run` | agent -> broker | - |
| 0x0032 | `ApplyFixups` for a patch loaded earlier (for lists above the 1 MiB frame limit, send several) | broker -> agent | `Reply` |
| 0x0033 | `RunInitializers` for a patch loaded earlier | broker -> agent | `Reply` |

`ReserveRangeResult` and `PatchLoaded` carry the status themselves so a refusal still says why and how far it
got. A request whose payload does not decode is answered with `Reply` (CML5201..5203): `is_request_type`
and `peek_request_id` know the new request types, and the agent sends that refusal.

### Fix-up triple (ADR-0025)

The wire fix-up is `(rva, kind, value)` plus `n`, 16 bytes: `u32 rva, u8 kind, u8 n, u16 reserved(0), u64 value`.

| kind | value | what the agent writes |
|---|---|---|
| `Rel32` (n = 0..5) | the **absolute target** (symbol + the in-place addend the broker read) | `int32(value - (site_va + 4 + n))`, range-checked in the agent |
| `Addr64` | absolute value | 8 bytes, any alignment |
| `SlotWrite` | absolute value | 8 bytes, atomic, 8-aligned (`__cml_slot_<name>`) |

Choice: the broker does the addend arithmetic (ADR-0025), but the agent still needs the real site
address to range-check, so the wire carries the absolute target and N and the agent computes the
displacement. An out-of-range REL32 is CML4207 and fails the whole patch with nothing written.
`ADDR32NB` has no wire kind (the decoder rejects kind 4); the broker refuses it. Counts are bounded
by the payload (a lying count cannot force an allocation): 60000 fix-ups and 16384 initializers per
message, 5 candidates.

## Behaviour

Per candidate, with the loader lock held for steps 1-3:

0. (Once per request, before any candidate is touched, no lock.) Read ImageBase and SizeOfImage from the
   candidate file's header with `CreateFile` + `ReadFile` (nothing is mapped or loaded) and compare them with
   the announced base and size. A mismatch is CML4206 for the request (the message names both values), with
   nothing released and no retry: a wrong announcement is a broker bug, not a race. A file that cannot be read
   or is not an x64 PE image is CML4204.
1. Check that the image range (rounded up to 64 KiB) lies inside address space the agent owns.
2. Release **exactly that range**. `VirtualFree` cannot release part of a reservation, so the whole
   allocation containing the range is released and the parts outside the image range are reserved again
   immediately; only the image range is open to other threads.
3. `LoadLibraryExW(path)`.
4. Verify the module sits at the requested base and `SizeOfImage` equals the announced size.

Then (lock not held, the patch is marked busy): apply REL32/ADDR64 fix-ups, then thunk slots, then run
the named initializers, then answer `PatchLoaded`. Any failure inside this transaction (from step 3 on, up to the
answer) unloads the DLL (`FreeLibrary`) and reserves the range again where it can. Step 3 can still fail
(CML4202, CML4206) if the file changed after step 0 or the OS maps it elsewhere; CML4202 is now a defensive
path and has no test, because step 0 catches every header the tests can construct.

* **Retry.** A `/FIXED` image cannot move, so a retry means another pre-linked file at another base:
  a `LoadPatch` carries up to 5 candidates (each with its own base and fix-ups, which depend on the base)
  and the agent moves to the next one when the range was taken (CML4203 internally) or is not owned any
  more (CML4205). If at least one attempt collided and none loaded, the answer is CML4203 whose message
  gives the breakdown ("N collided, R not reserved, 0 other"). If no attempt collided, the last non-collision
  diagnostic is returned instead (for example CML4205); a hard failure keeps its own code. A broker that prefers to
  relink on demand sends one candidate and retries itself on CML4203; the agent has already put the
  rest of the block back to reserved.
* **Collision detection.** If `LoadLibraryExW` fails, the range is probed before anything is re-reserved: a
  range that is no longer free, or `ERROR_INVALID_ADDRESS` / `ERROR_ILLEGAL_DLL_RELOCATION` /
  `ERROR_NOT_ENOUGH_MEMORY`, is a collision; anything else (missing file, bad format) is CML4204 and not retried.
* **Reservations.** `ReserveRange` computes a window around the module: within `reach` (1.5 GiB) of it and
  within REL32 reach of every byte of it in both directions (`block_end <= module_base + 0x7FFF0000`,
  `block_start >= module_end - 0x7FFF0000`), scans free regions with `VirtualQuery`, and reserves blocks
  nearest-first, packed from the module outwards. It succeeds with fewer blocks than asked and
  reports how many.
* **Protection.** Only the regions that are not writable are changed (`PAGE_READONLY` -> `PAGE_READWRITE`,
  executable -> `PAGE_EXECUTE_READWRITE`, modifier bits kept), written, restored exactly, and
  `FlushInstructionCache` is called for executable regions. Writes must lie in one committed `MEM_IMAGE`
  region.
* **Initializers.** The table entries are 8-byte pointers (`.CRT$XCU`), validated up front (inside the image,
  executable target; null entries are skipped like the CRT does), then called in order inside `__try`.
  A fault is CML4209; initializers that already ran are not undone. A stack overflow is caught, then
  `_resetstkoflw()` restores the guard page; if that fails the message says "the stack could not be restored" and
  the thread refuses further initializer runs (CML4209). A C++ exception (code 0xE06D7363) is caught as well,
  because an initializer must not kill the host, and the message says so.
* **Live patches and staged requests.** A patch is *live* from the moment `load_patch` returns success (the
  `PatchLoaded` answer with status 0 exists) until it is unloaded; while LoadPatch still works on it, it is busy
  and not live. `ApplyFixups` / `RunInitializers` address live patches only. **A failing staged request never
  unloads a live patch**: it returns the CML42xx diagnostic and leaves the record and the image alone (fix-ups
  are validated before any write, so nothing was written; a faulting initializer may have had side effects).
  Only a failure inside the LoadPatch transaction unloads. The broker unloads explicitly with
  `ReleaseRange(UnloadPatch)`. Overlapping requests on one patch get CML4212.
* **Unload verifies the unmap.** `FreeLibrary` only drops a reference. After it, `GetModuleHandleExW(FROM_ADDRESS |
  UNCHANGED_REFCOUNT)` must no longer find the image; if it does (someone else loaded the same DLL), the record
  is kept, the reservation is NOT restored, and CML4213 "patch image still referenced elsewhere; not unloaded" is
  returned. The loader's own reference is already gone, so a later unload only re-checks and completes.
* **Module polling.** The agent's module snapshots (`send_module_list`, `poll_modules`) go through
  `PatchLoader::enumerate_modules_without_patches()` once the loader exists: patch images are removed from the
  list under the loader lock, so no `ModuleLoaded` / `ModuleUnloaded` is ever sent for a patch DLL and a snapshot
  cannot see a patch between its `LoadLibrary` and its record. The filter is tested at the snapshot/diff level
  (`diff_modules` of consecutive snapshots); I did not add an end-to-end test through a broker pipe.

### Threading and the heap

Every public function may be called from any thread. One mutex guards the tables and is held while a
candidate is released/loaded and during reservation scans (so a scan cannot take a range that a
load just released); it is not held while fix-ups or initializers run. `apply_fixups` does not allocate on
its success path (asserted by a test that sets `heap::set_alloc_forbidden(true)` around it, so the
WP-10 window can use it); the release/load path allocates only before the first `VirtualFree`, apart
from the slow path in which another thread already took part of a neighbouring block.
`PatchLoader::shared()` is created on first use and never destroyed (patches and reservations belong
to the process, not to an `Agent`), so the existing agent create/destroy heap-balance tests are unaffected.
Requests run on the agent thread: a hanging initializer stalls the broker connection (no timeout). The
`PatchLoader` API itself is thread-agnostic, so WP-12 can run initializers through `SyncPoint` instead
if it wants them on the application thread (plan 4.10 says "the applying thread").

## Diagnostics (CML4200..4214)

| id | Meaning | What to do |
|---|---|---|
| 4200 | request parameters unusable (zero or misaligned size, bad counts, no candidates) | send a valid request |
| 4201 | no free address space (of the asked size) within REL32 reach of the module | free address space near the module, use fewer or smaller blocks |
| 4202 | DLL loaded at a base other than requested | link with `/FIXED /BASE:<reserved address>` |
| 4203 | range taken by another allocation on every attempt | retry the reload |
| 4204 | `LoadLibraryExW` failed for another reason | check the file and its dependencies |
| 4205 | image range not inside address space the agent reserved | reserve a block first |
| 4206 | the DLL's ImageBase / SizeOfImage differ from the announcement (read from the file before anything is released; also checked after the load) | send the /BASE and SizeOfImage of the DLL that was linked |
| 4207 | REL32 displacement does not fit 32 bits | place the patch nearer the module |
| 4208 | fix-up site outside the image, misaligned slot, unwritable memory | report with the agent log |
| 4209 | initializer entry invalid or it faulted | fix the global's constructor |
| 4210 | no live patch loaded at that base | send `LoadPatch` first |
| 4211 | `ReleaseRange`: range not owned or not unused | unload patches first |
| 4212 | another request is using that patch | wait for its answer |
| 4213 | `FreeLibrary` failed, or the patch image is still referenced elsewhere after it (record kept, reservation not restored) | release the other reference and unload again |
| 4214 | `VirtualQuery` failed while scanning | retry |

## Tests (`unit.agent_loader`, runs in every matrix cell)

The test exe is the "host module". Patch DLLs are copies of one **prototype** (`proto/patch_proto.cpp`,
`/NOENTRY /NODEFAULTLIB /FIXED /DYNAMICBASE:NO /BASE:0x6600000000`, no imports, no CRT) whose PE header
`ImageBase` is rewritten per test.
Why not relink at test time: a `/FIXED` image has no relocations and the code is RIP-relative, so
rewriting the header gives a valid image at any 64 KiB aligned base in microseconds. That is the same
under cl/link and clang-cl/lld-link, needs no tool at test time, and makes 500 distinct bases cheap.
The one thing that is not position independent is the initializer table (absolute pointers, like
`.CRT$XCU`); those entries are re-pointed with ADDR64 fix-ups, which exercises writes into read-only
pages. One test loads the prototype itself at its real linker-chosen base, where no fix-up is needed.

* scan and reserve near the host (distance, alignment, REL32 reach both ways, really reserved), partial
  release re-reserves the rest, invalid parameters, destructor returns the space;
* release-and-load: exact base, rest of the block still reserved, bump allocation behind it, unload gives
  the range back, loading twice into one range is refused;
* all fix-up kinds, protection restored on code / read-only / table pages, the REL32 stub **executes**
  and reaches the host function; slots; initializers in order, in another order, null entry, fault,
  entry outside the image, bad RVAs;
* REL32 out of range: rejected, DLL unloaded, block reusable; validation happens before any write;
* unload on failure for: base mismatch (an ASLR DLL), wrong `SizeOfImage`, missing file, non-PE file,
  range not reserved, fix-up failure after load, invalid requests;
* the dispatcher for every message type, errors as `Reply`, results through the wire encoder;
* stress: 500 patches into the default 4 x 64 MiB blocks, all at their bases, fix-ups / slots /
  protection / stub call / initializer order checked for each, then all unloaded and the block is whole
  again;
* failure injection (hook between release and `LoadLibraryExW`; a second thread takes the range): two
  collisions then success on the third candidate, five collisions then CML4203 with `attempts == 5`, the
  agent usable afterwards, single-candidate failure and caller-side retry, skipped candidates, plus a free-running
  thief thread (only clean outcomes are asserted);
* four threads loading into one block; busy patches refused (CML4212 from inside the load);
* private heap: `live_blocks()` balances across load / failure / unload cycles (operator new routed to the
  agent heap exactly as in the DLL), and `apply_fixups` allocates nothing with allocation forbidden;
* portable (every host): reach window, block planning, REL32 limits, wire round trips, truncation of every
  prefix, lying counts, bad kinds / n / reserved bytes, frame limits.

Added after review: a live patch plus failing staged requests (bad RVA, unreachable REL32, site outside the
image, faulting initializer, and through the dispatcher) stays loaded, callable and byte-for-byte unchanged;
announced sizes one page too small / too large / one granule too large and a foreign ImageBase are CML4206 with no
release (a hook counts releases) and no retry; unload with a second `LoadLibrary` reference fails with CML4213,
keeps the record, does not restore the reservation, and completes after the other reference is freed; module
snapshots/diffs never mention a patch; fault classification with synthetic codes plus a real stack overflow in a
recursive initializer on a worker thread (caught, guard page restored, a normal load on the same thread works);
the CML4203 breakdown and the "no collision, return the real reason" case; `ReserveRangeResult` round trips,
truncation, lying counts and request-id peeking.

## Learned

* Facts gathered before writing: clang-cl ignores `execute` in `#pragma section(".x", read, execute)`
  when the data is `const` (the lld-linked prototype showed `0x40000040`); the prototype therefore also
  links with `/SECTION:.cmlx,ER`. `far` is a macro in `windows.h`. doctest `*_MESSAGE` arguments bind
  like `mb * arg`, so `a + b` needs parentheses.
* `VirtualFree` cannot release part of a reservation. "Release exactly the block" is implemented as
  release-the-allocation, re-reserve-the-neighbours, which keeps the window to the image range.

## Deferred

* TLS in patches (WP-24); patches are not checked for a TLS directory.
* Running initializers on the application thread through `SyncPoint` (needs WP-12's plan).
* No timeout for an initializer that never returns.
* The retry policy above the agent (when the broker relinks instead of sending several candidates) is WP-12.
* Undoing initializers that ran before a later one faulted (atexit registrations made by an initializer
  that ran are not removed when the patch is unloaded).
