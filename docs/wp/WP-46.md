# WP-46: planner coverage on unity builds (F-41.1..3, R-54; ADR-0043)

Branch `wp/46-unity-planner`, one PR. Diagnostic range of ADR-0043: CML3630–3649. Used: **CML3630** (lambdas named by a hash
whose pairing their code does not prove, error). R-54 refuses with the existing CML3207, as the ADR asks. Review: high (bind
planner).

The rule of the package (ADR-0042, ADR-0043): a wrong pairing is never acceptable; what cannot be proven is refused; an
over-refusal is acceptable and gets a KNOWN_LIMITATIONS row.

## Round 1: what the refusals were (evidence before code)

Source: the trace `broker.log` of corpus run 45627596782 (WP-40's last pull_request run), artifacts `corpus-jolt-msvc` and
`corpus-jolt-clang-cl`, and local builds of the repros with clang 18 + lld (`--target=x86_64-pc-windows-msvc -O2 -gcodeview`).

**F-41.2 (cl).** Two questions, two answers.

- *Do cl's `<lambda_HASH>` names change between two compiles of a TU when another function changes?* No. In every refused cl
  reload every closure name of the patch is in the old compiland with the same hash: batch 12 39 of 39, batch 2 4 of 4, batch 14
  15 of 15, batch 1 5 of 5. The batch-12 edit inserts lines above lambdas of `PhysicsSystem.cpp` (the include and the marker),
  so the hash does not depend on the line.
- *Why 90 old records against 39?* Every extra old record is a call operator with **external linkage** (a lambda of an inline
  function whose COMDAT the linker took from this unit), which the patch already pairs by its public name: batch 12 51 of 51
  (`static=0 decision=patch-hooked source=pdb-public`), batch 2 50 of 50, batch 14 61 of 61, batch 1 14 of 14.
- *The defect.* cl's legacy lambda processor (Jolt is `/std:c++17` without `/permissive-`; our fixtures are C++20, which turns
  on `/Zc:lambda` and gives `<lambda_N>@?1??f@@`) names every closure `<lambda_<32 hex>>` in **no scope**. The planner's
  closure-set rule (WP-37, `pair_overloads_by_signature`) groups the closures by their enclosing function, so every hash-named
  closure of the unit falls into one pseudo-function `@`; the old set was read from every compiland record named `operator()`,
  external ones included, the new set from the static members only. They never agreed. Batch 8 and batch 0 reloaded under cl
  because their external lambdas' COMDATs came from other objects (batch 8: 22 static call operators on both sides).

**F-41.3 (clang-cl).** The second old record is the **scalar deleting destructor**. clang's CodeView record for `??_G<Class>`
carries the destructor's display name and the destructor's type. The repro (`std::string` replaced by a struct with a
destructor) shows two `S_LPROC32 System::Process::LocalCollector::~LocalCollector`, type 0x1023 both, at `0001:0256` (`??1`
in the lld map) and `0001:0464` (`??_G`); only the second has `S_LOCAL should_call_delete` (`flags = param`). The Jolt log
shows the same for `~ReductionCollideShapeCollector` and `~LeafShapeCollector` in batch 12.

**F-41.1 (clang-cl).** Each overload's `rtti` would pair by its procedure, as under cl (WP-40 item 7); only the guard stopped
it, because clang-cl records no `$TSS0`. No static of the batch was bound, so no section layout was learned. Locally `rtti` and
its guard sit together in one `.bss` that is not a COMDAT (`rtti` at +0x0, its guard at +0x18 for the first overload).

**R-54.** At `-O2` clang keeps the closure class of a lambda it inlined everywhere in the TPI, with a scoped unique name
(`.?AV<lambda_0>@?0??o2_step@@YAXXZ@`, `planner_pairing_o2/lambdas.cpp`), though no `operator()` procedure exists.

The orchestrator's rulings (ADR-0043, WP-46): D1 option B (the counting fix plus a proof by code of every hash-named pairing,
rule (d)'s single changed pair allowed, otherwise CML3630; a cl C++17 fixture); D2 accepted (R-54 may refuse for inlined
lambdas without statics); F-41.3, F-41.1 and R-54 as proposed.

## What was built

### F-41.2: hash-named lambdas (`bind_plan.cpp`, `hook_narrowing.cpp`, `pipeline.cpp`)

1. **The counting fix.** In the closure-set comparison an old call operator whose address carries a public symbol that the
   patch defines with external linkage under the same decorated name is left out (`taken_by_public`): it pairs by that public
   name (decide_defined) like every external function. Log `WP46-PUBLIC-LAMBDAS group=... old=N taken-by-public=N`. The set
   rule itself is unchanged: a lambda added or removed anywhere in the unit still refuses every hash-named call operator of it
   (CML3214).
2. **The proof.** After pass B the planner lists, per hash-named closure (`<lambda_` + 32 lower-case hex + `>`), the static
   functions of it that it hooked and the statics it bound (`BindPlan::hashed_lambdas`; `note_hashed_lambdas`). A closure with
   bound statics and no hooked function (its call operator inlined, or new) is refused at once with CML3630: nothing could
   prove it. The pipeline then runs `prove_hashed_lambdas` (after rule (d)'s re-plan, before the bitmask proof): each listed
   function is judged with the WP-25 comparator against the old function it is hooked to, with the plan's decisions (so its
   statics are compared at the old lambda's addresses). Proven when every lambda's code is unchanged, or exactly one lambda's
   changed (rule (d): the edited one). Two or more changed, or any that cannot be compared: CML3630 naming the lambdas. Log
   `WP46-HASHED-LAMBDAS object=... closures=N unchanged=N changed=N unknown=N proven=unchanged|one-changed|refused`.
3. Functions with external linkage are not listed: they pair by their decorated public name, as every external function does.
   Evidence that this name is not unit-local: batch 8's external lambdas have their old procedures in other compilands, i.e. the
   same decorated name occurs in several units.
4. Evidence line for the hash question: `WP46-HASH-SET group=... scope=... old=N new=N common=N same|changed` at Info for every
   hash-named set the planner compares.

The statics of hash-named lambdas (`pair_statics_by_closure`) already pair by the exact closure name (the scope-less closure
`<lambda_HASH>@@` is its own unique name); they now need their lambda's code to prove it (point 2).

### F-41.3: the deleting destructor (`bind_plan.cpp`, `pair_overloads_by_signature`)

In a destructor group (`~X`), an old candidate whose procedure has a parameter `S_LOCAL should_call_delete`
(`PdbIndex::proc_info`) is a deleting destructor and not a candidate. A destructor has no parameters, so a real destructor is
never dropped. Without the recorded parameter the group stays ambiguous (CML3214). Log `WP46-DELETING-DTOR group=... dropped=N
left=N`. The patch's own `??_G` stays a new function, as before.

### F-41.1: guards without a record (`bind_plan.cpp`, `pair_statics_by_procedure`, `learn_guard_layout`, `settle_guards`)

In a compiland that records no `$TSS<n>` guard at all (clang-cl), a static that is the **only one of its name in its
function** (its function is its identity; no order is involved) is no longer refused by the by-place step for its record-less
`$TSS` guard. It pairs by its function, and the pair is remembered (`place_taught_`). After pass B, `learn_guard_layout` builds
the layout `settle_guards` uses: `delta_` plus what those pairs teach, with learn_delta's rules (no COMDAT section, one delta and
one image section per object section; a disagreement drops the section's layout, also the one `delta_` had). Only
`settle_guards` reads it, so no static's pairing depends on it; there it places the guard with WP-40's checks (inside the
compiland's contribution, the same image section, on no recorded variable) or refuses with CML3600. cl records its `$TSS`
guards, and its `$S<n>` bitmask is not relaxed: `planner_pairing`'s cl path is unchanged. Logs `WP46-GUARD-BY-PLACE` and
`WP46-GUARD-LAYOUT`.

### R-54: a lambda inlined everywhere (`core/cml_pdb`, `bind_plan.cpp` pass A)

- `cml_pdb`: `PdbIndex::closure_classes()` lists every class or struct of the TPI whose unique name starts with
  `.?A?<lambda_`, once each, without the unit's discriminator. The first call walks the TPI once (`TypeStream::walk`, which
  reads chunks that are not loaded yet for the walk only and does not keep them), the result lives as long as the index; an
  unreadable or incomplete stream is an error, never a shorter list. Log `WP46-CLOSURES pdb=... closures=N records=N complete=1
  ms=...`. Nothing calls it on the hot path of a cl compiland.
- Planner, pass A: an own static of a function `f` with candidate records (in `f`), in a compiland whose S_COMPILE3 says clang,
  is refused (CML3207, log `WP46-R54`) when the old TPI has a closure class of `f` (any scope level) that has no call operator
  procedure in the compiland (`closures_with_proc_`, by the class of each `operator()` procedure's signature). Then the record
  in `f` may be that lambda's static.

## How to run

- Linux pre-check: `cmake -S . -B b -G Ninja -DCML_ALLOW_NON_WINDOWS=ON && ninja -C b cml_test_bind cml_test_pdb cml_test_harness`.
- Windows: `ctest -R "unit.bind|unit.pdb|unit.harness|fixture.legacy_lambdas"`; `cmltest --scenario tests/harness/scenarios/legacy_lambdas.toml`.
- Corpus: `corpus.yml`, `only=jolt`; the WP46 lines are in each cell's `broker.log` artefact.

## What was learned

- cl's legacy lambda processor names closures `<lambda_<32 hex>>` with no scope, in decorated names and type records alike; the
  hash of an unchanged lambda did not change when lines above it moved.
- The old compiland's records of external lambdas depend on which object the linker took each COMDAT from, so a count over the
  compiland's records includes functions of the patch that pair elsewhere.
- clang-cl records a deleting destructor under the destructor's name and type; its `should_call_delete` parameter is the one
  difference in the records.

## Deferred, and why

- **Adding or removing a lambda in a unit compiled with the legacy processor** refuses every hash-named lambda of it (the set
  rule). Proposed KNOWN_LIMITATIONS row.
- **Two or more lambdas changed in one reload** of such a unit: CML3630 (rule (d)'s allowance is one). Proposed row.
- **R-54 over-refusal:** under clang-cl at `-O2`, an own function-local static of a function that has a lambda the compiler
  inlined everywhere (with or without statics) is refused with CML3207. Proposed row.
- **External hash-named lambdas** pair by their public name without a proof by code, as every external function does.
