# WP-02: cml_coff and cml_pe readers

## What was built

### `core/cml_coff` (`cml/coff/coff.h`)

A non-owning, bounds-checked reader for COFF objects, regular and `/bigobj`.

- `Object::parse(ByteSpan)` validates the whole container up front (headers, section table, symbol table, string table, relocation table ranges, symbol name offsets, symbol section numbers). Afterwards every accessor is safe. `read_file` / `load_object_file` / `OwnedObject` load a file into an owned buffer.
- **Stable indices for the WP-06 writer.** A symbol's `index` is the raw symbol-table index, aux records included. `symbols()` lists primary records only, `symbol_at(raw_index)` returns null for aux slots. Raw spans are kept for the header, section table, symbol table, string table, each section header / data / relocation table (including the `LNK_NRELOC_OVFL` record), each symbol record and its aux bytes. The raw 8-byte name fields are preserved. Nothing is normalised.
- Sections: characteristics, alignment, long names (`/nnn` and `//base64`), `IMAGE_SCN_LNK_NRELOC_OVFL` extended relocation counts.
- Symbols: storage class, 32-bit section number (sign-extended 16-bit in regular objects), inline or string-table names, typed aux decoding (`section_definition`, `function_definition`, `weak_external`, `file_name`; bigobj `NumberHighPart` handled).
- Relocations: `RelocType` enum covering every `IMAGE_REL_AMD64_*` (0x00..0x10), raw type kept; `resolve_relocations()` resolves each target symbol.
- Queries: `find_symbol`, `find_section`, `section_of`, `comdat(section)` (selection, section symbol, leader; associated section for Associative), `associative_children`, `weak_external_default`.
- `.drectve`: `parse_directives()` / `Object::directives()` returns a list with kind, name, value, raw text and, for `/alternatename`, `/FAILIFMISMATCH`, `/MERGE`, an `lhs=rhs` pair. Handles quotes, BOM, any whitespace.

### `core/cml_pe` (`cml/pe/pe.h`)

PE32+ reader, `Image::parse(bytes, ImageKind::OnDisk | InMemory)` plus `Image::parse_mapped_module(base)` (reads SizeOfImage from the headers at `base`; the only function that dereferences a raw pointer).

- DOS/NT/optional headers, data directories, section headers. PE32 is rejected (CML1303).
- `rva_to_offset` / `offset_to_rva` / `read_rva` / `read_cstring_rva`: through the section table on disk, identity in memory.
- Directories: exports (name, ordinal, forwarders, gaps), imports (per DLL, by name or ordinal, `iat_slot_rva` per entry, in-memory images without a lookup table report `names_available = false`), debug directory + CodeView RSDS (GUID, age, PDB path), exception directory (`ExceptionTable` with `sorted` flag and `find(rva)`), load config (GuardFlags, cookie, CFG pointers/table), TLS directory.

### Tests (`unit.coff`, `unit.pe`)

- Synthetic objects / images built by independent builders (`tests/unit/coff/obj_builder.h`, `tests/unit/pe/pe_builder.h`): all aux kinds, COMDAT queries, bigobj with 70000 sections (32-bit numbers incl. `NumberHighPart`), 70000 extended relocations, directives, PE in both layouts. Malformed input: truncated headers, string offsets out of range, relocation counts past the end, bigobj with bad version / class id, dangling relocation targets, every PE directory, plus exhaustive truncation and byte-flip loops over every accessor.
- Acceptance tests on objects built from fixture `basic` and `bigobj`, and on `fixture_basic.exe` (imports with IAT slot checks, CodeView/PDB, exception table, GuardFlags checked against an independent raw read, TLS).
- Windows only: the test exe itself (`GetModuleHandleW(nullptr)`), `kernel32.dll` exports against `GetProcAddress`, and the fixture exe mapped with `LoadLibraryExW(LOAD_LIBRARY_AS_IMAGE_RESOURCE)`, each compared with the on-disk parse.
- Round-trip support for WP-06: `tests/unit/coff/coff_independent.h` is an independent minimal parser; `compare_with_reader()` checks every field. `writer_roundtrip_hook()` is the plug point: WP-06 assigns a `std::vector<uint8_t>(*)(const Object&)` rewriter to it (from a static initialiser in its test TU) and `test_coff_roundtrip.cpp` then demands byte identity for synthetic and fixture objects. With no writer installed a copy-through rewriter keeps the plumbing covered.

### Fixture `bigobj` (new, `tests/fixtures/bigobj`)

TICK loop plus a configure-time generated `bigobj_funcs.cpp`. cl: `/bigobj` always yields the bigobj format, 200 functions suffice. clang-cl accepts `/bigobj` but ignores it (LLVM only switches format above 65279 sections), so 25000 functions (3 sections each) are generated there.

## Compiler differences and lessons

Observed on the CI runners (cl 19.4x / VS 2022 and 2025, clang-cl 18-20 from the runner image) and, for clang, a local cross-compile with clang 18.

**cl vs clang-cl object differences (relevant to later WPs)**

- Section names: cl uses `.text$mn` (`.text$di` for dynamic initialisers, `.text$x` for catch funclets, `.xdata$x` / `.rdata$r` for EH and RTTI data); clang-cl uses plain `.text`, `.rdata`, `.xdata`, `.pdata` (all COMDAT). Never match on the exact name; match on prefix, or better go through symbols and `Object::comdat()`.
- COMDAT selection: cl gives non-inline functions `NoDuplicates` (1) and inline functions/templates/RTTI `Any` (2); clang uses `Any` for linkonce and `NoDuplicates` for the fallback/weak default bodies. `.xdata`/`.pdata`/`.debug$S` children are `Associative` (5) to their function section in both compilers (cl also for leaf functions: `inline_twice` has `.pdata`/`.xdata`). cl's EH adds several associative `.xdata` sections per function (`$stateUnwind$`, `$tryMap$`, `$handlerMap$`, `$ip2state$`) and `.voltbl`.
- `.pdata` relocations are `ADDR32NB` in both; cl targets static labels (`$LN7`, `$unwind$...`) inside the function/xdata sections, clang targets section symbols. `.xdata` relocations are all `ADDR32NB`.
- C++ EH personality: cl `__CxxFrameHandler4`, clang-cl `__CxxFrameHandler3`.
- `.CRT$XCU`: cl points straight at `??__E<var>@...` (ADDR64); clang points at a static `_GLOBAL__sub_I_<file>` wrapper that calls the `??__E` function (REL32), and under optimisation inlines it into the wrapper.
- Weak externals: only clang emits `IMAGE_SYM_CLASS_WEAK_EXTERNAL` (for `__attribute__((weak))`; characteristics = SearchAlias, tag -> defined `.weak.<name>.default.<other>` symbol). cl emits an ordinary external; `/alternatename` is in `.drectve` for both (`/alternatename:a=b`) and creates NO weak symbol; the left-hand name stays an undefined external.
- String literals: cl without `/GF` (Debug) uses static `$SG<n>` symbols in a plain `.rdata`; with `/GF` (O2) or clang they are `??_C@_...` COMDATs (Any). Match literals through the relocation that references them.
- RIP-relative references: cl uses `REL32` and `REL32_1..4` (addend encoded in the type), clang only `REL32` (addend in the instruction stream). Treat them as one family (`is_rel32_family`).
- Extra cl-only sections/symbols: `.debug$S/.debug$T`, `.rtc$IMZ/.rtc$TMZ` (Debug /RTC1), `.chks64`, `@comp.id`, `@feat.00`, `@vol.md`, `_Avx2WmemEnabledWeakValue`. clang adds `.llvm_addrsig` and `.debug$S` only with debug info.
- `.drectve` default lib: `/DEFAULTLIB:"LIBCMT[D]"` (static CRT) in both; cl adds `/DEFAULTLIB:"OLDNAMES"` and a long list of `/FAILIFMISMATCH` entries.
- `/bigobj`: cl emits the bigobj format for every TU of a target compiled with the flag, small or not. clang-cl accepts and **ignores** `/bigobj`; LLVM writes bigobj only above 65279 sections. Below that it writes a regular object whose 16-bit section numbers run unsigned up to 65279 (a symbol in section 50000 is stored as 0xC350). The reader therefore treats a regular object's 16-bit section number as unsigned except 0xFFFF (absolute) and 0xFFFE (debug). This was a real bug caught by CI (clang-cl RelWithDebInfo, 50011 sections).
- Sections per function in the generated bigobj fixture: 2 in clang-cl RelWithDebInfo, 4 in clang-cl Debug; hence 40000 functions.

**Linker output** (identical for cl and clang-cl compiled fixtures, link.exe): sections `.text .rdata .data .pdata .fptable .rsrc .reloc` (plus `_RDATA _guard_c _guard_d memcpy_` for the clang-cl objects); DllCharacteristics `0x8160` (no GuardCf); load config Size 0x140 with GuardFlags `0x100` (CF_INSTRUMENTED, set because the CRT libs are /guard:cf) but no function table; non-zero security cookie; **no TLS directory** in the static-CRT fixture exe; CodeView RSDS with age 1 pointing at `<build>\bin\fixture_basic.pdb`. Consequence: do not infer CFG from `DllCharacteristics & GuardCf` and `GuardFlags & CF_INSTRUMENTED` interchangeably. WP-18 should test `CfFunctionTablePresent` plus a non-empty table for "usable CFG" and the DllCharacteristics bit for "linked with /guard:cf".

**Fixture sensitivity (suggestion for the fixture owner, not changed here)**

Under clang-cl RelWithDebInfo (`/O2 /Ob0`) most of what `extras.cpp` exists to produce is folded away: the inline and template COMDATs, the static data, the string literal and the EH personality (the `guarded_length` try/catch disappears). cl keeps them. To get strict coverage in every cell without touching the fixture, `unit.coff` compiles `extras.cpp` a second time with `/Od /Ob0` (`coff_cov_extras_objs`, CMake's RelWithDebInfo `/Ob1` still inlines at `/Od` under cl, hence the explicit `/Ob0`); the fixture's own objects are tested for what survives optimisation. Making `s_counter`, `k_table`'s index, and the calls in `extras_value` opaque (volatile or an external function) would let the fixture itself carry the coverage.
