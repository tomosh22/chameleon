# WP-28: Fuzzing and failure injection

Branch `wp/28-fuzz-injection`, one PR. Diagnostic ranges of ADR-0035: CML1280-1289 (COFF), CML1380-1389 (PE),
CML1480-1489 (PDB), CML4650-4699 (agent), CML5960-5989 (broker). Agent message block 0x00C0-0x00CF.

## Fuzz targets

| Target | Input | What runs |
|---|---|---|
| `coff` | an `.obj` | `Object::parse`; then sections, symbols, aux decoding, `resolve_relocations`, COMDAT info, associative children, directives, `find_symbol`, `symbol_at`; `ObjectModel::from_object` + `write`, `rewrite`. |
| `pe` | a PE file | `Image::parse` as on-disk and as in-memory image; exports, imports, debug entries, CodeView, exception table (`find`), load config, TLS, `read_rva` / `read_cstring_rva` / address mapping probed at each section's edges. |
| `pdb` | a `.pdb` | written to a scratch file (cml_pdb maps files), `PdbIndex::open_pdb` twice (lazy and with `preload_all_symbols`); every query: compilands, build env, files, publics, globals, `find_proc_by_rva`, contributions, `load_all`; `is_valid_pdb_image`; inputs starting with `MZ` also go to `read_codeview_ref_from_image`. |
| `ipc` | a frame, or `[u16 type][u16 version][payload]`, or text | `decode_frame`, `parse_frame_header`, `decode_message` with the type and version taken from the input (so each of the 27 message types is reachable in both directions), `peek_request_id`, `is_request_type`; every decoded message is encoded again and must decode to the same message and re-encode to the same bytes (round trip); UTF-8 validation and sanitising. |
| `control` | a control-pipe line | the hand-written JSON parser (`json::parse`, then serialise / parse / serialise must be stable), `decode_request`, `decode_server_message`, encoders, `status_from_json`. The JSON parser is hand-written, so it is a target of its own. |

How to run one locally (clang-cl):

```
cmake -S . -B build-fuzz -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_CXX_COMPILER=clang-cl -DCML_FUZZ=ON
cmake --build build-fuzz --target cml_fuzz_coff
build-fuzz\bin\cml_fuzz_coff.exe -max_total_time=600 -max_len=65536 corpus-work tests\fuzz\corpus\coff
```

A reproducer is replayed with `cml_fuzz_<target> <file>` (libFuzzer build or the plain replay build). To regenerate the seeds:
`cmake --build . --target cml_fuzz_gen_seeds` and `cml_fuzz_gen_seeds tests/fuzz/corpus`.

## Bugs found

None. No fuzz run found a crash, a sanitizer report, a hang or a round-trip mismatch, so no reader was changed and the ids
reserved for reader hardening (CML1280-1289 COFF, CML1380-1389 PE, CML1480-1489 PDB, CML4656-4699 agent, CML5970-5984 and CML5986-5989 broker)
are unused. This is the honest result of what was run, not a claim that the readers are bug-free:

* CI, the `fuzz` workflow on this PR, run 42474656725 on commit 49bbda9 (clang-cl 20.1.8 libFuzzer + ASan, 601 s per target, all
  green): coff 4,132,156 runs (6,875/s), pe 685,323 (1,140/s), pdb 1,369,690 (2,279/s), ipc 13,888,631 (23,109/s), control
  2,491,634 (4,145/s). The same workflow's job `no-fault-injection` (cl RelWithDebInfo, `-DCML_FAULT_INJECTION=OFF`) is green.
  Earlier green runs of the same targets: 42464592138, 42460152164, 42455794140.
* Locally (Linux, no libFuzzer available there): a coverage-guided mutation loop of my own over the same entry points,
  g++ AddressSanitizer + UndefinedBehaviorSanitizer (`-fno-sanitize-recover`), about 1.1 M to 3.4 M executions per target in
  three rounds, no finding. It is blind to the PDB records' structure, so it is weaker than libFuzzer.
* The reproducer rule is in place for the future: a crash uploads `crashes/` as the artefact `fuzz-crash-<target>`; the fix
  adds the file to `tests/fuzz/corpus/<target>/`, where `fuzz.replay.<target>` runs it in every cell from then on.

## Failure injection

Compiled in under CMake option `CML_FAULT_INJECTION` (default ON; `CML_FAULT_INJECTION=1` is defined for every target). With
it OFF the broker does not advertise `fault-injection`, the commands do not exist, the agent answers `ArmFault` with CML4655
and every injection point is a constant `false`.

Control commands (capability `fault-injection`):

| cmd | args | result |
|---|---|---|
| `fault-stages` | - | `{stages:[...], details:[{name, side, id, where}]}` in pipeline order |
| `inject-failure` | `{stage, pid?, count?}` | `{stage, armed:true, count, side, id, processes:[pid...]}`; `{"stage":"none"}` disarms every stage in the broker and in the agents and answers `{stage:"none", armed:false}` |

`count` (default 1, at most 1000) is the number of passes of the stage that fail; the stage disarms itself afterwards. `pid`
limits the arming to one process (for a broker stage: only that process's reloads fail); without it an agent stage is armed in
every connected agent. A broker stage armed twice keeps the latest arming.

* A `pid` that matches no agent is CML5961 for every stage, `none` included, and nothing is changed.
* Arming agents is **all or nothing**: when one agent refuses (CML5962, the message names its pid) the agents armed before it are
  disarmed again (`ArmFault` with `count` 0 disarms that one stage), then the error is returned.
* `none` disarms the broker's stages and then every target agent, trying all of them. If some agent cannot be disarmed the
  answer is CML5971 naming the pids (the others are disarmed). An agent built without injection answers `none` with success: it has
  nothing armed.
* `reservation` is refused (CML5970) when an enabled module of a target process has reserved its address space already, because
  the counter would otherwise fire on an unrelated later reload: a module reserves once, on its first patch.

| Stage | Where it fails | Diagnostic | Notes |
|---|---|---|---|
| `pdb-load` | the broker's mapping of the PDB: it is dropped, then fails to open | CML5963 | the next reload maps it again |
| `change-detection` | the sweep that hashes the sources | CML5964 | |
| `compile` | before the compiler runs; the application's compile-error hook runs | CML5965 | |
| `bind-plan` | before `plan_bind` of the first compiland | CML5966 | |
| `reservation` (agent) | `ReserveRange` answers with the status | CML4650 | a module is reserved once, so only its first patch asks |
| `link` | before the linker runs | CML5967 | |
| `pre-apply` | before the SECREL sites are written into the DLL (the DLL is linked) | CML5968 | the linked image's slice of the reserved address space is given back |
| `send-patch` | `LoadPatch` is not sent | CML5969 | same |
| `patch-load` (agent) | after the DLL was mapped and placed; the real cleanup path unloads it | CML4651 | the slice is given back (the broker does so for every refused `LoadPatch`) |
| `hook-install` (agent) | inside the window with the application's threads suspended, before anything is written | CML4652 | one lock-free atomic decrement, no allocation, no lock; the diagnostic text is built after the threads run again; the batch fails like any other (CML4305 and friends) and the threads are resumed. Only a reload's own `InstallHooks` can consume it: the installer takes an `injectable` flag, false for a revert, a quiet re-point (WP-22) and for the rollback below |
| `post-patch-hooks` (agent) | after the hooks were installed, BEFORE they are committed and before the application's post-patch hooks run: the installed hooks are rolled back (two windows with the threads suspended) | CML4653 | functions that were hooked to an earlier patch are re-pointed to it, the others get their original bytes back; the application's post-patch hooks then run as after any failed install and see the failure in `cml_last_patch_status()`; nothing is committed. If the rollback itself fails (partly), the answer is CML4656 and the broker keeps the image mapped |

Other ids: CML5960 bad request (unknown stage, bad count or pid), CML5961 no agent with that pid, CML5962 the agent refused
`ArmFault` (its own CML4654 bad stage / CML4655 not compiled in is in the message), CML5970 stage not applicable
(`reservation` after the reservation), CML5971 some agents could not be disarmed, CML4656 post-patch-hooks failed and the
rollback was incomplete (patch kept mapped), CML5985 harness step (`inject_failure`).

**Never free an image a live hook can target.** The agent stages are built so that this holds: `patch-load` fails before any hook
exists, `hook-install` fails before anything is written, and `post-patch-hooks` rolls the hooks back before answering CML4653.
When that rollback is incomplete the agent answers CML4656 instead; the broker does not send `ReleaseRange(UnloadPatch)`, remembers
the hooks as installed (like after a hook timeout, CML5309) and records the patch as a live batch, so the image stays mapped for
the life of the process. A later `revert` of such a batch may report the hooks it cannot find; restart the application.

**Address space.** A patch that was linked but never loaded (`pre-apply`, `send-patch`, a refused `LoadPatch`, including the
agent's `patch-load` failure) hands its slice of the reserved blocks back (`Reservation::release_tail`) when it is the newest
slice of its block, so failures do not use the reservation up. A slice whose range was taken by someone else (CML4203/4205) and a
patch whose `LoadPatch` timed out stay consumed.

Every injected failure takes the stage's normal error path: the reload is refused with the stage's diagnostic (a `diag` event as
well), a patch that was already loaded is unloaded, nothing is hooked, and the application keeps running its previous code. The
reload that follows without injection applies the same edit.

## Scenario

`inject_stages` (fixture `inject`, `compute_value()` returns one more than before for each stage, edits in `edits/stacked/`)
runs, for each of the eleven stages, edit - `inject_failure` - `reload` expecting the stage's id - `expect_diag` of that id -
`expect_stdout` of the previous value - clean `reload` - `expect_stdout` of the new value; then a disarm check
(`inject_failure link`, `none`, reload succeeds) and `expect_monotonic calls`. The reservation goes first because a module is
reserved once. It runs in every cell under `--require-all-capabilities`.

## Decisions

* **clang-cl for the fuzz workflow: the LLVM 20.1.8 of the windows-2022 image** (`C:\Program Files\LLVM`). Its runtimes are
  `clang_rt.fuzzer-x86_64.lib` and, for AddressSanitizer, a static thunk plus the runtime DLL
  (`clang_rt.asan_static_runtime_thunk-x86_64.lib`, `clang_rt.asan_dynamic-x86_64.lib`, `clang_rt.asan_dynamic-x86_64.dll`);
  the old static `clang_rt.asan-x86_64.lib` is not shipped any more. libFuzzer is built for the static CRT, so the fuzz binaries
  use `/MT` like the rest of the project (a `/MD` try failed to link: `RuntimeLibrary` mismatch against the fuzzer library), and
  the DLL is copied next to them by a post-build step. `tests/fuzz/CMakeLists.txt` still takes the old static runtime when an
  LLVM install has it, and fails at configure time, naming the files it looked for, otherwise. The step upgrades LLVM with
  chocolatey if a future image lacks the runtimes.
* **One diagnostic per stage, with the stage name in the message** (CML5963-5969 broker, CML4650-4653 agent), so a scenario
  can tell exactly which stage failed and a user reading a log sees "injected failure at the stage 'link'".
* **Several stages armed at once are allowed**; `none` disarms all of them. `count` > 1 makes a stage fail repeatedly.
* **pdb-load drops the mapping first** (`ModuleIndex::release_pdb`) and then fails, so the next reload maps the PDB again.
* **patch-load fails after the DLL was mapped and placed** and takes the real cleanup path (`unload_after_failure`), so the
  scenario shows that the range is usable again for the next attempt.
* **hook-install fails in the window, before the verify-and-write step**, with one lock-free atomic decrement; nothing is
  written, the threads are resumed by the normal exit path of the attempt, and the text of the diagnostic is built after that
  (the no-allocation rule). `unit.agent_hook` is untouched and stays 25/25.
* **post-patch-hooks** (coordinator's ruling): the stage fires after the hooks are installed but before `session->commit()` and
  before the application's post-patch hooks run. The agent rolls the request's hooks back under the suspended-threads windows
  (reverting functions that were new, re-pointing functions an earlier patch had hooked) and answers CML4653; the broker unloads the
  patch like for any other `InstallHooks` failure. The post-patch hooks never see a status-0 patch that is later removed: they run
  after the failed install, as WP-17 specifies, and `cml_last_patch_status()` is CML4653. A fault *inside* an application hook is a
  different thing: it is contained by the WP-17 guard (CML5652) and does not fail the reload.
* **`fault-injection` is advertised whenever the broker has a reload service**, and the broker-side stages fire for every
  process unless `pid` is given. The agent stages need an agent that was built with the option too (CML4655 otherwise).
* **The UI treats the capability as passive** (`broker/cml_ui/src/commands.cpp`): `ui.self_test` requires every advertised
  capability to be covered by the command table or listed as passive, and the UI has no button for fault injection.
* **`CML_FAULT_INJECTION=OFF` is built and tested in CI**: job `no-fault-injection` of `fuzz.yml` configures with cl
  RelWithDebInfo, builds `cml_agent`, `cml_broker` and the three unit tests that touch injection, and runs them. The OFF paths are
  `#if` blocks, not `if constexpr`, so there is no unreachable code under `/W4 /WX`.
* **Seeds use `.bin`** because `.gitignore` drops `*.obj`, `*.exe` and `*.pdb`.

## Deferred / limitations

* The fuzzers are not structure-aware and have no dictionaries; the checked-in seeds are small. The nightly job caches the
  grown corpus between runs (`actions/cache`), the cache may be evicted.
* Not fuzzed: the hook decoder, the user-hook record scanner, the bind planner and the toolchain command-line parser (outside
  the brief's list); the PDB target feeds a scratch file because `cml_pdb` maps files, so it is the slowest.
* AddressSanitizer needs the release CRT: `Debug` (`/MTd`) cannot be fuzzed; the workflow uses RelWithDebInfo.
* The reservation stage is only reachable on a module's first patch (the address space is reserved once) and arming it later is
  refused (CML5970); a new process gives another chance.
* Failure injection covers the stages of the reload pipeline. It does not cover `revert`, `restart`, the crash handler or the
  compile-on-save watcher, and it is not persistent: a broker restart forgets what is armed.
* The release packaging has to configure with `-DCML_FAULT_INJECTION=OFF` (nothing in this package does it).
