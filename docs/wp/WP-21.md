# WP-21: Hot-restart

Plan section 4.12, diagnostic ranges CML4450-4499 (agent) and CML5800-5849 (broker), harness ids CML5840-5841 (ADR-0032).
Message types `Restart` 0x0061, `RestartInfo` 0x0062, `ReenableModules` 0x0063. Control capability `restart`, command
`restart`, event `restarted`.

## The sequence (`restart {pid?, timeout_ms?, registration_timeout_ms?}`)

**Budgets.** `timeout_ms` (default 60 s) bounds everything *before* the old process is terminated: the agent's preparation, the pre-restart hooks included, and taking over the process. After `TerminateProcess` the new process has its **own** budget, `registration_timeout_ms` (default 30 s), for registering, enabling its modules, building its PDB indexes and re-applying the session's edits, so a slow preparation can never leave a killed process with no time to come back. **Reloads are held off for the whole restart**: the broker takes the reload lock (`ReloadService::lock_reloads()`) first; a restart refuses (CML5803) while a reload runs, and a reload (hotkey, compile-on-save) that arrives during a restart is refused with the existing busy diagnostic CML5304. The restart's own re-applying reload runs under that lock (`reload_locked`). The baselines are taken after the preparation, right before the old process is terminated, so every patch applied before that is in them.

1. **Prepare.** The broker sends `Restart` to the agent of the process. The agent runs the application's `CML_PRERESTART_HOOK`
   functions and answers `RestartInfo`: image path, command line, working directory and environment block (captured when the
   agent started), the values of its three standard handles, and the modules the application enabled (with their options). An
   agent that refuses, does not answer in time (for example synchronised mode and the application never reaches `SyncPoint()`),
   or answers with a failure leaves the process **untouched** (CML5804). When the broker gives up waiting it sends `RestartCancel`
   (0x0064): the agent keeps at most one restart job and drops a cancelled one before its hooks run, so hooks never run later for
   a restart nobody carries out (the job serves the newest request if several arrive). The agent checks that the launch parameters
   fit one message (exact encoded size) and that the environment was captured, **before** it runs the hooks, and refuses with an
   answer (CML4450 / CML4451) instead of dropping the connection. The broker refuses an answer without a usable environment block
   (never "restart with nothing"). If the hooks ran and a later step fails before the process is terminated (for example CML5805),
   the diagnostic says so: "N pre-restart hook(s) ran; the process was not restarted".
2. **Take over.** `ProcessHost::open(pid, std handles)` opens the old process (`PROCESS_TERMINATE | PROCESS_DUP_HANDLE |
   SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION`) and duplicates its standard handles into the broker, inheritable. Failing
   here (CML5805) also leaves the process untouched.
3. **Terminate and relaunch.** `TerminateProcess`, wait for the exit (CML5806), then `CreateProcessW(image, command line,
   environment + CML_RESTART_TOKEN, working directory)` with `STARTF_USESTDHANDLES` and a handle list that holds exactly the
   duplicated standard handles (CML5807 if it cannot start). The broker closes its copies right after.
4. **Register.** The new agent's `Hello` carries the token. The broker polls the connections for it, and notices a new process that
   exits before it registers (CML5812) or never registers within `registration_timeout_ms` (CML5808: the process is **left running**).
   Only the process the broker started counts: the Hello must carry the token **and** come from the pid `CreateProcess` returned, so a child that inherited the variable cannot be taken for the restarted process.
   `new_pid` of the result is the pid the new agent reported in its `Hello`.
5. **Modules.** After the module list arrived, the broker gives the application 300 ms to enable its modules by itself, then sends
   `ReenableModules` for those of the old process that are still missing, and waits up to 3 s for them. Modules that never show up
   are reported (warning CML5809 and `not_enabled` in the result), the restart goes on.
6. **Indexes and the session's edits** (next section), then the `restarted` event `{"event":"restarted","old_pid","new_pid"}` and the
   result `{old_pid, new_pid, modules:[...], not_enabled:[...], hooks_run, restart_ms, reapplied_files?, patched?, changed_files?,
   reapply_error?}`.

## Restart keeps the session's changes

The relaunched process runs the original binary, but the edits that had been patched into the old process are on disk. The new
process's source baseline is taken from the files as they are now, so a plain sweep would find nothing. The broker therefore
carries the old baseline over:

* `SourceBaseline::accept()` remembers, for every file, its stamp **before its first accepted patch** (`originals`).
* Before the old process is terminated the broker takes `session_snapshot()` of every module whose index is ready: the stamps as they
  stand plus the originals.
* Once the new module's index is ready, `restore()` puts the stamps of the old baseline back (a file that was saved but not yet reloaded
  stays a pending edit) and sets every original file to the hash of the original content with a size and time no file can have, so the next
  sweep reads it and compares hashes. A file the user edited back to its original content is therefore not recompiled.
* One ordinary `reload {pid: new_pid, confirm: true}` follows (same rules as any reload; it retries while a save-triggered reload
  holds the lock). `confirm` is set because the user confirmed these edits when they were first reloaded and nobody can be asked now.
* The originals travel with the new baseline, so a second restart re-applies the same files again (the `hot_restart` scenario does two).

If this reload fails the restart still succeeds (the new process runs the original code): the result has `reapply_error`, a warning
CML5810 is published and the harness step fails.

## Standard handles (design)

The new process must keep the old one's output, or a launcher loses it. The **broker** duplicates the handles **out of** the old process
(`DuplicateHandle(old, h, broker, &copy, 0, TRUE, DUPLICATE_SAME_ACCESS)`) from the three values the agent reported, so the agent
needs no handle to the broker process. `CreateProcessW` then inherits exactly those handles: `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, no other
handle of the broker leaks into the application. A handle that two of the three share is duplicated once. A file or pipe stays the same
kernel object, so the new process **appends to the same stream** (the harness reads one output file and keeps its cursor). A handle that
cannot be copied is a warning (CML5811); the new process then gets none for it.

## Console

The agent records whether the process had a console when it started (`GetConsoleProcessList`; flag `kRestartInfoHadConsole` of
`RestartInfo`). The relaunch follows it:

* the old process had **no** console: the new one is created `DETACHED_PROCESS`, so a console application does not get a window it never had;
* it had one and the broker has a console too (the harness, a terminal): the child inherits the **broker's** console (flags cannot attach a child to a different one);
* it had one and the broker has **none** (detached, e.g. started by the agent): the broker calls `AttachConsole(old_pid)` while the old process still exists, creates the child (which inherits that console), and `FreeConsole()`s again. The new process then appears in the console of the old one. If `AttachConsole` fails the child gets a console of its own (warning in the log).

Reasoning: a console cannot be handed over by `CreateProcess` flags alone, and `AttachConsole` is the only way to put a child of a console-less broker into an existing console; it is limited to that one case and undone right after, so the broker's own state is not changed when it has a console. Tested: the flag on the wire and its use by the host (portable tests), the agent's value (`unit.agent_hook`); the attach path itself only runs against a real detached broker (not in CI).

## What is restored, and what is not

Restored: image, the command line exactly as `GetCommandLineW` returned it, the working directory, the whole environment block as it
was when the agent started (plus `CML_RESTART_TOKEN`, replacing a stale one), the three standard handles, the enabled modules with their
options, the session's edits.

**Not** restored: any handle other than the standard ones, objects the old process inherited or shared (mutexes, shared memory, sockets),
the parent process (the new process is a child of the broker; a launcher waiting for the old pid sees it exit), the console title and
console modes, the current directory of other drives, environment changes the application made after the agent started (they are
not wanted: the original environment is the point), window state, the exit code of the old process (it is terminated with 0), and
debugger attachment (the IDE plugin's job, M6). The pre-restart hook is the application's chance to save what it wants to keep.

## Diagnostics

Broker (`restart_diag_ids.h`):

| id | meaning | what to do |
|---|---|---|
| 5800 | this broker cannot restart processes (no process host) | restart the application yourself |
| 5801 | bad arguments, or no `pid` given and not exactly one process connected | pass `pid` |
| 5802 | no connected process with that pid | see `status` |
| 5803 | another restart or a reload is running | `wait`, try again |
| 5804 | the agent refused or did not answer; **the process was not touched** | in synchronised mode reach `SyncPoint()`; see the agent's id |
| 5805 | the process cannot be opened for termination / handle copy; not touched | run the broker as the same user |
| 5806 | the old process could not be terminated | close it yourself |
| 5807 | the old process is gone, the new one could not be started | start the application yourself |
| 5808 | the new process did not register in time; **left running** | check it creates its agent at start-up; raise `timeout_ms` |
| 5809 | (warning) a module of the old process is not enabled in the new one | enable it from the application |
| 5810 | (warning) the session's edits could not be re-applied | fix the error and `reload` |
| 5811 | (warning) a standard handle could not be handed on | redirect to a file or pipe the application owns |
| 5812 | the new process exited before it registered | run it by hand |
| 5840, 5841 | harness: the restart step failed / the result or event differs from the scenario | |

environment too large for one message (more than 400 Ki UTF-16 units together), 4452 out of memory, 4453 a module could not be queued

## The scenario

`hot_restart` (fixture `hot_restart`, launched with `--label=kept`): value 1, edit, reload, value 2; `restart` (expecting `patched = 1`);
the `PRERESTART` line of the hook (printed by the old process, with the edited code, into the same output file); `START ... restarted=1`
and `AGENT module not enabled by the application` (the fixture does **not** enable its module when `CML_RESTART_TOKEN` is set, so the module
is enabled again only if the broker did it); `TICK n=0 value=1` (the new process starts from the original binary); `expect_module_enabled`
against the new pid; `value=2 ... restarted=1 label=kept cwd_ok=1 env_ok=1` (edit re-applied; command line, working directory and
environment survived); then a second restart that again ends in `value=2`.

## Decisions

* **The broker duplicates the std handles, the agent only reports their values.** The brief offered the reverse as an example. This needs no
  handle to the broker process in the agent, and the agent needs no `PROCESS_DUP_HANDLE` right.
* **The hello token is an optional trailing field**, not a message of its own: no ordering problem between `Hello` and a following message,
  and old frames still decode. Payload version stays 1; `agent_abi_version` is untouched.
* **Wide strings on the wire** (`u32 units` + UTF-16LE units): the environment and command line travel exactly, lone surrogates included.
* **`restarted` is opt-in** (`subscribe` with `events` naming it), like `progress`: the default set of `subscribe` is unchanged, and the
  existing tests that count it stay valid. The harness step subscribes itself.
* **The agent's list of enabled modules is authoritative** for what to enable again (it knows the options); the broker's own list is used if
  the agent reports none.
* **`new_pid` is the pid in the new agent's `Hello`**, not the one `CreateProcess` returned: they are the same for a normal program and
  differ for a launcher stub that starts the real application.
* **The old process is terminated, not asked to exit.** The plan says "terminates"; the pre-restart hook is the cooperative part.

## Deferred / limitations

* `CML_RESTART_TOKEN` stays in the new process's environment (the application reads it to know it was restarted; the plan names it for that). Review item 8 asked the agent to clear it; instead the broker accepts a registration only when token and pid match, which stops a child from being matched, and the stale token is replaced by every later restart.
* `Agent::ScheduleRestart()` (the application asking for a restart) is still `CML_STATUS_NOT_IMPLEMENTED`: the plan's section 5 lists it, the
  brief of this package asks for the control command; both `unit.agent` and `header_check` pin the current return value.
* A broker started with a short `--exit-when-idle` exits during the gap in which no agent is connected.
* Edits that were saved but not yet reloaded are carried over as pending edits. When the restart re-applies patched files, its reload
  compiles them too (they are changed files); when nothing had been patched, the restart runs no reload and they wait for the next one.
* Modules loaded lazily by the application after start-up cannot be enabled again until they are loaded (warning CML5809); the application
  enables them itself when it loads them.
* The relaunched process is a child of the broker, not of the original launcher.
* A restart does not wait for the pre-restart hooks longer than `timeout_ms`; a hook that never returns (immediate mode) blocks the agent
  thread and the restart is refused after the timeout (CML5804), the process keeps running.
* The standard handles of a process that runs without any (`NULL`) are not given a `NUL` device in the new process.
* Only the Windows broker restarts processes (`native_process_host()` is null elsewhere, the capability is not advertised).
