# WP-23: Re-execute function after crash

Plan section 4.11, the fourth action next to Continue, Leave function and Ignore (WP-20). ADR-0035 generalised the plan's
"arguments reloaded from the home space": the values come from the locations **the PDB records** for the parameters of the
faulting function, because clang-cl at `-O0` spills parameters to its own locals, not to the home space.

## What was built

* **PDB** (`core/cml_pdb`): `PdbIndex::proc_info(proc)` (it reuses the existing IPI table code, now also loading the TPI stream once, and stops reading the compiland at the end of the function) returns `ProcInfo`: `S_FRAMEPROC` (frame size, the registers locals and
  parameters are addressed from, "optimised for speed"), the direct children of the function (`S_LOCAL` + `S_DEFRANGE_*`, and
  `S_REGREL32`) with their locations and code ranges, and the parameter list from the function type (TPI/IPI streams:
  `LF_FUNC_ID`/`LF_MFUNC_ID` -> `LF_PROCEDURE`/`LF_MFUNCTION` -> `LF_ARGLIST`), each classified for the x64 convention
  (integer-class with size, float/double, or "unsupported" with the reason: by-value class, member pointer, 80-bit, ...).
  `this` is the first parameter of a non-static member function. Functions returning a class, and variadic ones, are reported as
  "parameters not known" because a hidden argument shifts the registers.
* **IPC** (`core/cml_ipc`, ADR-0035 block 0x00B0-0x00BF): `Reexecute` 0x00B0 (broker -> agent request, answered by `Reply`), and a
  new optional trailing field of `Exception`: `frames` (innermost first; `rip`, `entry_rsp`, `rsp`, `rbp`, `r13`,
  `function_start`). An `Exception` without frames is byte-identical to WP-20's. `agent_abi_version` is unchanged.
* **Agent** (`agent/src/crash`): `ExceptionGate::unwind_frames` (RtlVirtualUnwind on the agent thread, from the context the faulting
  thread stored), `compute_reexecute` / `resolve_reexecute`. The recipe: unwind to the chosen frame, check that its entry RSP is the
  one the broker saw (CML4601), check the target is executable (CML4602), read each register parameter from
  `[base register of that frame + offset]` (RSP/RBP/R13; CML4603 otherwise), then build the **entry state** of the function:
  `RSP = entry RSP` (so the return address and the caller's home space and stack arguments are where the function expects them),
  the callee-saved registers the caller had (the unwind restores them), `RIP = target`, `RCX/RDX/R8/R9` and `XMM0-3` loaded.
  The handler returns `EXCEPTION_CONTINUE_EXECUTION` with that context, exactly as Leave does. The held thread's stack is untrusted
  (the fault may be a stack smash): the handler records the thread's `NT_TIB` stack limits; every unwind step (frames report, Leave,
  Re-execute) requires an aligned RSP inside them, runs `RtlLookupFunctionEntry`/`RtlVirtualUnwind` under `__try/__except`, needs RSP to
  move up, and stops at a return address that is not executable code, keeping the frames gathered so far. The agent thread therefore
  cannot fault while unwinding. Answering a held thread claims its slot with one compare-exchange (`None` -> `Resolving`), re-validates
  id and state, computes the context while nobody else can release the slot, and publishes the answer last (the held thread keeps
  waiting while the answer is `Resolving`); a slot that was released or reused meanwhile is never given a context computed for another
  thread. Leave and Continue use the same claim. Everything runs on the agent thread;
  the handler's rules (no allocation, no lock) are unchanged.
* **Broker** (`broker/cml_core/reexecute.*`, `exception_service.*`): decides, per held thread, whether `reexecute` is offered.
  * **Frame**: the innermost frame whose function has a *newer patch version*: `hooked[entry]` (union over the process's modules)
    differs from the snapshot taken when the fault was reported. Frames above are discarded without destructors, as Leave does.
  * **"Unoptimised"** is decided from the compiland's **recorded build command** (`S_ENVBLOCK` for cl, `S_BUILDINFO` for clang-cl,
    via `PdbIndex::build_env`): the last `/O` option must be `/Od` (or `-O0`). An unknown level is *not guessed*: CML5902. The
    S_FRAMEPROC "optimised for speed" bit is NOT used (cl sets it even at /Od; CI evidence). S_COMPILE3 carries no `/O` level.
  * **Locations**: if the function has `S_LOCAL` records flagged as parameters, they are matched to the parameters by order (the
    counts must be equal; unnamed parameters have no record -> refused) and the range covering the faulting RVA is used
    (`FramePointerRelative` is relative to the `S_FRAMEPROC` parameter base register; `RegisterRelative` has its own). A
    location "in a register" is refused. Otherwise (MSVC `S_REGREL32`, no flag) parameter *i* is the record whose address, from the
    reported frame registers, equals the home slot `entry RSP + 8 + 8*i`.
  * The event `exception` carries `actions` (with `"reexecute"` only when offered) and `reasons.reexecute` ("CML59xx: ..." when
    not). When a patch is applied or reverted the broker re-evaluates the pending threads of that process and, if the verdict or
    its reason changed, publishes `{"event":"exception_updated","pid","exception_id","actions","reasons"}` (delivered to everyone
    subscribed to `exception`) and updates the pending list. A patch that replaced a function whose re-execute is refused (the
    optimised one) changes the reason ("...; a patch has replaced X, but it cannot be re-executed"), so the client hears of it.
  * An offered `reexecute` carries `notes.reexecute` (the parameters-at-the-fault and repeated-side-effects caveat) in the event and
    in the pending list. The stored body is rebuilt from the base body on every change of the offer, so a withdrawn offer leaves no
    `reexecute_function`, `reexecute_frame` or `notes` behind.
  * **Patches during evaluation.** The pending entry is registered before the (slow) evaluation; evaluations and the re-evaluations
    triggered by `patch_applied` / `patch_reverted` are serialised (`eval_mutex_`), so a patch that lands while the first evaluation runs
    is found by the re-evaluation that follows, and no `exception_updated` overtakes the `exception` event. **Remaining window:** the hook
    table is snapshotted when the broker receives `Exception`; a patch that was committed between the fault and that moment counts as
    present at the fault (the agent does not report the patch generation it saw; that would need a protocol change). Such a function is
    then not offered, with CML5900, and a later patch offers it.
  * `exception-action {"action":"reexecute"}` is refused with CML5908 (carrying the reason) while it is not offered; an agent
    refusal (CML46xx) keeps the thread held for another action.
  * Capability `reexecute`.
* **Harness**: step `expect_exception_updated` (`offers`, `lacks`, `reason`, `within_s`), the same three keys on `expect_exception`,
  `exception_action` accepts `reexecute`. Bodies in `tests/harness/src/exception_steps.cpp`.
* **Fixture `crash_reexecute`**: `step(int* p, int k, double scale)` in `step.cpp`, compiled `/Od` in every configuration (per-source
  option; the Debug `/RTC1 /JMC` are dropped for the directory so `/O2` and `/Od` TUs can coexist); `opt_step(int* p, int k)` in
  `opt.cpp`, compiled `/O2`. `main.cpp` makes one crashing call of each (`step(nullptr, 13, 2.75)`, later `opt_step(nullptr, 21)`) after
  the harness' signal and prints `TICK n= stage= result= seen_k= seen_scale= opt=`.
* **Scenario `crash_reexecute`**: crash in `step` (event lacks `reexecute`, reason CML5900) -> `fix_step.edit` -> reload ->
  `exception_updated` offers `reexecute` -> action `reexecute` -> the TICK line `result=102756 seen_k=13 seen_scale=2.750`
  (= -7 + 13 + 2750 + 100000: the new body ran with the original `int`, and the `double` came back through XMM2; `p` was null and the
  fix survived it) -> the loop goes on -> crash in `opt_step` (reason CML5901) -> `fix_opt.edit` -> `exception_updated` still without
  `reexecute` (reason mentions the optimisation) -> `reexecute` refused CML5908 -> Leave -> `opt=0`, then `opt=5xxx`.

## Diagnostics

Agent (`agent/src/crash/diag_ids.h`, CML4600-4649):

| Id | Meaning | What to do |
|---|---|---|
| CML4600 | the stack of the held thread cannot be unwound to the chosen frame | Leave or Ignore |
| CML4601 | the chosen frame was entered with another RSP than the broker saw | Leave or Ignore (the stack changed) |
| CML4602 | the replacement function address is not executable code | Leave or Ignore |
| CML4603 | a parameter's location cannot be read (unsupported base register, unreadable memory, bad size) | Leave or Ignore |
| CML4604 | the return address of the chosen frame is not executable code (damaged stack; Leave answers CML4402 for the same) | Ignore |

Broker (`broker/cml_core/include/cml/core/reexecute_diag_ids.h`, CML5900-5919); 5900-5907 appear as `reasons.reexecute`:

| Id | Meaning |
|---|---|
| CML5900 | no patch applied since the fault has replaced a function on the thread's stack |
| CML5901 | the function's compiland was built with optimisation |
| CML5902 | the recorded build command does not show that optimisation was off |
| CML5903 | the faulting frame cannot be identified (patch code, module not enabled, PDB not loaded) |
| CML5904 | the function type cannot be read or shifts the arguments (variadic, returns a class) |
| CML5905 | a register parameter is a by-value aggregate, member pointer, 80-bit float, ... |
| CML5906 | the PDB does not tell where a register parameter lives (or it is in a register / unnamed / ambiguous) |
| CML5907 | the agent reported no usable stack |
| CML5908 | `exception-action reexecute` while it is not offered |

## Tests

* `unit.reexecute` (portable): `build_recipe` on cl-shaped and clang-shaped records and every refusal; wire format of `Exception.frames`
  and `Reexecute` (incl. lying counts); `ExceptionService` against a scripted agent (events, `exception_updated`, action, refusals);
  `proc_info` on synthetic PDBs (TPI/IPI, S_REGREL32, S_LOCAL + all DEFRANGE kinds, members, classification, nesting); on Windows the
  **PDB of the fixture built by the cell's compiler**: `step` must give a complete recipe (`WP23-RECORDS` lines print the records),
  `opt_step` must be refused as optimised.
* `unit.agent_exception` (Windows, child processes): unwinding survives a damaged stack (garbage return address, RSP out of range or
  misaligned, a real frame with garbage RSP/RBP, no limits at all) with a truncated frame list, and Re-execute/Leave refuse a
  non-code return address; a resolve racing with a release of the gate; re-execute reloads `p`, `k` and a double from the home space of a hand-assembled
  stub and runs the replacement; refusals (wrong entry RSP, wrong frame, unsupported register, non-code target, unreadable
  memory) leave the thread held; `unwind_frames` invariants.
* `unit.harness`: new step keys and the checked-in scenario (it must check the exact result, not "a number").

## Limitations (proposed KNOWN_LIMITATIONS wording)

* **Re-execute repeats side effects.** Whatever the function did before the fault (writes, allocations, locks, I/O) happens again in
  the new body.
* **Re-execute reloads the parameters' values AT THE FAULT, not the values the function was called with.** They are equal only if the
  function did not assign to a parameter (or take its address and change it) before the fault: `k = k + 1; crash();` re-executes with
  the incremented `k`. Nothing detects this (the PDB does not say whether a home slot is written); only unoptimised code, which keeps
  parameters in fixed places, is eligible, and every offer carries `notes.reexecute` saying so.
* **By-value aggregates** (class/struct/union parameters in the first four positions), member pointers, 80/128-bit floats, variadic
  functions and functions returning a class by value are never offered (a hidden pointer or a copy shifts the registers).
* **Destructors and `__finally`/`__except` of the frames that are discarded do not run** (frames above the re-executed one, and the
  re-executed frame's own locals): objects with destructors in them leak or stay locked.
* **Only frames in an enabled module with a loaded PDB** can be re-executed. A thread that faulted inside *patch code* (a function
  already patched once) is not offered re-execute of that frame (patch PDBs are not indexed); an outer frame of an enabled module that
  a newer patch replaced still can be.
* **"Unoptimised" is read from the recorded build command**; a compiland whose command has no `/Od`/`-O0` is refused even if it is
  in fact unoptimised.
* Stack-passed arguments (the fifth and later) stay in the caller's frame and are re-read by the new body from there; the home space
  of the first four belongs to the caller and is rewritten by the new body's prolog.
* A frame between the fault and the re-executed one that held a lock or a handle keeps it.
* Re-executing the same frame twice in a row is just another fault, another event.
