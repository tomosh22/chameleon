# WP-50: first-reload cost and hot-restart time (R-47, R-55)

One branch (`wp/50-reload-cost`), one PR. ADR-0044, section WP-50: measure before changing anything, then fix what the
measurement shows, within the broker, the agent's timing and logging, and caching. Hook-installation semantics and the
restart protocol are not changed.

**State: round 2.** Round 1 measured (nothing that decides what is hooked, how, or how a restart proceeds was changed);
round 2 implements the approved fixes: the include-scan cache across a hot-restart, a faster include scanner, and the
background read of the module image. The hooks' first-touch cost waits for a ruling (pull request). Hook-installation
semantics and the restart protocol are unchanged.

### What proves it

* `unit.broker_core`:
  * `WP-50: the scan cache hits only for the same module stamp; a changed size, time, PDB or option misses and the new scan
    replaces it` (portable): absent, hit with another spelling of the path, a miss with the reason for each field, the entry
    replaced by a relinked module's scan, the bound of 32 entries with the least recently used dropped.
  * `WP-50: an index of the same module file takes the file lists from the scan cache; a changed module stamp scans again`
    (Windows, `test_static_lib.cpp`): cold, then warm with the same tracked files and skipped compilands, cold again after the
    module's time changes, warm after that, `off` without a cache.
  * `WP-50: a header reached again with a new stack directory resolves its includes as a full search would`: the three ways
    a new directory relates to the earlier answer; the expected sets are what the scanner of origin/main returns.
  * `WP-50: the module file is read in the background once the index is ready, the first reload uses that copy, and a drop
    releases it`, and `WP-50: a module file that cannot be read is reported by the read, not stored`.
  * The existing include-scan tests (WP-15) unchanged and green.
* Differential check (local, not committed: it compiles the origin/main scanner under other names next to the new one):
  3400 random include trees (2 to 9 directories, the same header names in several of them, quoted, angled, `../` and
  subdirectory includes, forced includes, random -I lists), every translation unit's `dependencies()` and `pch_files()`
  compared: 0 differences.
* Local timing (Linux, Release, a synthetic tree of 3400 headers in 100 directories, 26 -I directories, 40 translation units,
  file reader in memory): 63.8 s with the origin/main scanner, 1.9 s with the new one, the same 73713 dependencies.

## Round 4: the causes, measured, and their fixes (rulings of the orchestrator in advance)

Measured on e38508d (ci 46039339634, pdb-benchmark job 140643057242):

```
WP50-HOOKS side=agent request=4 batch=1 op=install hooks=275 installed=275 ... total_us=327670 ... prefetch_us=288 prefetch=api prefetch_pages=74 ... plan_us=326337 probe_us=326148 query_us=325743 queries=1100 ... stop_us=168 ... write_us=226 ...
WP50-HOOKS side=agent request=7 batch=2 ... total_us=1055 ... probe_us=174 query_us=162 queries=275 ...
WP50-PLAN module=bench_project.exe object=tu_0450.obj total_ms=110.7 ... bind_ms=98.3 export_parses=0 ... pdb_module_symbols_ms=0.0 pdb_publics_ms=0.0 pdb_buildinfo_ms=0.0
WP50-PLAN ... (reload 2) total_ms=46.4 ... bind_ms=28.1 ...; reloads 3-5: bind_ms 23.5 / 17.9 / 17.2
```

* **Hooks: VirtualQuery, confirmed.** 99.9 % of the first batch's probing is the 1100 VirtualQuery calls (296 µs each);
  the 275 targets' reads take 0.4 ms. Later batches ask 275 times for 0.16 ms in total. The prefetch (round 3) changed
  nothing and is removed (ruling 2): `PrefetchVirtualMemory`, its fallback, the dispatcher's call, the three
  `WP50-HOOKS` fields and their tests are gone.
* **Fix (ruling 1): a per-batch region cache.** During the planning of one batch (under the installer's mutex, before any
  VirtualProtect or write of the batch, nothing in the suspension window) every VirtualQuery answer is kept with the range it
  covers ([BaseAddress, BaseAddress + RegionSize): pages of equal attributes), and a question inside a kept range gets the
  kept answer. The addresses planning may ask about (each replacement, each target and the two ends of its padding) are asked
  in ascending order first, so one query of the lowest address of a region covers the rest. A failed query is not kept; the
  cache is dropped when planning ends. `queries` counts the calls made.
  Proof of identical decisions: `unit.agent_hook` `WP-50: planning with the per-batch VirtualQuery cache decides exactly as
  planning without it`: the same 60 targets (both strategies, with and without padding), a refused batch (a 3-byte function,
  an address inside another target) and a batch with a non-executable replacement, planned by an installer with the cache
  and one without (`InstallerOptions::test_no_region_cache`): batch result, every outcome's status, strategy and
  diagnostic id equal; fewer VirtualQuery calls with the cache.
* **Plan: whole-module type tables.** The first bind plan is 75-80 ms slower (98.3 against 17-28 ms) with no export
  parse and no change in the PDB's timed lazy tables (module symbols, publics, build info: all 0). What remains of cml_pdb's
  lazily built state that a bind plan touches is the type streams: the signature reader's TPI / IPI (WP-37: stream header and
  type-index offset table, then chunks) and the full TPI table that `proc_info` resolves parameter types through; both are
