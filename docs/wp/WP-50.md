# WP-50: first-reload cost and hot-restart time (R-47, R-55)

One branch (`wp/50-reload-cost`), one PR. ADR-0044, section WP-50: measure before changing anything, then fix what the
measurement shows, within the broker, the agent's timing and logging, and caching. Hook-installation semantics and the
restart protocol are not changed.

**State: round 2.** Round 1 measured (nothing that decides what is hooked, how, or how a restart proceeds was changed);
round 2 implements the approved fixes: the include-scan cache across a hot-restart, a faster include scanner, and the
background read of the module image. The hooks' first-touch cost waits for a ruling (pull request). Hook-installation
semantics and the restart protocol are unchanged.

## Round 2: the fixes (rulings of the orchestrator on round 1)

| Ruling | What | File |
|---|---|---|
| 1 (approved) | **Scan cache.** `ScanCache` (in `ReloadService`, for the session, at most 32 module files, least recently used dropped) keeps the result of the file-list and include-scan phase of an index (`ScanResult`: tracked files, header -> compilands, PCH files, unverified PCH users, skipped compilands, the scan's statistics), keyed by the module path and stamped with the module file's size and last-write time, the GUID and age of the PDB indexed, and `scan_includes`. An index whose module stamp equals the entry's takes it instead of scanning; any difference misses and the new scan replaces the entry. `WP50-SCAN-CACHE hit|miss module=... reason=same-stamp|absent|size|mtime|pdb|options|stat-failed`; `IndexStatus::scan_cache` / `WP50-INDEX ... cache=cold|warm|off` / `WP50-RESTART ... index_cache=`. Unchanged: the PDB is opened again (ADR-0017), the build-requirement audit runs, the source baseline is taken fresh. Set-option `cache_include_scan` (default true). The cached graph is the one the session's reloads of the first instance used: an index is never re-scanned after a reload either. | `module_index.{h,cpp}`, `reload_service.{h,cpp}`, `pipeline.h` |
| 1 (scanner) | **The include scanner itself.** Same results (differential check below), different bookkeeping: every path is interned once (read once, found or missing, with its directory and whether it is a system path); every (directory, include name) question is answered once per scanner (all translation units of an index share it), so a search step is a hash lookup instead of building, normalising and looking up a path; a file's set of stack directories is a bit set of directory ids (union = word operations, no string sets copied); a header reached again with directories it had not searched is expanded over those new directories only: an answer from its own directory stands (searched first), an answer from a stack directory changes only to a new stack directory whose path sorts before it, an answer from -I (or none) to the new stack directory with the smallest path that has the file. Exactly what a full search in path order gives; the unchanged answer is passed only the new directories (the file it names has the others). `Stats::resolved` counts the questions that had to build a path. | `include_scan.{h,cpp}` |
| 2 (approved) | **The module image in the background.** When a module's index becomes Ready, `ReloadService` queues a read of the module file (one worker thread, holds the state only while it reads); `ModuleState::ensure_image` serialises the background read and a reload's read (`image_mutex`), so a reload that comes during the read waits for it instead of reading a second copy (two copies of the benchmark's executable would cross the memory limit). `release_image()` when the state is dropped (disable, unload, another base, the agent's disconnect): the copy goes, and a background read that comes late stores nothing, so a WP-45 re-enable (a new state) reads afresh. `WP50-ONEOFF what=module-image image=background ...`; a reload that had to read it itself logs `image=reload`. Set-option `prefetch_module_image` (default true; the unit-test rig turns it off because its tests rewrite the module file after the enable). The pipeline no longer holds the module mutex while the file is read. | `module_state.{h,cpp}`, `reload_service.{h,cpp}`, `pipeline.cpp` |
| 3 (data first) | **Hooks: not changed.** The 229 ms are the first touch of the targets' code pages in the agent's planning (before any thread is stopped); see "Decision needed" in the pull request. | — |

### What proves it

* `unit.broker_core`:
  * `WP-50: the scan cache hits only for the same module stamp; a changed size, time, PDB or option misses and the new scan
    replaces it` (portable): absent, hit with another spelling of the path, a miss with the reason for each field, the entry
    replaced by a relinked module's scan, the bound of 32 entries with the least recently used dropped.
  * `WP-50: an index of the same module file takes the file lists from the scan cache; a changed module stamp scans again`
    (Windows, `test_static_lib.cpp`): cold, then warm with the same tracked files and skipped compilands, cold again after the
    module's time changes, warm after that, `off` without a cache.
  * `WP-50: a header reached again with a new stack directory resolves its includes as a full search would`: the three ways
    a new directory relates to the earlier answer; the expected sets are what the scanner of origin/main returns.
  * `WP-50: the module file is read in the background once the index is ready, the first reload uses that copy, and a drop
    releases it`, and `WP-50: a module file that cannot be read is reported by the read, not stored`.
  * The existing include-scan tests (WP-15) unchanged and green.
* Differential check (local, not committed: it compiles the origin/main scanner under other names next to the new one):
  3400 random include trees (2 to 9 directories, the same header names in several of them, quoted, angled, `../` and
  subdirectory includes, forced includes, random -I lists), every translation unit's `dependencies()` and `pch_files()`
  compared: 0 differences.
* Local timing (Linux, Release, a synthetic tree of 3400 headers in 100 directories, 26 -I directories, 40 translation units,
  file reader in memory): 63.8 s with the origin/main scanner, 1.9 s with the new one, the same 73713 dependencies.

## Round 3: the hooks' first touch, and the rest of the first plan

The orchestrator approved option (a) for the 229 ms of the first `InstallHooks`: the agent asks for the targets' code pages
before it plans, with every thread running.

| Piece | File | Notes |
|---|---|---|
| Prefetch | `agent/src/hook/installer.{h,cpp}` (`prefetch_code_pages`) | The pages that `plan_hook` reads (kLookBehind before each entry to kLookAhead after it), sorted, without duplicates, merged into runs, passed to `PrefetchVirtualMemory` in one call (resolved at run time from kernel32 / kernelbase). Where it is missing or fails, one byte of every page is read with ReadProcessMemory into a local (no allocation; a page that cannot be read is skipped). The page list is built first; nothing of this runs with threads suspended, and a failure is logged (info) and never an error. |
| Dispatcher | `agent/src/hook/dispatch.cpp` | At the very start of every InstallHooks with hooks, before the hook records are collected and the pre-patch hooks run (so the page-in overlaps them), and before the installer plans. No protocol change. |
| Evidence | `agent/src/hook/hook_timing.h` | `WP50-HOOKS ... prefetch_us=... prefetch=api|touch|none prefetch_pages=...` after `wait_us`. |
| Plan breakdown | `broker/cml_core/src/pipeline.cpp` | `WP50-PLAN module=... object=... total_ms=... object_ms=... image_ms=... bind_ms=... export_parses=... prove_ms=... narrow_ms=... rest_ms=... hooks_planned=...` per recompiled object, to find the first plan's remaining ~80 ms (round 1 could not attribute them: the bind planner's first queries of the module's PDB, whose lazily built tables (types, IPI) and symbol pages are touched for the first time, or export parses, are the candidates). |
| Docs | `docs/TROUBLESHOOTING.md` | the prefetch fields, `WP50-PLAN`, and the two set-options with their defaults. |

Tests: `unit.agent_hook` `WP-50: prefetch_code_pages asks for every target page once, by the API or by reading a byte of
each` (pages counted once for duplicate targets, the API path, the forced fallback reading every page, an unmapped address
skipped, an empty request); the dispatcher test checks `prefetch=api|touch` with a non-zero page count before the answer;
the line test checks the new keys and their order.
