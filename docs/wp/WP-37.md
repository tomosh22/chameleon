# WP-37: PDB type stream; static overloads and lambda-local statics (R-02, R-03, ADR-0042)

Branch `wp/37-pdb-types`. Diagnostic ranges of ADR-0042: CML1430-1459 (PDB reader; 1430-1434 used), CML3570-3599 (planner;
**none used**: the planner's new outcomes are reasons appended to the existing CML3214 / CML3207, no new id was needed).

## What the corpus had found

- **F-4 (Dear ImGui).** `imgui_internal.h` declares `static inline float ImFloor(float)` and
  `static inline ImVec2 ImFloor(const ImVec2&)`. Every translation unit that includes it has two internal-linkage functions
  with one display name; the PDB records both as `S_LPROC32 'ImFloor'`. The planner had nothing but names, refused to pair
  them by position and raised CML3214 for the whole TU.
- **Godot `SNAME`.** `([]() -> const StringName & { static StringName sname = ...; return sname; })()`: every use is a lambda
  with a function-local static `sname` and a guard `$TSS0`. The planner's scope of a function-local static was the last
  component of the enclosing function's name, here `operator()`, so every `sname` of the translation unit was a candidate for
  every other (CML3207), and call operators that share a display name (cl numbers the lambdas of every function from 1, so
  the lambdas of two overloads are both `<lambda_1>`) were ambiguous overloads (CML3214).

## What was built

### `cml_pdb`: type records (`cml/pdb/type_records.h`)

| Piece | Where | Notes |
|---|---|---|
| `TypeSource` | `type_records.h` | "a set of type records by index": `find_type`, `find_id`. Three implementations, below. |
| `function_signature()` | `src/type_records.cpp` | The ONE canonical-signature routine. Input: a type index (`LF_PROCEDURE` / `LF_MFUNCTION`) or an id index (`LF_FUNC_ID` / `LF_MFUNC_ID`). |
| TPI / IPI of a linked PDB | `src/detail/type_stream.*`, `src/index_types.cpp` | `PdbIndex::types()`, `PdbIndex::proc_signature(SymbolView)`, `type_stream_stats()`. Lazy and sparse, see below. |
| `.debug$T` of an object | `ObjectTypes`, `inspect_debug_t()` | Types and ids share one index space. Recognises a type-server reference (`LF_TYPESERVER2`) and precompiled types (`LF_PRECOMP`). |
| A compiler PDB as type server | `TypeServerPdb` | Opened for its types only (a compiler PDB has no DBI stream, so `PdbIndex` cannot open it). |
| `.debug$S` of an object | `read_object_procs()` | The procedure records (`S_GPROC32` / `S_LPROC32` and their `_ID` forms) with the offset of their code-offset field, which the caller resolves through the COFF relocations. |
| `SymbolView::type_is_id` | `types.h`, `index_symbols.cpp` | Whether a proc record was an `_ID` form (its `type_index` is then an IPI index). Stored in the spare top bit of `SymRec::kind`; the record stays 28 bytes. |

**The signature text.** `F(cc=<calling convention>,fa=<function attributes>,r=<return>,a=[<parameters>])`, for a member function
`MF(cc=..,fa=..,r=..,c=<class>,this=<type of this>,adj=<this adjustment>,a=[..])`. Types are rendered structurally:
`t<hex>` a built-in type, `P<attributes>(..)` a pointer or reference (with `;of=<class>;rep=<n>` for a pointer to member),
`M<cvu>(..)` a modifier, `A<bytes>(..)` an array, `B<len>:<pos>(..)` a bit field, nested function types as above, and classes,
structs, unions and enums by `U{<unique name>}` when the record has a unique name, else `N<leaf kind>{<name>}` (C). No type
index of a record appears in the text, so a forward reference and the definition of one class are the same, and the text of
a function is the same in the linked PDB and in an object of the same compiler. Unique names are written without the
translation unit's hash (`without_tu_discriminator`: cl's `` `a8f45668 `` after a function-local type, `?A0x<hash>@` of the
anonymous namespace), because both sides are always the records of one translation unit. Example (the fixture):
`F(cc=0,fa=0,r=U{.?AUSoVec2@@},a=[P1002C(M1(U{.?AUSoVec2@@}))])` is `SoVec2 so_floor(const SoVec2&)`.

**Lazy and sparse (decision point 1).** Opening an index reads nothing of the type streams, not even their headers. The first
lookup reads the 56-byte stream header and the *type-index offset table* of the hash stream (one `(type index, offset)` pair
for about every 8 KiB of records; link.exe, lld-link and the compiler's PDB writer all produce it). A lookup then finds the
chunk between two table entries, reads only that chunk (in place when its blocks are consecutive in the file, else a copy of
that chunk) and walks its records once. A stream without a usable table is one chunk, read whole on the first lookup (what
WP-23's `proc_info` does). The existing `IpiTable` of WP-23 / the build-info reader is untouched.

**Untrusted input (decision point 6).** Header, table and records are bounds-checked. A table that lies (unsorted, offsets
outside the records, a chunk whose record count differs from what the table promises) makes the table unusable or that chunk
"bad": its indices are not found, nothing wrong is returned. A signature is limited to 40 levels of nesting, 4096 records,
1024 arguments and 64 KiB of text, so a pointer that points at itself or an argument list that fans out ends in "unknown".
Unknown record kinds (including `LF_CLASS2` / `LF_STRUCTURE2`, whose layout is not documented) are "unknown", never guessed.

Diagnostics (all reach the user as the reason inside a CML3214 / CML3207 message; `docs/TROUBLESHOOTING.md` has the entries):

| Id | Meaning |
|---|---|
| CML1430 | the TPI / IPI stream of a PDB is missing or its header is invalid |
| CML1431 | a type record needed for a signature is malformed, missing, of an unknown kind or nested too deeply |
| CML1432 | the object's `.debug$T` is absent, not C13, empty, or refers to a compiler PDB that cannot be read |
| CML1433 | a `.debug$S` section is malformed, or a function has no procedure record |
| CML1434 | the compiler PDB an object names belongs to another compilation (GUID differs) |

### `broker/cml_core`: the planner

- `bind_types.{h,cpp}`, `ObjectSignatures`: the new side. Nothing is read before the first question. Then: the object's
  `.debug$T` decides where the types are (`debugT`: its own records; `typeserver`: the compiler PDB named by
  `LF_TYPESERVER2`, whose GUID must be the recorded one; `unreadable` otherwise), every `.debug$S` section is walked for
  procedure records, and the SECREL relocation on a record's code-offset field names the function (section and offset). The
  broker logs one line per object it had to read: `WP37-TYPES source=debugT|typeserver|unreadable object=... procs=N detail=...`.
- Pass B of the static matching (`bind_plan.cpp`):
  - **functions**: one-to-one by canonical signature (`BindSource::CompilandSignature`, `compiland-static-signature`). A member
    whose signature no old function of that name and scope has is a new function (not hooked); an old function without a
    partner is left alone. Equal signatures on either side are CML3214. If *any* signature of the group is unreadable nothing
    is paired by signature and the planner does what it did before (exact qualified name, then CML3214); the message says why.
  - **function-local statics of lambdas** (pass B0, before the layout step): the old record's lambda is identified by the
    unique name of the class of the enclosing member function (`.?AV<lambda_1>@?1??f@@YAXXZ@`), the new symbol's by its
    decorated scope: the text after `??R` of the nested function name starts with the same qualified name
    (`bind_names.h: call_operator_scope`). The comparison is a prefix test of two strings; nothing of the decorated name is
    interpreted, and no signature is read from it. (`BindSource::CompilandClosure`, `compiland-static-closure`.) The matches
    teach the section layout (old RVA minus section offset), which is what places the guard variables under clang-cl
    (it records no `$TSS0`).
- Every step is logged at trace (`bind: overloads '<name>': ...`, `bind: closure statics '<name>': ...`): both signatures,
  the pairing, "new function", "ambiguous" and the reason when types are unreadable.

### The safety rule for lambdas that ADR-0042 does not spell out

A lambda's name is a number the compiler assigns (`<lambda_2>`). clang-cl numbers the lambdas of the whole translation unit,
so the number is the lambda's identity only while the lambdas are the same as before. Local experiment (clang 18): moving one
function above another renumbered every lambda, and pairing by name alone bound `SNAME("alpha")` to the storage of
`SNAME("beta")`, an accepted reload with the wrong static. The planner therefore pairs by closure **only when the closures
that hold a static of that name are the same set in the old image and in the patch** (per enclosing function). If one was
added or removed nothing is paired, nothing is taken from the section layout either, and the statics stay CML3207 with the
reason in the message ("... are not the same as in the old image (2 there, 3 in the patch); a lambda's compiler-assigned
number is its only identity ..."). A function whose lambdas had no such static before gets new statics. What remains
undetectable is a pure reordering of two lambdas inside one function with the count unchanged (see "Limitations").

### The two guards against "nothing matched, so everything is new"

Found by the first CI run (see "What was learned"): when the two sides spell a name differently for a reason the reader does
not know, no pair matches, and "no partner means new" turns every function and static of the group into a new one without
a word. The old functions would stay unhooked and the statics would start from scratch. Two checks turn that into a refusal:

- **Overloads.** A group in which *not one* signature of the patch occurs among the old signatures is not declared new: it
  stays CML3214 ("none of the N signature(s) in the patch occurs among the M of the old image ..."). As soon as one pair
  matches, the spelling is evidently the same on both sides and the rest of the group follows ADR-0042 point 3 (no partner:
  new function).
- **Lambda statics.** Which old records belong to the lambdas of the function is established twice, independently: by the
  display name of the record's enclosing proc (`` `f'::`2'::<lambda_1>::operator() ``, lambda numbers aside) and by the
  closure class's unique name. Only when both name the same records does the planner decide anything (pair, or "new" when
  there are none); otherwise CML3207 ("... cannot be identified consistently (2 by the name of their function, 0 by their
  closure class)").

## What was learned

- **cl appends the translation unit's hash to the unique name of a function-local type.** A closure is
  `` .?AV<lambda_1>@?1??ls_step@@YAHXZ@`a8f45668 ``; the eight digits are the hash of the unit's anonymous namespace
  (`?s_constructions@?A0xa8f45668@@3HA` in the same object). The decorated name of a symbol in that lambda
  (`?sname@?1???R<lambda_1>@?1??ls_step@@YAHXZ@QEBAAEAULsName@@XZ@4U3@A`) has no such suffix, and clang-cl writes none
  (`.?AV<lambda_0>@?0??ls_step@@YAHXZ@`). The first CI run compared the names as recorded: the unit tests compile the
  edited source from a copy at another path, the hash differed (`9bfd0ef1` in the fixture's PDB, `a8f45668` in the object),
  no lambda found its partner, and the planner declared every lambda static and call operator **new** without a
  diagnostic. Two consequences: the canonical signature leaves the hash out (`without_tu_discriminator`; both sides are
  always one translation unit, where it is a constant), and "nothing matched" is no longer read as "everything is new"
  (the two guards under "What was built").
- **cl numbers the lambdas of each function from 1, clang-cl numbers the lambdas of the translation unit from 0.** In
  the fixture `ls_over(int)` and `ls_over(double)` both hold `<lambda_1>` under cl, `<lambda_3>` and `<lambda_4>` under
  clang-cl. Under cl the PDB names the call operators `` `ls_step'::`2'::<lambda_1>::operator() ``, so the lambdas of
  two overloads have one display name: that, not a hash in the name, is what made the planner raise CML3214 for
  `scene_tree.cpp`. The class in the signature (`c=U{.?AV<lambda_1>@?1??ls_over@@YAHH@Z@}` against `...YAHN@Z@`) tells
  them apart.
- **cl records the guard `$TSS0` as an `S_LDATA32` of the lambda's call operator, clang-cl records none** (as WP-07 found
  for plain functions). Under clang-cl the guards are placed by the section layout that the closure matches teach.
- **A linked PDB's TPI stream is large even for a small program and its blocks are not consecutive.** Fixture
  `static_overloads` (two 30-line translation units): 1.08 MiB of type records in 125 chunks (CRT and STL types), and
  the one chunk a reload needed was a copy (`bytes_copied=8196`): link.exe interleaves the stream's blocks with other
  streams. Reading the stream whole (what WP-23 does) would copy all of it; on Godot's 523 MB PDB that is the difference
  between a few chunks and the whole type stream in private memory.
- **The type-server path works on the first try for objects whose compiler PDB is at rest.** In `unit.bind_fixtures` the
  edited translation units are compiled `/Zi` like the fixture, and under cl every one of them took
  `WP37-TYPES source=typeserver` (the object library's compiler PDB) and paired correctly.
- **clang-cl at `/O2` splits an internal-linkage array into scalars named `name.N`**
  (`?s_last@?A0x520C9D4F@@3PAHA.0`, `.1`, `.2`), which the planner treats as compiler-generated and therefore as new data.
  The fixture's array is external for that reason. This is a hole of the WP-26c family (state of such a static is
  silently reset by a reload under clang-cl RelWithDebInfo) and is **not fixed here**; reported to the orchestrator.
- **The replay binary of `fuzz_pdb` read a destroyed string at exit** (the scratch-file cleanup was constructed before
  the path it deletes). Found by the local AddressSanitizer build of the replay; fixed (two lines).

## Limitations and what was deferred

- **A lambda's identity is its compiler-assigned number.** The planner refuses when the set of lambdas holding a static of
  that name changed, but two lambdas of one function that swap places with the count unchanged keep their numbers and
  are paired by them: `SNAME("a")` and `SNAME("b")` exchanged in the source would exchange their (already initialised)
  statics. The same has always been true for the hooks of lambdas' call operators. Detecting it needs a second identity
  (the code or the initialiser of the lambda), which is not in the type records. Proposed KNOWN_LIMITATIONS text below.
- **Adding or removing an `SNAME`-like use in a function refuses the translation unit** (CML3207 with the reason). That is
  the safe half of the point above. Under clang-cl, where lambdas are numbered per translation unit, a lambda added
  *anywhere above* shifts the numbers of every later function and refuses as well.
- **Precompiled types of a `/Z7 /Yu` object are not resolved** (`LF_PRECOMP`: the types live in the PCH object's
  `.debug$P`). The object's own records are read; a signature that needs a PCH type is unknown and its group stays
  CML3214, as ADR-0042 allows. Resolving them means finding and reading the PCH object. The default patch compile of a
  `/Zi` PCH project keeps `/Zi` (ADR-0026) and takes the type-server path, which is implemented.
- **`LF_CLASS2` / `LF_STRUCTURE2` and other record kinds without a published layout are "unknown".** None occurred in the
  fixtures or the corpus (the real-PDB test asserts that every function of fixture `basic`'s own translation units has a
  readable signature under cl and clang-cl); if one occurs, the message names the kind.
- **Same-named function-local statics in overloaded *non-lambda* functions** (`static int n;` in `f(int)` and in
  `f(double)`) are still told apart only by the section layout, else CML3207. The enclosing function's signature would
  settle it; the new side would have to map the decorated scope to a function symbol of the object. Not in ADR-0042.
- **Pass A is unchanged** (ADR-0042 point 5): one static function and one old record of that name pair without a look at
  the signature, and one lambda static with one old record of that name in any call operator pairs without a look at
  the closure. The types are now available to tighten both.
- **A group of overloads in which no signature matches is refused, not declared new** (see "The two guards"). A single
  edit that changes the signature of every overload of a set at once is therefore CML3214.
- **No new planner id** (CML3570-3599 unused) and no change to `ci.yml`.
- The fuzz seeds with type streams are synthetic (the unit tests' builders) plus the two debug sections of one
  clang-compiled object; a real linked PDB is 70 KiB at least and was not checked in.
- Not measured: the first-lookup cost on a PDB whose hash stream has no offset table (the reader then walks the whole
  stream once, as WP-23 does). link.exe, lld-link and the compiler PDB writer all write the table.
