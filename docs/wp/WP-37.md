# WP-37: PDB type stream; static overloads and lambda-local statics (R-02, R-03, ADR-0042)

Branch `wp/37-pdb-types`. Diagnostic ranges of ADR-0042: CML1430-1459 (PDB reader; 1430-1434 used), CML3570-3599 (planner;
CML3570 used, a warning). The planner's refusals are reasons appended to the existing CML3214 / CML3207.

The package went to CI three times with the Godot cell: the first two heads never reached it (pushes cancelled the run),
the third (`54c5a64`) was refused there. What that run showed, the review of PR #64 and the amendment of ADR-0042 that
followed are part of this document ("The Godot run", "After the review").

## What the corpus had found

- **F-4 (Dear ImGui).** `imgui_internal.h` declares `static inline float ImFloor(float)` and
  `static inline ImVec2 ImFloor(const ImVec2&)`. Every translation unit that includes it has two internal-linkage functions
  with one display name; the PDB records both as `S_LPROC32 'ImFloor'`. The planner had nothing but names, refused to pair
  them by position and raised CML3214 for the whole TU.
- **Godot `SNAME`.** `([]() -> const StringName & { static StringName sname = ...; return sname; })()`: every use is a lambda
  with a function-local static `sname` and a guard `$TSS0`. The planner's scope of a function-local static was the last
  component of the enclosing function's name, here `operator()`, so every `sname` of the translation unit was a candidate for
  every other (CML3207), and call operators that share a display name (cl numbers the lambdas of every function from 1, so
  the lambdas of two overloads are both `<lambda_1>`) were ambiguous overloads (CML3214).
- **Godot, two more things in the same file** (found only when the lambdas paired, corpus run 45438434773):
  - `SNAME` inside block 11 or later of a function (`SceneTree::_flush_scene_change`, `::process_timers`). cl writes the
    block of a local entity into its decorated name, one digit up to block 10 (`?1?`) and letters from 11 on (`?L@?`); the
    planner's name reader knew only the digit.
  - `SceneTree::get_argument_options()`:
    `if (p_idx == 0) { static const Vector<StringName> names = {...}; } else if (p_idx == 1) { static const Vector<StringName> names = {...}; }`.
    Two statics with one name, one type and one function, no lambda. Types cannot tell them apart, and under cl no layout
    can: cl puts every function-local static into a COMDAT section of its own
    (`?g@?1??statics_value@@YAHXZ@4UGuarded@@A ... section=18 value=0x0`, `$TSS0 ... section=19 value=0x0`, next to the
    file-scope `s_calls ... section=4 value=0x4`; fixture `statics`, cl, job 138519187366). ADR-0042 did not cover this
    shape; it was amended (below).

## What was built

### `cml_pdb`: type records (`cml/pdb/type_records.h`)

| Piece | Where | Notes |
|---|---|---|

| `function_signature()` | `src/type_records.cpp` | The ONE canonical-signature routine. Input: a type index (`LF_PROCEDURE` / `LF_MFUNCTION`) or an id index (`LF_FUNC_ID` / `LF_MFUNC_ID`). |
| TPI / IPI of a linked PDB | `src/detail/type_stream.*`, `src/index_types.cpp` | `PdbIndex::types()`, `PdbIndex::proc_signature(SymbolView)`, `type_stream_stats()`. Lazy and sparse, see below. |
| `.debug$T` of an object | `ObjectTypes`, `inspect_debug_t()` | Types and ids share one index space. Recognises a type-server reference (`LF_TYPESERVER2`) and precompiled types (`LF_PRECOMP`). |
| A compiler PDB as type server | `TypeServerPdb` | Opened for its types only (a compiler PDB has no DBI stream, so `PdbIndex` cannot open it). |
| `.debug$S` of an object | `read_object_procs()` | The procedure records (`S_GPROC32` / `S_LPROC32` and their `_ID` forms) with the offset of their code-offset field, which the caller resolves through the COFF relocations. |
| `SymbolView::type_is_id` | `types.h`, `index_symbols.cpp` | Whether a proc record was an `_ID` form (its `type_index` is then an IPI index). Stored in the spare top bit of `SymRec::kind`; the record stays 28 bytes. |

**The signature text.** `F(cc=<calling convention>,fa=<function attributes>,r=<return>,a=[<parameters>])`, for a member function
`MF(cc=..,fa=..,r=..,c=<class>,this=<type of this>,adj=<this adjustment>,a=[..])`. Types are rendered structurally:
`t<hex>` a built-in type, `P<attributes>(..)` a pointer or reference (with `;of=<class>;rep=<n>` for a pointer to member),
`M<cvu>(..)` a modifier, `A<bytes>(..)` an array, `B<len>:<pos>(..)` a bit field, nested function types as above, and classes,
structs, unions and enums by `U{<unique name>}` when the record has a unique name, else `N<leaf kind>{<name>}` (C). No type
index of a record appears in the text, so a forward reference and the definition of one class are the same, and the text of
a function is the same in the linked PDB and in an object of the same compiler. Unique names are written without the
translation unit's hash (`without_tu_discriminator`: cl's `` `a8f45668 `` after a function-local type, `?A0x<hash>@` of the
anonymous namespace), because both sides are always the records of one translation unit. Example (the fixture):
`F(cc=0,fa=0,r=U{.?AUSoVec2@@},a=[P1002C(M1(U{.?AUSoVec2@@}))])` is `SoVec2 so_floor(const SoVec2&)`.

**Lazy and sparse (decision point 1).** Opening an index reads nothing of the type streams, not even their headers. The first
lookup reads the 56-byte stream header and the *type-index offset table* of the hash stream (one `(type index, offset)` pair
for about every 8 KiB of records; link.exe, lld-link and the compiler's PDB writer all produce it). A lookup then finds the
chunk between two table entries, reads only that chunk (in place when its blocks are consecutive in the file, else a copy of
that chunk) and walks its records once. A stream without a usable table is one chunk, read whole on the first lookup (what
WP-23's `proc_info` does). The existing `IpiTable` of WP-23 / the build-info reader is untouched.

**Untrusted input (decision point 6).** Header, table and records are bounds-checked. A table that lies (unsorted, offsets
outside the records, a chunk whose record count differs from what the table promises) makes the table unusable or that chunk
"bad": its indices are not found, nothing wrong is returned. A signature is limited to 40 levels of nesting, 4096 records,
1024 arguments and 64 KiB of text, so a pointer that points at itself or an argument list that fans out ends in "unknown".
Unknown record kinds (including `LF_CLASS2` / `LF_STRUCTURE2`, whose layout is not documented) are "unknown", never guessed.

Diagnostics (all reach the user as the reason inside a CML3214 / CML3207 message; `docs/TROUBLESHOOTING.md` has the entries):

| Id | Meaning |
|---|---|
| CML1430 | the TPI / IPI stream of a PDB is missing or its header is invalid |
| CML1431 | a type record needed for a signature is malformed, missing, of an unknown kind or nested too deeply |
| CML1432 | the object's `.debug$T` is absent, not C13, empty, or refers to a compiler PDB that cannot be read |
| CML1433 | a `.debug$S` section is malformed, or a function has no procedure record |

### `broker/cml_core`: the planner

- `bind_types.{h,cpp}`, `ObjectSignatures`: the new side. Nothing is read before the first question. Then: the object's
  `.debug$T` decides where the types are (`debugT`: its own records; `typeserver`: the compiler PDB named by
  `LF_TYPESERVER2`, whose GUID must be the recorded one; `unreadable` otherwise), every `.debug$S` section is walked for
  procedure records, and the SECREL relocation on a record's code-offset field names the function (section and offset). The
  broker logs one line per object it had to read: `WP37-TYPES source=debugT|typeserver|unreadable object=... procs=N detail=...`.
- Pass B of the static matching (`bind_plan.cpp`):
  - **functions**: one-to-one by canonical signature (`BindSource::CompilandSignature`, `compiland-static-signature`). A member
    whose signature no old function of that name and scope has is a new function (not hooked); an old function without a
    partner is left alone. Equal signatures on either side are CML3214. If *any* signature of the group is unreadable nothing
    is paired by signature and the planner does what it did before (exact qualified name, then CML3214); the message says why.
  - **function-local statics of lambdas** (pass B0, before the layout step): the old record's lambda is identified by the
    unique name of the class of the enclosing member function (`.?AV<lambda_1>@?1??f@@YAXXZ@`), the new symbol's by its
    decorated scope: the text after `??R` of the nested function name starts with the same qualified name
    (`bind_names.h: call_operator_scope`). The comparison is a prefix test of two strings; nothing of the decorated name is
    interpreted, and no signature is read from it. (`BindSource::CompilandClosure`, `compiland-static-closure`.) The matches
    teach the section layout (old RVA minus section offset), which is what places the guard variables under clang-cl
    (it records no `$TSS0`).
  - **several statics of one name in one function** (pass B, step 4, after the layout step; ADR-0042 as amended after
    the Godot run and detailed after the second and third review). It is the fallback for statics the layout has no
    opinion on, which is cl's case (a COMDAT section per function-local static, so no layout at all). Where the known
    layout of a section (clang-cl: the statics share a section and other matched statics agree on old RVA minus
    offset) **predicts an old record of the group** for a static of the function, the existing layout step has decided
    and wins: what it placed stays (`compiland-static-rva`, no warning), and no static of that function and name is
    paired by place (CML3207 for what is left: "the layout of object section N places other statics named 'names' of
    'f' and no old one at its offset; the layout decides ...", or "... puts it on the old record at rva X, which another
    static of the patch was already paired with"). Where the layout predicts nothing for any of them (no layout, or a
    known one that points at no old record of the group, as after an unrelated static was added in front of them),
    they are paired by place. A pairing by place never teaches, contradicts or drops a section layout. And it is made
    only if every **guard variable** of the blocks these statics are declared in is already bound to its old record
    (cl records guards; clang-cl does not): a guard without a record could only come from a section layout, which here
    is unknown or does not describe these statics, so the patch would get a fresh guard (CML3211) and construct the
    bound old object a second time. That is refused (CML3207, "the guard variable 'f::$TSS0' (...) of static 1 of 2
    has no record in the old image ..."), as the whole shape was before WP-37. Statics without a function scope are
    not offered to this step. The rule itself: the
    k-th data record of that name in the old procedure is paired with the k-th in the patch object's procedure
    (`BindSource::CompilandProcedure`, `compiland-static-procedure`) only when (a) both sides have the same number of
    them, (b) the canonical types of every pair are equal, (c) every pair sits in the same blocks: the index of each
    enclosing `S_BLOCK32` among its parent's blocks, read by the same code from the PDB's module stream
    (`PdbIndex::proc_statics`) and from the object's `.debug$S` (`ObjectProc::statics`); and the function itself is
    matched to its old version (a static function: the record it was bridged to; an external one: the procedure at
    the address of its public symbol). An earlier step that paired one of them differently also refuses. Anything else
    stays CML3207 with what differs
    ("... the function declares 3 of them in the patch and 2 in the old image", "... static 2 of 2 has another type ...",
    "... is declared in another block than in the old image (block path 1 there, 0.0 in the patch)"). A pairing of
    several is never silent: **CML3570** (warning) on every such reload, "Function-local statics 'names' of
    'SceneTree::get_argument_options' (2) are matched by their order in the function; if you reordered or replaced blocks
    that declare them, their values may be exchanged." One static of the name in the function needs no order and gets
    no warning: its function is its identity (the statics of two overloads `f(int)` / `f(float)`, which share the
    display name `f::n`, now pair too). With the warning the broker logs `WP37-ORDER function=... statics=... count=N
    warning=CML3570`, which cmltest prints after the reload (the evidence line of the cl cells).
  - **thread-local statics**: a function-local `thread_local` paired by its closure or by its function is accepted by
    the TLS invariant like one paired by name (`CompilandStatic`): all three sources are the compiland's own
    `S_LTHREAD32` records, and both steps only ever see candidates of the member's storage kind.
- Every step is logged at trace (`bind: overloads '<name>': ...`, `bind: closure statics '<name>': ...`,
  `bind: statics '<name>' of '<function>': record 1 of 2 (block path 0, type M1(U{...})) ... paired ...`): both
  signatures, the pairing, "new function", "ambiguous" and the reason when types are unreadable.
- The name reader (`bind_names.cpp`, WP-07) reads a function scope whose block number is written in letters
  (`function_scope_length`: `?L@?`, `?BA@?`), in `display_name`, `enclosing_function`, `is_tu_private_name` and
  `call_operator_scope`.

### The safety rule for lambdas that ADR-0042 does not spell out

A lambda's name is a number the compiler assigns (`<lambda_2>`). clang-cl numbers the lambdas of the whole translation unit,
so the number is the lambda's identity only while the lambdas are the same as before. Local experiment (clang 18): moving one
function above another renumbered every lambda, and pairing by name alone bound `SNAME("alpha")` to the storage of
`SNAME("beta")`, an accepted reload with the wrong static. The planner therefore pairs by closure **only when the closures
that hold a static of that name are the same set in the old image and in the patch** (per enclosing function). If one was
added or removed nothing is paired, nothing is taken from the section layout either, and the statics stay CML3207 with the
reason in the message ("... are not the same as in the old image (2 there, 3 in the patch); a lambda's compiler-assigned
number is its only identity ..."). A function whose lambdas had no such static before gets new statics. What remains
undetectable is a pure reordering of two lambdas inside one function with the count unchanged (see "Limitations").

The same rule holds for the **call operators** (review of PR #64, finding 3). The class in a call operator's signature is
the closure, so pairing by signature is pairing by lambda number: insert an `int()` lambda in front of another in
`ls_over(int)` and cl makes the new one `<lambda_1>`; the old `<lambda_1>` would be hooked to the new, unrelated body
(another capture layout behind a stored `std::function`). The call operators of a function pair only when the set of
its closures is the same on both sides; otherwise CML3214 ("the lambdas of the enclosing function are not the same as
in the old image (1 call operator(s) there, 2 in the patch) ..."). When the types are unreadable and the planner falls
back to exact names, lambdas pair by name only if the names of the patch are exactly the names of the old image.

### The two guards against "nothing matched, so everything is new"

Found by the first CI run (see "What was learned"): when the two sides spell a name differently for a reason the reader does
not know, no pair matches, and "no partner means new" turns every function and static of the group into a new one without
a word. The old functions would stay unhooked and the statics would start from scratch. Two checks turn that into a refusal:

- **Overloads.** A group in which *not one* signature of the patch occurs among the old signatures is not declared new: it
  stays CML3214 ("none of the N signature(s) in the patch occurs among the M of the old image ..."). As soon as one pair
  matches, the spelling is evidently the same on both sides and the rest of the group follows ADR-0042 point 3 (no partner:
  new function).
- **Lambda statics.** Which old records belong to lambdas of a function of that *name* is established twice,
  independently: by the display name of the record's enclosing proc (`` `f'::`2'::<lambda_1>::operator() ``, lambda
  numbers aside) and by the closure class's unique name, read as the class of a call operator
  (`display_name("??R" + closure)`). A record the names put there and the closure classes do not is spelled in a way
  the reader does not know: CML3207 ("... cannot be identified consistently (2 by the name of their function, 0 by
  their closure class)"). The other direction is accepted: a closure whose unique name is exactly the decorated scope
  of a symbol identifies its record however the procedure's display name is spelled. (Until the Godot run the two had
  to be equal, and the comparison mixed two things, the function's name on one side and its full decorated spelling on
  the other; that made the lambdas of another overload a contradiction, review finding 2. Now: names are compared with
  names, and the pairing itself uses the full decorated function.) When functions of that name have such statics in
  their lambdas but none of them is a function of the patch (same name, other parameter list), nothing is declared new
  either: a lambda that is new in an overload cannot be told from one whose function changed.

## What was learned

- **cl appends the translation unit's hash to the unique name of a function-local type.** A closure is
  `` .?AV<lambda_1>@?1??ls_step@@YAHXZ@`a8f45668 ``; the eight digits are the hash of the unit's anonymous namespace
  (`?s_constructions@?A0xa8f45668@@3HA` in the same object). The decorated name of a symbol in that lambda
  (`?sname@?1???R<lambda_1>@?1??ls_step@@YAHXZ@QEBAAEAULsName@@XZ@4U3@A`) has no such suffix, and clang-cl writes none
  (`.?AV<lambda_0>@?0??ls_step@@YAHXZ@`). The first CI run compared the names as recorded: the unit tests compile the
  edited source from a copy at another path, the hash differed (`9bfd0ef1` in the fixture's PDB, `a8f45668` in the object),
  no lambda found its partner, and the planner declared every lambda static and call operator **new** without a
  diagnostic. Two consequences: the canonical signature leaves the hash out (`without_tu_discriminator`; both sides are
  always one translation unit, where it is a constant), and "nothing matched" is no longer read as "everything is new"
  (the two guards under "What was built").
- **cl numbers the lambdas of each function from 1, clang-cl numbers the lambdas of the translation unit from 0.** In
  the fixture `ls_over(int)` and `ls_over(double)` both hold `<lambda_1>` under cl, `<lambda_3>` and `<lambda_4>` under
  clang-cl. Under cl the PDB names the call operators `` `ls_step'::`2'::<lambda_1>::operator() ``, so the lambdas of
  two overloads have one display name: that, not a hash in the name, is what made the planner raise CML3214 for
  `scene_tree.cpp`. The class in the signature (`c=U{.?AV<lambda_1>@?1??ls_over@@YAHH@Z@}` against `...YAHN@Z@`) tells
  them apart.
- **cl records the guard `$TSS0` as an `S_LDATA32` of the lambda's call operator, clang-cl records none** (as WP-07 found
  for plain functions). Under clang-cl the guards are placed by the section layout that the closure matches teach.
- **cl puts every function-local static into a COMDAT section of its own**, also in a function that is not inline
  (`section=18 value=0x0` and `section=19 value=0x0` for `g` and `$TSS0` of `statics_value`; every lambda static of
  fixture `lambda_statics` likewise, sections 47 to 56). The planner's layout step and the "closure matches teach the
  layout" above therefore do nothing under cl: they are clang-cl mechanisms. Under cl a function-local static is
  identified by its name and scope or not at all, which is why the two `names` of Godot needed their own rule.
- **cl writes the block number of a local entity in letters from block 11 on** (`?L@?`, `?N@?`), and it counts far more
  than braces: the `SNAME` of `_flush_scene_change` is four braces deep and in block 11. The name reader had been run
  only on fixtures with a handful of blocks.
- **cl quotes a local scope around the whole name of its function**: the funclet of a lambda is
  ``` ``ls_over'::`2'::<lambda_1>::operator()'::`1'::dtor$0 ``` (cl Debug, job 138519187232). So a lambda in a function
  of an anonymous namespace is presumably ``` ``anonymous namespace'::f'::`2'::<lambda_1>::operator() ```; the unit test
  for review finding 1 uses that spelling, clang-cl's was confirmed locally with clang 18 and lld
  (`` `anonymous namespace'::anon_pair::<lambda_0>::operator() ``, closure `.?AV<lambda_0>@?0??anon_pair@?A0x9428A4E1@@YAXXZ@`,
  paired by closure), and cl's is printed by every cl cell as `LOCAL-OTHER lambda_statics ...` without being a gate:
  `anon.cpp` is not edited by any test. If cl spells it differently the lambdas of such a function are refused
  (CML3207), not mispaired.
- **A linked PDB's TPI stream is large even for a small program and its blocks are not consecutive.** Fixture
  `static_overloads` (two 30-line translation units): 1.08 MiB of type records in 125 chunks (CRT and STL types), and
  the one chunk a reload needed was a copy (`bytes_copied=8196`): link.exe interleaves the stream's blocks with other
  streams. Reading the stream whole (what WP-23 does) would copy all of it; on Godot's 523 MB PDB that is the difference
  between a few chunks and the whole type stream in private memory.
- **The type-server path works on the first try for objects whose compiler PDB is at rest.** In `unit.bind_fixtures` the
  edited translation units are compiled `/Zi` like the fixture, and under cl every one of them took
  `WP37-TYPES source=typeserver` (the object library's compiler PDB) and paired correctly.
- **clang-cl at `/O2` splits an internal-linkage array into scalars named `name.N`**
  (`?s_last@?A0x520C9D4F@@3PAHA.0`, `.1`, `.2`), which the planner treats as compiler-generated and therefore as new data.
  The fixture's array is external for that reason. This is a hole of the WP-26c family (state of such a static is
  silently reset by a reload under clang-cl RelWithDebInfo) and is **not fixed here**; reported to the orchestrator.
- **The replay binary of `fuzz_pdb` read a destroyed string at exit** (the scratch-file cleanup was constructed before
  the path it deletes). Found by the local AddressSanitizer build of the replay; fixed (two lines).

## Found, not fixed

Five wrong or silent outcomes and one safe but unnecessary refusal that exist on `main` and are not this package's to
fix (ADR-0042 point 5, or outside it). Each with the smallest program that shows it. The fifth was found while this
package's fixture was tried at `-O2` with a local clang; it is the most serious of them.

1. **A new file-scope static function `f` is hooked onto an existing `X::f` of the same translation unit** (wrong pairing).

   ```cpp
   struct Foo { static int helper(int v); };
   int Foo::helper(int v) { return v + 1; }
   // the edit adds:
   static int helper(int v) { return v * 2; }
   int use(int v) { return helper(v); }
   ```

   `static_candidates` falls back to "every proc whose last name component is `helper` and that is not in a lambda"
   when no record has the exact display name, and pass A pairs one new function with one such record. Probed with a
   temporary unit test on this branch (old compiland: `S_GPROC32 Foo::helper` with its public; patch object: static
   `?helper@@YAHH@Z`): decision `patch-hooked`, "matched record 'Foo::helper' at rva 0x1060 (compiland-static)". Every
   caller of `Foo::helper` then runs the new static function. A candidate that has a public symbol with another
   decorated name can never be the old version of a static function; `publics_at_rva` settles it without types.

2. **clang-cl at `/O2` splits an internal-linkage aggregate; a reload resets it** (silent state loss).

   ```cpp
   namespace { int s_last[3] = {0, 0, 0}; }
   int step() { s_last[0] += 1; s_last[1] += 2; s_last[2] += 3; return s_last[0] + s_last[1] + s_last[2]; }
   ```

   clang-cl RelWithDebInfo names the pieces `?s_last@?A0x520C9D4F@@3PAHA.0`, `.1`, `.2`; the planner takes such names for
   compiler-generated data and gives the patch fresh copies (`-> patch-new-data`, first CI run of fixture
   `lambda_statics`, job 138501033988 of run 45410038930). The counters restart at their initial values after any
   reload of the file, without a diagnostic. (Fix: bind `name.N` to the old pieces when the old object has the same
   pieces, else refuse like CML3500.)

3. **A clang-cl guard variable can be placed on an unrelated old address** (wrong pairing, pass C).

   ```cpp
   static int s_a = 1;                          // old and new
   int f() { static int n = compute(); return n + s_a; }   // the edit adds this function-local static
   ```

   clang-cl records no guard, so pass C places a guard at "old RVA = section offset + the delta every matched static
   of the section agrees on", provided the address belongs to this compiland. A guard that is new (its static was just
   added) has no old address; if the delta happens to map its offset onto other data of the compiland, the guard is
   bound there and the static's initialisation is skipped or repeated according to whatever that memory holds. WP-07
   documented the inference; it has no check that the old image had a guard at that address. (WP-37 only keeps the
   statics it refuses out of this step.)

4. **Two lambdas of one function that swap places keep their numbers and exchange their statics** (also their hooks).

   ```cpp
   void use() { emit(SNAME("alpha")); emit(SNAME("beta")); }
   // the edit swaps the two calls: SNAME("beta") is now <lambda_1> and is paired with the storage of "alpha",
   // which is already initialised, so it yields "alpha".
   ```

   The compiler's number is the only identity a lambda has in the debug records. The same-set rule catches every edit
   that changes how many lambdas hold such a static (and under clang-cl, which numbers per translation unit, a lambda
   added anywhere above), but not a swap. The same is true of two same-named statics in two blocks of a function since
   the amendment, where at least CML3570 says so on every reload; for lambdas nothing is printed. (Fix: a second
   identity, for example the code of the lambda or of the static's initialiser, compared before pairing.)

5. **clang-cl with inlining (`/O2`, i.e. `/Ob2`): the static of an inlined lambda becomes new while its guard is bound to
   the old one** (an accepted reload with wrong state).

   ```cpp
   struct Name { int id; int hits; };
   Name make(int id);
   int step() { Name& n = ([]() -> Name& { static Name sname = make(7); return sname; })(); return n.id + ++n.hits; }
   ```

   When clang inlines the call operator it emits no procedure for it and records `sname` as an `S_LDATA32` directly in
   `step` (seen with `llvm-pdbutil dump --symbols`: `S_GPROC32 ls_step`, three `S_LDATA32 sname`, then the inline
   sites). The patch object's symbol is still `?sname@?1???R<lambda_0>@?0??step@@YAHXZ@...`, a static of an
   `operator()`; the planner looks for a record named `sname` in a procedure called `operator()`, finds none
   ("static data 'sname' has no record in compiland 0: new") and gives the patch a new, zero-filled `sname`. Pass C then
   binds the guard `$TSS0` to the old guard by the section layout, and the old guard says "initialised". The patched
   `step()` would then use an object that was never constructed (the plan was read, the patch was not run: this host
   has no Windows). Local evidence (clang 18, lld, this
   package's fixture `lambda_statics` at `-O2`): all seven `sname` `-> patch-new-data`, all seven `$TSS0`
   `-> bind-old-data source=compiland-layout`. The matrix does not hit it: CMake's RelWithDebInfo is `/O2 /Ob1`, where
   clang-cl does not inline the call operators (they are hooked in the clang-cl RelWithDebInfo cells), and Debug does not
   inline. Not changed here: the candidate search and pass C are WP-07's, outside ADR-0042. (Two fixes, either is enough
   to stop the wrong state: a guard is never placed by layout when the static of the same decorated scope was decided
   "new" in this plan, which also closes finding 3; and the statics of an inlined lambda are looked up in the procedure
   of the enclosing function, where the by-place rule of this package can pair them.)

6. **A thread-local guard that pass C places from the section layout is refused** (CML3102; safe, but the reload fails).

   ```cpp
   int next() { static thread_local Counter c = make_counter(); return ++c.n; }   // clang-cl
   ```

   clang-cl records no guard variable, so the guard of `c` (thread-local itself) is placed by pass C with the source
   `compiland-layout`. The TLS invariant of the planner accepts a SECREL only to a thread-local whose source is a
   thread-local record (`PdbGlobal`, `CompilandStatic`, `CompilandRva`, and since this package `CompilandClosure` /
   `CompilandProcedure`); `CompilandLayout` is not among them, so the reference to the guard raises CML3102. Reported by
   the second review of PR #64; read from the code, not reproduced with a compiler here. Left as it is on purpose: an
   address inferred from a layout is weaker evidence than a record, and widening the invariant is not this package.

## Limitations and what was deferred

- **A lambda's identity is its compiler-assigned number.** The planner refuses when the set of lambdas holding a static of
  that name changed, but two lambdas of one function that swap places with the count unchanged keep their numbers and
  are paired by them: `SNAME("a")` and `SNAME("b")` exchanged in the source would exchange their (already initialised)
  statics. The same has always been true for the hooks of lambdas' call operators. Detecting it needs a second identity
  (the code or the initialiser of the lambda), which is not in the type records. Proposed KNOWN_LIMITATIONS text below.
- **Adding or removing an `SNAME`-like use in a function refuses the translation unit** (CML3207 with the reason). That is
  the safe half of the point above. Under clang-cl, where lambdas are numbered per translation unit, a lambda added
  *anywhere above* shifts the numbers of every later function and refuses as well.
- **Precompiled types of a `/Z7 /Yu` object are not resolved** (`LF_PRECOMP`: the types live in the PCH object's
  `.debug$P`). The object's own records are read; a signature that needs a PCH type is unknown and its group stays
  CML3214, as ADR-0042 allows. Resolving them means finding and reading the PCH object. The default patch compile of a
  `/Zi` PCH project keeps `/Zi` (ADR-0026) and takes the type-server path, which is implemented.
- **`LF_CLASS2` / `LF_STRUCTURE2` and other record kinds without a published layout are "unknown".** None occurred in the
  fixtures or the corpus (the real-PDB test asserts that every function of fixture `basic`'s own translation units has a
  readable signature under cl and clang-cl); if one occurs, the message names the kind.
- **Statics matched by their place in a function can be exchanged by an edit** that swaps the blocks declaring them, or
  removes one and adds another of the same type in the same position. Count, type and block path are checked; CML3570
  warns on every reload that pairs this way. (ADR-0042 as amended.) Where the section layout places them instead
  (clang-cl), the same edit has the same effect and nothing warns: the layout step is WP-07's and positional too.
- **Under cl the record of a static in a function with internal linkage carries a qualified name**
  (``` ``anon_pair'::`2'::<lambda_1>::operator()'::`2'::sname ``` for the fixture's anonymous-namespace function; an
  external function's is the plain `sname`). The candidate search and the closure pairing take the last component and
  are not affected; the by-place rule compares plain names, so two same-named statics in two blocks of a `static` or
  anonymous-namespace function are refused under cl (CML3207, "declares 0 of them"), not paired. Seen in the logs of
  `c582fef`, not changed in this package.
- **Under clang-cl a guarded static cannot be paired by place** (its guard has no record): two same-named
  `static const T x = f();` in two blocks reload only where the section layout places them, which is the common case
  (any other matched static of the section teaches it). Without a layout, or after the statics moved in their
  section, the function is refused (CML3207), as on `main`. Statics without a guard are paired by place there too.
- **Statics of lambdas paired by closure under clang-cl teach the section layout, and their guards are placed from
  it.** If those statics contradict each other about the layout (the lambdas were reordered), the layout is dropped
  and the guards get the existing warning CML3211 ("fresh guard", WP-07's documented behaviour for any static matched
  by name whose guard is not found): the statics are constructed again. Not changed here; the by-place step refuses
  in the corresponding situation, the closure step warns.
- **The place of a static inside an inlined call is not followed** (`S_INLINESITE`): such a record refuses the function's
  statics of that name (CML3207). Under cl function-local statics of an inlined function are COMDAT data of that
  function and are not affected; clang-cl at `/O2` can record a static local of an inlined function inside the caller.
- **A lambda nested in a lambda**: cl's display name quotes each level (` ``f'::`2'::<lambda_1>::operator()'::`2'::... `),
  which `normalized_pdb_name` does not read. The call operator of the inner lambda then has no exact name; its statics
  still pair by closure (an exact closure is accepted whatever the name), but if the names put a record in a lambda the
  closure does not confirm, CML3207. Not tested with a compiler.
- **Pass A is unchanged** (ADR-0042 point 5): one static function and one old record of that name pair without a look at
  the signature, and one lambda static with one old record of that name in any call operator pairs without a look at
  the closure. The types are now available to tighten both.
- **A group of overloads in which no signature matches is refused, not declared new** (see "The two guards"). A single
  edit that changes the signature of every overload of a set at once is therefore CML3214.
- **One planner id**, CML3570 (warning). No change to `ci.yml`.
- The fuzz seeds with type streams are synthetic (the unit tests' builders) plus the two debug sections of one
  clang-compiled object; a real linked PDB is 70 KiB at least and was not checked in.
- Not measured: the first-lookup cost on a PDB whose hash stream has no offset table (the reader then walks the whole
  stream once, as WP-23 does). link.exe, lld-link and the compiler PDB writer all write the table.
