# WP-13: Test harness cmltest

## What was built

- **`tests/harness`**: `cmltest.exe` (Windows) on top of `cmltest_core` (portable: TOML-subset reader, scenario model,
  regex engine, unified-diff applier, report/JUnit writer). See `tests/harness/README.md` for options, the
  scenario format and the TOML/regex subsets. Scenario: `tests/harness/scenarios/basic.toml`.
- **Control protocol** (this document, below): JSON codec + line transport + client in `core/cml_ipc`
  (`json.h`, `control.h`, `control_ids.h`), minimal server in `broker/cml_core` (`control_server.*`,
  `process_registry.*`), `cml_broker --headless --control-pipe NAME`.
- **CI**: after the existing steps, `cmltest` runs the `basic` scenario with `--generator ninja` in all 8 cells, once more with
  `--generator msbuild` on msvc/Debug per OS; JUnit, logs and dumps are uploaded as `cmltest-<os>-<compiler>-<config>`.

## How to run

`build\bin\cmltest.exe --scenario tests\harness\scenarios\basic.toml --build-dir build --generator ninja --config Debug --cxx cl --junit out.xml`

## What `basic` proves now

Passed: build from a scratch copy, launch (broker + control pipe + fixture with agent), `expect_stdout value=1`,
`expect_module_enabled` (via `status`), `edit` of the copy. Then `reload` and the following `expect_stdout value=2`
are **skipped** with `capability 'reload' not provided by broker (lands in WP-12)`; the run is PARTIAL
(`PARTIAL: 2 steps skipped for missing broker capabilities`, JUnit `<skipped/>`). WP-12 must add
`--require-all-capabilities` to the CI steps.

## Control protocol

**Transport.** Named pipe `\\.\pipe\cml_control_<logon-session SID>`; override with `CML_CONTROL_PIPE` or
`cml_broker --control-pipe NAME`. Same pipe code and DACL as the agent pipe (current user only, remote clients rejected,
`FILE_FLAG_FIRST_PIPE_INSTANCE`, clients verify the server runs as the same user, CML5209). In WP-13 the broker serves
it only when `--control-pipe` or `CML_CONTROL_PIPE` is given (several headless brokers run side by side in tests);
WP-12 should serve the default name always.

**Framing.** UTF-8 JSON objects, one per line (`\n`, a trailing `\r` is tolerated, blank lines ignored). Max 1 MiB per
line. JSON limits: depth 32, string 256 KiB, 65536 elements per container, no duplicate keys, no lone surrogates.
Unknown members are ignored (forward compatible). A connection carries one request at a time per client;
requests are answered in order.

```
request   {"id":N,"cmd":"<name>","args":{...}}              id: any integer; cmd: [a-z0-9_-]{1,64}; args optional object
response  {"id":N,"ok":true,"result":{...}}
          {"id":N,"ok":false,"diag":{"id":"CMLnnnn","message":"...","action":"..."}}     id is null if the request id was unreadable
event     {"event":"<name>", ...}                            unsolicited, may appear between any two lines
```

**Capabilities.** `status` returns the exact list of what the broker provides; clients check before using a command
(`cmltest` does). Names: `status`, `reload`, `wait`, `set-option`, `subscribe`, `diag-events`. A command whose capability
is missing is answered with `CML5402`. New capabilities and new result members are backward compatible.

**Commands.**

| cmd | args | result | capability |
|---|---|---|---|
| `status` | none | `{"version":"0.1.0","capabilities":["status"],"processes":[{"pid":N,"modules":[{"path":"C:\\..\\x.exe","enabled":true}]}]}`; `"modules_truncated":true` if a process had more than 2000 modules (enabled first) | `status` (WP-13) |
| `reload` | `{"pid"?:N,"timeout_ms"?:N}` (WP-12 may refine) | `{"generation":N,...}`; returns when the patch is live or failed | `reload` (WP-12) |
| `wait` | `{"for":"idle","timeout_ms":N}` (WP-12 to define) | `{}` | `wait` (WP-12) |
| `set-option` | `{"name":s,"value":s\|n\|b}` | `{"name":s,"previous":v}` | `set-option` (WP-12) |
| `subscribe` | `{"events"?:["diag","patch_applied","log"]}` | `{"events":[...]}`; events then arrive on this connection | `subscribe` (WP-12) |

**Events (WP-12).** `{"event":"diag","id":"CML3101","message":..,"action":..,"pid"?:N}` (advertised by
`diag-events`), `{"event":"patch_applied","pid":N,"module":s,"generation":N}`, `{"event":"log","level":s,"message":s}`.

**Errors.** Malformed JSON (`CML5400`) and invalid requests (`CML5401`) get an error response and the connection stays
usable. An over-long line (`CML5403`) gets an error response and the connection is closed.

## Learned

- `std::regex` aborts on a bad pattern under the repo-wide `_HAS_EXCEPTIONS=0`; a small own engine (explicit stack, step budget) replaced it.
- The portable parts (JSON, TOML, regex, diff, report) and, with mingw-w64 + wine, the pipe tests and even a full
  `cmltest` run with a prebuilt fixture were exercised before CI; wine does not enforce `FILE_FLAG_FIRST_PIPE_INSTANCE`
  (one pipe test fails there only), and `fs::copy(recursive)` into an existing directory failed under that runtime, so
  copying is a plain loop. This is not a substitute for the CI results below.
- A diag event carries the diagnostic's `id`; events are therefore recognised by their `event` member only.

## Deferred

- `reload`, `wait`, `set-option`, `subscribe`, diag/patch/log events: WP-12 (client side already implemented and gated by capability).
- Default-name control pipe always on: WP-12.
- Negative scenarios (`expect_diag`) need WP-12's events.
