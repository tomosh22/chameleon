# WP-61: the agent's first-list race (R-71)

Branch `wp/61-first-list`, wave 15 (ADR-0047), review: high (agent). No new diagnostic ids, no change to the agent, the broker or
the wire.

## The failure

`unit.agent` "WP-48 review 1: when the session's first module list cannot be built, a request right after it still finds the
module" failed once on windows-2025 msvc RelWithDebInfo (ci 46143341335 attempt 1, job 140973916698):
`test_agent.cpp(1176): CHECK( known_before_enable )`, while `empty_list_first`, `seen_enable`, `CHECK_FALSE(disagreement)` and
`CHECK(events->reason == 0)` held. The job log has nothing more about that test: the scripted broker logged nothing, and the
broker log lines printed after it belong to another test (the real `ConnectionServer`).

## Root cause: the test's broker answered without the ABI, not an agent path

The test creates the agent first (no broker exists), sets the enumeration failures, then constructs the `ScriptedBroker`, and only
after the constructor returns stores `welcome_abi = 3`:

```cpp
ScriptedBroker broker(pipe);                                // the listener thread creates the pipe in here
broker.welcome_abi.store(cml::ipc::kAgentAbiModuleEvents);  // ... and the ABI is set only after the constructor returned
```

The constructor starts the listener thread and returns once `pipe_exists` sees the pipe (`wait_until` polls with `Sleep(5)`, one
timer tick of up to ~16 ms on Windows). The agent is already running `try_connect` in a loop (back-off 50, 100, ... 1000 ms, each
attempt `pipe_exists` + `connect_pipe`). When one of its attempts falls between `CreateNamedPipeW` and the store, its Hello is
answered with `welcome.agent_abi_version = welcome_abi.load() == 0`: the agent sets `broker_events_ = false` (a broker before
WP-48) and, by design, reports every module change as `ModuleLoaded` / `ModuleUnloaded`, never as `ModuleEvents`.

The test looked for the module only in `ModuleEvents`. In such a session it finds none, while every other check holds:

| Check | In a session that got Welcome without the ABI |
|---|---|
| `empty_list_first` | holds: the session's list could not be built, it went out empty |
| `seen_enable` | holds: the request goes out |
| `known_before_enable` (a ModuleEvents naming the exe before the request) | **false**: there is no ModuleEvents at all; the module went as a `ModuleLoaded` before the request |
| `CHECK(events->reason == 0)` | never evaluated (no ModuleEvents), so it cannot fail |
| `CHECK_FALSE(disagreement)` | holds: CML4722 needs the trusted path |

That is exactly the signature of the failure. The race is also in "WP-48 review round 3 (2)" (same set-up: agent first, ABI stored
after the constructor); every other ABI-3 test constructs the broker before the agent exists, so the agent cannot connect before
the store.

### Evidence

1. **Deterministic reproduction** (new test, runs in every cell): `WP-61: to a Welcome without the ABI the failed first list's
   module goes as ModuleLoaded before the request (R-71's signature)` runs the same session against a broker that answers Welcome
   with ABI 0, which is what an agent that connected inside the window got. It prints
   `WP61-REPRO welcome_abi=0 empty_list_first=1 seen_enable=1 module_events_before_enable=0 module_loaded_before_enable=1
   module_events=0 cml4722=0` and checks it: R-71's signature, and the broker still learnt the module before the request (as a
   ModuleLoaded), so the agent did nothing wrong.
2. **The window measured on Windows**: the scripted broker now records, all from a time origin taken just before its first
   `CreateNamedPipeW` (the earliest moment an agent, or the constructor's own `pipe_exists` poll, can see the pipe), when each
   message arrived, when it built each Welcome (the moment it reads `welcome_abi`) and what that Welcome said; "WP-48 review 1"
   prints `WP61-WINDOW hello_us=<n> welcome_us=<n> constructor_returned_us=<n> welcome_before_constructor_returned=<0|1>
   welcome_abi=<n>`. Before WP-61 the test stored the ABI only after the constructor had returned, so a run with
   `welcome_before_constructor_returned=1` is one in which that test's Welcome certainly went out without the ABI. CI's WP-61
   repeat step counts them (`welcome_before_constructor=H` in its `WP61-REPEAT` line). **H is a lower bound** of the runs that
   hit the old window: that window ran on past the constructor's return, up to the `welcome_abi.store` after it, and a Welcome
   built in that gap is not counted.
3. **The agent paths named in R-71, checked against the code** (agent/src/agent.cpp, module_diff.cpp; none of them gives the
   signature):
   * the 1 s list resend (`poll_modules` -> `send_module_list(session_start=false)`): its pre-report is an untrusted poll
     (`known_trusted=false`) against the broker's view (`module_track_.known`, empty after the empty first list), so the
     snapshot diff, the exe included, goes out as ModuleEvents before the list and before the request;
   * a poll that ran before the request was queued: it is untrusted too (`full_list_pending_` is set by the failed list and is
     only cleared by a list that could be built), so it reports the same diff; `polled_seq_` only advances after it;
   * the ring's drained events: the exe was loaded long before the agent, so no notification names it; the drained events
     (`deferred`) only add other modules;
   * the request's own poll (`flush_outgoing`, `seq > polled_seq_`): whether it takes the resend branch or the untrusted poll,
     it reports the exe before the request.
   The only way left for a request to go out without the exe having been reported is a *real* enumeration failure in that poll
   (`proc::enumerate_modules` failing in the poll, or in all 3 attempts of the resend; the injected failures are used up by the
   session's first list): then `poll_modules` returns true without a
   report and the request goes out. That gives a different signature (the module would come in a ModuleEvents only after the
   request, from the next resend), the broker refuses the request (CML5212, not loaded), and it is the documented pre-WP-48
   behaviour ("requests queued meanwhile go out normally and the broker answers them on their own merits"). It was left as it is
   (see Deferred).

## What was built

| Piece | Where |
|---|---|
| `ScriptedBroker(pipe, abi, hook)` and an `abi` parameter on the full constructor: the ABI is in `welcome_abi` before the listener thread starts, so the first Welcome already has it. All ABI-3 tests use it; no test stores the ABI after construction any more | `tests/unit/agent/test_agent.cpp` |
| The scripted broker records the time of each message and of each Welcome (microseconds after a time origin taken just before its first `CreateNamedPipeW`), the ABI each connection's Welcome said (`welcome_sent`), and gives a `timeline(index)` (arrival order, times, `ipc::describe` of each message) | same |
| `InjectedEnumerationFailures`: arms the agent's injected enumeration failures and disarms them in its destructor, so a REQUIRE that throws cannot leave failures behind for later tests in the process (the counter lives in cml_agent.dll, which stays loaded). Used by `run_first_list_failed_session` (both tests that share it) and by "WP-48 review round 3 (2)", which never disarmed them before | same |
| "WP-48 review 1" now runs through `run_first_list_failed_session`; it checks that the session spoke ABI 3, that the exe was in a ModuleEvents before the request, that no ModuleLoaded was sent, no resync before the request and no CML4722; it prints `WP61-WINDOW`, and on a failed check the broker timeline and the agent's own log (`CML_AGENT_LOG`, if set) | same |
| New test: the R-71 signature reproduced deterministically (above) | same |
| CI step `WP-61 first-list repeat evidence (x50)` in windows-2025 / msvc / RelWithDebInfo (the cell of the failure): 50 fresh processes of `cml_test_agent.exe` running "WP-48 review 1", the WP-61 test and "WP-48 review round 3 (2)", each with `CML_AGENT_LOG` and `CML_LOG_LEVEL=debug`; a run passes when doctest exits 0 and reports at least one passed and 0 failed test cases (so a new `WP-61:*` test needs no change to the step); stops at the first failure and prints its output and the agent's log; run 1's agent log is kept in `ci-logs/` as a sample. Last line `WP61-REPEAT <cell> runs=N passed=P failed=F welcome_before_constructor=H` (also in the step summary; H is a lower bound, see Evidence 2) | `.github/workflows/ci.yml` |

## How to run

`ctest -R unit.agent`, or only these cases:
`cml_test_agent.exe "--test-case=WP-48 review 1: when the session*,WP-61:*,WP-48 review round 3 (2): after a refused list sent again*"`
(set `CML_AGENT_LOG=<file>` and `CML_LOG_LEVEL=debug` first to get the agent's Debug log; the agent reads them once, when
cml_agent.dll is loaded, so only in a process that loads it for these tests).

## What was learned

* An agent that is already looking for the pipe connects within milliseconds of `CreateNamedPipeW`, before the code that created
  the broker gets control back. Anything a test broker answers in the handshake must be configured before it listens.
* A test that looks for one message type should check the session spoke the protocol it assumes (`welcome_sent`): the failure then
  names itself instead of looking like an agent ordering bug.

## Deferred

* The pre-existing path above (a request sent after a poll that could not enumerate the modules) is unchanged: the broker refuses
  the request (CML5212) instead of acting on a wrong list, which is what ADR-0043 asks; holding requests until a snapshot succeeds
  would change the request flow for every caller and was not needed for R-71. If wanted, it is a separate roadmap item.
