# WP-45: re-apply session edits to re-loaded and late-enabled modules (F-42.1..F-42.3)

Branch `wp/45-module-reenable`, ADR-0043 (orchestrator's decision for WP-45; review: high). Diagnostic range CML5600–5619 (two
used). No new agent message types; `agent_abi_version` unchanged.

Status: **final review round fixed** (round 2, 1f8ace0, met the acceptance: corpus 45586903693 `godot-gdextension / msvc pass=21 expected_fail=0 fail=0`, ci 45586904011 `plugin_reload passed=29`, `plugin_late_load passed=32` in all 8 cells; the high review's findings are fixed in the round after it, see "Review round 1", "Review round 2" and "Final ruling").

## The defects (docs/wp/WP-42.md)

* **F-42.1** A module freed and loaded again (FreeLibrary + LoadLibrary, same base) got a new module state whose baseline was the
  edited file on disk: the edits were not re-applied, the old code ran, no diagnostic.
* **F-42.2** The new state's patch counter started at 0 again, so its first patch was linked to `<session>/<module>/p<pid>/g1`,
  the path of the freed instance's patch DLL, which is still loaded: LNK1104 (CML3350).
* **F-42.3** After a hot-restart, the edits of a module the new process enabled only later (CML5809) were never re-applied.

## What was built

| Piece | Where |
|---|---|
| Kept baselines ("carries"): when a module's state is dropped and its baseline holds accepted edits (originals), the baseline is kept per (pid, normalised path), with whether the image is still loaded (`live_base`: the module was disabled, not freed) | `ReloadService::on_session_changed`, `leaving_baseline` (`reload_service.cpp`) |
| The next instance of the module in that process takes the carry: its index applies it right after taking the baseline, before Ready (`ModuleIndexSpec::carried`), so no reload ever sweeps the instance without it | `module_index.{h,cpp}` |
| Restore vs. adopt: a fresh image (freed + loaded, at the same or another base; a late module after a restart) gets `SourceBaseline::restore` (the files patched before count as changed: the next reload re-applies them, as hot-restart does). The same image disabled and enabled again gets the new `SourceBaseline::adopt` (stamps and originals taken over as they are: it still runs the patches; nothing is recompiled, and the originals survive for a later restart or reload) | `source_baseline.{h,cpp}` |
| The re-apply worker: one thread in the ReloadService (started on first use, joined by the destructor) that waits for the instance's index, takes the reload lock, and runs one reload of that module with `confirm: true` (the restart's re-apply, for one module). `wait idle` waits for queued and running re-applies; a `reload` the user asks for meanwhile waits for it instead of being refused busy (CML5304) | `ReloadService::queue_reapply`, `reapply_loop`, `reapply_one`, `run_reload`, `wait` |
| Late modules after a hot-restart: for every module the restart could not enable (CML5809) its carried baseline is handed to the new process (`ReloadService::carry_to_late_module`); when the module is enabled later its enable re-applies the edits. If it was enabled in the moment between the restart's check and the hand-over, the worker restores the baseline and reloads at once. CML5809 now says "the session's edits of its N file(s) are re-applied when it is enabled". Baselines kept for modules of the old process that are not enabled at restart time (freed, disabled) travel with the restart too (`kept_baselines`) | `restart.cpp` |
| Unique work directories: `ModuleState::instance` (1, 2, ... per pid and module path, kept by the service, never reset, also across agent reconnects) names the patch work directory: `p<pid>` for the first instance (unchanged layout), `p<pid>-i<n>` for later ones. No patch of a later instance can be written to the path of an earlier instance's still-loaded patch DLL | `module_state.h`, `pipeline.cpp` (`make_work_dir`) |
| A carry goes with its process, not with its connection: kept when the agent disconnects from a process that still runs, dropped when the process is known to have exited (`ProcessHost::has_exited`, re-checked 5 times over 160 ms). When an agent registers, the carries other agents stored for its pid stay only on a proven match of the process identity: restart token, command line and creation time (`ProcessHost::creation_time`, broker-side: `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetProcessTimes`), both creation times known and equal; anything else is dropped (logged at info with the module and the files). No carry is stored for an agent that is gone or has not registered | `ReloadService::detach`, `on_session_changed`, `carry_to_late_module`, `restart_win.cpp` |

Every decision is logged at trace (`reenable: decision=carry|adopt|reapply|reapply-existing|image-gone|nothing-to-carry|abandoned|reapplied
module=... pid=... instance=... origin=... originals=...`, `restart: decision=carry-to-late-enable|restore-now|kept-baseline-carried ...`,
`index: carried baseline applied: module=... mode=restore|adopt files=... originals=...`), the outcome at info.

### Diagnostics (CML5600–5619)

| Id | Severity, stage | When | Message names |
|---|---|---|---|
| CML5600 | warning, `enable` | the reload that re-applies the edits failed (its diagnostic inside, e.g. the compile error) | the module, the process, the edited files (up to five, then "and N more"); "Fix the error and run `reload`; the edits stay pending until a reload applies them." |
| CML5601 | warning, `enable` | the instance's PDB index failed, so the edits cannot be re-applied | the module, the process, the files, the index's diagnostic |

The failing reload's own diagnostic (a compile error, CML3350, ...) is published as before. A module that goes away before its
re-apply ran hands its carry on to the next instance (nothing is lost, nothing to report); shutdown abandons it quietly (logged).

### Not changed

* A module disabled and enabled again while loaded used to start from the files on disk too; that was right for the code (the image
  still runs the patches) but lost the originals, so a later restart or reload-after-free could not re-apply them. It now adopts the
  baseline (above).
* A module whose index is not ready when the restart re-applies (the existing CML5810 warning) is not deferred to the worker; it keeps
  its warning.

## Agent change (round 2, approved by the orchestrator as an amendment to ADR-0043)

The agent's hook installer keeps a record per hooked address (`agent/src/hook/installer.cpp`, `records_`), and before this package
nothing removed the records of a module that was unloaded. After FreeLibrary + LoadLibrary at the same base the fresh image has its
original bytes at those addresses, but the installer still found a record there and planned a *re-point* whose expected bytes are the
old jump: the install failed with CML4312 ("the bytes are not the ones recorded"). That blocked F-42.1 and F-42.2 at the hook step in
the same process (the restart path, F-42.3, starts a new agent and was not affected).

* `hook::Installer::forget_range(base, size)` drops the records whose target lies in `[base, base + size)`: under the installer's
  batch mutex (so it runs after any install or revert in flight, never while threads are suspended), erase only (no allocation).
* `Agent::poll_modules` calls it for every unloaded module before it sends `ModuleUnloaded`, so the broker's re-apply can never reach
  the agent before the records are gone; logged at debug (`module unloaded: base=... size=... hook_records_dropped=N`).
* No new message; `agent_abi_version` unchanged.
* `unit.agent_hook`: `WP-45: forget_range drops the records of an unloaded module; a hook of the image loaded again is a first install`
  (both strategies): with the stale record the install fails CML4312 and writes nothing; after forget_range only the record in the
  range is gone, the other module's hook is intact, and the new install is `Installed` (not `Repointed`) with the new image's bytes as
  its original (revert restores them).

The patch DLLs of the freed instance stay loaded (their records, which are keyed by the hooked old entry, are gone with the module).

## What was learned

* "Module state" and "module instance" are different things: the broker keyed everything per path, while the process can map the
  same path several times in a session. Whatever must be unique per mapping (patch file paths) needs an instance number; whatever
  describes the session's edits (the baseline's originals) must outlive the mapping.
* Applying the carried baseline inside the index, before Ready, is what makes the re-apply race-free against the user's reloads and
  compile-on-save: no sweep can see the instance with the on-disk baseline.

## Deferred

* FreeLibrary + LoadLibrary within one agent module poll (500 ms) at the same base is invisible to the agent and therefore to the
  broker (no ModuleUnloaded / ModuleLoaded): the new image runs the original code silently. Detecting it needs the agent (for example a
  load-time stamp per module entry), so it is a KNOWN_LIMITATIONS row, not a fix here (roadmap R-53).
* An agent that disconnects from a live process and reconnects keeps the carries it had, but the states of the modules that were
  enabled at the disconnect do not leave one (as before this package): their new states start from the files on disk, which is right
  for the code (the image still runs the patches) but loses the originals for a later free + load or restart. Carrying them needs the
  certainty that the process did not exit, which `has_exited` only gives for "exited".
