# WP-30: VS Code extension

`integrations/vscode/` (TypeScript, no runtime dependencies). Architecture: a client of the control pipe only (ADR-0021 framing,
ADR-0032 shapes, ADR-0038 contract). Diagnostics: CML5990-5993 (ADR-0038).

## What was built

| Piece | File | Notes |
|---|---|---|
| Control client | `src/controlClient.ts` | `net.connect` on the named pipe. `LineSplitter` (partial lines, CRLF, blank lines, split UTF-8, 1 MiB limit), id-matched requests (queued, one at a time per connection), events, timeouts. |
| Session | `src/session.ts` | Two connections like `cml_ui`: commands (`status`, `reload`, `restart`, `revert`, `exception-action`) and a second one that only carries events after `subscribe`. Reconnect with back-off (0.5, 1, 2, 5 s). Capability gate: a command the broker does not advertise is not sent (CML5992); a CML5402 answer to an advertised command is mapped to CML5992 and remembered for the connection. |
| Pipe name | `src/pipeName.ts` | Setting, else `CML_CONTROL_PIPE`, else `\\.\pipe\cml_control_<logon-session SID>` (same rule as `resolve_control_pipe_name`). The SID comes from `whoami /groups` (the `S-1-5-5-X-Y` group), then PowerShell's `WindowsIdentity.Groups` (`whoami /groups` does not list the logon-id group on the GitHub runners); fall-backs: a single existing `cml_control_*` pipe, then the user SID. |
| Text and status | `src/format.ts` | Event formatting, compiler-line parser (cl/clang-cl `file(line[,col]): error C1234: text`, clang `file:line[:col]: error: text`), status bar model, subscription list by capability. |
| Diagnostics | `src/diagIds.ts` | see below |
| VS Code glue | `src/extension.ts` | commands, output channel, `DiagnosticCollection`, status bar item, exception notification. The only file that imports `vscode` (a unit test enforces it). |
| Problem matchers | `package.json` | `$chameleon` (cl, clang-cl) and `$chameleon-clang`; `format.test.ts` checks that they are the same expressions the parser uses and match sample lines. |
| CI | `.github/workflows/vscode.yml` | windows-2022: `npm ci`, `npm run lint`, `npm test`, build `cml_broker`/`cml_agent`, build the `basic` fixture, integration test, `npm run package`, upload the `.vsix` and logs. |

Commands: `Chameleon: Reload`, `Hot-Restart`, `Revert Last`, `Revert All`, `Show Output`, `Connect`, `Disconnect`. Default key for Reload:
`Ctrl+Alt+F9`.

## How to run

* Unit tests (any OS with Node 22): `cd integrations/vscode && npm ci && npm test`. They run a fake broker on a named pipe (Unix
  socket off Windows): framing in pieces and one byte at a time, an event between request and answer, serial requests, CML5402,
  no broker (CML5990), lost pipe (CML5991), no answer or bad line (CML5993), reconnect, a missing capability (CML5992), pipe name
  derivation, event formatting, parser and status bar.
* Integration test: `integrations/vscode/test/integration/run.ts` (see the CI step). It starts `cml_broker --headless` on its **default**
  control pipe (no `--control-pipe`, no `CML_CONTROL_PIPE`, so the derivation is exercised), connects through the extension's `Session`
  (`status`, `subscribe`), starts the `basic` fixture with the agent, waits for the module to be enabled and indexed, edits the
  scratch copy of `logic.cpp`, sends `reload` (expects the `patch_applied` event and `value=2` on the fixture's stdout), then `revert`
  with scope `last` (expects `patch_reverted` and `value=1` again). Greppable lines start with `WP30-IT`; the last is
  `WP30-IT reload=ok revert=ok`.
* Package: `npm run package` writes `integrations/vscode/chameleon-hot-reload-0.1.0.vsix` (exactly one `.vsix`).

## Diagnostics (CML5990-5993; client side only, `src/diagIds.ts`)

| id | meaning | what to do |
|---|---|---|
| CML5990 | no broker answers on the control pipe (not started, wrong pipe, other user), or the default pipe name could not be derived | start `cml_broker` or `cml_ui` as the same user, or set `chameleon.controlPipe` to the pipe the broker was started with |
| CML5991 | the control connection was lost after it was established | check that the broker runs; the extension reconnects by itself (`chameleon.autoConnect`) or run `Chameleon: Connect` |
| CML5992 | the broker does not provide a command or capability (older broker) | use a broker that advertises it; the command stays disabled until then |
| CML5993 | the broker's answer is unusable: not JSON, wrong shape, no capability list, line over 1 MiB, or no answer in time | check the broker log; use matching versions of broker and extension |

Broker diagnostics (CML5300, CML5850, ...) are passed through unchanged with their own text.

## Decisions

* **Problems entries come from `diag` events, not from the output channel.** VS Code applies problem matchers to tasks and terminals, not to
  output channels. The matcher is contributed as asked (for tasks), and the extension feeds a `DiagnosticCollection` with the same
  expressions from the `diag` message text. How many Problems appear therefore depends on whether the broker's diag message carries the
  compiler's lines (`file(line): error ...`); a diag without such a line only shows in the output channel.
* **Two connections** (commands and events), as `cml_ui` does, so a 60 s reload never delays event delivery and `status` stays answerable
  on the event side's behalf.
* **`exception` is opt-in** (`chameleon.watchExceptions`, default off). WP-20: subscribing to `exception` makes the agents hold a faulting
  thread until a client decides. With the setting on, the extension shows a notification with the event's actions
  (Continue / Leave function / Ignore) and sends `exception-action`. Without it the output channel never shows `exception`.
* **`log` and `progress` are not subscribed** (chatty); `restarted` and `patch_reverted` only when the broker advertises `restart`/`revert`.
* **Pipe name via `whoami`.** Node cannot read the token's logon-id group. `whoami` and PowerShell ship with every Windows. Locale-independent
  because the SID prefix `S-1-5-5-` is matched, not the group text.
* **Default key `Ctrl+Alt+F9`**, not `Ctrl+Alt+F11` (the `cml_ui` global hotkey would fire in both).
* **Test runner `node:test`** (built into Node), so the dev dependencies are only typescript, `@vscode/vsce` and two `@types` packages.
  Lint is `tsc --noEmit` with strict options and no unused code; no eslint.
* **`vsce package --skip-license --allow-missing-repository --no-dependencies`**: the repository has no licence file yet and the extension has
  no runtime dependencies.

## Manual checklist (Windows, VS Code 1.85 or later, the `.vsix` from the CI artefact `chameleon-vscode-vsix`)

Prepare: a built Chameleon tree (`cml_broker.exe`, `cml_agent.dll`, and `cml_ui.exe` if you want it) and one of the fixtures, for example
`build\bin\fixture_basic.exe` built in a scratch copy as cmltest does, or any application that calls `cml::CreateDefaultAgent`.

1. Install: `code --install-extension chameleon-hot-reload-0.1.0.vsix`, restart VS Code. The status bar (left) shows
   `Chameleon: disconnected` with a warning background. Hover: the tooltip says CML5990 and "Click to connect".
2. Run `Chameleon: Show Output` (Ctrl+Shift+P). The "Chameleon" channel opens and has a CML5990 line.
3. Start `cml_broker.exe --headless` in a terminal (no pipe options). Within about five seconds the status bar turns to
   `Chameleon: no process`, the output shows `connected to the broker 0.1.0 (capabilities: ...)`.
4. Start the fixture with the agent, for example `fixture_basic.exe --agent` from the folder that has `cml_agent.dll`. The status bar
   shows `1 process`.
5. Open the fixture's source (`logic.cpp` of the build you started), change `return 1;` to `return 2;`, save.
6. Press `Ctrl+Alt+F9`. The status bar shows `reloading` briefly, then `reload ok, gen 1`; the output shows `reload requested`,
   `patch applied: module fixture_basic.exe ...` and `reload ok: generation 1, 1 patched ...`; the fixture's console now prints `value=2`.
7. Introduce a syntax error in `logic.cpp`, save, press `Ctrl+Alt+F9`. The status bar shows the error icon and `reload failed CML....`, a
   warning notification names the diagnostic and what to do, the output shows the `diag` event. If the diag text contains
   `logic.cpp(12): error C...`, the Problems panel lists it and clicking it opens the file at that line.
8. Fix the error, reload again: Problems are empty, `reload ok`.
9. Run `Chameleon: Revert Last`. Output: `patch reverted ...` and `revert last ok`; the fixture prints the previous value.
10. Reload again, then `Chameleon: Revert All`: a modal asks first; after "Revert All" the fixture prints `value=1`.
11. Hot-restart (needs a restart-capable setup, for example the `hot_restart` fixture): `Chameleon: Hot-Restart`. With one process it runs
    at once; with two processes a quick pick appears. Output: `restarted: process A replaced by B`.
12. Stop the broker (close its terminal). The status bar turns to disconnected within a second, the output shows CML5991. Start the broker
    again: the status bar reconnects by itself.
13. `Chameleon: Disconnect`: status `disconnected`, no reconnection while the broker runs. `Chameleon: Connect`: connected again.
14. Set `chameleon.controlPipe` to `\\.\pipe\nonexistent`: the status bar goes disconnected with CML5990. Clear the setting: it reconnects.
15. Against an older broker without `revert` (or by hand: any broker whose `status` lacks `revert`): `Chameleon: Revert Last` shows
    "CML5992: this broker ... does not provide ... 'revert'" and sends nothing; the status bar tooltip names the missing capability.
16. Optional: set `chameleon.watchExceptions` to true, make the fixture crash (the `crash` fixture): a notification offers the
    actions; choose one and the program continues as WP-20 describes.

## Deferred / limitations

* The Problems panel depends on the broker putting compiler lines into the `diag` message (see Decisions); I did not change the broker.
  A follow-up could add a structured `file`/`line` to the `diag` event (ADR-0038 allows added fields).
* Hot-restart is covered by the unit tests (request shape, capability gate) and the manual checklist, not by the real-broker test: the
  `basic` fixture does not support it; `hot_restart` needs the harness's restart machinery.
* No process picker for reload or revert: they act on all processes (the broker's default). `Hot-Restart` picks one.
* No debugger integration (re-attach after a hot restart is WP-31's job for Visual Studio; VS Code is not in scope).
* The `.vsix` is unsigned and not published to the marketplace.
* Not exercised by CI: the `vscode`-API glue in `src/extension.ts` (no VS Code instance runs in CI); it is a thin layer over tested modules
  and covered by the manual checklist.
* `@vscode/vsce-sign` (Microsoft licence) is in the dev dependency tree as an optional dependency of `vsce`; it is not in the `.vsix`.
