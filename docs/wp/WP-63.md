# WP-63: read the guard bit or guard each static tests (R-69; ADR-0047)

Branch `wp/63-guard-bits`, one PR. Review: high (bind planner). Diagnostics: no new id; the two WP-59 `CML3600` messages
of an external guard end with what the code showed (or why it could not be read).

## The defect

WP-59 (#89, docs/wp/WP-59.md, review item 2) refused an inline function that keeps a constant-initialised
`static int calls = 0;` and gains a dynamic static (`b6_const`). The statics of an inline function and their guard are
external symbols; the guard's name ties it to every static of the function (clang's and cl's bitmask `??_B<scope>@5<n>`
without thread-safe statics) or of the block (the external `?$TSS<n>@<block>@4HA` of one static with them). So the guard is
tied to `calls` (bound to the running process by its public) and to the new static: "bound next to new", CML3600. The case
where `calls` becomes dynamic as well (`b7_both`) defines the same symbols in the same sections, and there a fresh guard
runs calls' new initialiser over the live value. Only the code says which statics test the guard.

## What was built

- `broker/cml_core/src/guard_code.cpp` (`cml/core/guard_code.h`): `read_guard_code` reads, from every code section of the
  patch that refers to the guard, which candidate statics (those the guard's name ties, read-only ones left out) are
  initialised under it. It sweeps each section linearly with the agent's length decoder from offset 0 and from every
  function symbol (as WP-36's SiteProver: every relocation passed must be exactly the displacement or an immediate of one
  decoded instruction), and classifies every instruction that refers to the guard. Anything else is "not read" and the
  planner refuses as before. The shapes, per kind:

  | Kind | Use | Shapes read |
  |---|---|---|
  | bitmask (`??_B`, and an external `?$S<n>`) | read | `mov r, [g]` (8B, 8A), `movzx`, `test`, `cmp`, `bt` |
  | | claim (one bit) | `or r32, imm` / `or r8, imm8` / `bts r32, imm8` immediately followed by `mov [g], r` (the store not a branch target); `or [g], imm`; `bts [g], imm8` |
  | | release (EH funclet) | `and [g], imm`, `btr [g], imm8`, or `and r, imm` + `mov [g], r` |
  | thread-safe (`?$TSS<n>`) | read | `mov r32, [g]`, `cmp r32, [g]`, `cmp [g], r32`, `cmp [g], imm` |
  | | claim | `lea rcx, [g]` immediately followed by `call _Init_thread_header` (direct, or through `__imp_`) |
  | | end of region | `lea rcx, [g]` + `call _Init_thread_footer` |
  | | abort (EH funclet) | `lea rcx, [g]` + `call _Init_thread_abort` |

  Every use must be a plain RIP-relative operand at the guard's own offset (0..3 into a bitmask, 0 for a `$TSS`); the
  offset is read as `A + bytes behind the field - k` for `REL32_k` (clang writes `REL32` with the tail folded into the
  addend, cl `REL32_k`). A claim's region:
  - bitmask: from the claim to the first instruction that a branch from outside the region reaches (a join), refers to
    the guard again, or ends the flow (jmp, ret, int3/ud2; a `jmp` to the next instruction, clang -O0's invoke
    destination, falls through). Both layouts are covered: clang's out-of-line block that jumps back, cl's block that a
    `jne` skips;
  - thread-safe: from the header call to the footer, in a straight line: no jmp/ret/trap, no second header or abort, and
    no branch into it from outside.

  The region must refer to exactly ONE candidate: that is the static initialised under the claim. Every bit (or the
  `$TSS`) belongs to one static and every static to one bit; at least one claim must exist. A guard whose address is
  stored in data (debug information aside), or a section symbol of the guard's section (in any code section) or of a
  candidate's (in a section that uses the guard) is not read. The reader also lists the candidates whose address the code
  that uses the guard puts in a register or an immediate (`lea`, a relocated immediate: anything but a RIP-relative memory
  operand), inside a region or not (`address_taken`).
- `bind_plan.cpp`, `settle_external_guard`: where the name's tie would refuse (bound statics next to new ones, or bound
  statics and no old guard of the name), `guard_code_statics` reads the code. When every static the code initialises
  under the guard is new, and no bound static of its scope has its address taken (a region could write it through that
  address while naming another static: `n6_addr`, refused with "... but it takes the address of <static> ..."), the guard
  is new (`PatchNewData`, "external guard of new statics, read from the patch's code"),
  and the bound statics of its scope that the code does not initialise under it are recorded in `code_untied_`, so that
  `require_bound_guards` does not count that guard as theirs (they need none: constant-initialised, or guarded by another
  guard of their block, which is settled on its own). Otherwise, and whenever the code is not read, the CML3600 stands,
  with `; the patch's code initialises <statics> under it` or `; which of them are initialised under it cannot be read from
  the patch's code (<why>)` added. Every reading logs `WP63-GUARD-CODE guard=... object=... scope=N guarded=N|unread
  bound=N new=N verdict=new-guard|refused` (info), the claims at trace.
- An external `?$S<n>` is settled like `??_B` (WP-59 left it "as decided"): clang's MicrosoftMangle.cpp says MSVC spells an
  inline function's bitmask `??_B` too, but should cl spell it `$S<n>` and make it external, it is never bound by its
  name next to new statics, and the cl `/Zc:threadSafeInit-` cell reads it the same way.
- `reloc_field_width` moved in front of the planner class (it is used by `guard_code_statics`); unchanged.
- Fixture `guard_bits` (/O2 /Ob2 in every cell, as `planner_pairing_o2`): `bits_nts.cpp` (`/Zc:threadSafeInit-`) and
  `bits_ts.cpp` (thread-safe), each an inline `noinline` function with `static int calls = 0;`. Edit `nts_1` adds
  `static GbName extra = gb_make(300000);` to the first, `ts_2` the same (400000) to the second. Scenario
  `tests/harness/scenarios/guard_bits.toml`: both reloads must apply in every cell (`patched = 1`, no error allowed); `nts`

## What was learned

- clang's bits are the statics' static-local numbers (WP-59), and a constant-initialised static simply never claims its
  bit: in b6 the code claims 0x2 only, in b7 0x1 and 0x2. With thread-safe statics a constant-initialised static has no
  guard at all, and the dynamic one's `$TSS<n>` is still numbered by its place among all statics (`$TSS1` in s1).
- clang folds the bytes behind a RIP-relative field into the addend of a plain `REL32` (`cmp dword ptr [g], -1` has
  `REL32` with addend -1, `and byte ptr [g], ~2` the same); cl uses `REL32_1`. The offset into the target is
  `A + tail - k` either way.
- An inline function's no-thread-safe statics get EH cleanups under /EHsc that clear their bit (clang: `and byte ptr`
  in a `?dtor$<n>` funclet of the same section); thread-safe ones call `_Init_thread_abort`. Neither claims anything.
- `parse_layout` (imgrel_site.cpp) reads a ModRM byte for opcodes it does not list as having none (jcc rel8, `test al`),
  so its "known" verdict is not used for those here.

## Residual (for the orchestrator to rule on)

The proof ties a claim to the one candidate its region refers to by relocation. A bound static that the reading leaves
out could still be written in a region through an address the region did not form itself. An address formed in the code
that uses the guard (`lea`, an immediate) is caught: such a bound static keeps the refusal (`n6_addr`). Not caught: an
address read from memory (a pointer variable holding it, set elsewhere) or returned by a call, used inside a region that
names another static only, i.e. an initialiser of a new static that writes the kept static through a pointer it loads.
Neither compiler's code for a static's initialiser does that by itself; it takes such source (`static Obj a = init(*p_to_calls = 5);`
with `p_to_calls` a global pointer). The bitmask's claim is also read as "the bits the `or` sets", without proving that the
register held the bitmask's value before (both compilers load it from the bitmask right before).

## Deferred

- Bound statics next to new ones under one guard (a function that keeps a dynamic static and gains another, `n5`): the
  code shows which bit each static claims, but whether the old function gave the bound one the same bit needs the old
  code read the same way (or the unchanged function, WP-59's proof). Still CML3600.
- Internal functions' guards (`$TSS<n>` / `$S<n>` with internal linkage; their rules are WP-40's / WP-46's, which place
  a guard by its record or by the section layout): not read from the code here.
- `??__J` (thread-local bitmask) stays WP-24's.
