# WP-63: read the guard bit or guard each static tests (R-69; ADR-0047)

Branch `wp/63-guard-bits`, one PR. Review: high (bind planner). Diagnostics: no new id; the two WP-59 `CML3600` messages
of an external guard end with what the code showed (or why it could not be read).

## The defect

WP-59 (#89, docs/wp/WP-59.md, review item 2) refused an inline function that keeps a constant-initialised
`static int calls = 0;` and gains a dynamic static (`b6_const`). The statics of an inline function and their guard are
external symbols; the guard's name ties it to every static of the function (clang's and cl's bitmask `??_B<scope>@5<n>`
without thread-safe statics) or of the block (the external `?$TSS<n>@<block>@4HA` of one static with them). So the guard is
tied to `calls` (bound to the running process by its public) and to the new static: "bound next to new", CML3600. The case
where `calls` becomes dynamic as well (`b7_both`) defines the same symbols in the same sections, and there a fresh guard
runs calls' new initialiser over the live value. Only the code says which statics test the guard.

## What was built

- `broker/cml_core/src/guard_code.cpp` (`cml/core/guard_code.h`): `read_guard_code` reads, from every code section of the
  patch that refers to the guard, which candidate statics (those the guard's name ties, read-only ones left out) are
  initialised under it. It sweeps each section linearly with the agent's length decoder from offset 0 and from every
  function symbol (as WP-36's SiteProver: every relocation passed must be exactly the displacement or an immediate of one
  decoded instruction), and classifies every instruction that refers to the guard. Anything else is "not read" and the
  planner refuses as before. The shapes, per kind:

  | Kind | Use | Shapes read |
  |---|---|---|
  | bitmask (`??_B`, and an external `?$S<n>`) | read | `mov r, [g]` (8B, 8A), `movzx`, `test`, `cmp`, `bt` |
  | | claim (one bit) | `or r32, imm` / `or r8, imm8` / `bts r32, imm8` immediately followed by `mov [g], r` (the store not a branch target); `or [g], imm`; `bts [g], imm8` |
  | | release (EH funclet) | `and [g], imm`, `btr [g], imm8`, or `and r, imm` + `mov [g], r` |
  | thread-safe (`?$TSS<n>`) | read | `mov r32, [g]`, `cmp r32, [g]`, `cmp [g], r32`, `cmp [g], imm` |
  | | claim | `lea rcx, [g]` immediately followed by `call _Init_thread_header` (direct, or through `__imp_`) |
  | | end of region | `lea rcx, [g]` + `call _Init_thread_footer` |
  | | abort (EH funclet) | `lea rcx, [g]` + `call _Init_thread_abort` |

  Every use must be a plain RIP-relative operand at the guard's own offset (0..3 into a bitmask, 0 for a `$TSS`); the
  offset is read as `A + bytes behind the field - k` for `REL32_k` (clang writes `REL32` with the tail folded into the
  addend, cl `REL32_k`). A claim stored from a register must be proven to set one bit in the guard's value: on every
  path back from the `or` the register is loaded from the guard (`mov r32,[g]`, a byte `mov r8,[g+n]`) with only test /
  cmp / bt / jumps / nop between (review round 1). A claim's region (review round 1) is every instruction reachable from
  the claim (direct branches followed, calls return, a jump with a relocation is a tail call) that no function start of
  the section reaches without passing the claim, up to the next use of the guard (bitmask) or the guard's footer
  (thread-safe: every path ends there or rejoins the rest of the code, none at a ret, no second header or abort). Nothing
  may enter it from outside. Both layouts are covered: clang's out-of-line block that jumps back, cl's block that a `jne`
  skips, and initialisers with their own branches (a ternary).

  The region must WRITE exactly ONE candidate (a store or read-modify-write to it, or its address formed, as for a
  constructor; a candidate it only reads does not count): that is the static initialised under the claim. Every bit (or
  the `$TSS`) belongs to one static and every static to one bit; at least one claim must exist. Every function of a section
  that uses the guard must decode completely, with no indirect jump and no branch into an instruction. A guard whose
  address is stored in data (debug information aside; matched by name and by the guard's section), any other symbol of the
  guard's section (in any code section), or another symbol of a candidate's section (in a section that uses the guard) is
  not read. The reader also lists the candidates whose address the code that uses the guard puts in a register or an
  immediate (`lea`, a relocated immediate: anything but a RIP-relative memory operand), inside a region or not
  (`address_taken`).
- `bind_plan.cpp`, `settle_external_guard`: where the name's tie would refuse (bound statics next to new ones, or bound
  statics and no old guard of the name), `guard_code_statics` reads the code. When every static the code initialises
  under the guard is new, and no bound static of its scope has its address taken (a region could write it through that
  address while naming another static: `n6_addr`, refused with "... but it takes the address of <static> ..."), the guard
  is new (`PatchNewData`, "external guard of new statics, read from the patch's code"),
  and the bound statics of its scope that the code does not initialise under it are recorded in `code_untied_`, so that
  `require_bound_guards` does not count that guard as theirs (they need none: constant-initialised, or guarded by another
  guard of their block, which is settled on its own). Otherwise, and whenever the code is not read, the CML3600 stands,
  with `; the patch's code initialises <statics> under it` or `; which of them are initialised under it cannot be read from
  the patch's code (<why>)` added. Every reading logs `WP63-GUARD-CODE guard=... object=... scope=N guarded=N|unread
  bound=N new=N verdict=new-guard|refused` (info), the claims at trace.
- An external `?$S<n>` is settled like `??_B` (WP-59 left it "as decided"): clang's MicrosoftMangle.cpp says MSVC spells an
  inline function's bitmask `??_B` too, but should cl spell it `$S<n>` and make it external, it is never bound by its
  name next to new statics, and the cl `/Zc:threadSafeInit-` cell reads it the same way.
- `reloc_field_width` moved in front of the planner class (it is used by `guard_code_statics`); unchanged.
- Fixture `guard_bits` (/O2 /Ob2 in every cell, as `planner_pairing_o2`): `bits_nts.cpp` (`/Zc:threadSafeInit-`) and
  `bits_ts.cpp` (thread-safe), each an inline `noinline` function with `static int calls = 0;`. Edit `nts_1` adds
  `static GbName extra = gb_make(300000);` to the first, `ts_2` the same (400000) to the second. Scenario
  `tests/harness/scenarios/guard_bits.toml`: both reloads must apply in every cell (`patched = 1`, no error allowed); `nts`
  / `ts` continue from where they were (`expect_monotonic since_reload`), the new statics count from 300001 / 400001, and
  `made` goes 0 -> 1 -> 2 (each new static constructed once). `test_wp63_scenarios.cpp` (unit.harness) checks the
  scenario's shape.

## What was learned

- clang's bits are the statics' static-local numbers (WP-59), and a constant-initialised static simply never claims its
  bit: in b6 the code claims 0x2 only, in b7 0x1 and 0x2. With thread-safe statics a constant-initialised static has no
  guard at all, and the dynamic one's `$TSS<n>` is still numbered by its place among all statics (`$TSS1` in s1).
- clang folds the bytes behind a RIP-relative field into the addend of a plain `REL32` (`cmp dword ptr [g], -1` has
  `REL32` with addend -1, `and byte ptr [g], ~2` the same); cl uses `REL32_1`. The offset into the target is
  `A + tail - k` either way.
- An inline function's no-thread-safe statics get EH cleanups under /EHsc that clear their bit (clang: `and byte ptr`
  in a `?dtor$<n>` funclet of the same section); thread-safe ones call `_Init_thread_abort`. Neither claims anything.
- `parse_layout` (imgrel_site.cpp) reads a ModRM byte for opcodes it does not list as having none (jcc rel8, `test al`),
  so its "known" verdict is not used for those here.

## Residual (ruled on in review round 1)

- Accepted: a kept static written inside a region through an address read from memory (a pointer variable set elsewhere)
  or returned by a call. An address formed in the code that uses the guard (`lea`, an immediate) is caught: such a bound
  static keeps the refusal (`n6_addr`). Such a write is the new static's initialiser writing the kept static, which runs
  once: the program's own semantics, not a re-initialisation.
- Not accepted (fixed in review round 1): "the bits the `or` sets" without proving what the register held. The register
  must now be loaded from the guard on every path (or the claim is a memory-destination `or`/`bts`).

## Review round 1 (high review of aec54fe)

1. A bitmask claim could be pinned on the wrong static: the region stopped at the first jmp/ret/join and counted any
   candidate it referred to, so a ternary initialiser (`calls = pick(x) ? 1 : make_int(2)` next to new `x`, `a`) pinned
   calls' bit on x, which it only reads, and calls (bound) got a fresh bitmask. Now the region follows the branches (the
   instructions only the claim reaches) and counts only the candidate it writes. Unit case `R-69 (review 1): a ternary
   initialiser ...`: pins calls (with aec54fe's reader: x).
2. Proved over partial code: only the guard's references had to be decoded. Now every function of a section that uses the
   guard must decode completely (and every reference to the guard or a candidate is in a decoded instruction); an
   indirect jump or a branch into an instruction refuses too. Unit case: `lea rcx,[calls]` behind data the sweep cannot
   pass refuses.
3. Aliases: any relocation into the guard's section that does not name the guard refuses (any code section); in a section
   that uses the guard, so does one into a candidate's section that does not name that candidate; data references are
   matched by the guard's section number as well as its name.
4. bts/btr: only the 32-bit form of a bit below 32 is read (66 / REX.W or a bit >= 32 refuses).
5. Cost: the function symbols are bucketed by section in one pass (on the first reading only), and a code section is
   described (relocations copied) only when it refers to the guard or its section; the reader checks for the guard before
   it copies or sorts. Nothing runs in a plan that reads no guard's code.
6. build.sh (wp63 and wp59): W=/ is refused (`case "$W" in /)`; `"$W/"` made it `//`).
7. docs/TROUBLESHOOTING.md: the "... but it takes the address of ..." ending is listed.
- Residual (b): the register-load proof above; unit case `R-69 (review residual b)` (`mov eax,[other]; ...; or eax,1;
  mov [M],eax`) refuses. Consequence: clang -O0's bitmask claim (reloaded from a stack slot) is no longer read (refused,
  as before WP-63); the thread-safe shape at -O0 still reads, and the fixture is /O2 in every cell.

## Review round 2 (delta high re-review of aec54fe..a581685)

1. A register stored to the guard after `and`/`btr` was a release without proof; `mov eax,1; and eax,0xFF; mov [g],eax`
   wrote arbitrary bits unseen. Releases stored from a register now get the same proof as claims (loaded from the guard on
   every path back). Unit case `R-69 (review 2, item 1)`.
2. Writes were a list of writing opcodes, which missed cmpxchg8b/16b, shld/shrd, stmxcsr/fxsave/xsave and the x87 stores.
   Inverted (`reads_only`): an instruction that references a candidate writes it unless it is a pure read (mov / movsxd /
   movzx / movsx loads, cmp, test, bt, the ALU and imul forms that read memory into a register, the SSE loads movups /
   movss / movsd / movaps / movlps / movhps / movq / movdqa / movdqu / F3 movq, comiss / ucomiss). Unit case: a region that
   writes a and does `cmpxchg16b [calls]` writes two statics, refused.
3. Thread-safe paths that leave the bracket: a region instruction without a successor that is not the footer (a ret, a
   tail call `jmp` with a relocation, the end of the section) refuses. Unit case `'t'` (a branch to a tail call).
4. Function starts are entered from outside: the register-store check, the lea + call check and the walk back from an
   `or`/`and` treat an index in `entries` as an extra predecessor from outside. Unit case: function A's load falls through
   into function B's `or`, refused.
5. A thread-safe path may end at a trap right behind a call (`call _CxxThrowException; int3`, an inlined throw). Unit case
   `'x'`, proved.
6. `read_guard_code` takes pointers to the cached section descriptions; the first reading of a plan indexes once which
   sections refer to which symbol name and which symbol section (`sections_by_target_`, `sections_by_target_section_`),
   and later readings look the guard up there.
7. Comments of guard_code.h and test_guard_code.cpp: the write-based rule and the any-alias refusal.

## Review round 3 (delta re-review of a581685..582ab5f; convergence ruling, ADR-0018)

Principle applied: anything outside the reader's explicit model refuses.

1. A conditional tail call (`jne ?other`, rel32 with a relocation) left the bracket unseen (its fall-through was a
   successor). Any branch out of the section (a relocated jmp / jcc, `jump_to == kNone`) in a region refuses, in both
   walks. Unit case `'r'`.
2. Jumps or falls into a sibling function: no fall-through successor crosses a function start in any walk (an instruction
   that would is `falls_off` and refuses in a region); in the thread-safe walk a successor that is an entry refuses. Unit
   cases `'s'` (a branch to a sibling function's start) and a bitmask region that runs on into the next function.
3. `reads_only` adds the memory-source reads: SSE/SSE2 sqrt/add/mul/sub/min/div/max, and/andn/or/xor, the conversions
   (0F 2A/2C/2D/5A/5B/E6), cmpps/ss/pd/sd (none / 66 / F2 / F3), bsf/bsr/tzcnt/lzcnt/popcnt, and the x87 loads fld m32/m64,
   fild m32/m64. Unit case: `static double d = f() * scale;` (`mulsd xmm0,[scale]`, `movsd [d],xmm0`) is proved.
4. Only int3 (CC) or ud2 (0F 0B) right behind a call ends a thread-safe path; `int imm8` refuses. Unit case `'i'`.
5. Entries the reader did not model: every symbol defined in a code section (any type) and every relocation target in it
   from any linked section of the object (`GuardEntryRef`, computed by `relocation_target_offsets`: the symbol's offset plus
   the addend, and for a REL32 that is not a call / jmp / jcc rel32 every tail from k to 4) is an entry: entered from
   outside, also a start of the shared code. An offset inside an instruction refuses, except from `.xdata` (clang's
   ip2state keys sit one byte behind a call's return address: lookup keys, not entries; seen in n3/s3 and the fixture).
   Debug information is not linked (it has no relocations in the plan) and transfers no control. A function with catch
   handlers (`$tryMap$` / `$handlerMap$` symbols of it) is not read at all: its continuations re-enter it. Unit case:
   `lea rax,[.text$mn+0x0a]` pointing at a claim's `or` refuses; a call's rel32 names its target exactly.
6. The cmpxchg16b case requires "writes 2 of them" (so 0F C7 /1 decodes and counts as a write); an `xchg [calls],eax` case
   was added.

## Deferred

- Bound statics next to new ones under one guard (a function that keeps a dynamic static and gains another, `n5`): the
  code shows which bit each static claims, but whether the old function gave the bound one the same bit needs the old
  code read the same way (or the unchanged function, WP-59's proof). Still CML3600.
- Internal functions' guards (`$TSS<n>` / `$S<n>` with internal linkage; their rules are WP-40's / WP-46's, which place
  a guard by its record or by the section layout): not read from the code here.
- `??__J` (thread-local bitmask) stays WP-24's.
